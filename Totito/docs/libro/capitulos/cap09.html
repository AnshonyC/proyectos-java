El ciclo diario

Trabajar con Git es repetir un ciclo corto, muchas veces al día:

  1. Traer lo último (git pull), si trabajas con GitHub o con otras personas.
  2. Editar: escribes código en NetBeans, compilas, pruebas.
  3. Mirar qué cambió: git status.
  4. Comparar línea por línea: git diff.
  5. Preparar lo que va junto: git add.
  6. Guardar con un buen mensaje: git commit.
  7. Subir: git push.

Hagamos una vuelta completa. Abre Tema.java con notepad Tema.java y, debajo de la línea de MORADO, agrega esta (con sus cuatro espacios al principio):

    public static final Color LAVANDA = new Color(0xC8, 0xBC, 0xF6);

Guarda y cierra. Ahora, el paso 3:

git status
On branch main

  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   Tema.java

no changes added to commit (use "git add" and/or "git commit -a")

«Cambios que no están preparados para el commit: modified, Tema.java». Git te ofrece dos caminos: git add para prepararlo, o git restore para descartar el cambio (lo verás en «Deshacer»).

git diff: qué cambió exactamente

git diff
diff --git a/Tema.java b/Tema.java
index 7e01ffe..d1b89cc 100644
--- a/Tema.java
+++ b/Tema.java
@@ -7,6 +7,7 @@ public final class Tema {
     /** Color de la O (en todo el juego la O es azul). */
     public static final Color AZUL = new Color(0x2F, 0x84, 0xFF);
     public static final Color MORADO = new Color(0xA0, 0x5C, 0xFF);
+    public static final Color LAVANDA = new Color(0xC8, 0xBC, 0xF6);

     private Tema() {
     }

Un diff (de difference) es la lista de diferencias entre dos versiones de un archivo. Al principio asusta, pero se lee fácil:

  • diff --git a/Tema.java b/Tema.java: compara la versión «a» (la de antes, la guardada) con la «b» (la de ahora).
  • index 7e01ffe..d1b89cc 100644: identificadores internos de las dos versiones del contenido. Puedes ignorar esta línea.
  • --- a/Tema.java y +++ b/Tema.java: las líneas que empiecen con - son de la versión vieja; las que empiecen con +, de la nueva.
  • @@ -7,6 +7,7 @@: la cabecera del trozo (en inglés, hunk). Quiere decir: «en la versión vieja, desde la línea 7, se muestran 6 líneas; en la nueva, desde la 7, se muestran 7». Después de los @@ Git pone, como pista, la línea más cercana que parece el inicio de una función o clase: public final class Tema {.
  • Las líneas que empiezan con un espacio son contexto: no cambiaron; Git las muestra (tres antes y tres después) para que sepas dónde está el cambio.
  • La línea con + es la que agregaste. En la terminal de Windows sale en verde; las de - (borradas) salen en rojo.

Una línea modificada aparece como una borrada y una agregada. Por ejemplo, si cambiaras el rosa, verías:

-    public static final Color ROSA = new Color(0xFF, 0x3B, 0xD4);
+    public static final Color ROSA = new Color(0xFF, 0x6E, 0xE0);

Si el diff es largo, Git usa el paginador: avanza con la barra espaciadora y sal con q.

Lee tu diff antes de cada commit Es la mejor costumbre que puedes tener con Git. En el diff descubres el System.out.println("prueba") que olvidaste quitar, el archivo que cambiaste sin querer, o la línea que borraste por error. Diez segundos de lectura te ahorran commits de «arreglo lo que rompí».

git add y git diff --staged

git add Tema.java
git diff
git diff --staged

Después del git add, git diff no muestra nada. No es que el cambio desapareciera: git diff compara la mesa con la bandeja, y ahora son iguales. Para ver lo que está en la bandeja comparado con el último commit (es decir, lo que vas a guardar), se usa git diff --staged, que muestra el mismo diff de antes. Resumen:

ComandoComparaPregunta que responde
git diffMesa ↔ bandeja¿Qué cambié que todavía no preparé?
git diff --stagedBandeja ↔ último commit¿Qué va a entrar en el próximo commit?
git diff HEADMesa ↔ último commit¿Qué cambié en total desde la última foto?
git diff 64f842d 8607176Un commit ↔ otro¿Qué cambió entre esas dos fotos?

git commit y git push

git commit -m "Tema: agregar el color lavanda"
[main 8607176] Tema: agregar el color lavanda
 1 file changed, 1 insertion(+)

En el laboratorio no hay remoto, así que el ciclo termina aquí. En el Totito, el último paso es git push, que envía los commits nuevos a GitHub:

Enumerating objects: 5, done.

La última línea es la importante: «en GitHub, la rama main pasó del commit b49d01a al 097adbd».

git commit -a no incluye archivos nuevos Verás el atajo git commit -am "mensaje": la -a (all) prepara automáticamente todos los archivos modificados antes del commit. Es cómodo, pero ignora los archivos nuevos (sin seguimiento): si creaste src\Jugador.java y haces git commit -am, el archivo no entra. Y además mete todo lo modificado, quieras o no. Úsalo solo cuando hayas revisado git status y sepas que todo lo modificado va junto.

Commits pequeños y atómicos

Un commit atómico es el que contiene un solo cambio lógico, completo: ni medio cambio, ni tres cambios mezclados. «Atómico» viene de átomo en su sentido antiguo: lo que no se puede dividir.

Imagina que una tarde en el Totito haces tres cosas: corriges un error en la detección de empate de Tablero.java, pruebas un color nuevo en Tema.java y mejoras el README.md. Tienes dos opciones:

Un commit giganteTres commits atómicos
Cambios del martes (3 archivos)Tablero: corregir la deteccion de empate
Tema: rosa mas intenso para la X
README: explicar como ejecutar el juego

Ahora supón que una semana después el rosa nuevo no te gusta. Con tres commits, deshaces solo el del color (con git revert, más abajo) y el arreglo del empate sigue ahí. Con el commit gigante, deshacerlo se lleva también el arreglo. Por eso:

  • Se pueden deshacer por separado.
  • Se entienden de un vistazo: el mensaje describe todo lo que hay dentro.
  • Se revisan fácil: en un pull request (capítulo 10), un diff de 15 líneas se revisa con atención; uno de 800, no.
  • Encuentras errores más rápido: si el juego se rompió, sabes en qué commit pequeño pasó.

Para separar el trabajo de la tarde en tres commits, agrega los archivos de uno en uno:

git add src/Tablero.java
git commit -m "Tablero: corregir la deteccion de empate"
git add src/Tema.java
git commit -m "Tema: rosa mas intenso para la X"
git add README.md
git commit -m "README: explicar como ejecutar el juego"

¿Y si en un mismo archivo hay dos cambios que deberían ir en commits distintos? Existe git add -p (patch), que te muestra cada trozo del diff y te pregunta si lo agregas o no (y sí, n no, q salir, ? ayuda). Es una herramienta avanzada muy útil; pruébala en el laboratorio cuando te sientas cómodo.

Señales de que tu commit es demasiado grande El mensaje necesita la palabra «y» («Agregar sonidos y corregir el marcador y…»); no puedes resumirlo en 50 caracteres; tocas más de tres o cuatro archivos sin relación; o han pasado horas desde el último commit. La regla práctica del libro: cada vez que algo funciona, commit.

Buenos mensajes de commit

El mensaje es la nota debajo de la foto. Lo vas a leer tú dentro de meses, o un compañero que no estuvo ahí. Las convenciones más extendidas son estas:

  1. Una primera línea corta, de 50 caracteres o menos, que resuma el cambio. Es lo que muestran git log --oneline y GitHub en sus listas; si es más larga, se corta con «…».
  2. En forma de orden o infinitivo: en inglés se usa el imperativo (Add lavender color, «agrega el color lavanda»); en español lo más común es el infinitivo («Agregar el color lavanda») o el imperativo («Agrega el color lavanda»). Elige uno y sé constante. Una prueba útil: la frase debe completar «Si aplicas este commit, va a…»: «…agregar el color lavanda». No «Agregué», no «Agregando».
  3. Empieza con mayúscula y sin punto final.
  4. Opcional: el componente delante, seguido de dos puntos: Tablero:, Tema:, README:. El libro lo usa en casi todos sus commits; así sabes de un vistazo qué parte del juego tocó.
  5. Si hace falta explicar más, un cuerpo: una línea en blanco después del título y luego un párrafo que diga por qué hiciste el cambio (el «qué» ya lo dice el diff). Las líneas del cuerpo, de unos 72 caracteres como máximo.
MalPor quéMejor
cambiosNo dice nada: todos los commits son cambiosTema: agregar el color lavanda
arreglos¿Qué se arregló? ¿Dónde?Tablero: corregir la deteccion de empate
asdf / . / wipMensaje de prisa: dentro de un mes no sabrás qué esPanelTablero: dibujar la linea ganadora
Tablero.javaSolo el archivo: ¿qué le pasó?Tablero: estado y reglas del juego
Arreglé el bug del empate, cambié colores y agregué sonidosTres cambios en uno; pasado; demasiado largoTres commits, cada uno con su línea
AHORA SI FUNCIONA!!!Emoción, no informaciónBotonNeon: repintar al soltar el mouse

Un mensaje con cuerpo, desde PowerShell

Cada -m que pongas se convierte en un párrafo: el primero es el título y los siguientes, el cuerpo. Git pone la línea en blanco entre ellos.

git commit -m "Partida: no permitir jugar despues de ganar" -m "Un clic rapido despues de la victoria todavia marcaba una ficha y sumaba al marcador. Ahora jugar() revisa el estado y no hace nada si la partida ya termino."

Si prefieres escribirlo con calma, haz git commit sin -m: Git abre el editor que configuraste en el capítulo 7. Escribe el título en la primera línea, deja una en blanco, escribe el cuerpo, guarda y cierra. Las líneas que empiezan con # son instrucciones de Git y no se guardan. Si cierras el editor sin escribir nada, Git cancela el commit (Aborting commit due to empty commit message): es una forma segura de arrepentirte.

Mirar el historial

git log --oneline
git log --oneline --graph --all
git show 8607176
git log -p Tema.java
git log --oneline --author="Ana"
  • git log --oneline: una línea por commit, lo más reciente arriba.
  • --graph --all: dibuja las ramas con caracteres (*, |, /, \) e incluye todas las ramas, no solo la actual. Es el comando que más usarás para entender «dónde estoy».
  • git show 8607176: el mensaje y el diff completo de ese commit. Sirve también git show HEAD (el último) o git show HEAD~1 (el anterior: la ~1 significa «un paso atrás»; HEAD~2, dos pasos).
  • git log -p Tema.java: todos los commits que tocaron ese archivo, cada uno con su diff (-p de patch). Ideal para responder «¿cuándo y por qué cambió este color?».
  • --author="Ana": solo los commits de quien coincida con ese nombre.

Ramas: trabajar en una idea sin tocar las demás

Como viste en el capítulo 6, una rama es una etiqueta que apunta a un commit y avanza sola con cada commit nuevo. Los comandos básicos:

git branch
git switch -c instrucciones
git branch
* main
Switched to a new branch 'instrucciones'
* instrucciones
  main
  • git branch sin nada más lista las ramas. El asterisco marca dónde está HEAD (la rama actual).
  • git switch -c instrucciones: switch significa «cambiar», y -c (create) significa «créala primero». La rama nueva nace apuntando al mismo commit donde estabas, y HEAD se mueve a ella. Responde «Cambiado a una rama nueva 'instrucciones'».

Ahora haz un commit en esta rama: crea un README.md con notepad README.md, escribe dentro una línea como «# Laboratorio de Git» y otra que explique para qué sirve, guarda, cierra, y:

git add README.md
git commit -m "README: explicar el laboratorio"
Get-ChildItem
git switch main
Get-ChildItem

Mira lo que pasa con Get-ChildItem: en la rama instrucciones ves README.md y Tema.java; al cambiar a main, README.md desaparece de la carpeta. No se borró: existe solo en el commit de la rama instrucciones, y main todavía no lo tiene. Así de real es el cambio de rama: Git reescribe tu carpeta para que coincida con el commit de la rama elegida. Si tienes el proyecto abierto en NetBeans, verás los archivos aparecer y desaparecer.

git log --oneline --graph --all
* 3fe3d3e (instrucciones) README: explicar el laboratorio
* 8607176 (HEAD -> main) Tema: agregar el color lavanda
* 64f842d Tema: colores basicos
Cambiar de rama con cambios sin guardar Si tienes archivos modificados y cambias de rama, Git hace una de dos cosas: si esos cambios no chocan con la otra rama, se los lleva contigo (siguen en tu mesa, sin commit); si chocan, se niega con error: Your local changes to the following files would be overwritten by checkout («tus cambios locales se sobrescribirían») y no cambia nada. En ambos casos lo más limpio es hacer commit o guardar los cambios con git stash (más abajo) antes de cambiar de rama.

Nombres de ramas

Usa minúsculas, palabras separadas por guiones, y un nombre que diga qué se hace ahí: interfaz-neon, sonidos, arreglo-empate, dificultad-ia. Sin espacios, sin tildes, sin ñ. Muchos equipos usan prefijos: feature/sonidos (función nueva), fix/empate (arreglo), docs/readme (documentación).

Fusionar ramas: merge

Para traer el trabajo de una rama a otra, te colocas en la rama que recibe y le pides que fusione la otra: «estando en main, fusiona instrucciones».

Fusión rápida (fast-forward)

git switch main
git merge instrucciones
Updating 8607176..3fe3d3e
Fast-forward
 README.md | 3 +++
 1 file changed, 3 insertions(+)
 create mode 100644 README.md

Fast-forward significa «avance rápido», como en un reproductor de música. Desde que creaste instrucciones, main no tuvo commits nuevos: la historia es una línea recta. Git no necesita juntar nada; solo mueve la etiqueta main hacia adelante hasta el commit de instrucciones. No se crea ningún commit nuevo.

Cuando una rama ya está fusionada y no la necesitas, bórrala; el trabajo no se pierde, porque sus commits ya forman parte de main:

git branch -d instrucciones
Deleted branch instrucciones (was 3fe3d3e).

La -d (delete) es prudente: si la rama tiene commits que no están fusionados en ninguna parte, se niega (error: the branch 'x' is not fully merged) y te dice que uses -D (mayúscula) si de verdad quieres tirarlos. Piénsalo dos veces antes de usar -D.

Fusión de tres vías (con commit de fusión)

Ahora el caso en que las dos ramas avanzaron. Crea una rama, agrega un color, vuelve a main y cambia otra cosa:

git switch -c cian
notepad Tema.java

Debajo de la línea de AZUL agrega public static final Color CIAN = new Color(0x40, 0xC8, 0xFF);, guarda, cierra, y:

git commit -am "Tema: agregar el color cian"
git switch main
notepad README.md

Agrega al final del README una línea «Cada rama es una idea distinta.», guarda, cierra, y:

git commit -am "README: agregar una nota sobre ramas"
git log --oneline --graph --all
* 44fdbf9 (cian) Tema: agregar el color cian
| * 54bb71a (HEAD -> main) README: agregar una nota sobre ramas
|/
* 3fe3d3e README: explicar el laboratorio
* 8607176 Tema: agregar el color lavanda
* 64f842d Tema: colores basicos

El dibujo muestra la bifurcación: desde 3fe3d3e, cada rama tiene un commit propio. Ya no hay línea recta, así que main no puede «avanzar» hasta cian sin perder su propio commit. Git tiene que combinar las dos historias:

git merge cian --no-edit
Merge made by the 'ort' strategy.
 Tema.java | 1 +
 1 file changed, 1 insertion(+)

«Fusión hecha con la estrategia 'ort'» (ort es el nombre del algoritmo de fusión que usa Git por defecto; no tienes que elegirlo). Git miró tres versiones —por eso se llama «de tres vías»—: el ancestro común (3fe3d3e, donde las ramas se separaron), la punta de main y la punta de cian. Lo que cambió en cada lado respecto al ancestro, lo juntó. Como los cambios estaban en archivos distintos, no hubo nada que decidir.

El resultado es un commit de fusión (merge commit), un commit especial con dos padres. La opción --no-edit acepta el mensaje automático, Merge branch 'cian'; sin ella, Git abriría tu editor para que lo cambies si quieres.

*   620c464 (HEAD -> main) Merge branch 'cian'
|\
| * 44fdbf9 (cian) Tema: agregar el color cian
* | 54bb71a README: agregar una nota sobre ramas
|/
* 3fe3d3e README: explicar el laboratorio

Borra la rama ya fusionada con git branch -d cian. En el capítulo 61 harás exactamente esta clase de fusión, pero a través de un pull request en GitHub (capítulo 10): GitHub crea un commit de fusión con un mensaje como Merge pull request #1 from ana-lopez/interfaz-neon.

Un conflicto de verdad, paso a paso

Git fusiona solo cuando los cambios están en lugares distintos. Pero si las dos ramas cambiaron las mismas líneas de forma diferente, Git no puede saber cuál es la buena, y te lo pregunta. Eso es un conflicto. No es un error ni algo que hiciste mal: es una pregunta. Vamos a provocar uno.

La historia: tú quieres el rosa de la X más claro, y tu compañera lo quiere más intenso. Cada quien lo cambia en su rama.

1. Preparar el choque

git switch -c rosa-clara
notepad Tema.java

En la línea de ROSA cambia 0xFF, 0x3B, 0xD4 por 0xFF, 0x6E, 0xE0. Guarda, cierra, y mira el diff antes del commit (fíjate en el par -/+ de una línea modificada):

git diff
git commit -am "Tema: rosa mas claro para la X"
git switch main
notepad Tema.java

Ahora, en main, cambia la misma línea, pero a 0xFF, 0x1F, 0xB8. Guarda, cierra:

git commit -am "Tema: rosa mas intenso para la X"
git log --oneline --graph --all -4
* 2d454c7 (HEAD -> main) Tema: rosa mas intenso para la X
| * 755882a (rosa-clara) Tema: rosa mas claro para la X
|/
*   620c464 Merge branch 'cian'

2. Intentar la fusión

git merge rosa-clara
Auto-merging Tema.java
CONFLICT (content): Merge conflict in Tema.java
Automatic merge failed; fix conflicts and then commit the result.

«Fusionando automáticamente Tema.java. CONFLICTO (de contenido) en Tema.java. La fusión automática falló; arregla los conflictos y luego haz commit del resultado». Git se detuvo a medio camino y te espera. Respira: nada se perdió. Pregunta cómo está todo:

git status
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   Tema.java

no changes added to commit (use "git add" and/or "git commit -a")
  • You have unmerged paths: «tienes archivos sin fusionar».
  • Las dos salidas: arreglar y hacer git commit, o abortar con git merge --abort, que deja todo exactamente como estaba antes del git merge. Es tu botón de pánico.
  • both modified: Tema.java: «modificado por ambos». Este es el archivo en conflicto. La pista dice que, al resolverlo, uses git add para marcarlo como resuelto.

3. Leer el archivo en conflicto

Abre Tema.java (notepad Tema.java, o en NetBeans). Git escribió dentro las dos versiones, separadas por unas marcas:

    /** Color de la X (en todo el juego la X es rosa). */
<<<<<<< HEAD
    public static final Color ROSA = new Color(0xFF, 0x1F, 0xB8);
=======
    public static final Color ROSA = new Color(0xFF, 0x6E, 0xE0);
>>>>>>> rosa-clara
    /** Color de la O (en todo el juego la O es azul). */
MarcaSignificado
<<<<<<< HEADEmpieza la versión de donde estás (HEAD, o sea main): el rosa intenso.
=======Separador entre las dos versiones.
>>>>>>> rosa-claraTermina la versión de la rama que estás fusionando: el rosa claro.

Todo lo que está fuera de las marcas (el comentario de arriba, la línea de AZUL) no tuvo conflicto y está bien. Tu trabajo es dejar el archivo como debe quedar y borrar las tres marcas. Tienes tres opciones:

  • Quedarte con la versión de main (borra desde ======= hasta >>>>>>> rosa-clara, y la línea <<<<<<< HEAD).
  • Quedarte con la de rosa-clara (lo contrario).
  • Escribir algo nuevo que combine las dos ideas. Aquí, después de hablarlo con tu compañera, deciden un rosa intermedio:
    /** Color de la X (en todo el juego la X es rosa). */
    public static final Color ROSA = new Color(0xFF, 0x45, 0xD8);
    /** Color de la O (en todo el juego la O es azul). */

Guarda el archivo. Antes de seguir, comprueba que no quedó ninguna marca. En PowerShell, Select-String busca texto dentro de archivos (es como el «buscar» del Bloc de notas, pero desde la terminal):

Select-String -Path Tema.java -Pattern '<<<<<<<|>>>>>>>|^=======$'

Si no imprime nada, está limpio. (El patrón va entre comillas simples para que PowerShell no interprete ningún símbolo; busca cualquiera de las tres marcas, y la barra vertical | significa «o»).

Las marcas olvidadas rompen la compilación Si dejas una marca en un archivo Java, el compilador se queja de inmediato, con errores que parecen absurdos: 
Tema.java:6: error: illegal start of type
<<<<<<< HEAD
^
«Inicio de tipo ilegal» en una línea que empieza con <<<<<<<: es una marca de conflicto que sobrevivió. Por eso, después de resolver un conflicto en el Totito, siempre compila y prueba (en NetBeans, Clean and Build) antes del commit.

4. Marcar como resuelto y terminar la fusión

git add Tema.java
git status
On branch main
All conflicts fixed but you are still merging.
  (use "git commit" to conclude merge)

Changes to be committed:
	modified:   Tema.java

«Todos los conflictos arreglados, pero sigues en medio de la fusión. Usa git commit para concluirla». Aquí git add no significa «archivo nuevo», sino «ya decidí cómo queda este archivo». Si intentas hacer el commit antes del git add, Git se niega: Committing is not possible because you have unmerged files.

git commit --no-edit
git log --oneline --graph -4
[main a72bccc] Merge branch 'rosa-clara'
*   a72bccc (HEAD -> main) Merge branch 'rosa-clara'
|\
| * 755882a (rosa-clara) Tema: rosa mas claro para la X
* | 2d454c7 Tema: rosa mas intenso para la X
|/

Listo: el commit de fusión guarda tu decisión. Borra la rama con git branch -d rosa-clara. Has resuelto tu primer conflicto.

Resolver el conflicto desde NetBeans

Si abres en NetBeans una carpeta con conflictos (con File → Open Project en el Totito, o File → Open File en el laboratorio), el archivo en conflicto aparece con su nombre en rojo. Tienes dos caminos:

  • A mano, igual que en el Bloc de notas: abres el archivo, ves las marcas, editas, borras las marcas, guardas. Luego git add y git commit en PowerShell (o desde el menú Team).
  • Con la herramienta de fusión: clic derecho sobre el archivo → Git → Resolve Conflicts… (también está en el menú Team). Se abre una ventana con las dos versiones arriba, una a cada lado, y el resultado abajo. Encima de cada versión hay botones para aceptar ese lado (Accept), aceptar y pasar al siguiente conflicto (Accept & Next) o aceptar ambos (Accept Both); también puedes escribir directamente en el panel del resultado. Al terminar pulsas OK y NetBeans guarda el archivo y lo marca como resuelto (el equivalente de git add). Después haces el commit. Los nombres exactos de los botones pueden variar un poco entre versiones de NetBeans.

Cómo tener menos conflictos

  • Trae los cambios a menudo (git pull al empezar el día) y fusiona las ramas pronto: las ramas que viven semanas acumulan diferencias.
  • Commits pequeños: si hay conflicto, es pequeño y fácil de entender.
  • No reformatees archivos enteros (por ejemplo, con el «Format» de NetBeans sobre todo el archivo) en el mismo commit que un cambio real: cambias cientos de líneas sin querer, y cualquiera que haya tocado ese archivo tendrá conflicto.
  • Ponte de acuerdo: si dos personas van a tocar Tema.java a la vez, que lo sepan. Centralizar los colores en una sola clase (como hace el Totito) ayuda: el conflicto queda en un lugar obvio.

Deshacer cosas

Git casi nunca pierde nada que haya llegado a un commit, y tiene una herramienta para cada clase de arrepentimiento. Primero, el mapa:

SituaciónComando¿Peligroso?
Cambié un archivo y quiero volver a como estaba en el último commitgit restore archivoPierdes ese cambio sin commit
Hice git add de algo que no quería en este commitgit restore --staged archivoNo: el cambio sigue en tu mesa
El último commit tiene un error en el mensaje o le faltó un archivo, y no lo he subidogit commit --amendNo, si no se subió
Un commit (subido o no) introdujo algo malo y quiero anularlogit revert hashNo: crea un commit nuevo
Quiero quitar commits locales del historialgit resetSí, con --hard
Tengo que cambiar de tarea sin hacer commit de lo que llevogit stashNo
Hice un desastre y quiero ver dónde estaba antesgit reflogNo: solo mira

git restore: descartar cambios de la mesa

Abre Tema.java, cambia el morado por cualquier cosa, guarda, y:

git status -s
git restore Tema.java
git status -s
 M Tema.java

Después del restore, git status -s ya no muestra nada: el archivo volvió a ser exactamente el del último commit. Es el «deshacer todo lo que hice desde la última foto» para ese archivo. Úsalo cuando un experimento salió mal.

restore no tiene vuelta atrás Los cambios que descartas con git restore nunca estuvieron en un commit, así que Git no los guardó en ninguna parte: desaparecen. NetBeans tiene su propio historial local (clic derecho → History) que a veces te salva, pero no cuentes con ello. Antes de un restore, mira el git diff para estar seguro de lo que vas a perder.

git restore --staged: sacar de la bandeja

Imagina que creaste un notas.txt con apuntes personales, cambiaste el README, y por costumbre hiciste git add .:

git add .
git status -s
git restore --staged notas.txt
git status -s
M  README.md
A  notas.txt
M  README.md
?? notas.txt

notas.txt pasó de A (agregado a la bandeja) a ?? (sin seguimiento). El archivo sigue en tu carpeta, intacto; solo salió de la bandeja. Ahora el commit llevará solo el README. (Si nunca quieres que notas.txt entre, agrégalo al .gitignore).

git commit --amend: corregir el último commit

git commit -m "README: agregar la autroa"
git commit --amend -m "README: agregar la autora"
git log --oneline -2
[main 74d3a8e] README: agregar la autora
 Date: Mon Oct 12 14:44:06 2026 -0600
 1 file changed, 2 insertions(+)
74d3a8e README: agregar la autora
a72bccc Merge branch 'rosa-clara'

Amend significa «enmendar». Reemplaza el último commit por uno nuevo que tiene el contenido de la bandeja y el mensaje que le des. El commit con «autroa» ya no aparece en git log. También sirve cuando olvidaste un archivo (por ejemplo, en el Totito):

git add src/Jugador.java
git commit --amend --no-edit

--no-edit conserva el mismo mensaje. El commit «se rehace» incluyendo el archivo olvidado.

Solo si no lo subiste Recuerda el capítulo 6: un commit es inmutable. --amend no lo modifica; crea uno nuevo, con otro hash, y abandona el viejo. Si el viejo ya estaba en GitHub, tu historial y el de GitHub ya no coinciden, git push será rechazado, y si alguien ya lo había descargado, le causarás problemas. Regla: --amend solo para commits que no hiciste push. Para los subidos, usa git revert.

git revert: anular un commit con otro commit

git revert --no-edit HEAD
git log --oneline -3
[main 9690e2c] Revert "README: agregar la autora"
 Date: Mon Oct 12 14:44:11 2026 -0600
 1 file changed, 2 deletions(-)
9690e2c Revert "README: agregar la autora"
74d3a8e README: agregar la autora
a72bccc Merge branch 'rosa-clara'

git revert crea un commit nuevo que hace exactamente lo contrario del commit indicado: si aquel agregó dos líneas, este las quita. El commit original sigue en el historial, y el nuevo deja constancia de que se deshizo (su mensaje, si lo miras con git show, dice This reverts commit 74d3a8e…). Como no se borra ni se reescribe nada, es la forma segura de deshacer algo que ya está en GitHub. En lugar de HEAD puedes poner el hash de cualquier commit anterior: git revert 2d454c7. (Sin --no-edit, Git abre el editor para que ajustes el mensaje).

git reset: mover la rama hacia atrás (con mucho cuidado)

git reset mueve la etiqueta de la rama actual a otro commit, como si los commits posteriores no se hubieran hecho. Tiene tres modos, que deciden qué pasa con los cambios de esos commits:

ModoLa ramaLa bandejaTu carpetaÚsalo para
--softRetrocedeConserva los cambios (preparados)IntactaRehacer el último commit, por ejemplo juntando dos en uno
--mixed (por defecto)RetrocedeSe vacía (cambios sin preparar)IntactaDeshacer el commit pero conservar el trabajo para reorganizarlo
--hardRetrocedeSe vacíaSe sobrescribe: los cambios se pierdenTirar de verdad todo lo hecho desde ese commit

Pruébalo en el laboratorio. Haz un commit cualquiera (cambia el lavanda a 0xD0, 0xC0, 0xFF y git commit -am "Tema: lavanda mas brillante") y luego:

git reset --soft HEAD~1
git status -s
M  Tema.java

El commit desapareció del historial, pero su cambio está en la bandeja, listo para otro commit. HEAD~1 significa «el commit anterior al actual».

git reset HEAD
git status -s
Unstaged changes after reset:
M	Tema.java
 M Tema.java

Con el modo por defecto (--mixed), el cambio sale de la bandeja pero sigue en tu archivo.

git reset --hard HEAD
HEAD is now at 9690e2c Revert "README: agregar la autora"

Y con --hard, el archivo vuelve a ser el del commit y el cambio se pierde.

GRAN ADVERTENCIA sobre git reset --hard
  • git reset --hard borra sin preguntar todo cambio sin commit de los archivos seguidos. No hay papelera de reciclaje.
  • Nunca hagas reset hacia atrás de commits que ya subiste a GitHub. Tu rama y la de GitHub dejarán de coincidir; el siguiente git push será rechazado, y la única forma de «ganar» sería forzar el envío (git push --force), que borra el trabajo de GitHub, incluido el de tus compañeros. Para lo subido, usa git revert.
  • Antes de un --hard, haz git status y git diff. Si dudas, haz primero git stash: es gratis y reversible.
  • Si a pesar de todo te equivocaste, lee la siguiente sección de inmediato.

git reflog: la red de seguridad

Git anota en un diario local cada vez que HEAD se mueve: cada commit, cada cambio de rama, cada reset. Ese diario es el reflog (reference log):

git reflog -6
9690e2c HEAD@{0}: reset: moving to HEAD
9690e2c HEAD@{1}: reset: moving to HEAD
9690e2c HEAD@{2}: reset: moving to HEAD~1
a5c3937 HEAD@{3}: commit: Tema: lavanda mas brillante
9690e2c HEAD@{4}: revert: Revert "README: agregar la autora"
74d3a8e HEAD@{5}: commit (amend): README: agregar la autora

Ahí está el commit «lavanda mas brillante» (a5c3937), que habías «borrado» con el reset. Los commits abandonados siguen guardados en .git durante semanas (por defecto, al menos 30 días). Para recuperarlo, vuelve a apuntar la rama a él:

git reset --hard a5c3937
HEAD is now at a5c3937 Tema: lavanda mas brillante

Recuperado. (También podrías crear una rama en ese punto, git branch rescate a5c3937, sin tocar la actual). Lo que el reflog no puede recuperar son los cambios que nunca llegaron a un commit: otra razón para hacer commits a menudo.

Las llaves en PowerShell Si quieres escribir algo como HEAD@{3} en un comando, ponlo entre comillas simples: git show 'HEAD@{3}'. En PowerShell, @{ tiene un significado especial (crea una tabla de datos) y sin comillas el comando falla de formas raras. Lo mismo con 'stash@{0}', que verás enseguida.

git stash: guardar en un cajón lo que llevas a medias

Estás probando un rosa dorado en Tema.java, a medias, y te avisan de que hay que arreglar algo urgente en main. No quieres hacer commit de un experimento a medias, pero tampoco perderlo. git stash («esconder») guarda tus cambios en un cajón y te deja la mesa limpia:

git status -s
git stash push -m "probando rosa dorado"
git status -s
git stash list
 M Tema.java
Saved working directory and index state On main: probando rosa dorado
stash@{0}: On main: probando rosa dorado

Tu carpeta volvió al último commit (el segundo git status -s no muestra nada). Ahora puedes cambiar de rama, arreglar lo urgente, hacer commit, volver… y cuando quieras recuperar el experimento:

git stash pop

pop («sacar») aplica los cambios guardados y los quita del cajón (Dropped refs/stash@{0}). Otros comandos del cajón:

ComandoQué hace
git stash listLista el cajón; el más reciente es stash@{0}
git stash applyComo pop, pero deja una copia en el cajón
git stash drop 'stash@{0}'Tira esa entrada del cajón (con las comillas, por PowerShell)
git stash push -u -m "..."Incluye también archivos nuevos sin seguimiento; sin -u, el stash los deja en la mesa
git stash show -pMuestra el diff de lo guardado

El stash es para pausas cortas. Si un experimento va a durar días, mejor una rama con commits.

Etiquetas: marcar versiones

Una etiqueta (tag) es un nombre fijo para un commit importante. A diferencia de una rama, no se mueve nunca: v0.1.0 será siempre «la primera ventana jugable», aunque sigas haciendo commits. En el capítulo 33 pondrás tu primera etiqueta en el Totito; así se hace:

git tag -a v0.1.0 -m "Primera version jugable"
git tag
git log --oneline --decorate -2
v0.1.0
a5c3937 (HEAD -> main, tag: v0.1.0) Tema: lavanda mas brillante
9690e2c Revert "README: agregar la autora"
  • -a (annotated): crea una etiqueta anotada, que guarda quién la puso, cuándo y un mensaje (-m). Hay también etiquetas «ligeras» (git tag v0.1.0, sin -a), que son solo un nombre; para versiones usa siempre las anotadas.
  • v0.1.0: el nombre. La v de «versión» y tres números: mayor.menor.parche. Es el sistema SemVer (versionado semántico), que se explica a fondo en el capítulo 67.
  • git tag sin más lista las etiquetas; git show v0.1.0 muestra la etiqueta (autor, fecha, mensaje) y el commit al que apunta.

Si olvidaste etiquetar en su momento, puedes etiquetar un commit anterior dando su hash: git tag -a v0.1.0 9b2f904 -m "Primera version jugable". Y si te equivocaste, git tag -d v0.1.0 la borra (solo en tu PC).

Las etiquetas no se suben solas git push sube commits, pero no etiquetas. Para enviarlas a GitHub, una por una o todas: 
git push origin v0.1.0
git push --tags
En GitHub aparecerán en la sección Tags del repositorio, y a partir de ellas se crean los Releases (capítulos 10 y 67).

Trabajar con GitHub: push, fetch y pull

En el Totito tienes el remoto origin. git status te dice siempre cómo está tu rama respecto a la de GitHub:

Mensaje de git statusSignificaQué hacer
Your branch is up to date with 'origin/main'.Igual que GitHub (según lo último que Git sabe)Nada
Your branch is ahead of 'origin/main' by 2 commits.Tienes 2 commits que GitHub no tienegit push
Your branch is behind 'origin/main' by 1 commit, and can be fast-forwarded.GitHub tiene 1 commit que tú nogit pull
Your branch and 'origin/main' have diverged…Los dos tienen commits que el otro no tienegit pull (fusiona) y luego git push

Ojo con «según lo último que Git sabe»: git status no consulta internet. Para actualizar lo que tu PC sabe de GitHub sin tocar tus archivos, usa git fetch («ir a buscar»). git pull es git fetch + git merge: trae y fusiona de una vez.

From https://github.com/ana-lopez/totito
   76c3110..15bcb16  main       -> origin/main
Updating 76c3110..15bcb16
Fast-forward
 README.md | 2 ++
 1 file changed, 2 insertions(+)

Esa es la salida de un git pull típico: la primera parte es el fetch (origin/main avanzó) y la segunda la fusión, aquí una fusión rápida.

Cuando GitHub rechaza tu push

Si en GitHub hay commits que tú no tienes (porque editaste algo en la página, o lo subiste desde otra computadora, o un compañero), tu push será rechazado:

To https://github.com/ana-lopez/totito.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/ana-lopez/totito.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.

«Rechazado: el remoto contiene trabajo que tú no tienes localmente. Si quieres integrarlo, usa git pull antes de volver a hacer push». Git te protege de borrar el trabajo de otros. La solución es justo esa: git pull (que, gracias a pull.rebase false del capítulo 7, hará una fusión; si hay conflictos, se resuelven como ya sabes), y luego git push. Si el pull abre el editor para el mensaje de fusión, guarda y cierra, o usa git pull --no-edit.

La rutina sana Al empezar a trabajar: git pull. Al terminar cada tarea: git push. Así tu PC y GitHub nunca se alejan mucho, y si tu computadora falla, solo pierdes lo de hoy.

.gitignore a fondo, y qué hacer si ya subiste algo que no debías

El .gitignore que creaste en el capítulo 5 es una lista de patrones, uno por línea:

PatrónIgnora
target/La carpeta target y todo su contenido, esté donde esté (la barra final indica «carpeta»)
*.classCualquier archivo que termine en .class (el * significa «cualquier texto»)
nbproject/private/Solo esa subcarpeta de NetBeans, con tus ajustes personales
Thumbs.dbUn archivo con ese nombre exacto (miniaturas que crea Windows)
/notas.txtCon barra al inicio: solo el notas.txt de la carpeta raíz del proyecto
!importante.classCon !: una excepción, «este sí, aunque otra regla lo ignore»
# comentarioNada: las líneas con # son notas

Para saber qué regla ignora un archivo: git check-ignore -v ruta.

El .gitignore no actúa sobre lo que ya está guardado

Esto sorprende a todos alguna vez: si un archivo ya está en un commit, agregarlo después al .gitignore no hace nada; Git lo sigue vigilando. Pruébalo en el laboratorio: crea notas-privadas.txt, haz commit «por error», y luego:

Add-Content .gitignore "notas-privadas.txt"
git rm --cached notas-privadas.txt
git status -s
rm 'notas-privadas.txt'
D  notas-privadas.txt
?? .gitignore
  • Add-Content agrega una línea al final del .gitignore (si no existe, lo crea).
  • git rm --cached archivo: «quítalo del repositorio, pero déjalo en mi carpeta». Sin --cached, git rm lo borraría también del disco. Para una carpeta entera, agrega -r (recursivo): git rm -r --cached target.
  • El status muestra D (borrado del repositorio, preparado) y el .gitignore nuevo.
git add .gitignore
git commit -m "Dejar de versionar las notas privadas"
[main f24690f] Dejar de versionar las notas privadas
 2 files changed, 1 insertion(+), 1 deletion(-)
 create mode 100644 .gitignore
 delete mode 100644 notas-privadas.txt

Desde ahora Git ignora el archivo, que sigue en tu carpeta. Pero atención: sigue existiendo en el historial. Cualquiera con acceso al repositorio puede verlo en el commit anterior con git show HEAD~1:notas-privadas.txt. Para un archivo pesado o molesto, esto basta. Para una contraseña o un token, no: el capítulo 10 explica qué hacer (resumen: considera el secreto robado y cámbialo de inmediato).

Git desde NetBeans

En el libro usamos PowerShell para que entiendas cada paso, pero NetBeans tiene Git integrado y te ayuda a ver el estado mientras programas. Cuando abres el Totito, NetBeans detecta solo que es un repositorio:

  • Colores en la ventana de proyectos: verde para archivos nuevos, azul para modificados, rojo para conflictos, gris para ignorados.
  • Marcas en el margen del editor: junto a los números de línea aparecen franjas de color en las líneas agregadas, cambiadas o borradas desde el último commit. Al hacer clic en una franja ves la versión anterior de esa línea.
  • Menú Team: Commit…, Show Changes (el equivalente a git status), Diff, Show History (el git log de un archivo), ramas, fusiones, Remote → Push/Pull y Resolve Conflicts….

Usa lo que te resulte más cómodo; lo importante es que sepas qué hace cada botón por dentro, y eso ya lo sabes. La chuleta completa de comandos está en el Apéndice B.

Resumen

  • El ciclo diario es pull → editar → status → diff → add → commit → push; leer el diff antes de cada commit evita errores.
  • Los commits deben ser pequeños y atómicos, con una primera línea de 50 caracteres o menos, en infinitivo o imperativo, y un cuerpo que explique el porqué cuando haga falta.
  • git switch -c crea ramas y cambia a ellas; cambiar de rama reescribe tu carpeta. git merge fusiona: fast-forward si la historia es recta; de tres vías, con commit de fusión, si ambas ramas avanzaron.
  • Un conflicto es una pregunta: edita el archivo, borra las marcas <<<<<<< ======= >>>>>>>, compila, git add y git commit; git merge --abort es el botón de pánico.
  • Deshacer: restore (mesa), restore --staged (bandeja), commit --amend (último commit no subido), revert (commit subido, de forma segura), reset (con mucho cuidado, nunca sobre lo subido) y reflog para rescatar.
  • git stash guarda trabajo a medias; git tag -a v0.1.0 -m marca versiones y git push --tags las sube.
  • El .gitignore no afecta a lo ya guardado: usa git rm --cached, y recuerda que el historial conserva lo que se subió.
Aplícalo fuera del Totito Estas costumbres son las mismas en cualquier equipo de desarrollo:
  • En un trabajo de grupo de la universidad: cada integrante trabaja en su rama (login, reportes, base-de-datos), con commits pequeños, y se fusionan a main cuando funcionan. Los conflictos se resuelven hablando, como el del rosa.
  • Cuando un cliente reporta un error en producción: git stash lo que estabas haciendo, git switch main, rama arreglo-x, commit, fusión, etiqueta v1.0.1, y de vuelta a tu trabajo con git stash pop.
  • Cuando algo dejó de funcionar y no sabes por qué: git log -p archivo y git diff hash1 hash2 te muestran qué cambió; git revert deshace el commit culpable sin tocar lo demás.
  • En archivos de configuración de un servidor o de tus scripts: un repositorio con buenos mensajes te dice, meses después, por qué se cambió cada ajuste.
