Aquí aprendes a pasar comportamiento de un lado a otro como si fuera un dato: «cuando pulsen este botón, haz esto», «este icono se dibuja así». Son las flechitas -> y los dobles dos puntos :: que aparecen por todo el Totito, y las clases que viven dentro de otras clases. Sin esto, cada botón del juego necesitaría su propio archivo.

El problema: entregar una instrucción, no un dato

Hasta ahora, cuando llamabas a un método le pasabas datos: un número, un texto, un objeto Jugador. Pero muchas veces lo que quieres entregar es una acción. Piensa en el botón «Jugar» del menú: el botón sabe dibujarse y sabe detectar el clic, pero no sabe qué hacer después. Eso se lo tiene que decir quien lo crea: «cuando te pulsen, pide ir a la configuración».

En la vida diaria pasa igual. Cuando sales de viaje le dejas una nota a tu vecino: «cuando llegue el paquete, recíbelo y guárdalo en tu casa». No le das el paquete (todavía no existe); le das una instrucción para más tarde. El vecino la guarda y la ejecuta cuando ocurre el evento.

En el capítulo 24 viste la herramienta para esto: una interfaz. El botón acepta «cualquier objeto que cumpla ActionListener», y cuando lo pulsan llama a su método. El problema es que, sin lo que aprenderás en este capítulo, para cada botón tendrías que escribir una clase completa, en su propio archivo, con su nombre, su implements, su método… solo para decir una línea. Java ofrece formas cada vez más cortas de escribir esa «nota para el vecino». Las vemos de la más larga a la más corta.

Interfaces funcionales

Una interfaz funcional es una interfaz que tiene exactamente un método abstracto. Es el tipo de interfaz que representa «una sola acción»: Runnable (run()), ActionListener (actionPerformed(...)), y en el Totito PanelTablero.OyenteCasilla (casillaPulsada(...)) e Iconos.Icono (dibujar(...)).

Este último lo declara así src/Iconos.java (capítulo 42):

    /** Un icono sabe dibujarse en el cuadrado (x, y, tam, tam) con el color dado. */
    @FunctionalInterface
    public interface Icono {
        void dibujar(Graphics2D g, double x, double y, double tam, Color color);
    }

@FunctionalInterface es una anotación (como @Override, una etiqueta para el compilador que empieza con @). No cambia nada del programa: le pide a Java que compruebe que la interfaz tiene un solo método abstracto. Si mañana alguien le agrega un segundo método a Icono, el compilador lo detiene ahí mismo, en vez de romper los trece iconos del juego. Las interfaces funcionales son las únicas que se pueden escribir con lambdas y referencias a métodos; por eso vale la pena protegerlas.

Tres formas de entregar un comportamiento

Vamos a definir nuestra propia interfaz funcional, Operacion, que recibe dos enteros y devuelve otro, y a crear objetos que la cumplan de todas las formas posibles. Guárdalo como TresFormas.java:

public class TresFormas {
    public static void main(String[] args) {
        // 1) Con una clase que tiene nombre (la de abajo):
        Operacion suma = new Suma();

        // 2) Con una clase anonima: se escribe la clase y se crea el objeto en un solo paso.
        Operacion resta = new Operacion() {
            @Override
            public int aplicar(int a, int b) {
                return a - b;
            }
        };

        // 3) Con una lambda: solo lo que cambia (parametros -> resultado).
        Operacion multiplica = (a, b) -> a * b;

        // 4) Con referencias a metodos que ya existen:
        Operacion mayor = Math::max;                     // metodo static de la clase Math
        Operacion potencia = TresFormas::elevar;         // metodo static nuestro

        mostrar("suma", suma, 7, 3);
        mostrar("resta", resta, 7, 3);
        mostrar("multiplica", multiplica, 7, 3);
        mostrar("mayor", mayor, 7, 3);
        mostrar("potencia", potencia, 7, 3);
    }

    static int elevar(int base, int exponente) {
        int resultado = 1;
        for (int i = 0; i < exponente; i++) {
            resultado *= base;
        }
        return resultado;
    }

    static void mostrar(String nombre, Operacion op, int a, int b) {
        System.out.println(nombre + "(" + a + ", " + b + ") = " + op.aplicar(a, b));
    }
}

@FunctionalInterface
interface Operacion {
    int aplicar(int a, int b);
}

class Suma implements Operacion {
    @Override
    public int aplicar(int a, int b) {
        return a + b;
    }
}

El método mostrar recibe un parámetro de tipo Operacion y llama a op.aplicar(a, b). No sabe ni le importa cómo se creó ese objeto. Las cinco variables son objetos que cumplen Operacion; lo que cambia es cuánto tuviste que escribir para crearlos:

  1. Clase con nombre (Suma): lo que ya sabías del capítulo 24. Una clase, un implements, un método. Útil si la vas a usar en muchos lugares o si tiene datos propios.
  2. Clase anónima: la clase y el objeto se escriben juntos, sin nombre. La verás a fondo más abajo.
  3. Lambda: (a, b) -> a * b. Solo los parámetros y lo que se hace con ellos.
  4. Referencia a método: Math::max. Ni siquiera escribes el cuerpo: señalas un método que ya existe y que encaja.

La lambda, símbolo por símbolo

Una lambda (el nombre viene de la letra griega λ, que usaban los matemáticos para escribir funciones sin nombre) es un método sin nombre escrito en el lugar donde se necesita. Java la convierte en un objeto que cumple la interfaz funcional que se espera ahí. Desarmemos Operacion multiplica = (a, b) -> a * b;:

PiezaQué significa
Operacion multiplica =Una variable normal de tipo Operacion. Este tipo es el que le dice a Java qué interfaz debe cumplir la lambda (se llama el tipo destino).
(a, b)Los parámetros, entre paréntesis y separados por coma. No hace falta poner su tipo: Java lo deduce del método aplicar(int a, int b) de la interfaz. Si quieres, puedes escribirlo: (int a, int b). Los nombres los eliges tú; no tienen que coincidir con los de la interfaz.
->La flecha: un guion y un signo «mayor que», sin espacio entre ellos. Separa «lo que recibo» de «lo que hago». Léela como «se convierte en» o «entonces».
a * bEl cuerpo. Si es una sola expresión, se escribe sin llaves y sin return: su valor es lo que la lambda devuelve.
;Termina la sentencia de asignación, como en int x = 5;. No es parte de la lambda.

Hay algunas variantes que vas a ver en el Totito:

  • Un solo parámetro: se pueden quitar los paréntesis. e -> navegacion.irAlMenu() es lo mismo que (e) -> navegacion.irAlMenu().
  • Ningún parámetro: los paréntesis vacíos son obligatorios: () -> elegirModo(Partida.Modo.DOS_JUGADORES).
  • Cuerpo de varias líneas: va entre llaves, cada sentencia con su ;, y si la interfaz devuelve algo, con return: (a, b) -> { int r = a * b; return r; }. Fíjate que aquí sí hay ; dentro de las llaves, como en cualquier método.
Una lambda no se ejecuta donde se escribe Escribir e -> navegacion.irAlMenu() no va al menú. Crea un objeto que sabe ir al menú y lo guarda. Se ejecutará cuando alguien llame a su método (en un botón, cuando lo pulsen). Es la nota para el vecino: escribirla no recibe el paquete.

Lambdas en los botones del Totito

Este es el uso más común. En src/PantallaMenu.java (capítulo 56):

        BotonNeon jugar = BotonNeon.menu("Jugar", Iconos.JUGAR, Tema.ROSA);
        jugar.addActionListener(e -> navegacion.irAConfiguracion());

addActionListener es un método que BotonNeon hereda de JButton (capítulo 22). Su parámetro es de tipo ActionListener, una interfaz funcional de Swing cuyo único método es void actionPerformed(ActionEvent e). Por eso la lambda tiene un parámetro, e: es el evento, un objeto con información del clic (qué botón fue, a qué hora, si había teclas apretadas). Aquí no lo usamos, pero la lambda tiene que aceptarlo porque el método de la interfaz lo recibe. El nombre e es una costumbre; podrías llamarlo evento.

Antes de que existieran las lambdas (Java 8, en 2014), esa misma línea se escribía con una clase anónima:

        jugar.addActionListener(new ActionListener() {
            @Override
            public void actionPerformed(ActionEvent e) {
                navegacion.irAConfiguracion();
            }
        });

Seis líneas y dos import más para decir lo mismo. Con siete u ocho botones por pantalla, el código se llenaba de ruido. La lambda deja a la vista solo lo que importa: qué pasa al pulsar.

Cuando la acción tiene varias líneas, se usan llaves. En src/PantallaJuego.java (capítulo 59), el botón «Reiniciar»:

        reiniciar.addActionListener(e -> {
            partida.reiniciar();
            comenzar(partida);
        });

Y no todo son botones. La interfaz Runnable (un único método void run(), sin parámetros) aparece cada vez que el Totito quiere guardar «algo que hacer después». En src/PantallaConfiguracion.java (capítulo 58):

        opcionDosJugadores.setAlSeleccionar(() -> elegirModo(Partida.Modo.DOS_JUGADORES));
        opcionContraIA.setAlSeleccionar(() -> elegirModo(Partida.Modo.CONTRA_IA));

OpcionModo (capítulo 51) guarda ese Runnable en un campo y, cuando le hacen clic, ejecuta alSeleccionar.run(). En PantallaJuego, el método esperar(int ms, Runnable accion) recibe una acción que se ejecutará cuando pase la pausa: así la computadora «piensa» 450 milisegundos antes de jugar. Y en el main de src/TotitoApp.java (capítulo 61):

        SwingUtilities.invokeLater(() -> new TotitoApp().setVisible(true));

«Cuando el hilo de Swing esté listo (capítulo 37), ejecuta esto: crea la ventana y muéstrala.»

Pruébalo sin ventanas

Este programa imita lo que hace Swing por dentro: un botón que guarda una lista de oyentes y los avisa al pulsarse. Guárdalo como BotonesDeMentira.java:

import java.util.ArrayList;
import java.util.List;

public class BotonesDeMentira {
    public static void main(String[] args) {
        Menu menu = new Menu();
        menu.jugar.pulsar();
        menu.instrucciones.pulsar();
        menu.salir.pulsar();
    }
}

/** Como ActionListener de Swing: "algo que reacciona a un clic". */
@FunctionalInterface
interface OyenteAccion {
    void accionRealizada(String evento);
}

/** Un boton muy simplificado: guarda oyentes y los avisa al pulsarse. */
class Boton {
    private final String texto;
    private final List<OyenteAccion> oyentes = new ArrayList<>();

    Boton(String texto) {
        this.texto = texto;
    }

    void agregarOyente(OyenteAccion oyente) {
        oyentes.add(oyente);
    }

    void pulsar() {
        System.out.println("(clic en \"" + texto + "\")");
        for (OyenteAccion oyente : oyentes) {
            oyente.accionRealizada("clic:" + texto);
        }
    }
}

class Menu {
    final Boton jugar = new Boton("Jugar");
    final Boton instrucciones = new Boton("Instrucciones");
    final Boton salir = new Boton("Salir");
    private int clics;

    Menu() {
        jugar.agregarOyente(e -> irAConfiguracion());              // lambda
        instrucciones.agregarOyente(e -> System.out.println("  Mostrando instrucciones (" + e + ")"));
        salir.agregarOyente(this::despedirse);                       // referencia a metodo
        // Un mismo boton puede tener varios oyentes:
        salir.agregarOyente(e -> {
            clics++;
            System.out.println("  Total de veces que se pidio salir: " + clics);
        });
    }

    private void irAConfiguracion() {
        System.out.println("  Pasando a la configuracion");
    }

    private void despedirse(String evento) {
        System.out.println("  ¡Hasta luego! (" + evento + ")");
    }
}

Observa el orden: cuando se ejecuta el constructor de Menu no se imprime nada. Las lambdas solo se guardan en las listas de cada botón. Se ejecutan después, en pulsar(), una por una. Y el botón «Salir» tiene dos oyentes: Swing también permite eso.

Fíjate también en que la lambda puede llamar a irAConfiguracion(), que es private. Una lambda escrita dentro de una clase ve todo lo que esa clase ve, incluidos sus campos privados (por eso puede hacer clics++). Y dentro de una lambda, this sigue siendo el objeto Menu, no la lambda.

Los iconos del Totito son lambdas guardadas en constantes

En Iconos.java no hay trece clases de iconos. Hay trece constantes, y cada una guarda una lambda que sabe dibujar algo:

    /** Triangulo de "reproducir" (botones Jugar y Comenzar partida). */
    public static final Icono JUGAR = (g, x, y, t, c) -> {
        Path2D triangulo = new Path2D.Double();
        triangulo.moveTo(x + t * 0.24, y + t * 0.14);
        triangulo.lineTo(x + t * 0.86, y + t * 0.5);
        triangulo.lineTo(x + t * 0.24, y + t * 0.86);
        triangulo.closePath();
        Dibujo.trazoNeon(g, triangulo, c, (float) (t * 0.1), 0.6f);
        g.setPaint(new GradientPaint((float) x, (float) y, Tema.aclarar(c, 0.25f),
                (float) (x + t), (float) (y + t), c));
        g.fill(triangulo);
    };

Léelo por partes:

  • public static final Icono JUGAR =: una constante pública de la clase (capítulo 20) de tipo Icono. Se usa en cualquier parte como Iconos.JUGAR.
  • (g, x, y, t, c): cinco parámetros, en el mismo orden que dibujar(Graphics2D g, double x, double y, double tam, Color color). Se usan nombres de una letra (t por «tamaño», c por «color») porque aparecen decenas de veces en fórmulas como x + t * 0.24, y así se leen mejor. Los tipos no se escriben: Java los toma de la interfaz.
  • -> { ... }: un cuerpo de varias líneas que dibuja un triángulo con coordenadas relativas al tamaño (capítulo 42 explica la geometría).
  • };: la llave cierra la lambda y el punto y coma cierra la declaración de la constante. Es fácil olvidar ese ;, y el compilador te lo recordará.

¿Quién llama a dibujar? Quien tenga el icono. BotonNeon recibe un Iconos.Icono en sus métodos de fábrica y, al pintarse, hace icono.dibujar(g2, ...). Así, BotonNeon.menu("Jugar", Iconos.JUGAR, Tema.ROSA) produce un botón con triángulo, y BotonNeon.menu("Salir", Iconos.SALIR, Tema.MORADO) uno con puerta, sin que BotonNeon tenga un solo if para decidir qué dibujar.

¿Qué pasaría si no se hubiera hecho así? Habría dos alternativas, ambas peores. Una: un método dibujarIcono(String nombre, ...) con un switch gigante de trece casos, que habría que editar (y arriesgarse a romper) cada vez que se agrega un icono. Otra: trece clases, cada una en su archivo, con su implements Icono. La lambda en una constante es el punto medio: cada icono es un objeto independiente, pero todos viven juntos y cortos en un solo archivo. A esta idea de «elegir una forma de hacer algo pasándola como objeto» se le llama patrón Estrategia (Strategy), y el capítulo 27 la retoma.

Lo mismo en pequeño, en consola. El «lienzo» es una matriz de letras (capítulo 15) y cada icono es una lambda de cinco parámetros. Guárdalo como IconosDeTexto.java:

public class IconosDeTexto {
    public static void main(String[] args) {
        char[][] lienzo = new char[7][30];
        for (char[] fila : lienzo) {
            java.util.Arrays.fill(fila, '.');
        }
        Iconos.EQUIS.dibujar(lienzo, 1, 1, 5, 'X');
        Iconos.MARCO.dibujar(lienzo, 8, 1, 5, '#');
        Iconos.PERSONA.dibujar(lienzo, 15, 1, 5, '@');
        Iconos.EQUIS.dibujar(lienzo, 22, 0, 7, '*');   // el mismo icono, a otro tamano y color
        for (char[] fila : lienzo) {
            System.out.println(new String(fila));
        }
    }
}

/** Como Iconos del Totito, pero el "lienzo" es una matriz de letras. */
final class Iconos {

    @FunctionalInterface
    interface Icono {
        void dibujar(char[][] lienzo, int x, int y, int t, char c);
    }

    private Iconos() {
    }

    /** Las dos diagonales de un cuadrado de lado t. */
    static final Icono EQUIS = (l, x, y, t, c) -> {
        for (int i = 0; i < t; i++) {
            l[y + i][x + i] = c;
            l[y + i][x + t - 1 - i] = c;
        }
    };

    /** Solo el borde del cuadrado. */
    static final Icono MARCO = (l, x, y, t, c) -> {
        for (int i = 0; i < t; i++) {
            l[y][x + i] = c;
            l[y + t - 1][x + i] = c;
            l[y + i][x] = c;
            l[y + i][x + t - 1] = c;
        }
    };

    /** Referencia a un metodo que ya existe (como Iconos::persona en el Totito). */
    static final Icono PERSONA = Iconos::persona;

    private static void persona(char[][] l, int x, int y, int t, char c) {
        int centro = x + t / 2;
        l[y][centro] = c;                       // cabeza
        for (int i = x; i < x + t; i++) {
            l[y + 2][i] = c;                    // brazos
        }
        for (int i = 1; i < t; i++) {
            l[y + i][centro] = c;               // cuerpo
        }
        l[y + t - 1][centro - 1] = c;           // piernas
        l[y + t - 1][centro + 1] = c;
    }
}

Lo que una lambda puede usar de su alrededor

Una lambda puede usar variables locales del método donde está escrita. A eso se le llama capturar la variable. Pero hay una condición: la variable tiene que ser final o «efectivamente final», es decir, que nunca cambie de valor después de asignarse (aunque no lleve la palabra final).

¿Por qué? Porque la lambda se ejecuta después, quizá cuando el método ya terminó y sus variables locales ya no existen (las variables locales viven en la pila, capítulo 16, y desaparecen al salir del método). Java resuelve esto copiando el valor dentro de la lambda en el momento de crearla. Si la variable pudiera cambiar después, la copia y el original dirían cosas distintas, y nadie sabría cuál vale. Así que Java lo prohíbe.

El caso típico es un for. Este código intenta crear tres acciones, una por fila:

        for (int fila = 0; fila < 3; fila++) {
            acciones.add(() -> System.out.println("Casilla de la fila " + fila));
        }
Captura.java:8: error: local variables referenced from a lambda expression must be final or effectively final
            acciones.add(() -> System.out.println("Casilla de la fila " + fila));
                                                                          ^
1 error
error: compilation failed

fila cambia en cada vuelta (fila++), así que no es efectivamente final. La solución es crear, dentro del ciclo, una variable nueva que nunca cambia. Guárdalo como Captura.java:

import java.util.ArrayList;
import java.util.List;

public class Captura {
    public static void main(String[] args) {
        List<Runnable> acciones = new ArrayList<>();
        for (int fila = 0; fila < 3; fila++) {
            final int f = fila;   // una variable NUEVA en cada vuelta, que nunca cambia
            acciones.add(() -> System.out.println("Casilla de la fila " + f));
        }
        for (Runnable accion : acciones) {
            accion.run();
        }
    }
}

Este es exactamente el truco que usa la primera versión del Totito. En src/JuegoMain.java, método crearPanelTablero (capítulo 33), se crean nueve botones dentro de dos for anidados, y cada uno tiene que recordar su fila y su columna:

                final int f = fila;
                final int c = columna;
                boton.addActionListener((ActionEvent e) -> manejarClicCasilla(f, c));

Sin f y c, no compilaría. Y fíjate en (ActionEvent e): aquí el autor escribió el tipo del parámetro, cosa opcional; es equivalente a e ->.

Los campos no tienen esta restricción En PantallaJuego, la lambda del botón «Reiniciar» usa partida, que sí cambia (cada partida nueva se guarda ahí). Compila porque partida es un campo del objeto, no una variable local: la lambda no copia su valor, sino que lo lee a través de this cada vez que se ejecuta. Por eso al pulsar «Reiniciar» siempre se reinicia la partida actual, no la que existía cuando se creó el botón.

Referencias a métodos: ::

Muchas lambdas no hacen más que llamar a un método que ya existe, pasándole los mismos parámetros que reciben. Para esos casos hay una forma aún más corta: la referencia a método, que se escribe con dos signos de dos puntos seguidos, ::. Se lee «el método tal de tal cosa». No lleva paréntesis después del nombre del método, porque no lo estás llamando: lo estás señalando para que se llame después.

Hay cuatro formas, y el Totito usa casi todas:

FormaEn el TotitoLambda equivalente
objeto::metodo (de este objeto)this::alPulsarCasilla (PantallaJuego)(fila, columna) -> this.alPulsarCasilla(fila, columna)
objeto::metodo (de otro objeto)navegacion::salir (PantallaBase)() -> navegacion.salir()
Clase::metodoStaticIconos::persona (Iconos)(g, x, y, t, c) -> Iconos.persona(g, x, y, t, c)
Clase::new (constructor)JuegoMain::new (JuegoMain.main)() -> new JuegoMain()
Clase::metodoDeInstancia(no se usa; abajo verás Producto::getPrecio)p -> p.getPrecio()

La regla para que una referencia encaje: el método señalado debe recibir los mismos parámetros (en cantidad y tipo) que el método de la interfaz, y devolver algo compatible. Veamos cada uso real.

this::alPulsarCasilla

En el constructor de PantallaJuego:

        tablero.setOyente(this::alPulsarCasilla);

setOyente pide un PanelTablero.OyenteCasilla, cuyo método es void casillaPulsada(int fila, int columna). La pantalla tiene un método private void alPulsarCasilla(int fila, int columna): dos enteros, no devuelve nada. Encaja. Desde ahora, cada vez que el tablero llame a oyente.casillaPulsada(1, 2), en realidad se ejecutará alPulsarCasilla(1, 2) de esta pantalla. Nota que el método es private y aun así el tablero termina ejecutándolo: la referencia se creó dentro de la clase, que sí tiene permiso, y lo que se entrega es un objeto que cumple la interfaz, no el permiso de llamar métodos privados.

navegacion::salir y this::cerrar

En el constructor de PantallaBase:

        add(new Encabezado(navegacion::salir), BorderLayout.NORTH);

El constructor de Encabezado pide un Runnable alCerrar (un método sin parámetros que no devuelve nada), y navegacion.salir() tiene justo esa forma. Fíjate en lo interesante: salir pertenece a la interfaz Navegacion, no a Runnable, y aun así sirve. A Java no le importa el nombre del método ni de qué interfaz venga; le importa que la forma (parámetros y retorno) coincida. Gracias a esto Encabezado no necesita conocer Navegacion: solo sabe «cuando pulsen la X, ejecuto esto».

Lo mismo en TotitoApp:

        setContentPane(new PanelPrincipal(this::cerrar));

PanelPrincipal pide un Runnable alSalir, y TotitoApp le entrega su método privado cerrar(), que hace dispose() y System.exit(0). Así el panel puede cerrar el programa sin saber que está dentro de un JFrame.

Iconos::persona

En Iconos, la silueta de persona no es una lambda sino una referencia:

    /** Silueta de persona (tarjetas de jugador). */
    public static final Icono PERSONA = Iconos::persona;

¿Por qué? Porque el dibujo de una persona se necesita también dentro de otro icono, PERSONAS, que dibuja dos personas de distinto tamaño llamando dos veces a persona(...). Si fuera una lambda, no tendría nombre y no se podría llamar desde otro lado. Así que se escribió como método normal, private static void persona(Graphics2D g, double x, double y, double t, Color c), y la constante solo lo señala. Es una forma de no repetir código (el principio DRY, capítulo 27).

JuegoMain::new

En el main de la primera versión:

        SwingUtilities.invokeLater(JuegoMain::new);

invokeLater pide un Runnable. JuegoMain::new es una referencia a constructor: «cuando te ejecuten, crea un JuegoMain». El objeto creado se descarta, pero no importa: el constructor de JuegoMain ya hace setVisible(true) y la ventana queda abierta. TotitoApp prefirió la lambda () -> new TotitoApp().setVisible(true) porque ahí el constructor no muestra la ventana, y hacía falta una segunda llamada.

¿Lambda o referencia? Usa la referencia cuando la lambda solo pasaría sus parámetros a un método, sin hacer nada más: es más corta y el nombre del método documenta la intención (this::alPulsarCasilla se lee mejor que (f, c) -> alPulsarCasilla(f, c)). Si hay que cambiar parámetros, agregar valores o hacer dos cosas, usa la lambda.

Clases dentro de clases

Hasta ahora cada clase del Totito vivía en su propio archivo. Pero Java permite declarar una clase dentro de otra. Piensa en un mueble con cajones: el cajón es una pieza con su propia forma, pero no tiene sentido fuera de ese mueble, y guardarlo dentro lo mantiene ordenado y a mano. Hay cuatro tipos, y conviene distinguirlos.

1. Clase anidada estática (static class)

Una clase declarada dentro de otra con la palabra static. Es una clase normal y corriente, solo que su nombre vive dentro de la otra y puede ser privada. No está atada a ningún objeto de la clase de afuera. En el Totito hay dos.

En src/CampoTexto.java (capítulo 47), el filtro que no deja escribir más de 14 letras:

    /** Impide que el texto pase de MAXIMO caracteres. */
    private static class LimiteDeLargo extends DocumentFilter {
        @Override
        public void insertString(FilterBypass fb, int offset, String texto, AttributeSet attr)
                throws BadLocationException {
            replace(fb, offset, 0, texto, attr);
        }

Y en src/PantallaResultado.java (capítulo 60), la tarjeta con confeti:

    private static class TarjetaConConfeti extends Tarjeta {

        private static final Color[] COLORES = {Tema.ROSA, Tema.CIAN, Tema.MORADO};
        private boolean conConfeti = true;

        TarjetaConConfeti() {
            super(Tema.MORADO);
        }

Por qué así:

  • private: solo CampoTexto usa el filtro y solo PantallaResultado usa la tarjeta con confeti. Al ser privadas, ninguna otra clase las ve ni puede depender de ellas; se pueden cambiar o borrar sin miedo. Una clase de primer nivel (en su archivo) no puede ser private; una anidada sí.
  • static: ninguna de las dos necesita un objeto concreto de la clase de afuera. El filtro usa MAXIMO, que es una constante static de CampoTexto, y eso sí puede verlo. Ser static la hace más liviana y más clara: no guarda una referencia escondida al objeto exterior.
  • Dentro y no en su archivo: un archivo menos en src, y quien lea CampoTexto encuentra el filtro justo ahí, al final.

Las interfaces y los enums declarados dentro de una clase son siempre estáticos aunque no lo digan: PanelTablero.OyenteCasilla, Iconos.Icono, Partida.Modo (capítulo 26). Por eso se nombran desde fuera con el nombre de la clase y un punto.

2. Clase interna (sin static)

Si quitas el static, la clase pasa a ser interna: cada objeto suyo pertenece a un objeto concreto de la clase de afuera, y puede usar sus campos directamente, incluso los privados. Es como el aula de una escuela: el aula «3.º B» no existe en el aire, existe en una escuela determinada. El Totito no declara ninguna clase interna con nombre, pero sus clases anónimas (abajo) se comportan así. Lo verás en el ejemplo del final de esta sección.

3. Clase local

Una clase declarada dentro de un método. Solo existe dentro de ese método. Es rara; se usa cuando una pequeña clase de apoyo solo tiene sentido en un único lugar. El Totito no tiene ninguna.

4. Clase anónima

Una clase sin nombre que se declara y se instancia (se crea su objeto) en la misma expresión, con la forma new Tipo(...) { cuerpo }. Tipo puede ser una interfaz (como la Navegacion de mentira de VistaPrevia, capítulo 24) o una clase que se extiende. El caso más importante del Totito está en el constructor de src/PanelTablero.java (capítulo 48):

        MouseAdapter raton = new MouseAdapter() {
            @Override
            public void mouseMoved(MouseEvent e) {
                actualizarCasillaEncima(e.getX(), e.getY());
            }

            @Override
            public void mouseExited(MouseEvent e) {
                actualizarCasillaEncima(-1, -1);
            }

            @Override
            public void mousePressed(MouseEvent e) {
                actualizarCasillaEncima(e.getX(), e.getY());
                if (interactivo && oyente != null && filaEncima >= 0) {
                    oyente.casillaPulsada(filaEncima, columnaEncima);
                }
            }
        };
        addMouseListener(raton);
        addMouseMotionListener(raton);

Símbolo por símbolo:

  • MouseAdapter raton =: una variable local de tipo MouseAdapter.
  • new MouseAdapter(): «crea un objeto de… », y los paréntesis llaman al constructor del padre (aquí, sin argumentos).
  • {: la llave abierta justo después es lo que convierte esto en una clase anónima: «…de una clase nueva, sin nombre, que hereda de MouseAdapter y que es así:».
  • Tres métodos con @Override: los tres que interesan (mover el ratón, salir del tablero, presionar el botón).
  • };: la llave cierra la clase, y el punto y coma la asignación.

Dos cosas importantes. Primero, dentro de la clase anónima se usan interactivo, oyente, filaEncima y columnaEncima, que son campos privados de PanelTablero, y se llama a actualizarCasillaEncima, un método privado. Puede hacerlo porque una clase anónima creada dentro de un método de instancia es una clase interna: está atada a este panel. Segundo, el mismo objeto raton se registra dos veces: como oyente de clics (addMouseListener) y como oyente de movimiento (addMouseMotionListener). Eso funciona porque MouseAdapter implementa a la vez las dos interfaces.

CampoTexto hace algo parecido con new FocusAdapter() { ... } para volver a pintar el borde cuando el campo gana o pierde el foco, y SelectorSimbolo y OpcionModo usan new MouseAdapter() { ... } con un solo método.

¿Por qué ahí no se usa una lambda?

Por dos razones, y las dos son obligatorias:

  1. MouseAdapter es una clase (abstracta), no una interfaz. Las lambdas solo sirven para interfaces funcionales.
  2. Aunque se usara la interfaz MouseListener, esta tiene cinco métodos abstractos. Una lambda es un único método; no puede cumplir cinco.

Si lo intentas con una interfaz de dos métodos, el compilador lo dice claramente:

SinLambda.java:3: error: incompatible types: OyenteSensor is not a functional interface
        OyenteSensor oyente = () -> System.out.println("abierta");
                              ^
    multiple non-overriding abstract methods found in interface OyenteSensor
1 error
error: compilation failed

«OyenteSensor no es una interfaz funcional: hay varios métodos abstractos». Aquí entra la idea del adaptador: MouseAdapter es una clase que implementa las interfaces del ratón con todos sus métodos vacíos. Tú heredas de ella y sobrescribes solo los que te interesan; los otros ya están «cumplidos» sin hacer nada. Sin el adaptador, el PanelTablero tendría que escribir también mouseClicked, mouseReleased, mouseEntered, mouseDragged y mouseWheelMoved vacíos.

this en una lambda y en una clase anónima Dentro de una lambda, this es el objeto que la escribió (la pantalla, el panel). Dentro de una clase anónima, this es el objeto anónimo. Por eso en el MouseAdapter de PanelTablero se llama a actualizarCasillaEncima(...) sin this: Java lo busca primero en la clase anónima, no lo encuentra, y sigue buscando en PanelTablero.

Los cuatro tipos en un solo programa

Guárdalo como ClasesDentro.java. Usa una escuela (para la anidada estática, la interna y la local) y un sensor de puerta con su adaptador (para la anónima):

public class ClasesDentro {
    public static void main(String[] args) {
        // 1) Clase anidada ESTATICA: se crea sin necesitar un objeto Escuela.
        Escuela.Horario horario = new Escuela.Horario("07:30", "12:30");
        System.out.println("Horario: " + horario);

        // 2) Clase INTERNA (no estatica): cada Aula pertenece a UNA escuela concreta.
        Escuela escuela = new Escuela("Escuela Las Flores");
        Escuela.Aula aula = escuela.new Aula("3.º B");
        aula.presentarse();

        // 3) Clase LOCAL: declarada dentro de un metodo, solo existe ahi.
        escuela.imprimirLista(new String[]{"Ana", "Luis", "Sofía"});

        // 4) Clase ANONIMA que extiende una clase "adaptadora" con varios metodos.
        Sensor puerta = new Sensor();
        puerta.setOyente(new AdaptadorSensor() {
            @Override
            public void alAbrir() {
                System.out.println("Alguien abrió la puerta");
            }
            // alCerrar() no se escribe: el adaptador ya trae uno vacio.
        });
        puerta.abrir();
        puerta.cerrar();
        System.out.println("Fin");
    }
}

class Escuela {
    private final String nombre;

    Escuela(String nombre) {
        this.nombre = nombre;
    }

    /** Anidada estatica: no necesita (ni puede ver) el "nombre" de una escuela. */
    static class Horario {
        private final String entrada;
        private final String salida;

        Horario(String entrada, String salida) {
            this.entrada = entrada;
            this.salida = salida;
        }

        @Override
        public String toString() {
            return entrada + " a " + salida;
        }
    }

    /** Interna: cada Aula ve los campos de SU escuela (aqui, nombre). */
    class Aula {
        private final String grado;

        Aula(String grado) {
            this.grado = grado;
        }

        void presentarse() {
            System.out.println("Soy el aula " + grado + " de " + nombre);
        }
    }

    void imprimirLista(String[] alumnos) {
        class Renglon {   // clase local
            String formatear(int numero, String alumno) {
                return String.format("%2d. %s", numero, alumno);
            }
        }
        Renglon renglon = new Renglon();
        for (int i = 0; i < alumnos.length; i++) {
            System.out.println(renglon.formatear(i + 1, alumnos[i]));
        }
    }
}

/** Como MouseListener: varios metodos que hay que atender. */
interface OyenteSensor {
    void alAbrir();

    void alCerrar();
}

/** Como MouseAdapter: implementa todo con metodos vacios, para sobrescribir solo lo que importa. */
abstract class AdaptadorSensor implements OyenteSensor {
    @Override
    public void alAbrir() {
    }

    @Override
    public void alCerrar() {
    }
}

class Sensor {
    private OyenteSensor oyente;

    void setOyente(OyenteSensor oyente) {
        this.oyente = oyente;
    }

    void abrir() {
        oyente.alAbrir();
    }

    void cerrar() {
        oyente.alCerrar();
    }
}

Las interfaces funcionales que trae Java

Para no tener que inventar una interfaz como Operacion cada vez, el paquete java.util.function trae las formas más comunes ya hechas. Las cuatro más usadas:

InterfazMétodoFormaPara qué
Consumer<T>accept(T t)recibe algo, no devuelve nadahacer algo con cada elemento (imprimir, guardar)
Function<T, R>R apply(T t)recibe una cosa, devuelve otratransformar (producto → etiqueta)
Predicate<T>boolean test(T t)recibe algo, responde sí o nofiltrar (¿está agotado?)
Supplier<T>T get()no recibe nada, entrega algofabricar valores bajo pedido

A estas se suman Runnable (no recibe ni devuelve) y Comparator<T> (compara dos cosas para ordenarlas). Las listas de Java tienen métodos que las aceptan: forEach (con un Consumer), removeIf (con un Predicate) y sort (con un Comparator). Este inventario de una tienda las usa todas. Guárdalo como Tienda.java:

import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;
import java.util.function.Consumer;
import java.util.function.Function;
import java.util.function.Predicate;
import java.util.function.Supplier;

public class Tienda {
    public static void main(String[] args) {
        List<Producto> inventario = new ArrayList<>();
        inventario.add(new Producto("Arroz 1 lb", 6.50, 40));
        inventario.add(new Producto("Frijol negro", 9.75, 0));
        inventario.add(new Producto("Café molido", 32.00, 12));
        inventario.add(new Producto("Azúcar 5 lb", 21.25, 8));

        // Consumer: recibe algo y no devuelve nada.
        Consumer<Producto> imprimir = p -> System.out.printf("  %-14s Q%6.2f  (%d)%n",
                p.getNombre(), p.getPrecio(), p.getExistencia());

        System.out.println("Ordenado por precio:");
        inventario.sort(Comparator.comparing(Producto::getPrecio));
        inventario.forEach(imprimir);

        System.out.println("Ordenado por nombre, de Z a A:");
        inventario.sort(Comparator.comparing(Producto::getNombre).reversed());
        inventario.forEach(imprimir);

        // Predicate: recibe algo y responde true o false.
        Predicate<Producto> agotado = p -> p.getExistencia() == 0;
        inventario.removeIf(agotado);
        System.out.println("Sin los agotados quedan " + inventario.size() + " productos");

        // Function: recibe algo y devuelve otra cosa.
        Function<Producto, String> etiqueta = p -> p.getNombre().toUpperCase() + " - Q" + p.getPrecio();
        System.out.println("Etiqueta: " + etiqueta.apply(inventario.get(0)));

        // Supplier: no recibe nada y entrega algo nuevo cada vez que se le pide.
        Supplier<Producto> nuevo = () -> new Producto("(sin nombre)", 0, 0);
        System.out.println("Plantilla: " + nuevo.get().getNombre());
    }
}

class Producto {
    private final String nombre;
    private final double precio;
    private final int existencia;

    Producto(String nombre, double precio, int existencia) {
        this.nombre = nombre;
        this.precio = precio;
        this.existencia = existencia;
    }

    String getNombre() {
        return nombre;
    }

    double getPrecio() {
        return precio;
    }

    int getExistencia() {
        return existencia;
    }
}

La línea clave es Comparator.comparing(Producto::getPrecio). Producto::getPrecio es la quinta forma de referencia de la tabla: «para cualquier producto p, llama a p.getPrecio()». Comparator.comparing recibe esa «forma de sacar la clave» y fabrica un comparador que ordena por ella. .reversed() le da la vuelta. Compáralo con el Ranking.java del capítulo 24: allí Puntaje tenía un orden fijo, escrito dentro de la clase con Comparable; aquí el orden se elige desde fuera, en el momento, y el mismo inventario se ordena de dos maneras sin tocar Producto.

Puntos y comas en los decimales printf usa la configuración regional de tu Windows. En Guatemala los decimales llevan punto, como arriba; si tu Windows está configurado para un país que usa coma, verás 6,50. No es un error del programa.

Resumen

  • Una interfaz funcional tiene un solo método abstracto; @FunctionalInterface le pide al compilador que lo vigile. Solo ellas admiten lambdas y referencias.
  • Una lambda ((parámetros) -> cuerpo) es un método sin nombre que se convierte en un objeto de la interfaz esperada. No se ejecuta al escribirse, sino cuando alguien llama a su método.
  • Los botones del Totito usan lambdas con addActionListener; los iconos son lambdas guardadas en constantes static final (patrón Estrategia).
  • Una lambda solo puede capturar variables locales efectivamente finales; por eso JuegoMain copia fila y columna en f y c. Los campos no tienen esa restricción.
  • Una referencia a método (::) señala un método existente cuya forma encaja: this::alPulsarCasilla, navegacion::salir, this::cerrar, Iconos::persona, JuegoMain::new.
  • Clases dentro de clases: anidadas estáticas (LimiteDeLargo, TarjetaConConfeti), internas (atadas a un objeto exterior), locales y anónimas (el MouseAdapter de PanelTablero).
  • Se usa clase anónima y no lambda cuando hay que extender una clase o escribir varios métodos; los adaptadores traen todos los métodos vacíos.
  • java.util.function trae Consumer, Function, Predicate y Supplier; con Comparator.comparing ordenas listas por cualquier campo.
Aplícalo fuera del Totito
  • Cualquier aplicación con botones (una calculadora neón, capítulo 68): cada tecla con boton.addActionListener(e -> agregarDigito("7")) y las operaciones guardadas como lambdas en un mapa, "+" -> (a, b) -> a + b, en lugar de un switch enorme.
  • Tienda o inventario: removeIf(p -> p.getExistencia() == 0) para quitar agotados, sort(Comparator.comparing(Producto::getPrecio)) para ordenar, un Predicate por cada filtro que elija el usuario (por categoría, por precio máximo).
  • Sistema escolar: una clase Boleta con una clase anidada private static class Renglon para cada curso, y un Comparator para listar alumnos por promedio o por apellido según el botón que se pulse.
  • Banco: reglas de comisión como lambdas (Function<Double, Double>) que se eligen según el tipo de cuenta, y oyentes (Consumer<Movimiento>) que se avisan cada vez que hay un retiro, por ejemplo para mandar una alerta.
