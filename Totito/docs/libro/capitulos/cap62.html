Capítulo 62Probar y depurar

El Totito ya funciona, pero antes de empaquetarlo y regalarlo al mundo tienes que estar seguro de que funciona bien. En este capítulo aprendes a leer los mensajes de error como un mapa, a detener el programa a la mitad para mirar sus variables con el depurador de NetBeans y a probar el juego con una lista ordenada, para que ningún error llegue a manos de quien descargue tu instalador.

Por qué este capítulo va antes de empaquetar

En los capítulos 63 a 67 vas a convertir el Totito en un .jar, luego en una carpeta con Totito.exe, luego en un instalador y por último lo vas a publicar en GitHub. Cada uno de esos pasos copia tu programa tal como está. Si hay un error dentro, el error viaja en el .jar, en el .exe y en el instalador, y le llega a tu primo, a tu profesora y a cualquier persona del mundo que lo descargue. Arreglarlo después significa repetir todo el empaquetado y volver a publicar. Por eso se prueba antes.

Además, ningún programador escribe código sin errores. La diferencia entre quien empieza y quien tiene experiencia no es que el segundo no se equivoque: es que sabe encontrar el error rápido. Esa habilidad tiene nombre: depurar (en inglés debugging, «quitar bichos»). La palabra viene de la época de las computadoras gigantes, cuando un insecto real metido en un relé hacía fallar la máquina; hoy un «bug» es cualquier error en un programa.

Probar y depurar no son lo mismo. Probar es usar el programa a propósito para descubrir si algo falla («¿qué pasa si hago clic en una casilla ocupada?»). Depurar es, una vez que sabes que algo falla, averiguar por qué y corregirlo. Primero se prueba; si una prueba falla, se depura.

Las tres familias de errores

Todos los errores que te vas a encontrar en Java caen en una de tres familias. Saber en cuál estás te dice qué herramienta usar.

FamiliaCuándo apareceQuién te avisaEjemplo en el Totito
De compilaciónAl compilar (Clean and Build, o javac), antes de que el programa arranqueEl compilador, con un mensaje que dice archivo y línea. En NetBeans, un subrayado rojoOlvidar un ; en Jugador.java
De ejecuciónMientras el programa corre: compila bien, pero en algún momento «revienta»La máquina virtual de Java (JVM), con una excepción y un stack tracePedir la casilla (3, 0), que no existe
De lógicaEl programa corre sin quejarse, pero hace algo distinto de lo que queríasNadie. Lo descubres tú al probarQue el turno no cambie y la X juegue dos veces seguidas

Los de compilación son los más fáciles: el compilador te dice dónde están. Los de ejecución son intermedios: Java te dice dónde reventó, pero a veces la causa está antes. Los de lógica son los más difíciles, porque nadie te avisa; para ellos existen la lista de pruebas y el depurador.

Errores de compilación frecuentes

Cuando compilas, javac lee tu código como un corrector muy estricto lee un examen. Si algo no cumple las reglas del lenguaje, no genera ningún .class y te da una lista de errores. En NetBeans los ves de tres formas: un subrayado rojo bajo el código, un círculo rojo con una ! al lado del número de línea (si pasas el ratón encima, aparece el mensaje) y, al hacer Clean and Build, el texto completo en la ventana Output con un enlace azul que te lleva a la línea.

Los mensajes de javac salen en inglés aunque tu Windows esté en español (el JDK no trae traducción al español). Todos los ejemplos que siguen son reales: los provoqué a propósito con el JDK 21 y copié la salida tal cual. Todos tienen la misma forma:

Archivo.java:NÚMERO: error: QUÉ PASA
        la línea con el problema
        ^   ← el sombrerito señala la columna exacta

Regla práctica: arregla siempre el primer error de la lista y vuelve a compilar. Un solo error, como una llave que falta, puede confundir al compilador y producir diez mensajes más que desaparecen solos en cuanto corriges el primero.

1. Falta un punto y coma

public Jugador(String nombre, char ficha) {
    this.nombre = nombre
    this.ficha = ficha;
}
Jugador.java:6: error: ';' expected
        this.nombre = nombre
                            ^
1 error

';' expected significa «esperaba un punto y coma». El ; es el punto final de cada instrucción en Java (lo viste en el capítulo 11); sin él, el compilador no sabe dónde termina una orden y empieza la siguiente. Fíjate en que el sombrerito apunta al final de la línea 6: ahí es donde falta. Solución: escribir el ;.

2. Llaves que no cierran

public String getNombre() {
    return nombre;

}
Jugador.java:11: error: reached end of file while parsing
}
 ^
1 error

reached end of file while parsing = «llegué al final del archivo mientras lo leía». Traducción libre: «abriste más llaves { de las que cerraste y se me acabó el archivo esperando las que faltan». Aquí al método getNombre le falta su }, así que la última llave del archivo cierra el método y la clase se queda abierta. El número de línea no te dice dónde falta la llave, solo dónde se dio cuenta el compilador (al final). Para encontrarla, en NetBeans haz clic justo a la derecha de una llave: su pareja se resalta. Y usa Source → Format (Alt+Shift+F): si la sangría queda rara a partir de cierto punto, la llave que falta está ahí.

3. Tipos que no encajan

int victorias = "3";
char ficha = "X";
Prueba.java:3: error: incompatible types: String cannot be converted to int
        int victorias = "3";
                        ^
Prueba.java:4: error: incompatible types: String cannot be converted to char
        char ficha = "X";
                     ^
2 errors

incompatible types = «tipos incompatibles». Una caja de tipo int solo acepta números enteros; "3" entre comillas dobles es un String (un texto que casualmente tiene un 3). El segundo caso es el más traicionero del Totito: una ficha es un char y se escribe con comillas simples, 'X'; con comillas dobles, "X", es un texto de una letra. Solución: int victorias = 3; y char ficha = 'X'; (repasa el capítulo 12).

4. Símbolo no encontrado

Tablero tablero = new Tablero();
tablero.marcarcasilla(0, 0, 'X');
System.out.println(tablro);
Prueba.java:4: error: cannot find symbol
        tablero.marcarcasilla(0, 0, 'X');
               ^
  symbol:   method marcarcasilla(int,int,char)
  location: variable tablero of type Tablero
Prueba.java:5: error: cannot find symbol
        System.out.println(tablro);
                           ^
  symbol:   variable tablro
  location: class Prueba
2 errors

cannot find symbol = «no encuentro ese nombre». Es el error más común de todos. Un símbolo es cualquier nombre que tú inventaste: una variable, un método, una clase. Las dos líneas de abajo son oro: symbol dice qué nombre buscó y location dónde lo buscó. En el primer caso buscó un método marcarcasilla con tres parámetros (int,int,char) dentro de la clase Tablero y no lo hay: el método real es marcarCasilla, con C mayúscula. En el segundo buscó una variable tablro: falta una e. Las causas típicas son cuatro: una letra mal escrita, una mayúscula distinta, un import que falta (por ejemplo usar JButton sin import javax.swing.JButton;) o usar una variable fuera de las llaves donde se declaró (el alcance, capítulo 16).

5. Las mayúsculas importan

string nombre = "Ana";
system.out.println(nombre);
Prueba.java:3: error: cannot find symbol
        string nombre = "Ana";
        ^
  symbol:   class string
  location: class Prueba
Prueba.java:4: error: package system does not exist
        system.out.println(nombre);
              ^
2 errors

Java distingue mayúsculas de minúsculas: String y string son dos nombres distintos, y solo el primero existe. Lo mismo con System. El segundo mensaje es curioso: como system con minúscula no es ninguna clase conocida, Java supone que quizá es un paquete (una carpeta de clases) y dice «el paquete system no existe». Moraleja: cuando un mensaje te parezca absurdo, revisa primero las mayúsculas. La convención (capítulo 27) ayuda: las clases empiezan con mayúscula (Tablero), las variables y métodos con minúscula (tablero, marcarCasilla).

6. El nombre del archivo no coincide con la clase

Jugadores.java:1: error: class Jugador is public, should be declared in a file named Jugador.java
public class Jugador {
       ^
1 error

Una clase public debe vivir en un archivo con su mismo nombre exacto, mayúsculas incluidas. Pasa cuando renombras un archivo en el Explorador de Windows sin renombrar la clase, o al revés. En NetBeans, para cambiar el nombre de una clase usa siempre clic derecho → Refactor → Rename… (Ctrl+R): cambia la clase, el archivo y todos los lugares que la usan a la vez.

7. Falta un return

static boolean esX(char ficha) {
    if (ficha == 'X') {
        return true;
    }
}
Prueba.java:6: error: missing return statement
    }
    ^
1 error

El método promete devolver un boolean, pero si la ficha no es 'X' el código llega al final sin devolver nada. Java revisa todos los caminos posibles y se niega a compilar si alguno se queda sin respuesta. Solución: añadir return false; antes de la última llave.

Busca el mensaje, no lo memorices. No necesitas aprenderte estos textos. Cuando veas uno nuevo, copia la parte genérica (por ejemplo missing return statement, sin tus nombres de variables) y búscala en internet: casi seguro alguien tuvo el mismo problema. El apéndice D reúne los más comunes con su solución.

Leer un stack trace

Cuando un programa revienta mientras corre, Java lanza una excepción (un objeto que describe el problema, capítulo 26). Si nadie la atrapa con try/catch, la JVM detiene ese hilo e imprime un stack trace («rastro de la pila»): la lista de métodos que estaban en marcha en ese instante, del más reciente al más antiguo. Recuerda la pila de llamadas del capítulo 16: cada vez que un método llama a otro, el nuevo se apila encima. El stack trace es una foto de esa pila en el momento del accidente.

Provoca uno a propósito

La mejor manera de perderle el miedo es fabricar uno. Vas a crear un programita de usar y tirar en la carpeta herramientas, igual que PruebaConsola en el capítulo 32. Primero compila el proyecto en NetBeans (Run → Clean and Build Project, Shift+F11) para que exista target\classes. Luego, en PowerShell, desde la carpeta del proyecto:

cd $HOME\Proyectos\Totito
New-Item herramientas\ProvocarError.java
notepad herramientas\ProvocarError.java

Escribe esto en el Bloc de notas y guarda (Ctrl+S):

public class ProvocarError {
    public static void main(String[] args) {
        Tablero tablero = new Tablero();
        tablero.marcarCasilla(1, 1, 'X');
        System.out.println("Centro: " + tablero.obtenerCasilla(1, 1));
        System.out.println("Fuera: " + tablero.obtenerCasilla(3, 0));
    }
}

La línea 6 pide la casilla de la fila 3, que no existe: las filas válidas son 0, 1 y 2. Ejecútalo:

java -cp target\classes herramientas\ProvocarError.java

Esta es la salida real:

Centro: X
Exception in thread "main" java.lang.ArrayIndexOutOfBoundsException: Index 3 out of bounds for length 3
	at Tablero.obtenerCasilla(Tablero.java:44)
	at ProvocarError.main(ProvocarError.java:6)

Cómo se lee, renglón por renglón

  1. Centro: X — la línea 5 funcionó. Eso ya te dice algo: el error es después.
  2. Exception in thread "main" — «excepción en el hilo main». Un hilo es una línea de ejecución; main es el que arranca con tu método main. En un programa Swing verás a menudo "AWT-EventQueue-0", que es el hilo de eventos de la interfaz (el EDT del capítulo 37).
  3. java.lang.ArrayIndexOutOfBoundsException — el tipo de excepción. Su nombre ya explica casi todo: «índice de arreglo fuera de los límites».
  4. Index 3 out of bounds for length 3 — el mensaje: pediste el índice 3 de un arreglo de largo 3 (índices válidos: 0, 1, 2).
  5. at Tablero.obtenerCasilla(Tablero.java:44) — la primera línea at es donde reventó: en el método obtenerCasilla de la clase Tablero, archivo Tablero.java, línea 44 (return casillas[fila][columna];).
  6. at ProvocarError.main(ProvocarError.java:6) — quién llamó a ese método: main, en la línea 6. Si hubiera más niveles, seguirían hacia abajo hasta llegar al primer método que se ejecutó.
Dónde revienta no siempre es dónde está la culpa. El stack trace dice que el fallo ocurrió en Tablero.java:44, pero esa línea está bien: hace exactamente lo que debe. La culpa es de quien le pasó un 3. Por eso se lee el stack trace de arriba hacia abajo buscando la primera línea que sea código tuyo y sospechoso. Las líneas que empiezan con java., javax. o java.desktop/ son de la biblioteca de Java: casi nunca son el problema, se saltan.

En NetBeans no hace falta buscar la línea a mano: en la ventana Output, cada (Archivo.java:NN) sale como enlace azul; un clic y el editor salta a esa línea.

NullPointerException: el clásico

Cambia el contenido de ProvocarError.java por este (la clase se llama igual para no crear otro archivo):

public class ProvocarError {
    public static void main(String[] args) {
        Jugador ana = new Jugador("Ana", 'X');
        Jugador nadie = null;
        Partida partida = new Partida(ana, nadie, Partida.Modo.DOS_JUGADORES);
        System.out.println(partida.getEstado());
    }
}
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "Jugador.getFicha()" because "jugador2" is null
	at Partida.<init>(Partida.java:44)
	at ProvocarError.main(ProvocarError.java:5)

null significa «esta variable no apunta a ningún objeto» (capítulo 18). Si intentas llamar a un método sobre null, Java no tiene a quién pedírselo y lanza NullPointerException (NPE). Desde Java 14 el mensaje es muy claro: «no puedo invocar Jugador.getFicha() porque jugador2 es null». El <init> es el nombre interno que Java da a un constructor: reventó en el constructor de Partida, línea 44, la que compara las fichas de los dos jugadores. La causa real está en ProvocarError, línea 5, que le pasó un jugador vacío.

Las NPE más frecuentes en un programa Swing: usar un componente antes de crearlo con new, olvidar asignar un campo en el constructor, o un método que devuelve null y nadie lo revisa (como Partida.getGanador(), que devuelve null si hubo empate: por eso PantallaResultado pregunta el estado antes de pedir el nombre del ganador).

Una excepción que lanzaste tú

Ahora prueba a crear dos jugadores con la misma ficha:

Partida partida = new Partida(new Jugador("Ana", 'X'), new Jugador("Luis", 'X'),
        Partida.Modo.DOS_JUGADORES);
Exception in thread "main" java.lang.IllegalArgumentException: Los dos jugadores no pueden usar la misma ficha
	at Partida.<init>(Partida.java:45)
	at ProvocarError.main(ProvocarError.java:3)

Este error lo escribiste tú en el capítulo 38: la línea 45 de Partida dice throw new IllegalArgumentException(...). Es un error bueno: en vez de dejar que el juego siga en un estado absurdo (dos X), el programa se niega a continuar y dice exactamente por qué, en español. Esa es la idea de proteger los invariantes (capítulo 19): fallar pronto y con un mensaje claro.

Un stack trace largo: HeadlessException

No todos los stack traces son de dos líneas. Este lo obtuve ejecutando el Totito en un servidor sin pantalla (un equipo al que se entra solo por terminal):

or no headful library support was found,

	at java.desktop/java.awt.GraphicsEnvironment.checkHeadless(GraphicsEnvironment.java:164)

Aplica el método: salta las líneas de java.desktop/ y busca la primera tuya. Es TotitoApp.<init>(TotitoApp.java:18): el constructor de TotitoApp, en la línea super("Juego del Totito");, que crea la ventana. La siguiente, TotitoApp.lambda$main$0, es la lambda () -> new TotitoApp().setVisible(true) de la línea 46 (Java le pone ese nombre interno a las lambdas: «la lambda número 0 dentro de main»). Y el hilo es AWT-EventQueue-0 porque SwingUtilities.invokeLater mandó crear la ventana en el hilo de eventos. Moraleja: HeadlessException significa «quisiste abrir una ventana en un equipo sin pantalla». En tu Windows no la verás, salvo que ejecutes el juego con la opción -Djava.awt.headless=true, en una sesión remota rara o en un servidor.

«Caused by». A veces verás un stack trace con una o más secciones que empiezan con Caused by: («causado por»). Ocurre cuando una excepción se envuelve dentro de otra. La causa original es la última sección Caused by; empieza a leer por ahí. Lo verás, por ejemplo, con java -cp out totitoapp: «Error: Could not find or load main class totitoapp» y debajo «Caused by: java.lang.ClassNotFoundException: totitoapp» (la clase se llama TotitoApp, con mayúsculas).

Cuando termines de experimentar, borra el archivo para que no quede en el proyecto:

Remove-Item herramientas\ProvocarError.java

Depurar con System.out.println

La técnica más antigua y sencilla: escribir en la consola qué está pasando. Por ejemplo, para ver cada jugada, añade temporalmente una línea al principio de Partida.jugar:

public boolean jugar(int fila, int columna) {
    System.out.println("jugar(" + fila + ", " + columna + ") turno=" + turno + " estado=" + estado);
    if (estado != Estado.EN_CURSO) {
        ...

Ejecuta con F6, juega una partida y mira la ventana Output:

jugar(0, 0) turno=1 estado=EN_CURSO

Marca tus println temporales. Empiézalos siempre igual, por ejemplo System.out.println("DEPURAR " + ...). Antes de hacer commit, busca «DEPURAR» en todo el proyecto (en NetBeans, Edit → Find in Projects…, Ctrl+Shift+F) y bórralos. Y antes de un commit, git diff (capítulo 9) te muestra cualquier línea que se te haya quedado. Si quieres que el mensaje salga en rojo en NetBeans, usa System.err.println: es la salida de errores.

El depurador de NetBeans

El depurador (debugger) es una herramienta que ejecuta tu programa bajo vigilancia: puedes congelarlo en una línea, mirar el valor de todas las variables en ese instante, avanzar una línea a la vez y ver cómo cambian. Es como ver una jugada de fútbol en cámara lenta, cuadro por cuadro, con los nombres de los jugadores sobre la cabeza. Con println adivinas qué mirar antes de ejecutar; con el depurador decides qué mirar mientras el programa está detenido.

Vocabulario mínimo

TérminoQué es
Punto de interrupción (breakpoint)Una marca en una línea que dice: «cuando llegues aquí, detente antes de ejecutarla»
PausaEl estado del programa detenido: existe, tiene sus variables, pero no avanza
Paso (step)Ejecutar una sola línea y volver a detenerse
Vigilancia (watch)Una expresión que quieres ver siempre, como jugadores[turno].getNombre()
Pila de llamadas (call stack)Lo mismo que el stack trace, pero en vivo: qué métodos te trajeron hasta aquí

Paso 1: poner un punto de interrupción en Partida.jugar

  1. En NetBeans, abre Partida.java (Source Packages → <default package>, doble clic).
  2. Busca el método jugar. Su primera línea de código es la 67: if (estado != Estado.EN_CURSO) {.
  3. Haz un clic sobre el número 67 en el margen izquierdo. Aparece un cuadrado rojo-rosado en lugar del número y toda la línea se tiñe de ese color. Eso es el punto de interrupción. (También puedes poner el cursor en la línea y pulsar Ctrl+F8, Toggle Line Breakpoint.)
  4. Para quitarlo, otro clic en el mismo sitio.
Pon el punto en una línea con código. Si lo pones en una línea en blanco, en un comentario o en la línea de la firma del método, NetBeans puede moverlo a la siguiente línea ejecutable o mostrarlo como inválido (con un aspecto distinto, roto). La primera línea dentro del método es siempre una apuesta segura.

Paso 2: ejecutar en modo depuración

Ejecutar con F6 (Run) ignora los puntos de interrupción. Para que cuenten, hay que arrancar con el depurador: menú Debug → Debug Project, o Ctrl+F5, o el botón Debug Project de la barra de herramientas, justo a la derecha del triángulo verde de Run. NetBeans compila, arranca el juego conectado al depurador (verás en Output líneas sobre Maven y un mensaje de que el depurador se conectó) y la ventana del Totito aparece normal.

Juega: Jugar → escribe dos nombres → modo 2 jugadores → empieza la partida. Haz clic en la casilla del centro.

Paso 3: el programa se detiene

En cuanto haces el clic, NetBeans salta al frente y la línea 67 aparece resaltada en verde con una flecha en el margen. Eso significa: «estoy detenido justo antes de ejecutar esta línea». La ventana del Totito se queda congelada; si la tocas, puede que Windows la marque como «No responde». No te asustes, es lo esperado: el depurador detuvo el hilo de eventos, que es el mismo hilo que se encarga de redibujar la ventana (capítulo 37). Mientras esté en pausa, nadie la pinta.

Paso 4: mirar las variables

Abajo aparece la ventana Variables (si no la ves: Window → Debugging → Variables, Alt+Shift+1). Verás algo así:

thisPartida#1234 (un número de identificación del objeto)

fila y columna son los parámetros que recibió jugar: el clic fue en el centro, (1, 1). Haz clic en el triangulito junto a this para abrir el objeto Partida por dentro: verás sus campos tablero, jugadores, modo, ia (que vale null porque estás en modo 2 jugadores, ¡justo como dice la línea 49!), victorias, empates, turno (0), estado (EN_CURSO) y ganador (null). Puedes seguir abriendo: tablero → casillas muestra la matriz de 3×3 con sus ' '. Es tu programa visto por dentro, como una radiografía.

Truco rápido: pasa el ratón por encima de cualquier variable en el editor (por ejemplo sobre turno en la línea 70) y un globo te muestra su valor.

Paso 6: vigilancias (Watches)

La ventana Variables solo muestra variables. Una vigilancia muestra el resultado de cualquier expresión. Con el programa detenido, menú Debug → New Watch… (Ctrl+Shift+F7) y escribe:

jugadores[turno].getNombre()

Acepta. En la ventana Watches (Window → Debugging → Watches) verás el nombre del jugador al que le toca. Añade otra con tablero.verificarGanador() y otra con victorias[0] + " a " + victorias[1]. Cada vez que el programa se detiene, las vigilancias se recalculan solas. Para una consulta de una sola vez, sin dejarla fija, usa Debug → Evaluate Expression… (Ctrl+F9).

Las vigilancias también ejecutan código. Si escribes una vigilancia que cambia algo (por ejemplo tablero.marcarCasilla(0, 0, 'O')), el depurador la ejecuta de verdad y modifica la partida. Usa solo expresiones que pregunten, nunca que cambien.

Paso 7: la pila de llamadas en vivo

Abre Window → Debugging → Call Stack. Estando detenido en Partida.jugar verás, de arriba abajo: Partida.jugar:67, luego PantallaJuego.alPulsarCasilla:67 (la pantalla que recibió el clic), luego PanelTablero$1.mousePressed:64 (el MouseAdapter anónimo del capítulo 48, por eso lleva $1), y debajo muchas líneas de java.awt y javax.swing: el recorrido del clic desde el ratón hasta tu método. Puede que veas además alguna línea con un nombre raro que contiene Lambda: es el puente invisible que Java crea para la referencia a método this::alPulsarCasilla (capítulo 25). Doble clic en cualquier línea de la pila y el editor te lleva ahí, con las variables de ese nivel.

Si juegas contra la IA verás que el punto de interrupción también se activa sin que hagas clic: la llamada viene de Partida.jugarTurnoIA, que llamó un Timer de PantallaJuego. La pila te cuenta esa historia sin que tengas que leer todo el código.

Paso 8: puntos de interrupción condicionales

Detenerse en cada jugada puede cansar. Haz clic derecho sobre el cuadrado rojo de la línea 67 → Breakpoint → Properties. Marca Condition y escribe:

fila == 2 && columna == 2

Ahora el programa solo se detendrá cuando alguien juegue en la esquina inferior derecha. Otros ejemplos útiles: turno == 1 (solo en el turno del segundo jugador) o empates > 0. La ventana Window → Debugging → Breakpoints (Alt+Shift+5) lista todos tus puntos para activarlos, desactivarlos o borrarlos. Cuando termines, bórralos: no hacen daño fuera del modo depuración, pero estorban.

Ejercicio guiado: caza un error de lógica

Vas a sembrar un error a propósito y a encontrarlo con el depurador, como si no supieras dónde está.

  1. En Partida.java, línea 81, cambia turno = 1 - turno; por turno = 1; y guarda.
  2. Ejecuta con F6 en modo 2 jugadores. Primera jugada: X. Segunda: O. Tercera: ¡otra vez O! Y para siempre O. Es un error de lógica: nada revienta.
  3. Pon el punto de interrupción en la línea 67, ejecuta con Ctrl+F5 y añade la vigilancia turno. Juega tres veces avanzando con F8 y fíjate en qué línea turno deja de alternar. La encontrarás en la línea 81.
  4. Deshaz el error con Git, que para eso está (capítulo 9):
git restore src\Partida.java
La técnica en una frase. Para depurar un error de lógica: (1) descríbelo con precisión («a la tercera jugada sale O en vez de X»); (2) elige el método donde se decide esa cosa; (3) detente ahí; (4) avanza con F8 comparando lo que esperabas con lo que ves. La primera línea donde no coinciden es el error.

Una prueba manual es una acción concreta con un resultado esperado, que ejecuta una persona. Se escriben en una lista para no depender de la memoria: así cada versión se prueba igual. La prueba 20 es importante: un programa puede funcionar en NetBeans y fallar empaquetado (por ejemplo, si falta un módulo de Java o las tildes se ven mal por una codificación distinta). Probar cada paquete es parte del trabajo.

Prueba los bordes. Los errores se esconden en los extremos: el primer turno y el último, la casilla 0 y la 2, el nombre vacío y el de 14 letras, la primera partida y la décima. Una buena lista de pruebas siempre tiene casos «raros» a propósito: es lo que hará alguien que no conoce el programa.

Una probadita de pruebas automáticas

La lista de 20 pruebas lleva unos 15 minutos. Si cada vez que cambias algo tuvieras que repetirla entera, dejarías de hacerlo. Por eso existen las pruebas automáticas: pequeños programas que usan tu código y comprueban, solos y en segundos, que el resultado sea el esperado. Las reglas del Totito están en Partida, que no sabe nada de ventanas (capítulo 38): se pueden probar sin abrir ninguna. Esa separación era justo para esto.

Este es un probador casero, sin librerías. Si quieres usarlo, créalo como herramientas\PruebasPartida.java:

/**
 * Pruebas automaticas sencillas de Partida, sin librerias.
 * Ejecutar desde la carpeta Totito, despues de compilar:
 *   java -cp target/classes herramientas/PruebasPartida.java
 */
public class PruebasPartida {

    private static int fallos = 0;

    public static void main(String[] args) {
        // 1) La X gana con la fila de arriba.
        Partida p = nueva();
        p.jugar(0, 0); p.jugar(1, 0);   // X, O
        p.jugar(0, 1); p.jugar(1, 1);   // X, O
        p.jugar(0, 2);                  // X completa la fila 0
        comprobar("gana la X con la fila 0", p.getEstado() == Partida.Estado.VICTORIA);
        comprobar("el ganador es Ana", p.getGanador().getNombre().equals("Ana"));
        comprobar("Ana suma 1 victoria", p.getVictorias(0) == 1);

        // 2) Una casilla ocupada no se puede volver a jugar.
        p = nueva();
        p.jugar(1, 1);
        comprobar("casilla ocupada devuelve false", !p.jugar(1, 1));

        // 3) Empate: tablero lleno sin tres en linea.
        p = nueva();
        int[][] jugadas = {{0,0},{0,1},{0,2},{1,1},{1,0},{1,2},{2,1},{2,0},{2,2}};
        for (int[] j : jugadas) {
            p.jugar(j[0], j[1]);
        }
        comprobar("empate con el tablero lleno", p.getEstado() == Partida.Estado.EMPATE);

        // 4) Reiniciar limpia el tablero pero conserva el marcador.
        p.reiniciar();
        comprobar("tras reiniciar sigue el empate en el marcador", p.getEmpates() == 1);
        comprobar("tras reiniciar el centro esta vacio",
                p.getTablero().obtenerCasilla(1, 1) == Tablero.VACIA);

        System.out.println(fallos == 0 ? "TODO BIEN" : fallos + " PRUEBA(S) FALLARON");
        System.exit(fallos == 0 ? 0 : 1);
    }

    private static Partida nueva() {
        return new Partida(new Jugador("Ana", 'X'), new Jugador("Luis", 'O'),
                Partida.Modo.DOS_JUGADORES);
    }

    private static void comprobar(String descripcion, boolean seCumple) {
        System.out.println((seCumple ? "  OK    " : "  FALLA ") + descripcion);
        if (!seCumple) {
            fallos++;
        }
    }
}

La idea es simple: cada prueba prepara una situación (crea una partida y juega unas casillas), y luego comprobar recibe una descripción y una condición que debería ser verdadera. Si lo es, imprime OK; si no, FALLA y suma un fallo. Al final, System.exit(1) si algo falló: ese número (el código de salida) le dice a otros programas si todo salió bien (0) o no (cualquier otro). Ejecútalo después de compilar:

java -cp target\classes herramientas\PruebasPartida.java
  OK    gana la X con la fila 0
  OK    el ganador es Ana
  OK    Ana suma 1 victoria
  OK    casilla ocupada devuelve false
  OK    empate con el tablero lleno
  OK    tras reiniciar sigue el empate en el marcador
  OK    tras reiniciar el centro esta vacio
TODO BIEN

Ahora siembra otra vez el error de turno = 1;, recompila con Shift+F11 y vuelve a ejecutar: la primera prueba falla al instante, sin abrir ninguna ventana. Esa es la magia: el probador descubre en un segundo lo que a ti te costó una partida entera. Después restaura con git restore src\Partida.java.

En proyectos profesionales no se escribe el comprobar a mano: se usa JUnit, la librería estándar de pruebas de Java, que NetBeans y Maven ejecutan automáticamente con cada Clean and Build. Lo verás en el capítulo 69. Lo que aprendiste aquí (preparar, actuar, comprobar) es exactamente lo mismo, con otra ropa.

Git Este capítulo no tiene commit en el plan del libro: todo lo que tocaste era temporal. Antes de seguir, asegúrate de que no quedó nada sembrado:

Si git status dice nothing to commit, working tree clean, todo está como en la v1.0.0. Resumen

  • Hay tres familias de errores: de compilación (te avisa javac), de ejecución (te avisa la JVM con una excepción) y de lógica (no te avisa nadie: hay que probar).
  • En los errores de compilación, arregla el primero y recompila; cannot find symbol suele ser una letra o una mayúscula.
  • Un stack trace se lee de arriba abajo: tipo, mensaje, dónde reventó y quién llamó. Busca la primera línea de código tuyo; la culpa a veces está una línea más abajo.
  • System.out.println sirve para ver la historia de un programa; márcalo para no olvidarlo antes del commit.
  • El depurador de NetBeans: punto de interrupción (clic en el número de línea), Debug Project (Ctrl+F5), Step Over (F8), Step Into (F7), Step Out (Ctrl+F7), Continue (F5), Variables, Watches y Call Stack.
  • Mientras el depurador está en pausa, la ventana Swing se congela porque el hilo de eventos está detenido.
  • Una lista de pruebas manuales escrita garantiza que cada versión se pruebe igual, incluidos los casos raros.
  • Las pruebas automáticas comprueban la lógica en segundos; en el capítulo 69 darás el salto a JUnit.
Aplícalo fuera del Totito
  • Una app de ventas o inventario: pon un punto de interrupción condicional en el método que calcula el total, con la condición total < 0, para atrapar justo la venta que da un número imposible entre cientos de ventas normales.
  • Un programa que lee archivos o datos de un formulario: los NumberFormatException y NullPointerException aparecerán cuando el usuario escriba algo inesperado. Escribe en tu lista de pruebas casos como «campo vacío», «letras donde va un número» y «número negativo».
  • Un error que te reporta otra persona: pídele siempre el stack trace completo (una captura o el texto). Con la primera línea de código tuyo ya sabes por dónde empezar, sin adivinar.
  • Cualquier proyecto con reglas (una calculadora, un sistema de notas, el Conecta 4 del capítulo 68): separa la lógica de la interfaz como en Partida y escríbele un probador como PruebasPartida. Cada vez que cambies algo, lo ejecutas y en segundos sabes si rompiste lo que antes funcionaba.
