Capítulo 65jpackage: una carpeta portable con Totito.exe

En este capítulo conviertes el .jar en una carpeta con un Totito.exe de verdad, con tu icono y con su propio Java recortado a la medida. Quien la reciba hace doble clic y juega, sin instalar nada. Al final la comprimes en un .zip listo para compartir por correo, memoria USB o internet.

El problema que resolvemos

En el capítulo 63 viste el gran límite del .jar: solo funciona si la otra persona tiene Java 17 o más nuevo instalado. La solución es no depender de su computadora y llevar el Java con nosotros. Pero no todo el JDK: tu JDK 21 ocupa unos 300 MB y trae compiladores, herramientas y bibliotecas que el Totito jamás usa. Lo que necesitamos es un Java pequeño, recortado, que tenga solo lo que el juego necesita para correr. En este capítulo aparecen tres herramientas que vienen dentro de tu JDK y trabajan juntas:

HerramientaQué haceAnalogía
jdepsLee tu .jar y dice qué partes de Java usaRevisar la receta para saber qué ingredientes comprar
jlinkFabrica un Java recortado, solo con esas partesComprar solo esos ingredientes en vez de vaciar el supermercado
jpackageJunta tu .jar, ese Java recortado y un lanzador .exe con tu iconoArmar la canasta de regalo con todo y su moño

No necesitas instalar nada nuevo: jdeps, jlink y jpackage están en la carpeta bin del JDK de Temurin que instalaste en el capítulo 4, la misma de java y javac. Compruébalo:

jpackage --version
21.0.8

Tu número exacto puede ser otro (lo importante es que empiece por 21). Si PowerShell responde que jpackage no se reconoce como comando, el bin del JDK no está en el PATH: repasa el capítulo 4.

Qué es un runtime

Para ejecutar bytecode hace falta la máquina virtual (la JVM, el «motor») y la biblioteca de clases de Java: todas esas clases que usas sin haberlas escrito, como String, JFrame, Color o ArrayList. A ese conjunto, JVM más biblioteca, se le llama entorno de ejecución o runtime (en inglés Java Runtime Environment, JRE).

JDK y runtime. El JDK (Java Development Kit) es el runtime más las herramientas para desarrollar: javac, jar, jdeps, jlink, jpackage… Tú, que programas, necesitas el JDK. Quien solo juega necesita el runtime. Es la diferencia entre un taller mecánico completo y el motor que hace andar el carro: al cliente le entregas el carro, no el taller.

Los módulos de Java

Desde Java 9, la biblioteca de clases está dividida en módulos: paquetes grandes y con nombre, cada uno con una responsabilidad. Algunos de los más conocidos:

MóduloQué contiene¿Lo usa el Totito?
java.baseLo esencial: String, Math, arreglos, colecciones, archivos (java.io)… Todo programa lo necesitaSí
java.desktopInterfaces gráficas: AWT, Swing, Java2D, ImageIOSí
java.sqlBases de datos (JDBC, capítulo 69)No
java.net.httpConectarse a páginas y servicios webNo
java.xmlLeer y escribir XMLSolo indirectamente (lo pide java.desktop)
jdk.compilerEl compilador javacNo: es del JDK, no del juego

Un JDK completo trae decenas de módulos. Para saber cuáles usa exactamente el Totito, no hace falta adivinar: jdeps (Java dependencies) lee cada .class del .jar y anota de qué módulos son las clases que usa. Desde la carpeta del proyecto, con el .jar ya compilado:

cd $HOME\Proyectos\Totito
jdeps --print-module-deps target\Totito-1.0-SNAPSHOT.jar
java.base,java.desktop

Solo dos. Todo el Totito, con sus pantallas, su neón, su IA y su generador de icono, se apoya únicamente en lo esencial y en la parte gráfica. Esa línea es la lista de la compra para jlink.

Un detalle: java.desktop, a su vez, necesita otros módulos (por ejemplo java.xml, porque algunas partes de Swing leen configuración en XML). jlink los añade solo. El runtime que fabricaremos lleva, en total, estos cinco: java.base, java.datatransfer, java.xml, java.prefs y java.desktop. Lo comprobé fabricándolo y preguntándole con java --list-modules.

jlink: fabricar un Java a la medida

jlink toma los módulos que le pidas del JDK y construye con ellos una carpeta que es un runtime completo y funcional, con su propio bin\java.exe, pero mucho más pequeño. jpackage llama a jlink por dentro, así que no tienes que usarlo directamente. Pero para que veas que no hay magia, puedes probarlo una vez:

jlink --add-modules java.desktop --strip-debug --no-man-pages --no-header-files --compress=zip-6 --output dist\runtime-prueba
.\dist\runtime-prueba\bin\java --list-modules
.\dist\runtime-prueba\bin\java -jar target\Totito-1.0-SNAPSHOT.jar

La segunda línea muestra los cinco módulos; la tercera abre el Totito con ese Java recortado, no con el que instalaste. Esa carpeta ocupa unos 54 MB, frente a los ~300 MB del JDK. Cuando termines, bórrala; jpackage fabricará la suya:

Remove-Item -Recurse -Force dist\runtime-prueba
Remove-Item -Recurse -Force no pregunta. Borra la carpeta y todo su contenido sin pasar por la Papelera de reciclaje. Escribe la ruta con cuidado, usa Tab para autocompletarla y nunca lo uses con una ruta que no entiendas (capítulo 3). En todo este capítulo solo lo usamos dentro de dist\, que es una carpeta de cosas fabricadas que se pueden volver a fabricar.

jpackage, paso a paso

jpackage puede producir dos clases de resultado, según la opción --type:

  • --type app-image: una imagen de aplicación, es decir, una carpeta lista para usar con el .exe, tu .jar y el runtime. No instala nada en el sistema. Es lo que haremos en este capítulo.
  • --type exe o --type msi: un instalador de Windows. Lo harás en el capítulo 66.

Paso 1: el .jar recién compilado

En NetBeans, Run → Clean and Build Project (Shift+F11). Así te aseguras de empaquetar la última versión del código y no una vieja. Debe existir target\Totito-1.0-SNAPSHOT.jar (capítulo 63).

Paso 2: una carpeta de entrada solo con el .jar

New-Item -ItemType Directory -Force dist\entrada | Out-Null
Copy-Item target\Totito-1.0-SNAPSHOT.jar dist\entrada\

La primera línea crea dist\entrada (y dist si no existe). -Force hace que no se queje si ya existía, y | Out-Null descarta el texto que New-Item escribe, para que la pantalla quede limpia. La segunda copia el .jar ahí.

¿Por qué no darle a jpackage directamente la carpeta target? Porque jpackage copia todo lo que hay en la carpeta de entrada dentro de tu aplicación. En target hay además classes\, maven-status\, generated-sources\… y todo eso viajaría inútilmente en el paquete. Una carpeta de entrada limpia, con solo lo necesario, es la forma correcta. Si algún día tu programa usara librerías (otros .jar), también irían en esa carpeta.

Paso 3: el comando jpackage

Este es el comando completo. Escríbelo exactamente así, en PowerShell, desde la carpeta del proyecto. Es una sola orden repartida en siete líneas:

jpackage --type app-image --name Totito --input dist\entrada `
  --main-jar Totito-1.0-SNAPSHOT.jar --main-class TotitoApp `
  --icon recursos\totito.ico --app-version 1.0.0 --vendor "Tu Nombre" `
  --description "Juego del Totito" --add-modules java.desktop `
  --jlink-options "--strip-debug --no-man-pages --no-header-files --compress=zip-6" `
  --dest dist\app
El acento grave de PowerShell. El carácter ` al final de cada línea (el acento grave o backtick; en un teclado latinoamericano suele estar en la tecla a la derecha de la Ñ o junto al Enter, y a veces hay que pulsarlo dos veces o seguido de un espacio para que aparezca) significa en PowerShell «la orden continúa en la línea siguiente». Sirve para que un comando largo se pueda leer. Tiene una regla estricta: tiene que ser el último carácter de la línea. Si después del ` queda un espacio invisible, PowerShell da la orden por terminada ahí y trata la línea siguiente como otro comando, con un error del tipo El término '--main-jar' no se reconoce como nombre de un cmdlet. Si te pasa, o si te resulta incómodo, escribe todo en una sola línea larga, sin acentos graves: funciona igual.

Al pulsar Enter, jpackage trabaja entre 20 segundos y un minuto sin escribir casi nada. Si termina sin mostrar ningún error, funcionó. Ahora, opción por opción:

OpciónQué hacePor qué ese valor

--name TotitoNombre de la aplicaciónSerá el nombre de la carpeta y del lanzador: Totito\Totito.exe

--main-jar Totito-1.0-SNAPSHOT.jarCuál de los .jar de la entrada es el principalSe escribe relativo a --input: solo el nombre, sin dist\entrada\ delante
--main-class TotitoAppLa clase con el main que arrancaEl manifiesto ya lo dice, pero decirlo explícitamente evita sorpresas

--app-version 1.0.0Versión pública del programaLa que verá la gente (capítulo 67). En Windows solo admite números separados por puntos: 1.0-SNAPSHOT no vale
--vendor "Tu Nombre"Quién lo publica (el «fabricante»)Pon tu nombre real o artístico. Lleva comillas porque tiene un espacio
--description "Juego del Totito"Descripción cortaWindows la muestra en las propiedades del .exe y en el Administrador de tareas
--add-modules java.desktopQué módulos meter en el runtimeLo que dijo jdeps. java.base va siempre, no hace falta nombrarlo
--jlink-options "..."Opciones que jpackage le pasa a jlink al fabricar el runtimePara recortar aún más (siguiente tabla). Van entre comillas porque son varias

Y las cuatro opciones de reducción que van dentro de --jlink-options:

Opción de jlinkQué quita o hace¿Se nota?
--strip-debugBorra la información de depuración de las clases de Java (los números de línea, nombres de variables locales)Solo en los stack traces de clases de Java, que dirán (Unknown Source) en vez de un número de línea. Las líneas de tus clases se conservan, porque tu .jar no pasa por jlink
--no-man-pagesNo incluye las páginas de manual (documentación de comandos, típica de Linux)No

Una nota sobre --compress. La forma zip-6 es la sintaxis nueva, que existe desde el JDK 21. En tutoriales antiguos verás --compress=2; en el JDK 21 todavía funciona pero está marcada como obsoleta. Si algún día usas un JDK 17, tendrás que usar --compress=2, porque allí zip-6 no existe.

El tamaño: por qué importan esas opciones

Para este capítulo fabriqué la misma imagen de aplicación de tres formas, con el JDK 21, y medí el resultado:

VarianteTamaño de la carpeta
Sin --add-modules (jpackage mete todos los módulos estándar)~157 MB
Con --add-modules java.desktop, sin --jlink-options~83 MB
Con --add-modules java.desktop y las cuatro opciones de reducción (el comando de este capítulo)~54 MB

De 157 a 54 MB: casi tres veces menos, solo por decir qué necesitas. Las medidas las tomé en Linux; en Windows los números son parecidos (los archivos del runtime de Windows tienen otros nombres y tamaños), así que mira el tuyo y anótalo. Para saber cuánto ocupa tu carpeta:

"{0:N1} MB" -f ((Get-ChildItem dist\app\Totito -Recurse -File | Measure-Object Length -Sum).Sum / 1MB)

Esta línea suma el tamaño (Length) de todos los archivos de la carpeta (-Recurse -File) y lo divide entre 1MB, una constante de PowerShell que vale 1 048 576 bytes. "{0:N1}" -f le da formato con un decimal. También puedes hacer clic derecho en la carpeta → Propiedades.

¿54 MB para un totito? Sí: el juego son 77 KB; el resto es el Java que lleva dentro. Es el precio de que funcione en cualquier Windows sin instalar nada, y hoy en día es menos que una canción en buena calidad o un par de fotos de teléfono. Comprimido en .zip, más abajo, ocupa bastante menos.

Qué hay dentro de la carpeta

En Windows, jpackage deja esta estructura en dist\app\Totito (los detalles pueden variar un poco entre versiones del JDK):

RutaQué es
Totito.exeEl lanzador: un programa pequeño de Windows con tu icono que arranca el runtime de runtime\ y le pide ejecutar tu .jar
Totito.icoUna copia de tu icono
app\Totito-1.0-SNAPSHOT.jarTu juego, tal cual lo hizo Maven
app\Totito.cfgLa configuración del lanzador: qué .jar, qué clase y qué opciones
runtime\El Java recortado: bin, conf, legal, lib y release

El archivo Totito.cfg es texto. Míralo con Get-Content dist\app\Totito\app\Totito.cfg. El que obtuve es este:

[Application]
app.classpath=$APPDIR/Totito-1.0-SNAPSHOT.jar
app.mainclass=TotitoApp

[JavaOptions]
java-options=-Djpackage.app-version=1.0.0

$APPDIR es la carpeta app; app.mainclass es lo que pusiste en --main-class; y en [JavaOptions] jpackage deja la versión disponible para el programa como una propiedad del sistema. Es decir, Totito.exe hace lo mismo que harías tú con runtime\bin\java -cp app\Totito-1.0-SNAPSHOT.jar TotitoApp, pero sin consola, con tu icono y sin que nadie tenga que saber nada de Java.

La carpeta runtime\legal contiene las licencias de los componentes de Java. El JDK de Temurin es software libre (licencia GPL con la «excepción Classpath»), y esa excepción es justamente la que te permite distribuir su runtime junto con tu programa, sea libre o no. Deja esa carpeta tal cual: es la forma de cumplir la licencia.

Totito.exe no viaja solo. Si copias únicamente Totito.exe al escritorio y le haces doble clic, no funcionará: el lanzador busca app\ y runtime\ junto a él. La aplicación es la carpeta completa. Para tenerlo en el escritorio, crea un acceso directo (clic derecho en Totito.exe → Mostrar más opciones en Windows 11 → Enviar a → Escritorio (crear acceso directo)), o espera al instalador del capítulo 66, que lo hace solo.

Probar Totito.exe

.\dist\app\Totito\Totito.exe

El .\ del principio significa «a partir de la carpeta actual». La ventana del Totito se abre como siempre. Fíjate en tres cosas nuevas:

  • La barra de tareas muestra el icono del Totito, y al pasar el ratón por encima dice «Totito», no «Java».
  • PowerShell queda libre enseguida: Totito.exe es un programa de ventanas, no de consola.
  • En el Explorador (explorer dist\app\Totito), el archivo Totito.exe tiene tu icono. Haz clic derecho → Propiedades → pestaña Detalles: deberías ver la descripción «Juego del Totito» y la versión 1.0.0, tomadas de las opciones --description y --app-version.

Ahora la prueba de fuego: ¿funciona sin tu Java? La forma más fiable es probarlo en otra computadora que no tenga Java (la de un familiar, por ejemplo) después de comprimirlo, más abajo. Si no tienes otra a mano, al menos comprueba con el Administrador de tareas (Ctrl+Shift+Esc) que el proceso se llama Totito.exe; su Java es el de runtime\, no el que instalaste con winget. Y recorre la lista de pruebas manuales del capítulo 62: un programa empaquetado se prueba otra vez.

Si Totito.exe no abre: --win-console

Un lanzador sin consola tiene un inconveniente: si el programa revienta al arrancar, no ves ningún stack trace; simplemente no pasa nada. Para diagnosticarlo, fabrica una segunda imagen con la opción --win-console, que hace que el .exe abra una consola donde aparecen los mensajes y errores:

jpackage --type app-image --name Totito --input dist\entrada --main-jar Totito-1.0-SNAPSHOT.jar --main-class TotitoApp --add-modules java.desktop --win-console --dest dist\app-consola
.\dist\app-consola\Totito\Totito.exe

Lee el stack trace con lo que aprendiste en el capítulo 62. El error más típico a estas alturas es un NoClassDefFoundError o ClassNotFoundException de una clase de un módulo que no incluiste en --add-modules: si tu programa usara, por ejemplo, java.sql, tendrías que añadirlo (--add-modules java.desktop,java.sql). Por eso jdeps va primero. Cuando lo resuelvas, borra esa carpeta de diagnóstico con Remove-Item -Recurse -Force dist\app-consola: la versión que se comparte es la de dist\app, sin consola.

Comprimir para compartir

Una carpeta con cientos de archivos no se puede adjuntar a un correo ni subir cómodamente a una página. Se comprime en un único .zip. PowerShell trae un comando para eso:

Compress-Archive -Path dist\app\Totito -DestinationPath dist\Totito-1.0.0-portable.zip
ParteSignificado
Compress-ArchiveEl comando de PowerShell que crea archivos ZIP
-Path dist\app\TotitoQué comprimir. Al dar la carpeta (sin \* al final), el ZIP contendrá la carpeta Totito con todo dentro. Así, quien lo descomprima obtiene una carpeta ordenada, no cientos de archivos sueltos regados en su escritorio
-DestinationPath dist\Totito-1.0.0-portable.zipDónde y con qué nombre. El nombre dice qué es, qué versión y qué tipo (portable, que no se instala). En el capítulo 67 lo subirás a GitHub con este nombre

Si el ZIP ya existía de un intento anterior, Compress-Archive se queja; añade -Force al final para reemplazarlo. El archivo resultante ocupa notablemente menos que la carpeta (en mi prueba en Linux, con la misma compresión ZIP, unos 35 MB frente a 54). Míralo con Get-ChildItem dist\*.zip.

Probar el ZIP como lo haría otra persona

Expand-Archive dist\Totito-1.0.0-portable.zip -DestinationPath dist\prueba-zip
.\dist\prueba-zip\Totito\Totito.exe

Expand-Archive es el comando inverso: descomprime. Si el juego abre desde dist\prueba-zip, el ZIP está bien hecho. Bórralo después con Remove-Item -Recurse -Force dist\prueba-zip.

Primero descomprimir, luego jugar. El Explorador de Windows deja «entrar» en un ZIP como si fuera una carpeta, y hacer doble clic en Totito.exe desde ahí. No funciona bien: Windows extrae solo ese archivo a una carpeta temporal, sin app\ ni runtime\. Dile a quien reciba tu juego: clic derecho en el ZIP → Extraer todo…, y luego abrir Totito.exe en la carpeta extraída. En el capítulo 67 verás además el aviso de SmartScreen que puede aparecer la primera vez.

Las ventajas y límites del portable

A favorEn contra
No necesita Java ni permisos de administradorNo aparece en el menú Inicio ni crea accesos directos
Se puede llevar en una memoria USB y jugar en cualquier Windows de 64 bitsEl usuario tiene que descomprimir y recordar dónde lo dejó
Se «desinstala» borrando la carpetaNo se actualiza solo: para la versión nueva hay que reemplazar la carpeta
Ideal para probar o para personas que no quieren instalar nadaSolo sirve en Windows: para Linux o macOS hay que ejecutar jpackage en esos sistemas

La última fila es importante: jpackage no hace «compilación cruzada». El Totito.exe y el runtime de Windows se fabrican en Windows; en Linux, jpackage fabrica un ejecutable de Linux con un runtime de Linux (así comprobé yo los comandos de este capítulo, usando recursos/totito.png como icono, porque en Linux el icono es PNG). El .jar, en cambio, es el mismo para todos.

Git No hay commit en este capítulo: todo lo que fabricaste está en dist\, y el .gitignore que creaste en el capítulo 5 ya incluye la línea dist/. Compruébalo: 
git status
git check-ignore -v dist\Totito-1.0.0-portable.zip
git status no debe mostrar nada de dist, y git check-ignore -v te dice qué línea de qué archivo hace que se ignore (verás algo como .gitignore:3:dist/). Los 54 MB del runtime no tienen por qué estar en tu historial: se regeneran con un comando. El ZIP se compartirá como archivo de una Release de GitHub (capítulo 67).
Hito Tienes un Totito.exe con tu icono que funciona en cualquier Windows de 64 bits sin instalar Java, y un Totito-1.0.0-portable.zip listo para compartir.

Resumen

  • Un runtime es la JVM más la biblioteca de clases; el JDK es el runtime más las herramientas de desarrollo.
  • La biblioteca de Java está dividida en módulos; jdeps --print-module-deps dice que el Totito solo usa java.base y java.desktop.
  • jlink fabrica un runtime recortado con solo esos módulos (y los que ellos necesitan); jpackage lo usa por dentro.
  • jpackage --type app-image crea dist\app\Totito con Totito.exe, app\ (el .jar y Totito.cfg) y runtime\.
  • --add-modules java.desktop y las --jlink-options de reducción bajan el tamaño de ~157 MB a ~54 MB.
  • El acento grave ` continúa una orden en la línea siguiente y debe ser el último carácter de la línea.
  • La aplicación es la carpeta completa; --win-console ayuda a diagnosticar si no arranca.
  • Compress-Archive la convierte en Totito-1.0.0-portable.zip; quien lo reciba debe descomprimirlo antes de abrirlo.
Aplícalo fuera del Totito
  • Cualquier programa de escritorio en Java (el gestor de tareas o el inventario de la tienda del capítulo 68): los mismos tres pasos sirven sin cambios: jdeps para saber los módulos, una carpeta de entrada con tus .jar, y jpackage con tu nombre, icono y clase principal.
  • Programas con base de datos: si usas JDBC (capítulo 69), jdeps te dirá java.sql, y el conector de la base de datos (otro .jar) irá también en la carpeta de entrada. jpackage los pone todos en el classpath.
  • Herramientas internas de una empresa u oficina: una versión portable en una carpeta compartida de red o en una USB evita pedirle permisos de administrador al departamento de informática para instalar Java en cada equipo.
  • Programas para Linux o macOS: el mismo comando, ejecutado en esos sistemas con un icono .png (Linux) o .icns (macOS), produce la versión nativa de cada uno. Muchos proyectos de código abierto lo automatizan en GitHub Actions para fabricar las tres versiones a la vez.
Ejercicios
  1. Ejecuta jdeps --print-module-deps sobre tu .jar y anota el resultado. Luego ejecuta jdeps -s target\Totito-1.0-SNAPSHOT.jar (la -s es de summary, resumen) y compara las dos salidas.
  2. Fabrica la imagen sin --jlink-options en dist\app-sin-reducir y mide las dos carpetas con el comando de PowerShell de este capítulo. ¿Cuántos MB te ahorran las cuatro opciones en tu Windows?
  3. Abre dist\app\Totito\runtime\release con Get-Content y busca la línea MODULES. ¿Coincide con los cinco módulos de este capítulo? Pista: es un archivo de texto con líneas NOMBRE="valor".
  4. Escribe un pequeño script empaquetar.ps1 en la carpeta del proyecto que haga, en orden: borrar dist\app y dist\entrada si existen (if (Test-Path dist\app) { Remove-Item -Recurse -Force dist\app }), copiar el .jar, ejecutar jpackage y comprimir el ZIP con -Force. Ejecútalo con powershell -ExecutionPolicy Bypass -File .\empaquetar.ps1. Pista: Windows bloquea por defecto los scripts .ps1; esa opción lo permite solo para esta ejecución, sin cambiar la configuración del equipo.
  5. Reto: copia el ZIP a una memoria USB, llévalo a una computadora que no tenga Java (puedes comprobarlo con java -version en su PowerShell: debe responder que no se reconoce), descomprímelo y juega. Anota cuánto tardó en abrir la primera vez y la segunda.
