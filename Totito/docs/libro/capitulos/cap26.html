Capítulo 26Enums y excepciones

Dos herramientas para decir las cosas con precisión: los enums, para los valores que solo pueden ser unos pocos y bien conocidos (el modo de juego, el estado de la partida), y las excepciones, para avisar con fuerza cuando algo sale mal y el programa no puede seguir como si nada. El Totito usa las dos, y aquí verás exactamente dónde y por qué.

Primera parte: los enums

El problema: valores que solo pueden ser unos pocos

Una partida de totito, en cada momento, está en una de tres situaciones: en curso, terminada con victoria o terminada en empate. No hay una cuarta. ¿Cómo guardas eso en una variable?

Con lo que viste en la Parte III tendrías dos caminos, y los dos tienen trampa:

// Camino 1: un número que "significa" algo
int estado = 0;      // 0 = en curso, 1 = victoria, 2 = empate
estado = 7;          // Java lo acepta... ¿qué es el estado 7?

// Camino 2: un texto
String estado2 = "victoria";
if (estado2.equals("Victoria")) { ... }   // nunca entra: la V mayúscula lo cambia todo

En el primer camino el número 7 compila sin protestar, y quien lea if (estado == 2) tiene que adivinar qué es el 2. En el segundo, un error de dedo («Victoria» contra «victoria», «empate» contra «empata») no lo detecta nadie hasta que el juego se porta raro. El compilador no te puede ayudar porque, para él, int y String admiten millones de valores.

Piensa en el ascensor de un edificio de cinco pisos: tiene exactamente cinco botones. No puedes pedirle el piso 7 ni el piso «tres y medio», porque el botón no existe. Eso es un enum: un tipo cuyo conjunto de valores posibles está escrito, completo, en el código.

Enum (enumeración) Un tipo de dato con una lista cerrada de valores con nombre. Una variable de ese tipo solo puede valer una de esas constantes (o null). Si escribes un valor que no está en la lista, el programa no compila.

Cómo se escribe, símbolo por símbolo

Así declara el Totito los estados de la partida, dentro de Partida.java (lo construirás en el capítulo 38):

/** Como va la partida actual. */
public enum Estado { EN_CURSO, VICTORIA, EMPATE }
  • public: cualquier otra clase puede usar este tipo (lo viste en el capítulo 19). Las pantallas necesitan preguntar el estado, por eso es público.
  • enum: la palabra reservada que dice «lo que sigue es una enumeración», igual que class dice «lo que sigue es una clase».
  • Estado: el nombre del nuevo tipo. Como toda clase, empieza con mayúscula.
  • { … }: las llaves encierran el cuerpo del enum.
  • EN_CURSO, VICTORIA, EMPATE: las constantes, separadas por comas. Se escriben en MAYÚSCULAS con guion bajo entre palabras, la misma convención que las constantes static final del capítulo 20, porque eso es lo que son.
  • No lleva ; al final de la lista porque el enum no tiene nada más. Si después de las constantes vinieran campos o métodos, sí haría falta un punto y coma tras la última (lo verás más abajo).

Los modos de juego están escritos igual, pero en varias líneas para poder comentar cada constante:

/** Los dos modos que se eligen en la pantalla de configuracion. */
public enum Modo {
    /** Dos personas se turnan en el mismo equipo. */
    DOS_JUGADORES,
    /** El Jugador 2 es la computadora (IA_Minimax). */
    CONTRA_IA
}

Un enum es una clase (con objetos fijos)

Por dentro, Java convierte enum Estado en una clase especial y crea un único objeto por cada constante, una sola vez, cuando la clase se carga. Estado.VICTORIA es una referencia a ese objeto, como lo sería un campo public static final. Nadie puede hacer new Estado(): el compilador lo prohíbe. Por eso la lista es cerrada de verdad.

Esto tiene una consecuencia práctica muy cómoda: como solo existe un objeto VICTORIA en todo el programa, dos enums se comparan con == sin miedo. Con los String tenías que usar equals (capítulo 17) porque dos textos iguales pueden ser objetos distintos; con los enums no pasa. Mira cómo lo hace Partida.jugar:

public boolean jugar(int fila, int columna) {
    if (estado != Estado.EN_CURSO) {
        return false;
    }

Y el constructor de Partida decide si crea la IA comparando el modo:

this.ia = modo == Modo.CONTRA_IA ? new IA_Minimax(jugador2.getFicha(), jugador1.getFicha()) : null;

Enums dentro de otra clase

Modo y Estado están declarados dentro de la clase Partida. Son enums anidados: viven en el «apellido» de Partida. Desde dentro de Partida se escriben solos (Estado.EN_CURSO); desde fuera llevan el nombre completo, Partida.Estado.EN_CURSO o Partida.Modo.CONTRA_IA. Por ejemplo, la interfaz Navegacion (capítulo 39) declara:

void iniciarPartida(Jugador jugador1, Jugador jugador2, Partida.Modo modo);

¿Por qué dentro? Porque un modo de juego o un estado de partida no tienen sentido sin una partida. Leer Partida.Estado te dice de inmediato «el estado de la partida», no el estado de la ventana ni el de la conexión. Es la misma idea de las clases anidadas del capítulo 25: agrupar lo que va junto.

Lo que todo enum trae de regalo

Cada enum hereda unos métodos útiles. Este programa los muestra todos:

public class EnumsBasicos {

    enum Estado { EN_CURSO, VICTORIA, EMPATE }

    public static void main(String[] args) {
        Estado estado = Estado.EN_CURSO;
        System.out.println("Estado actual: " + estado);

        // Todas las constantes, en el orden en que se declararon
        for (Estado e : Estado.values()) {
            System.out.println(e.ordinal() + " -> " + e.name());
        }

        // De texto a constante
        Estado leido = Estado.valueOf("EMPATE");
        System.out.println("¿Leído es EMPATE? " + (leido == Estado.EMPATE));

        // Un switch que cubre los tres casos
        estado = Estado.VICTORIA;
        String mensaje = switch (estado) {
            case EN_CURSO -> "Sigue jugando";
            case VICTORIA -> "¡Tres en línea!";
            case EMPATE -> "¡Empate!";
        };
        System.out.println(mensaje);
    }
}

Switch con enums

El switch (capítulo 13) y los enums se llevan de maravilla. Dentro de cada case la constante se escribe sin el nombre del tipo: case EN_CURSO, no case Estado.EN_CURSO. Java ya sabe de qué tipo es lo que está entre paréntesis.

En el Totito, PantallaJuego.actualizar() (capítulo 59) usa un switch de instrucciones con flechas para escribir el letrero de arriba del tablero según el estado:

switch (partida.getEstado()) {
    case EN_CURSO -> {
        Color color = Tema.colorDeFicha(enTurno.getFicha());
        String texto = partida.esTurnoDeIA()
                ? "La computadora está pensando…"
                : "Turno de " + enTurno.getNombre();
        turno.setTexto(texto, Tema.aclarar(color, 0.35f), color);
    }
    case VICTORIA -> {
        Color color = Tema.colorDeFicha(partida.getGanador().getFicha());
        turno.setTexto("¡Tres en línea!", Tema.aclarar(color, 0.35f), color);
    }
    case EMPATE -> turno.setTexto("¡Empate!", Tema.LAVANDA, Tema.MORADO);
}

Cuando un caso necesita varias instrucciones, van entre llaves { }; cuando es una sola, basta con ponerla después de la flecha y terminar con ;. Con la flecha no hay que escribir break: cada caso termina solo.

Y en BotonNeon.paintComponent (capítulo 44) aparece la otra forma, el switch como expresión, que produce un valor que se guarda en una variable:

double arco = switch (estilo) {
    case MENU -> 30;
    case ICONO -> 16;
    default -> alto;        // pildora: extremos totalmente redondos
};

Léelo así: «el arco de las esquinas vale 30 si el estilo es MENU, 16 si es ICONO y, en cualquier otro caso (PILDORA y CONTORNO), la altura completa del botón, lo que hace los extremos perfectamente redondos». Observa el ; después de la llave de cierre: toda la expresión es parte de una asignación, y una asignación termina en punto y coma.

Aquí está la ventaja escondida de los enums: un switch expresión tiene que cubrir todos los casos. Como Java conoce la lista completa de constantes, puede comprobarlo. Si te olvidas de una y no pones default, no compila:

static String texto(Estado estado) {
    return switch (estado) {
        case EN_CURSO -> "Sigue jugando";
        case VICTORIA -> "¡Tres en línea!";
    };
}

               ^

Con un int eso sería imposible de detectar. Por eso, cuando agregas una constante a un enum, conviene preferir switches sin default: el compilador te lleva de la mano a cada lugar que debes actualizar.

Enums con datos y comportamiento

Como un enum es una clase, puede tener campos, un constructor y métodos. Cada constante «nace» llamando a ese constructor con sus propios datos. Piensa en los tamaños de café de una cafetería: no solo hay tres tamaños, cada uno sabe cuántos mililitros lleva y cuánto cuesta.

public class EnumConDatos {

    /** Tamaños de café de una cafetería: cada uno sabe su precio y sus mililitros. */
    enum Tamano {
        PEQUENO("Pequeño", 240, 12.00),
        MEDIANO("Mediano", 350, 15.50),
        GRANDE("Grande", 470, 18.75);

        private final String etiqueta;
        private final int mililitros;
        private final double precio;

        Tamano(String etiqueta, int mililitros, double precio) {
            this.etiqueta = etiqueta;
            this.mililitros = mililitros;
            this.precio = precio;
        }

        public double precioPorMililitro() {
            return precio / mililitros;
        }

        public int getMililitros() {
            return mililitros;
        }

        public String getEtiqueta() {
            return etiqueta;
        }

        public double getPrecio() {
            return precio;
        }
    }

    public static void main(String[] args) {
        for (Tamano t : Tamano.values()) {
            System.out.printf("%-8s %3d ml  Q%6.2f  (Q%.4f por ml)%n",
                    t.getEtiqueta(), t.getMililitros(), t.getPrecio(), t.precioPorMililitro());
        }
        Tamano pedido = Tamano.valueOf("MEDIANO");
        System.out.println("Pediste un " + pedido.getEtiqueta() + ": Q" + pedido.getPrecio());
    }
}

  • PEQUENO("Pequeño", 240, 12.00): la constante con paréntesis llama al constructor del enum con esos tres datos.
  • El ; después de GRANDE(...) es obligatorio: separa la lista de constantes del resto del cuerpo.
  • El constructor Tamano(...) no lleva public: el constructor de un enum es siempre privado, aunque no lo escribas, porque solo las constantes de la lista pueden usarlo.
  • Los campos son private final: cada tamaño tiene sus datos fijos para siempre (capítulos 19 y 20).

El Totito no necesitó enums con datos: sus enums son simples etiquetas y la información (colores, tamaños) vive en Tema y en los métodos de fábrica. Pero si quisieras agregar niveles de dificultad a la IA, un enum Dificultad { FACIL(2), MEDIO(4), DIFICIL(9); ... } con la profundidad máxima que puede explorar Minimax sería el lugar natural.

¿Y si el Totito no tuviera enums?

Imagina BotonNeon con int estilo: BotonNeon.crear("Jugar", 0), BotonNeon.crear("Volver", 2). Quien lea el código no sabe qué es el 2, nadie impide pasar un 9, y el switch de paintComponent necesitaría un default para «estilos desconocidos» que nunca deberían existir. Con Partida.Estado como String, un "VICTORIA " con un espacio de más rompería en silencio la pantalla de resultado. El enum convierte esos errores de ejecución, difíciles de encontrar, en errores de compilación, que NetBeans subraya en rojo antes de que corras nada.

Cuándo usar un enum Cuando puedas escribir en un papel la lista completa de valores posibles y esa lista cambie poco: estados, modos, categorías fijas, direcciones (NORTE, SUR, ESTE, OESTE), palos de la baraja. Si la lista la crea el usuario (nombres de productos, alumnos), no es un enum: es una lista de objetos normales.

Segunda parte: las excepciones

La idea: un aviso que no se puede ignorar

Hasta ahora, cuando un método no podía hacer su trabajo, devolvía algo especial: Tablero.marcarCasilla devuelve false si la casilla está ocupada (capítulo 19). Eso funciona cuando el problema es esperable y quien llama está listo para revisarlo. Pero hay situaciones en las que seguir como si nada sería peor que detenerse.

Piensa en una alarma de incendio en un edificio. Si se activa en el tercer piso, el aviso no se queda en ese cuarto: sube por el edificio hasta que alguien responsable lo atiende (el conserje, los bomberos). Y si nadie lo atiende, se evacúa todo el edificio. Una excepción es exactamente eso: un objeto que representa un problema, que se lanza en el punto donde ocurre y viaja hacia atrás por los métodos que se llamaron, hasta que alguno lo atrapa. Si nadie lo atrapa, el programa (más exactamente, ese hilo) se detiene y escribe un informe del problema.

Excepción Un objeto que describe un error ocurrido durante la ejecución. Lanzarla (throw) interrumpe el método en ese instante; la excepción sube por la pila de llamadas hasta encontrar un bloque catch que la atienda. Si no lo encuentra, el programa se detiene e imprime la traza de pila.

Lanzar: el constructor de Partida

En el Totito hay una regla que nunca debe romperse: los dos jugadores tienen fichas distintas. Si ambos jugaran con X, verificarGanador no sabría de quién es una línea de X, y en el modo contra la IA, IA_Minimax recibiría la misma ficha para ella y para su rival, así que sus cálculos no tendrían ningún sentido. El constructor de Partida se protege así:

public Partida(Jugador jugador1, Jugador jugador2, Modo modo) {
    if (jugador1.getFicha() == jugador2.getFicha()) {
        throw new IllegalArgumentException("Los dos jugadores no pueden usar la misma ficha");
    }
    this.jugadores = new Jugador[]{jugador1, jugador2};

Símbolo por símbolo:

  • throw: «lanza». Detiene el método aquí mismo; las líneas siguientes no se ejecutan.
  • new IllegalArgumentException(...): crea un objeto de la clase IllegalArgumentException («argumento no válido»), que viene con Java en el paquete java.lang (por eso no hace falta import). Las excepciones son objetos normales: se crean con new, como cualquier otro (capítulo 18).
  • "Los dos jugadores…": el mensaje, un String que se guarda dentro del objeto y que luego se puede leer con getMessage(). Escríbelo pensando en quien tendrá que arreglar el error: di qué estaba mal.
  • ;: throw es una instrucción y termina en punto y coma.

¿Por qué en el constructor y no más tarde? Porque así una partida inválida nunca llega a existir. Si el constructor lanza una excepción, el new Partida(...) no devuelve ningún objeto. Es la forma más fuerte de proteger una invariante, la idea del capítulo 19: el objeto está bien desde el primer instante o no está.

¿Y por qué IllegalArgumentException? Porque el problema no es de la partida ni del tablero: es que quien llamó pasó argumentos que no valen. Elegir la excepción con el nombre que mejor describe el problema es parte del mensaje. Las más usadas de Java para esto son IllegalArgumentException (un parámetro no vale), IllegalStateException (el objeto no está en condiciones de hacer eso ahora) y NullPointerException (llegó un null donde no debía, capítulo 18).

¿Entonces por qué marcarCasilla no lanza una excepción? Por la diferencia entre algo esperable y un error del programa. Que el usuario haga clic en una casilla ocupada es normal: pasa todo el tiempo y la respuesta correcta es ignorarlo, por eso marcarCasilla y Partida.jugar devuelven false. En cambio, que una pantalla cree una partida con dos fichas iguales no debería pasar nunca: si pasa, hay un error en el código de esa pantalla y conviene que salte a la vista. Regla práctica: boolean u otro valor de retorno para lo esperable; excepción para lo que indica un error o lo verdaderamente excepcional.

La traza de pila: leer el informe del error

Para verlo en acción, este programa trae una versión mini de la partida con la misma comprobación, y la llama primero bien y luego mal:

public class PartidaMini {

    public static void main(String[] args) {
        System.out.println("Creando una partida válida...");
        comenzar('X', 'O');
        System.out.println("Creando una partida con fichas repetidas...");
        comenzar('X', 'X');
        System.out.println("Esta línea nunca se imprime");
    }

    static void comenzar(char ficha1, char ficha2) {
        Juego juego = new Juego(ficha1, ficha2);
        System.out.println("Listo: " + juego);

    private final char ficha1;
    private final char ficha2;

    Juego(char ficha1, char ficha2) {
        if (ficha1 == ficha2) {
            throw new IllegalArgumentException("Los dos jugadores no pueden usar la misma ficha");
        }
        this.ficha1 = ficha1;
        this.ficha2 = ficha2;
    }

    @Override
    public String toString() {
        return "Juego " + ficha1 + " contra " + ficha2;
    }

Es la pila de llamadas del capítulo 16 «fotografiada» en el momento del error: arriba el método más reciente, abajo el primero. La excepción viajó de Juego() a comenzar y de ahí a main, buscando quién la atendiera; como nadie lo hizo, el programa terminó, y por eso «Esta línea nunca se imprime» no aparece.

Truco para depurar En una traza larga, busca la primera línea que mencione un archivo tuyo. Las de arriba suelen ser de Java (por ejemplo at java.base/...) y casi nunca están mal; la primera que dice Partida.java o PantallaJuego.java es donde debes mirar. En NetBeans, esas líneas de la ventana Output son enlaces: un clic y te lleva a la línea exacta. El capítulo 62 profundiza en depurar.

Un detalle sobre las ventanas: en un programa Swing como el Totito, los clics se procesan en otro hilo, el de eventos (capítulo 37). Si una excepción escapa de un clic, la traza aparece en Output como Exception in thread "AWT-EventQueue-0", ese clic no termina su trabajo, pero la ventana sigue abierta. Por eso un error puede pasar desapercibido si no miras la consola mientras pruebas.

La familia de las excepciones

Todas las excepciones son clases que heredan (capítulo 22) de una raíz común, Throwable («lanzable»). El árbol, simplificado:

  • Error: problemas de la máquina virtual, como quedarse sin memoria. Tu programa no puede hacer nada sensato con ellos; no se atrapan.
  • Exception y sus hijas: problemas que un programa sí puede prever y manejar. Se dividen en dos grupos, y la diferencia es importantísima.

Comprobadas y no comprobadas

Las no comprobadas (en inglés unchecked) son RuntimeException y todas sus hijas. Suelen indicar un error de programación: un índice fuera del arreglo, un null, un argumento inválido. Java no te obliga a hacer nada con ellas, porque lo correcto es arreglar el código, no atraparlas. IllegalArgumentException es de este grupo.

Las comprobadas (checked) son las demás hijas de Exception, como IOException (falló una lectura o escritura de archivo). Representan problemas del mundo exterior que pueden ocurrir aunque tu código esté perfecto: el disco está lleno, el archivo no existe, la red se cayó. Como son inevitables, Java te obliga a decidir qué hacer con ellas. Si no lo haces, no compila. Mira este intento de guardar el marcador en un archivo:

import java.io.FileWriter;

    public static void main(String[] args) {
        FileWriter archivo = new FileWriter("marcador.txt");
        archivo.write("Ana 3 - Luis 1");
        archivo.close();
    }
}

El mensaje lo dice todo: «excepción IOException no informada; debe ser atrapada o declarada para ser lanzada». Tienes exactamente esas dos salidas: atraparla con try/catch, o avisar con throws que tu método puede dejarla pasar. Las dos aparecen en el Totito.

Declarar con throws: GeneradorIcono

herramientas/GeneradorIcono.java (capítulo 64) escribe el archivo totito.ico. Sus métodos que tocan archivos llevan throws IOException en la firma:

public static void main(String[] args) throws IOException {

/** El formato .ico guarda los numeros "al reves" (little-endian). */
private static void corto(DataOutputStream salida, int valor) throws IOException {
    salida.writeByte(valor & 0xFF);
    salida.writeByte((valor >> 8) & 0xFF);
}

throws IOException (con s final, distinta de throw) va después de los paréntesis de los parámetros y significa: «este método puede terminar lanzando una IOException; quien me llame, que se haga cargo». No lanza nada por sí mismo: solo avisa. Es parte del contrato del método, igual que su tipo de retorno.

¿Por qué ahí está bien no atraparla? Porque GeneradorIcono es una herramienta que ejecuta el programador una vez. Si no puede escribir el icono, no hay nada razonable que hacer más que detenerse y mostrar la traza. Que main declare throws IOException significa exactamente eso: si ocurre, el programa se detiene y la traza explica qué archivo falló. Para una herramienta interna es lo más honesto; para el juego que usa la gente, no.

Hay un segundo caso, más sutil, en la clase interna LimiteDeLargo de CampoTexto (capítulos 25 y 47):

@Override
public void insertString(FilterBypass fb, int offset, String texto, AttributeSet attr)
        throws BadLocationException {
    replace(fb, offset, 0, texto, attr);
}

Aquí throws BadLocationException no es una decisión del Totito: el método sobrescribe uno de DocumentFilter, que ya declara esa excepción, y llama a replace, que también puede lanzarla. Una regla de la sobrescritura (capítulo 23): el método hijo puede declarar las mismas excepciones comprobadas que el padre, o menos, pero nunca más. Quien usa un DocumentFilter está preparado para BadLocationException y nada más; un hijo no puede sorprenderlo con otra.

Atrapar con try, catch y finally

La otra salida es atender el problema tú mismo. Analogía: un cajero de supermercado con un billete sospechoso. No cierra la tienda (eso sería dejar caer la excepción): sigue un procedimiento («si el billete es falso, pide otro») y continúa atendiendo. El procedimiento se escribe así:

public class Atrapar {

    public static void main(String[] args) {
        String[] escritos = {"2", "uno", "", "1"};
        for (String texto : escritos) {
            System.out.println("Fila escrita: \"" + texto + "\"");
            try {
                int fila = Integer.parseInt(texto);
                System.out.println("  Número válido: " + fila);
            } catch (NumberFormatException e) {
                System.out.println("  No es un número: " + e.getMessage());
            } finally {
                System.out.println("  (finally: esto se ejecuta siempre)");
            }
        }
        System.out.println("El programa sigue vivo.");
    }
}

Fila escrita: "2"
  Número válido: 2
  (finally: esto se ejecuta siempre)
Fila escrita: "uno"
  No es un número: For input string: "uno"
  (finally: esto se ejecuta siempre)
Fila escrita: ""
  No es un número: For input string: ""
  (finally: esto se ejecuta siempre)
Fila escrita: "1"
  Número válido: 1
  (finally: esto se ejecuta siempre)
El programa sigue vivo.
  • try { … }: «intenta». El bloque de código que podría fallar. Si una línea lanza una excepción, las siguientes del bloque se saltan.
  • catch (NumberFormatException e) { … }: «atrapa». Entre paréntesis va qué tipo de excepción atiende este bloque y un nombre de variable (e, por costumbre) para usar el objeto excepción dentro. Integer.parseInt lanza NumberFormatException cuando el texto no es un número. El catch solo atrapa ese tipo y sus hijos; cualquier otra excepción sigue subiendo.
  • e.getMessage(): el mensaje guardado en la excepción.
  • finally { … }: «finalmente». Se ejecuta siempre: si todo salió bien, si hubo excepción atrapada, incluso si hubo una que no se atrapó o un return dentro del try. Sirve para liberar algo que tomaste (cerrar un archivo, apagar un temporizador). Es opcional.

Puedes poner varios catch seguidos para distintos tipos. Java los revisa en orden y usa el primero que encaje, así que los más específicos van primero; si pones catch (Exception e) antes que catch (NumberFormatException e), el segundo nunca se alcanzaría y el compilador lo marca como error.

Mejor prevenir: PruebaConsola

Atrapar no es la única forma de lidiar con errores; a veces es mejor evitar que ocurran. herramientas/PruebaConsola.java (capítulo 32) lee números con un Scanner (capítulo 17). Si el usuario escribe letras, nextInt() lanzaría InputMismatchException; y si la entrada se cierra, NoSuchElementException. En vez de envolverlo todo en un try, el programa pregunta antes:

System.out.print("Tu jugada: ");
if (!teclado.hasNextInt()) {
    return;   // se cerro la entrada: terminar sin error
}
int fila = teclado.nextInt();

hasNextInt() responde true o false sin lanzar nada: «¿lo que viene es un entero?». Es como mirar si hay tráfico antes de cruzar en vez de confiar en el seguro médico. Cuando puedes comprobar una condición de forma barata, compruébala; reserva las excepciones para lo que no puedes prever.

try-with-resources: cerrar sin olvidarse

Un archivo abierto es un recurso: algo que el sistema operativo te presta y que hay que devolver. Si abres un archivo para escribir y no lo cierras, lo escrito puede no guardarse completo y Windows puede negarse a borrarlo o moverlo («el archivo está en uso»). Antes se cerraba en un finally, con bastante código repetitivo. Desde Java 7 existe una forma mejor: try con recursos. Es como un servicio de alquiler de bicicletas que te recoge la bici en la puerta de tu casa cuando terminas, pase lo que pase en el camino.

GeneradorIcono.main la usa para escribir el .ico:

try (DataOutputStream ico = new DataOutputStream(
        new FileOutputStream(new File(carpeta, "totito.ico")))) {
    // Cabecera: reservado (0), tipo 1 = icono, cantidad de imagenes.
    corto(ico, 0);
    corto(ico, 1);
    corto(ico, TAMANOS.length);
    // ... (las entradas y las imagenes)
}
  • try ( … ): entre los paréntesis, justo después de try, se declara y crea el recurso. Aquí, un DataOutputStream (escribe números en bytes) montado sobre un FileOutputStream (escribe en un archivo).
  • Al salir del bloque { }, por el camino que sea (terminó bien, hubo return o saltó una excepción), Java llama solo a ico.close(). No hay forma de olvidarlo.
  • Este try no tiene catch: no lo necesita, porque main ya declara throws IOException. El try-with-resources solo se encarga de cerrar; si algo falla, la excepción sigue subiendo, ya con el archivo cerrado.

Cualquier clase que implemente la interfaz AutoCloseable (capítulo 24) puede ir entre esos paréntesis. Este programa escribe el marcador en un archivo de texto, lo lee de vuelta, intenta leer uno que no existe, y muestra con un recurso de juguete que close() se llama incluso cuando hay un error:

import java.io.BufferedReader;
import java.io.FileReader;
import java.io.FileWriter;
import java.io.IOException;
import java.io.PrintWriter;

public class Recursos {

    public static void main(String[] args) {
        // 1) Escribir el marcador en un archivo de texto.
        try (PrintWriter salida = new PrintWriter(new FileWriter("marcador.txt"))) {
            salida.println("Ana 3");
            salida.println("Luis 1");
            salida.println("Empates 2");
        } catch (IOException e) {
            System.out.println("No se pudo guardar: " + e.getMessage());
        }

        // 2) Leerlo de vuelta, línea por línea.
        try (BufferedReader entrada = new BufferedReader(new FileReader("marcador.txt"))) {
            String linea;
            while ((linea = entrada.readLine()) != null) {
                System.out.println("Leído: " + linea);
            }
        } catch (IOException e) {
            System.out.println("No se pudo leer: " + e.getMessage());
        }

        // 3) Un archivo que no existe: la excepción se atrapa y el programa sigue.
        try (BufferedReader entrada = new BufferedReader(new FileReader("no-existe.txt"))) {
            System.out.println(entrada.readLine());
        } catch (IOException e) {
            System.out.println("Atrapada " + e.getClass().getSimpleName() + ": " + e.getMessage());
        }

        // 4) El cierre ocurre aunque haya un error dentro del bloque.
        try (Grifo grifo = new Grifo()) {
            System.out.println("Usando el grifo...");
            throw new IllegalStateException("se fue el agua");
        } catch (IllegalStateException e) {
            System.out.println("Atrapada: " + e.getMessage());
        }
    }
}

/** Un recurso de juguete: avisa cuando lo cierran. */
class Grifo implements AutoCloseable {
    Grifo() {
        System.out.println("Grifo abierto");
    }

    @Override
    public void close() {
        System.out.println("Grifo cerrado (close se llamó solo)");
    }
}

Leído: Ana 3
Leído: Luis 1
Leído: Empates 2
Atrapada FileNotFoundException: no-existe.txt (No such file or directory)
Grifo abierto
Usando el grifo...
Grifo cerrado (close se llamó solo)
Atrapada: se fue el agua

Fíjate en el orden de las últimas cuatro líneas: el grifo se cierra antes de que se ejecute el catch. Esa salida es la de este libro probada en Linux; en Windows, el mensaje del punto 3 sale en el idioma del sistema, algo como no-existe.txt (El sistema no puede encontrar el archivo especificado). Después de ejecutarlo verás marcador.txt en tu carpeta de prácticas: ábrelo con el Bloc de notas.

Observa también que FileNotFoundException fue atrapada por catch (IOException e): es hija de IOException, y un catch atrapa el tipo indicado y todos sus descendientes. Es el polimorfismo del capítulo 23 aplicado a los errores.

Un catch vacío con buena razón: Tema.elegirFamilia

Como regla, un catch vacío es sospechoso: «se tragó» un error sin decir nada. Pero el Totito tiene uno, y está justificado. Tema (capítulo 40) elige la fuente de letra buscando, entre las instaladas en la computadora, la primera de su lista de preferidas:

private static String elegirFamilia() {
    try {
        List<String> instaladas = Arrays.asList(
                GraphicsEnvironment.getLocalGraphicsEnvironment().getAvailableFontFamilyNames());
        for (String familia : FAMILIAS) {
            if (instaladas.contains(familia)) {
                return familia;
            }
        }
    } catch (RuntimeException e) {
        // Sin acceso a las fuentes del sistema: se usa la generica.
    }
    return Font.SANS_SERIF;
}

Tres decisiones a mirar con lupa:

  1. Por qué atrapar. Preguntarle al sistema qué fuentes hay depende de cosas fuera del control del juego: la configuración gráfica del equipo, permisos, un sistema sin entorno gráfico completo. En esos casos raros la consulta puede fallar con una excepción no comprobada. Y la elección de fuente es cosmética: si falla, el juego debe abrirse igual, con una letra genérica. Este método se llama al inicializar el campo static final String FAMILIA (capítulo 20); si la excepción escapara de ahí, Java la envolvería en un ExceptionInInitializerError y la clase Tema quedaría inutilizable: ninguna pantalla podría pedir un color. Un detalle estético tumbaría el programa entero.
  2. Por qué RuntimeException y no Exception. En ese bloque no hay ninguna llamada que lance excepciones comprobadas, así que no hay ninguna que atender. Atrapar RuntimeException dice con precisión «cualquier fallo inesperado en tiempo de ejecución de esta consulta». No se atrapa Error (quedarse sin memoria no se arregla eligiendo otra fuente).
  3. Por qué vacío, pero con comentario. No hay nada que hacer en el catch: la solución es la línea siguiente, return Font.SANS_SERIF;, que se ejecuta tanto si no se encontró ninguna fuente preferida como si hubo excepción. El comentario explica que el silencio es intencional. Un catch vacío sin comentario hace pensar al siguiente programador que alguien se olvidó de algo.

Esto tiene un nombre: degradar con elegancia. Ante un fallo en algo secundario, el programa ofrece una versión un poco menos bonita en lugar de no funcionar.

Excepciones propias

Puedes crear tus propias clases de excepción heredando de Exception (comprobada) o de RuntimeException (no comprobada). Valen la pena cuando el error es un concepto de tu problema y quien llama necesita distinguirlo o recibir datos extra. Un banco es el ejemplo clásico: intentar retirar más de lo que hay en la cuenta no es un error del programa, es algo que el cajero debe manejar.

public class Banco {

    public static void main(String[] args) {
        Cuenta cuenta = new Cuenta("Ana", 500.00);
        double[] retiros = {120.00, 450.00, -5.00, 80.00};
        for (double monto : retiros) {
            try {
                cuenta.retirar(monto);
                System.out.printf("Retiro de Q%.2f aprobado. Saldo: Q%.2f%n", monto, cuenta.getSaldo());
            } catch (SaldoInsuficienteException e) {
                System.out.printf("Rechazado: %s (faltan Q%.2f)%n", e.getMessage(), e.getFaltante());
            } catch (IllegalArgumentException e) {
                System.out.println("Error del programa: " + e.getMessage());
            }
        }
    }
}

/** Excepción propia y COMPROBADA: el que llame a retirar() está obligado a decidir qué hacer. */
class SaldoInsuficienteException extends Exception {
    private final double faltante;

    SaldoInsuficienteException(String mensaje, double faltante) {
        super(mensaje);
        this.faltante = faltante;
    }

    double getFaltante() {
        return faltante;
    }
}

class Cuenta {
    private final String titular;
    private double saldo;

    Cuenta(String titular, double saldoInicial) {
        this.titular = titular;
        this.saldo = saldoInicial;
    }

    void retirar(double monto) throws SaldoInsuficienteException {
        if (monto <= 0) {
            throw new IllegalArgumentException("el monto debe ser positivo: " + monto);
        }
        if (monto > saldo) {
            throw new SaldoInsuficienteException("saldo insuficiente en la cuenta de " + titular, monto - saldo);
        }
        saldo -= monto;
    }

    double getSaldo() {
        return saldo;
    }
}

Retiro de Q120.00 aprobado. Saldo: Q380.00
Rechazado: saldo insuficiente en la cuenta de Ana (faltan Q70.00)
Error del programa: el monto debe ser positivo: -5.0
Retiro de Q80.00 aprobado. Saldo: Q300.00
  • class SaldoInsuficienteException extends Exception: hereda de Exception, así que es comprobada. El nombre termina en Exception por convención, para que se reconozca de un vistazo.
  • super(mensaje): pasa el mensaje al constructor de la clase padre (capítulo 22), que lo guarda para getMessage().
  • El campo faltante es información extra: el cajero puede decirle al cliente cuánto le falta.
  • retirar usa los dos tipos con criterio: un monto negativo es un error del programa (IllegalArgumentException, no comprobada); el saldo insuficiente es una situación del negocio que el llamador debe atender (comprobada, y por eso la firma lleva throws).
  • Tras cada error el ciclo sigue: el retiro de 80 se aprueba. Atrapar dentro del for permite que un problema no detenga los demás.

catch (Exception e) { } vacío y sin comentarioEsconde todos los errores, incluso los que no imaginaste. El programa falla después, lejos de la causa.Atrapa el tipo concreto; si el silencio es intencional, explícalo como en Tema.

Falla rápido Es mejor que un error se detecte lo antes posible y cerca de su causa, como hace el constructor de Partida, que dejar que un dato inválido viaje por el programa y cause un fallo raro diez pantallas después. Las excepciones bien lanzadas son tu sistema de alarma temprana.

Resumen

  • Un enum es un tipo con una lista cerrada de constantes con nombre; cada constante es un objeto único, por eso se comparan con ==. El Totito usa Partida.Modo, Partida.Estado, BotonNeon.Estilo y Rotulo.Tipo.
  • Los enums traen values(), name(), ordinal() y valueOf(); pueden tener campos, constructor (siempre privado) y métodos.
  • El switch con enums usa las constantes sin prefijo; el switch expresión obliga a cubrir todos los casos, y el compilador avisa si falta uno.
  • Una excepción es un objeto que se lanza con throw, sube por la pila de llamadas y se atrapa con try/catch; finally se ejecuta siempre. Si nadie la atrapa, la traza de pila muestra el tipo, el mensaje y el camino del error.
  • Las comprobadas (como IOException) obligan a atrapar o a declarar con throws; las no comprobadas (RuntimeException y sus hijas) suelen indicar errores de programación.
  • try-with-resources cierra solo los archivos y demás recursos AutoCloseable, como en GeneradorIcono.
  • Para lo esperable, valores de retorno (marcarCasilla devuelve false); para los errores, excepciones (Partida rechaza fichas repetidas). Un catch vacío solo se justifica con un motivo y un comentario, como en Tema.elegirFamilia.
Aplícalo fuera del Totito
  • Tienda en línea: enum EstadoPedido { PENDIENTE, PAGADO, ENVIADO, ENTREGADO, CANCELADO } con un método puedePasarA(EstadoPedido otro) que impida saltos absurdos (de ENTREGADO a PENDIENTE). Y una excepción SinExistenciasException cuando se compra más de lo que hay en bodega.
  • Sistema escolar: enum Rol { ALUMNO, DOCENTE, DIRECTOR } para los permisos, y un constructor de Nota que lance IllegalArgumentException si la calificación no está entre 0 y 100: una nota inválida nunca llega a la base de datos.
  • Banco: excepciones comprobadas propias para lo que el cajero debe manejar (saldo insuficiente, cuenta bloqueada) y no comprobadas para los errores del programa (montos negativos). Cualquier archivo o conexión, siempre con try-with-resources.
  • Otro juego: en un Conecta 4 (capítulo 68), enum Direccion { HORIZONTAL, VERTICAL, DIAGONAL_SUBE, DIAGONAL_BAJA } con los pasos dFila, dColumna como campos simplifica la búsqueda de cuatro en línea; y la columna llena se maneja con un boolean, porque es algo esperable.
Ejercicios
  1. Escribe enum Dia { LUNES, …, DOMINGO } y un programa que recorra Dia.values() e imprima cada día con su ordinal(). Agrega un método esFinDeSemana() dentro del enum. Pista: dentro de un método del enum, this es la constante actual; compara this == SABADO || this == DOMINGO.
  2. Agrega una constante ABANDONADA al enum Estado de EnumsBasicos y ejecútalo sin cambiar nada más. ¿Qué error da el compilador y en qué línea? Arréglalo agregando el caso que falta.
  3. Modifica Atrapar para que, en vez de imprimir el error, pida el número otra vez con un Scanner hasta que el usuario escriba un entero entre 0 y 2. Pista: un while con una variable boolean valido; usa hasNextInt() y descarta lo inválido con next().
  4. Crea la clase Nota con un constructor que reciba un int y lance IllegalArgumentException con un mensaje claro si no está entre 0 y 100. Provoca el error a propósito, lee la traza y señala en qué línea nació la excepción y quién llamó al constructor.
  5. Reto: escribe un programa que guarde en tareas.txt una lista de tareas (una por línea) y luego la lea y numere, todo con try-with-resources. Después crea ArchivoVacioException (comprobada) y lánzala desde un método leerTareas() si el archivo no tiene ninguna línea.
