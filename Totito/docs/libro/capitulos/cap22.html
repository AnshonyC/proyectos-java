Capítulo 22Herencia

La herencia permite crear una clase nueva a partir de otra que ya existe: la nueva recibe todo lo que la vieja sabe hacer y solo escribe lo que cambia. Gracias a ella, el BotonNeon del Totito es un botón completo (responde al clic, al teclado y al ratón) aunque su archivo solo tenga 192 líneas. En este capítulo vas a entender cómo funciona, qué pasa por dentro cuando creas un objeto de una clase hija y, sobre todo, cuándo conviene usarla y cuándo no.

La idea: «es un tipo de»

Piensa en un taxi. Un taxi es un carro: tiene volante, motor, frenos, puertas y se maneja igual que cualquier carro. Nadie que fabrica taxis inventa de nuevo el motor; toma un carro y le agrega lo que le falta (el taxímetro, el rótulo del techo) y quizá cambia alguna cosa (la pintura). Si mañana mejoran los frenos de ese modelo de carro, todos los taxis hechos con él salen con los frenos nuevos.

En Java eso se llama herencia: una clase (la hija, también llamada subclase) se declara como «un tipo de» otra clase (la madre, también llamada superclase o clase padre). La hija recibe automáticamente los atributos y los métodos de la madre, y puede:

  • agregar atributos y métodos nuevos (el taxímetro);
  • cambiar el comportamiento de un método heredado escribiendo su propia versión (la pintura). Eso se llama sobrescribir y es el tema central del capítulo 23;
  • usar lo heredado como si lo hubiera escrito ella (manejar el carro).
La prueba del «es un» Antes de heredar, di la frase en voz alta: «un BotonNeon es un JButton». ¿Suena verdadero siempre, en todo lo que un JButton promete? Entonces la herencia tiene sentido. «Una Partida es un Tablero» suena raro: una partida tiene un tablero. Eso es composición (capítulo 21), no herencia.

Por qué el Totito la necesita

Un botón de verdad hace muchísimas cosas que normalmente no vemos: se entera de que el ratón pasó por encima, recuerda si está presionado, se puede activar con la barra espaciadora cuando tiene el foco, avisa a quien le interese que lo pulsaron (addActionListener), se puede deshabilitar, muestra un texto de ayuda (tooltip)… Todo eso ya lo programaron los autores de Swing en la clase JButton, que trae Java.

Lo único que el diseño del Totito necesitaba distinto era el aspecto: bordes de neón, degradados, un icono dibujado a mano. Entonces BotonNeon hereda de JButton todo el comportamiento y solo escribe de nuevo la parte que dibuja. Mira cómo lo dice el comentario del propio archivo (lo escribirás en el capítulo 44):

Serían miles de líneas, llenas de detalles fáciles de olvidar (¿te acordarías de que un botón también se pulsa con la barra espaciadora?).

Un ejemplo completo que puedes correr

Dejemos Swing un momento y veamos la herencia en un programa de consola. Una tienda vende productos; algunos, además, se vencen. Un producto perecedero es un producto, con un dato extra. Guarda esto como Herencia.java en tu carpeta de prácticas:

public class Herencia {
    public static void main(String[] args) {
        Producto pan = new Producto("Pan francés", 1.50);
        ProductoPerecedero leche = new ProductoPerecedero("Leche", 12.75, "2026-10-20");

        System.out.println(pan.describir());
        System.out.println(leche.describir());

        // Métodos que ProductoPerecedero NO escribió: los heredó de Producto.
        System.out.println("Nombre heredado: " + leche.getNombre());
        System.out.println("Precio con IVA: " + leche.precioConIva());
    }
}

class Producto {
    private final String nombre;
    private final double precio;

    Producto(String nombre, double precio) {
        this.nombre = nombre;
        this.precio = precio;
    }

    String getNombre() {
        return nombre;
    }

    double precioConIva() {
        return Math.round(precio * 1.12 * 100) / 100.0;
    }

    String describir() {
        return nombre + " - Q" + precio;
    }
}

class ProductoPerecedero extends Producto {
    private final String vence;

    ProductoPerecedero(String nombre, double precio, String vence) {
        super(nombre, precio);   // primero se arma la parte de Producto
        this.vence = vence;      // luego lo que solo tiene el hijo
    }

    @Override
    String describir() {
        return super.describir() + " (vence " + vence + ")";
    }
}

Recorre lo que pasó:

  • ProductoPerecedero solo declara un atributo (vence), un constructor y un método. Aun así, leche.getNombre() y leche.precioConIva() funcionan: los heredó.
  • leche.describir() no usó la versión de Producto sino la del hijo, que agrega la fecha. Eso es sobrescribir; la anotación @Override se explica a fondo en el capítulo 23.
  • Dentro de esa versión, super.describir() llama a la versión de la madre para no repetir su trabajo. Lo vemos en un momento.
  • El cálculo del IVA (12 % en Guatemala) existe una sola vez. Si cambia la tasa, se corrige en un único lugar y lo reciben todos los tipos de producto.

super: hablar con la madre

this (capítulo 20) significa «este objeto». super significa «la parte de este objeto que viene de la madre». Se usa de dos formas que conviene no confundir:

FormaDónde se usaPara qué
super(argumentos);Solo en la primera línea de un constructorEjecutar un constructor de la madre para que arme su parte del objeto.
super.metodo(argumentos)Dentro de cualquier método de la hijaLlamar a la versión de la madre de un método, aunque la hija lo haya sobrescrito.

super(...) en los constructores

Un objeto de una clase hija es como una casa con dos pisos: el primer piso lo construye la madre y el segundo la hija. No se puede levantar el segundo piso en el aire, así que Java exige que lo primero que haga el constructor de la hija sea pedirle a la madre que construya el primero. Esa petición es super(...).

Símbolo por símbolo, en super(color, 26); de TarjetaJugador:

  • super — «el constructor de mi madre» (aquí, de Tarjeta).
  • (color, 26) — los argumentos. Java busca en Tarjeta un constructor que reciba un Color y un int, y encuentra public Tarjeta(Color color, int arco). Con eso la tarjeta del jugador tiene esquinas de 26 píxeles en vez de las 30 de las demás tarjetas.
  • ; — fin de la instrucción, como siempre.

¿Y las clases que no escriben super(...), como Tarjeta, CampoTexto o PanelTablero? Java pone por su cuenta una llamada invisible a super(); (sin argumentos) como primera línea. Por eso CampoTexto funciona: JTextField tiene un constructor sin parámetros y Java lo llama solo.

Esa ayuda automática tiene una trampa. Si la madre no tiene un constructor sin parámetros, el super(); invisible no encuentra a quién llamar y el programa no compila. Pruébalo con SinSuper.java:

Léelo despacio: «el constructor Madre no se puede aplicar a los tipos dados; se requiere un String, se encontraron cero argumentos». El compilador señala la línea del constructor de Hija, porque ahí está el super(); que tú no escribiste. La solución es escribirlo tú, con su argumento: super("rosa");. «call to super must be first statement in constructor» Si escribes cualquier instrucción antes de super(...), por ejemplo this.titulo = titulo;, Java 21 se niega a compilar con ese mensaje («la llamada a super debe ser la primera instrucción del constructor»). La madre siempre se construye primero. (Versiones muy recientes de Java empiezan a relajar esta regla, pero con Java 21, que es la que usas, se cumple al pie de la letra.)

El orden de construcción, visto en vivo

Con tres generaciones se ve clarísimo que el constructor de más arriba termina primero. Guarda OrdenConstruccion.java:

public class OrdenConstruccion {
    public static void main(String[] args) {
        System.out.println("Creando una TarjetaDemo...");
        new TarjetaDemo("Jugador 1");

    }

class TarjetaDemo extends PanelDemo {
    TarjetaDemo(String titulo) {
        super("rosa");
        System.out.println("3) Constructor de TarjetaDemo: " + titulo);
    }

Aunque escribiste new TarjetaDemo(...), el primer mensaje es el del abuelo. Lo que ocurre es una cadena: TarjetaDemo empieza, su primera línea llama a PanelDemo; este empieza, su primera línea llama a ComponenteDemo; ese termina su trabajo, devuelve el control a PanelDemo, que termina, y por último termina TarjetaDemo. Es la misma pila de llamadas del capítulo 16.

En el Totito eso significa algo práctico: cuando el constructor de TarjetaJugador llega a la línea setLayout(null);, la parte de Tarjeta ya hizo setOpaque(false) y setAlignmentX(CENTER_ALIGNMENT), y la parte de JPanel (y de todos los de más arriba) ya está lista. La hija trabaja siempre sobre una madre terminada.

super.metodo(): «haz lo tuyo y luego yo agrego»

El segundo uso de super aparece cuando la hija sobrescribe un método pero no quiere reemplazar todo lo que hacía la madre, sino añadir algo. Es como cuando una panadería toma la receta base del pastel y solo le pone una decoración encima: primero hornea el pastel de siempre y luego decora.

En el Totito, Tarjeta sabe pintar la «caja de cristal» (rectángulo redondeado, semitransparente, con borde de neón). TarjetaJugador necesita esa misma caja y además el icono, el título y la palabra «Nombre». Su método de pintar empieza así:

    @Override
    protected void paintComponent(Graphics g) {
        super.paintComponent(g);   // la caja de cristal
        Graphics2D g2 = Dibujo.preparar(g);

        Iconos.Icono icono = esComputadora ? Iconos.COMPUTADORA : Iconos.PERSONA;
        icono.dibujar(g2, MARGEN + 22, MARGEN + 10, 42, color);
  • super — la versión de la madre (Tarjeta).
  • . — «de ella, quiero el miembro…».
  • paintComponent — el método que pinta.
  • (g) — le pasa el mismo pincel (Graphics) que Swing le dio a la hija.

¿Qué pasaría si se borra esa línea? La tarjeta del jugador se vería sin caja: el icono y el título flotando sobre el fondo, sin el rectángulo de cristal ni el borde rosa o azul. ¿Y si se llamara a paintComponent(g) sin el super.? Entonces el método se llamaría a sí mismo una y otra vez, sin fin, hasta que Java se quede sin pila y lance un StackOverflowError (recuerda la recursión del capítulo 16). El super. es lo que dice «la otra versión, la de mi madre».

El lugar de la llamada importa. CampoTexto también sobrescribe paintComponent, pero llama a super.paintComponent(g) al final:

        g2.dispose();
        super.paintComponent(g);   // el texto y el cursor los pinta Swing
    }

Primero pinta su fondo redondeado de neón y el texto de ayuda gris; luego deja que JTextField pinte encima lo que escribe el usuario y el cursor parpadeante. Si lo llamara al principio, su propio fondo taparía las letras. Regla práctica: lo que va debajo se pinta primero.

¿Y por qué Tarjeta no llama a super.paintComponent? Porque es transparente (setOpaque(false)) y dibuja ella misma todo su aspecto. La versión de JPanel solo rellenaría el fondo con un color liso cuando el panel es opaco; aquí no aportaría nada. Llamar o no a la madre es una decisión: llámala cuando lo que hace te sirve.

Las jerarquías reales del Totito

Cuando una clase hereda de otra que a su vez hereda de otra, se forma una jerarquía: un árbol genealógico de clases. El del Totito mezcla clases de Swing (que ya vienen con Java) y clases tuyas. Este es el árbol completo, comprobado con la herramienta javap del JDK:

Lee el árbol de arriba hacia abajo:

  • Object es la raíz de todo (enseguida la vemos).
  • Component (de AWT, la biblioteca gráfica más antigua de Java) es «cualquier cosa que ocupa un rectángulo en la pantalla»: tiene posición, tamaño, se puede pintar y recibe eventos del ratón y del teclado.
  • Container es un componente que puede contener otros: tiene add(...) y un administrador de diseño (layout).
  • JComponent es la base de casi todo Swing: agrega bordes, transparencia (setOpaque), texto de ayuda y el método paintComponent que el Totito usa en todas partes. Es abstracta: no puedes hacer new JComponent() (capítulo 24).
  • Por la rama de la derecha, Window → Frame → JFrame son ventanas de verdad, con barra de título. De ahí cuelgan TotitoApp y JuegoMain.

Puedes pedirle a Java que te recite la cadena de cualquier clase. getSuperclass() devuelve la madre de una clase; repitiéndolo hasta llegar a null se recorre el árbol hacia arriba. Guarda CadenaDeHerencia.java:

public class CadenaDeHerencia {
    public static void main(String[] args) {
        mostrarCadena(javax.swing.JButton.class);
        mostrarCadena(javax.swing.JPanel.class);
        mostrarCadena(Ficha.class);

        Ficha f = new Ficha();
        System.out.println("toString heredado de Object: " + f);
        System.out.println("getClass heredado de Object: " + f.getClass().getName());
        System.out.println("equals heredado de Object: " + f.equals(new Ficha()));
    }

    static void mostrarCadena(Class<?> clase) {
        String cadena = clase.getSimpleName();
        Class<?> padre = clase.getSuperclass();
        while (padre != null) {
            cadena = cadena + " -> " + padre.getSimpleName();
            padre = padre.getSuperclass();
        }
        System.out.println(cadena);
    }
}

Object: la madre de todas las clases

Si una clase no escribe extends, Java le pone en silencio extends Object. Tablero, Jugador, Partida e IA_Minimax heredan de Object sin decirlo, igual que la Ficha vacía del ejemplo. Por eso toda clase de Java, incluso una vacía, ya sabe hacer algunas cosas:

Método de ObjectQué hace por defecto
toString()Devuelve un texto que representa al objeto. Por defecto: nombre de la clase, @ y un número en hexadecimal (Ficha@20d3d15a). Ese número cambia cada vez que corres el programa; no te preocupes si ves otro.
equals(otro)Dice si dos objetos son «iguales». Por defecto solo es true si son el mismo objeto (igual que ==, capítulo 18). Por eso dos Ficha distintas dan false.
hashCode()Un número que resume al objeto; lo usan colecciones como HashSet. Debe ir de la mano con equals.
getClass()Devuelve la clase real del objeto. No se puede cambiar.

Cuando concatenas un objeto con un texto ("..." + f), Java llama solo a toString(). En el capítulo 23 vas a sobrescribir toString y equals para que digan algo útil, como Ana (X).

¿Para qué sirve tener una raíz común? Para poder escribir código que acepte cualquier objeto. System.out.println(Object x) imprime cualquier cosa porque sabe que todo objeto tiene toString(). Un ArrayList puede guardar productos, alumnos o jugadores porque todos son, en el fondo, Object.

protected: solo para la familia

En el capítulo 19 viste private (solo la clase) y public (todo el mundo). protected está en medio: lo pueden usar la clase, sus hijas (aunque estén en otro paquete) y las clases de su mismo paquete. Es como la receta secreta de una panadería familiar: no se le da a cualquier cliente, pero los hijos que abren su propia sucursal sí la reciben.

        normal.pintar();
        System.out.println();
        fiesta.pintar();
    }
}

class TarjetaTexto {
    private final String titulo;   // solo TarjetaTexto lo toca

    TarjetaTexto(String titulo) {
        this.titulo = titulo;
    }

    /** Los hijos pueden usarlo; el resto del programa no debería. */
    protected String marco() {
        return "+" + "-".repeat(titulo.length() + 2) + "+";
    }

    void pintar() {
        System.out.println(marco());
        pintarDecoracion();
        System.out.println("| " + titulo + " |");
        System.out.println(marco());
    }

    /** Gancho para las subclases: por defecto no dibuja nada. */
    protected void pintarDecoracion() {
    }
}

class TarjetaConConfeti extends TarjetaTexto {
    TarjetaConConfeti(String titulo) {
        super(titulo);
    }

    @Override
    protected void pintarDecoracion() {
        // Usa marco(), que es protected: el hijo sí puede.
        int ancho = marco().length();
        System.out.println(" " + "*".repeat(ancho - 2));
    }
}

La hija no puede leer titulo (es private), pero sí puede llamar a marco() (es protected) para saber el ancho. Y la madre, sin saber que existe una hija con confeti, la deja meter su decoración justo en el lugar previsto. Este truco tiene nombre, Template Method, y lo estudiarás en el capítulo 27.

protected en el Totito es casi público Como todas las clases del Totito están en el mismo paquete (el paquete por defecto), cualquier clase del juego podría llamar a tarjeta.forma(). El protected funciona aquí más como un aviso para las personas («esto es para las subclases») que como un candado. En proyectos con paquetes (capítulo 69) el candado sí se nota.

Una sola madre por clase

En Java cada clase tiene exactamente una madre directa (salvo Object, que no tiene ninguna). Esto se llama herencia simple. No puedes escribir class BotonPanel extends Boton, Panel; el compilador ni siquiera entiende la coma:

DosPadres.java:12: error: '{' expected
class BotonPanel extends Boton, Panel {
                              ^
1 error
error: compilation failed

¿Por qué esa restricción? Si las dos madres tuvieran un método con el mismo nombre (por ejemplo pintar()), ¿cuál heredaría la hija? Otros lenguajes, como C++, lo permiten y tienen reglas complicadas para resolverlo. Java eligió la sencillez: una sola madre, y para «parecerse a varias cosas a la vez» usa interfaces. PanelPrincipal lo hace: extends JPanel implements Navegacion, es decir, «es un panel y además cumple el contrato de navegación». Las interfaces son el tema del capítulo 24.

final: clases que no se pueden heredar

A veces quieres prohibir que alguien haga hijas de una clase. Se marca con final (capítulo 20). En el Totito son final las tres clases de utilidades: Tema, Dibujo e Iconos.

public final class Tema {

¿Por qué? Porque son cajas de herramientas con métodos y constantes static; no tiene sentido crear «un tipo especial de Tema». Hacerlas final deja clara la intención y evita que alguien herede de ellas por error. Si lo intentas, Java no compila. Ejemplo con una clase Paleta marcada como final:

final class Paleta {
}

class MiPaleta extends Paleta {
}
NoSePuede.java:10: error: cannot inherit from final Paleta
class MiPaleta extends Paleta {
                       ^
1 error
error: compilation failed

Java usa esto con clases muy importantes: String es final. Si alguien pudiera crear una hija de String que cambiara su comportamiento, ningún programa podría confiar en que un texto se comporta como texto. También se puede poner final a un método (public final void pintar()): la clase se puede heredar, pero ese método no se puede sobrescribir.

Cuándo NO heredar

La herencia es poderosa y por eso se abusa de ella. Es la relación más fuerte que puede haber entre dos clases: la hija depende de todos los detalles de la madre, y la madre ya no se puede cambiar sin pensar en sus hijas. Antes de escribir extends, hazte dos preguntas:

  1. ¿Es un tipo de, o tiene un? Si es «tiene un», usa composición (capítulo 21).
  2. ¿La hija puede cumplir TODO lo que promete la madre, sin excepciones? Si alguien recibe a la hija creyendo que es la madre, ¿todo sigue funcionando? Si la respuesta es «casi», no heredes.

Dos ejemplos clásicos donde la herencia sale mal. Guarda CuandoNoHeredar.java:

import java.util.ArrayList;

public class CuandoNoHeredar {
    public static void main(String[] args) {
        // 1) Una pila que HEREDA de ArrayList
        PilaMala platos = new PilaMala();
        platos.apilar("plato azul");
        platos.apilar("plato rosa");
        platos.add(0, "plato colado");   // heredado: ¡mete uno por abajo!
        System.out.println("Pila heredada: " + platos);

        // 2) Una pila que TIENE un ArrayList (composición)
        PilaBuena buena = new PilaBuena();
        buena.apilar("plato azul");
        buena.apilar("plato rosa");
        // buena.add(0, "plato colado");  <- no compila: PilaBuena no tiene add
        System.out.println("Pila con composición, arriba está: " + buena.verArriba());

        // 3) El cuadrado que "es un" rectángulo
        Rectangulo r = new Cuadrado(5);
        r.setAncho(10);   // a un rectángulo se le puede cambiar solo el ancho...
        System.out.println("¿Sigue siendo cuadrado? ancho=" + r.getAncho() + " alto=" + r.getAlto());
    }
}

class PilaMala extends ArrayList<String> {
    void apilar(String cosa) {
        add(cosa);
    }
}

class PilaBuena {
    private final ArrayList<String> cosas = new ArrayList<>();

    void apilar(String cosa) {
        cosas.add(cosa);
    }

    String verArriba() {
        return cosas.get(cosas.size() - 1);
    }
}

class Rectangulo {
    protected int ancho;
    protected int alto;

    Rectangulo(int ancho, int alto) {
        this.ancho = ancho;
        this.alto = alto;
    }

    void setAncho(int ancho) {
        this.ancho = ancho;
    }

    int getAncho() {
        return ancho;
    }

    int getAlto() {
        return alto;
    }
}

class Cuadrado extends Rectangulo {
    Cuadrado(int lado) {
        super(lado, lado);
    }
}
Pila heredada: [plato colado, plato azul, plato rosa]
Pila con composición, arriba está: plato rosa
¿Sigue siendo cuadrado? ancho=10 alto=5

La pila de platos. Una pila solo deja poner y quitar por arriba; esa es su regla (su invariante, capítulo 19). PilaMala hereda de ArrayList, y con ello hereda todos sus métodos públicos, incluido add(0, ...), que mete un plato por abajo. La regla se rompió y la clase no puede impedirlo. PilaBuena tiene una lista privada y solo ofrece lo que una pila debe ofrecer. (Esto no es un invento: la clase Stack de Java hereda de Vector y arrastra exactamente este problema; la documentación oficial recomienda usar otras clases en su lugar.)

El cuadrado. En matemáticas «un cuadrado es un rectángulo». Pero un Rectangulo de este programa promete algo más: «puedes cambiarme el ancho sin tocar el alto». Un cuadrado no puede cumplir esa promesa. Quien recibió un Rectangulo y le cambió el ancho terminó con un «cuadrado» de 10 por 5. La frase «es un» sonaba bien, pero la segunda pregunta (¿cumple todo lo que promete la madre?) falla. Esta idea tiene nombre formal, el principio de sustitución de Liskov, y la verás resumida en el capítulo 27.

Decisiones de este tipo en el Totito

  • Partida no hereda de Tablero. Si lo hiciera, cualquiera podría llamar a partida.marcarCasilla(...) (heredado) y poner una ficha saltándose los turnos y el marcador. Al tener un Tablero privado, Partida decide qué se puede hacer: solo jugar(fila, columna), que respeta los turnos.
  • PantallaJuego no hereda de PanelTablero. La pantalla tiene un tablero, un marcador, un letrero y dos botones. Es una pantalla (extends PantallaBase) que contiene un tablero.
  • PanelPrincipal hereda de JPanel, no de JFrame. Su comentario explica por qué: «Es un JPanel y no la ventana, asi se puede probar o dibujar en una imagen sin abrir una ventana real». TotitoApp (la ventana) solo lo coloca dentro. Comparado con JuegoMain, que es ventana y juego a la vez, esta separación hace que el juego se pueda mostrar en cualquier ventana o incluso dentro de otra aplicación.
  • Los componentes dibujados heredan de JComponent y no de JButton. OpcionModo se comporta como un botón de radio, pero no es un JButton: solo necesitaba pintarse y escuchar el clic. Heredar de JButton le habría traído texto, iconos, teclas y estados que no usa.
Regla práctica Hereda cuando quieras ser algo que ya existe y solo vayas a especializar (un botón que se dibuja distinto, una pantalla con el fondo común). Usa composición cuando quieras usar algo (una partida que usa un tablero). En caso de duda, empieza con composición: pasar de composición a herencia más adelante es fácil; deshacer una herencia que ya usan muchas clases, no.

Qué pasaría sin herencia en el Totito

  • BotonNeon, CampoTexto y las ventanas tendrían que reimplementar lo que ya hacen JButton, JTextField y JFrame: eventos, teclado, foco, copiar y pegar, la ventana del sistema operativo.
  • Las cinco pantallas repetirían el fondo y el encabezado. Un cambio de color sería cinco cambios.
  • Swing no podría dibujar tus componentes, porque Swing solo sabe tratar con objetos que son Component. add(tarjeta) funciona porque una Tarjeta es un JPanel, que es un Component. Esa idea, usar a la hija donde se espera a la madre, es el polimorfismo del capítulo 23.

Resumen

  • La herencia (class Hija extends Madre) crea una clase que es un tipo de otra: recibe sus métodos y atributos y solo escribe lo que agrega o cambia.
  • Los constructores no se heredan: la hija llama al de la madre con super(...) en la primera línea; si no lo escribe, Java pone super(); y falla si la madre no tiene constructor vacío.
  • El objeto se construye de arriba hacia abajo: primero la parte de la madre, luego la de la hija.
  • super.metodo() llama a la versión de la madre; en el Totito, TarjetaJugador pinta primero la caja de cristal con super.paintComponent(g).
  • Todas las clases heredan de Object (toString, equals, hashCode, getClass). Java tiene herencia simple: una sola madre.
  • protected abre un miembro a las hijas; final en una clase prohíbe heredarla (Tema, Dibujo, Iconos).
  • Hereda solo si la hija cumple todo lo que promete la madre; si la relación es «tiene un», usa composición (Partida tiene un Tablero).
Aplícalo fuera del Totito
  • Punto de venta: una clase Producto con el cálculo del IVA y del descuento, y hijas ProductoPorPeso (precio por libra) y Servicio (sin inventario). La factura trata a todos como Producto.
  • Interfaz de cualquier programa de escritorio: el mismo truco del Totito, class BotonRedondo extends JButton que solo sobrescribe paintComponent, te da botones con el estilo de tu marca sin perder nada del comportamiento de un botón normal.
  • Pantallas con una base común: en un sistema de inventario, una PantallaBase con el logotipo, el menú lateral y el pie de página, y pantallas hijas (PantallaProductos, PantallaVentas) que solo agregan su contenido.
  • Juego de rol: Personaje con vida y movimiento; Guerrero y Mago sobrescriben atacar(). Las armas, en cambio, mejor como composición: un personaje tiene un arma y puede cambiarla.
