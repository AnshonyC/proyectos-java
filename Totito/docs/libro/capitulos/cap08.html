Capítulo 8El primer repositorio del Totito

Vas a convertir la carpeta del Totito en un repositorio de Git, guardar su primera foto con los archivos del capítulo 5 y publicarla en tu cuenta de GitHub con un solo comando. Al final conocerás el plan de commits que seguirás durante todo el libro y sabrás por qué está hecho así.

Dónde estamos

En el capítulo 5 creaste la carpeta del proyecto con tres archivos: pom.xml (la receta de Maven), .gitignore (la lista de lo que Git debe ignorar) y README.md (la presentación del proyecto). En el capítulo 7 configuraste Git y conectaste tu PC con GitHub. Ahora juntamos todo.

Abre PowerShell y entra a la carpeta del proyecto. Todos los comandos de este capítulo se ejecutan desde ahí:

cd $HOME\Proyectos\Totito
Get-ChildItem -Force

Get-ChildItem lista el contenido de la carpeta (capítulo 3) y -Force hace que muestre también los archivos ocultos. Verás algo así (las fechas serán otras):

Las carpetas src, herramientas y recursos están vacías por ahora (ahí irán los .java desde el capítulo 29, las utilidades desde el 32 y el icono en el 64), y target la creó NetBeans al hacer Clean and Build en el capítulo 5. Si no ves target, no pasa nada. Son exactamente los pasos que el capítulo 5 te dejó anotados en su caja de Git; ahora los vas a entender uno por uno.

Asegúrate de estar en la carpeta correcta El error más común de este capítulo es ejecutar git init en la carpeta equivocada, por ejemplo en C:\Users\ana (tu carpeta personal entera). Eso convertiría todos tus documentos en un repositorio. Antes de seguir, mira que el indicador de PowerShell termine en \Proyectos\Totito>. Si te pasó, la solución está más abajo, en «Problemas típicos».

Paso 1: git init — crear el repositorio

git init -b main
Initialized empty Git repository in C:/Users/ana/Proyectos/Totito/.git/

«Se inicializó un repositorio de Git vacío en …/Totito/.git/». init viene de initialize, inicializar, y -b main (de branch) dice que la primera rama se llame main. Gracias al init.defaultBranch del capítulo 7 ya sería así, pero escribirlo no cuesta nada y funciona aunque estés en una computadora sin configurar. Lo que hizo fue crear la carpeta oculta .git, el «álbum» del capítulo 6. Git escribe las rutas con barras normales (/) incluso en Windows; es solo su costumbre.

Fíjate en la palabra empty, vacío: el álbum existe, pero no tiene ninguna foto. Tus tres archivos siguen en la mesa, sin guardar. Compruébalo:

Get-ChildItem -Force

Ahora aparece una línea nueva, d--h-- .git. La h significa hidden, oculta. En el Explorador de Windows no la verás a menos que actives Vista → Mostrar → Elementos ocultos, y está bien que sea así: no hay nada que tocar ahí dentro.

git init se hace una sola vez por proyecto Un proyecto se inicializa una vez en toda su vida. Si ejecutas git init otra vez en la misma carpeta, Git responde Reinitialized existing Git repository y no borra nada, pero no tiene sentido hacerlo. Y nunca lo ejecutes dentro de una subcarpeta de un proyecto que ya es repositorio (por ejemplo dentro de Totito\src): tendrías un repositorio dentro de otro, y Git se confunde.

Paso 2: git status — preguntar cómo está todo

git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.gitignore
	README.md
	pom.xml

git status es el comando que más vas a usar en tu vida con Git. No cambia nada; solo informa. Leámoslo línea por línea:

LíneaTraducciónQué significa
On branch mainEn la rama mainHEAD apunta a main. Es main y no master gracias a init.defaultBranch (capítulo 7).
No commits yetAún no hay commitsEl álbum está vacío.
Untracked files:Archivos sin seguimientoGit ve estos archivos pero nunca los ha guardado.
(use "git add <file>..." …)usa «git add <archivo>» para incluirlos en lo que se va a guardarGit siempre sugiere el siguiente paso entre paréntesis. Léelo: casi siempre es lo que necesitas.
nothing added to commit…no hay nada preparado para el commit, pero hay archivos sin seguimientoLa bandeja está vacía.

Ahora fíjate en lo que no aparece:

  • target no aparece porque el .gitignore tiene la línea target/. ¡Tu .gitignore ya está trabajando! Si quieres comprobar qué regla ignora algo, usa git check-ignore -v target, que responde con la línea exacta: .gitignore:1:target/ target (archivo, número de línea, regla, y lo ignorado).
  • src, herramientas y recursos no aparecen porque están vacías. Git no guarda carpetas vacías: solo guarda archivos, y las carpetas existen para Git solo porque contienen archivos. Cuando en el capítulo 29 crees src\Tablero.java, la carpeta src aparecerá sola (y lo mismo las otras dos, en los capítulos 32 y 64). (En otros proyectos verás un truco: poner dentro un archivo vacío llamado .gitkeep para forzar que la carpeta se guarde. Aquí no hace falta).
La versión corta git status -s (short, corto) da el mismo informe en una línea por archivo. Los archivos sin seguimiento salen con ?? delante. En el capítulo 9 verás todos los códigos.

Paso 3: git add — poner los archivos en la bandeja

git add pom.xml .gitignore README.md

git add copia el estado actual de esos archivos al área de preparación. Puedes nombrar varios archivos separados por espacios. No muestra nada si sale bien. Pregunta de nuevo:

git status
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   .gitignore
	new file:   README.md
	new file:   pom.xml

«Cambios que se van a guardar en el commit». Cada archivo dice new file, archivo nuevo. La pista entre paréntesis te dice cómo sacar un archivo de la bandeja si te equivocaste (unstage, quitar de preparación). En Windows, NetBeans muestra estos archivos en verde, el color de «nuevo para Git».

¿Y git add . ?

Verás muchísimo el comando git add . (con un punto). El punto significa «la carpeta actual», así que agrega todo lo que haya cambiado en la carpeta y sus subcarpetas, respetando el .gitignore. Es cómodo, pero tiene un riesgo: agrega también lo que no esperabas (un archivo de prueba, una nota personal, un archivo de configuración de NetBeans como nb-configuration.xml si se creó). Por eso, para el primer commit, es mejor nombrar los archivos uno por uno: sabes exactamente qué entra. Si usas git add ., haz siempre un git status antes del commit para revisar la lista.

El aviso LF/CRLF Si alguno de los archivos se creó con finales de línea de Linux, al hacer git add verás warning: in the working copy of 'README.md', LF will be replaced by CRLF the next time Git touches it. Como viste en el capítulo 7, es solo Git avisando de la traducción de finales de línea. No es un error.

Paso 4: git commit — sacar la primera foto

git commit -m "Estructura inicial del proyecto Totito"
[main (root-commit) b49d01a] Estructura inicial del proyecto Totito
 3 files changed, 51 insertions(+)
 create mode 100644 .gitignore
 create mode 100644 README.md
 create mode 100644 pom.xml

Primero, el comando:

  • git commit: toma todo lo que hay en la bandeja y lo guarda como un commit nuevo en el repositorio.
  • -m: viene de message. Lo que sigue entre comillas es el mensaje del commit. Sin -m, Git abriría el editor que configuraste en el capítulo 7 para que lo escribas ahí.
  • "Estructura inicial del proyecto Totito": el mensaje. Describe qué contiene esta foto. Va entre comillas porque tiene espacios. Es el primer mensaje del plan de commits del libro.

Ahora la respuesta de Git:

ParteQué significa
[mainEl commit se hizo en la rama main, que ahora apunta a él.
(root-commit)Commit raíz: el primero, el único sin padre.
b49d01a]El hash abreviado del commit. El tuyo será distinto, porque depende de tu nombre, la fecha y la hora exacta.
3 files changed, 51 insertions(+)Tres archivos cambiaron y se agregaron 51 líneas en total (el número depende de cómo escribiste tus archivos).
create mode 100644 .gitignoreSe creó el archivo con «modo 100644»: un archivo normal, no ejecutable. Es un detalle heredado de Linux que puedes ignorar.

Pregunta otra vez cómo está todo:

git status
On branch main
nothing to commit, working tree clean

«Nada que guardar, el directorio de trabajo está limpio». Significa que la mesa, la bandeja y la última foto son idénticas. Es el estado de calma al que vuelves después de cada commit.

Hito El Totito tiene historia. A partir de ahora, nada de lo que guardes con un commit se puede perder por un error en tu carpeta: siempre podrás volver a esta foto.

Paso 5: git log — mirar el historial

git log
commit b49d01a6c3c1c9f4020c112a1e7653865b27f213 (HEAD -> main)
Author: Ana López <12345678+ana-lopez@users.noreply.github.com>
Date:   Mon Oct 12 14:31:34 2026 -0600

    Estructura inicial del proyecto Totito
  • commit b49d01a6…: el hash completo, los 40 caracteres.
  • (HEAD -> main): «usted está aquí». HEAD apunta a main, y main apunta a este commit.
  • Author: tu nombre y correo, tal como los configuraste.
  • Date: fecha y hora, con la zona horaria (-0600 es la de Guatemala, seis horas menos que la hora universal).
  • Debajo, con sangría, el mensaje.

Cuando haya muchos commits, git log ocupará más de una pantalla y Git lo mostrará con un paginador: verás : o (END) al final de la pantalla. Avanza con la barra espaciadora o las flechas y sal pulsando la tecla q (de quit). Mucha gente cree que la terminal se trabó: solo hay que pulsar q.

La forma que usarás casi siempre es la versión de una línea por commit:

git log --oneline
b49d01a (HEAD -> main) Estructura inicial del proyecto Totito

Y para ver qué archivos entraron en un commit concreto:

git show --stat HEAD

show muestra un commit; HEAD significa «el commit donde estoy»; --stat resume qué archivos cambió y cuántas líneas, en lugar de mostrar todo el contenido.

Paso 6: crear el repositorio en GitHub y subirlo

Hasta aquí todo está solo en tu PC. Ahora vas a crear el repositorio totito en tu cuenta de GitHub, conectarlo con tu carpeta y subir el commit. Con gh es un solo comando:

gh repo create totito --private --source . --remote origin --push

Desarmemos cada pieza:

PiezaQué hace
gh repo createCrea un repositorio nuevo en GitHub. gh sabe en qué cuenta gracias a gh auth login.
totitoEl nombre del repositorio. Quedará en https://github.com/tu-usuario/totito. Usa minúsculas y guiones; nada de espacios ni tildes.
--privateRepositorio privado: solo tú (y quienes invites) pueden verlo. La alternativa es --public. Hay que elegir una de las dos.
--source .«Usa como origen el repositorio local que está en .», es decir, en la carpeta actual. Sin esta opción, gh crearía un repositorio vacío en GitHub sin relación con tu carpeta.
--remote originAgrega a tu repositorio local un remoto llamado origin que apunta al repositorio nuevo de GitHub. origin es el nombre que se usa por convención para «la copia principal en internet».
--pushDespués de crearlo, sube tus commits (hace un git push).

Si quieres, puedes agregar una descripción que se verá en la página del repositorio: --description "Juego del Totito en Java con interfaz neon". La respuesta será parecida a esta:

  • Created repository: el repositorio existe en GitHub.
  • Added remote: tu repositorio local ya conoce a origin.
  • Las líneas Enumerating / Counting / Compressing / Writing objects son Git empaquetando y enviando las fotos. Los «objetos» son las piezas internas de cada commit (archivos, carpetas y el commit mismo).
  • * [new branch] HEAD -> main: se creó la rama main en GitHub con tu commit.
  • branch 'main' set up to track 'origin/main': tu main local queda «emparejada» con la main de GitHub. Desde ahora basta con escribir git push o git pull, sin decir a dónde.

La recomendación del libro: empieza privado y, cuando llegues a la versión 1.0.0 y tengas un README bonito (capítulo 10), hazlo público para enseñarlo. Se cambia en la página del repositorio: Settings → General, al final, en la zona roja Danger Zone → Change repository visibility. También se puede con gh repo edit --visibility public (las versiones nuevas de gh piden añadir --accept-visibility-change-consequences para confirmar que entiendes lo que haces).

Comprobar la conexión

git remote -v

git remote -v (de verbose, detallado) lista los remotos con su dirección: una para traer (fetch) y otra para enviar (push), normalmente iguales. Y git status tiene una línea nueva: Your branch is up to date with 'origin/main', «tu rama está al día con la de GitHub». Esta línea te dirá en el futuro si tienes commits sin subir (ahead, adelante) o si hay commits en GitHub que no has bajado (behind, atrás).

Paso 7: ver tu repositorio en el navegador

gh repo view --web

Abre la página del repositorio en el navegador (--web). Sin --web, gh repo view muestra el nombre, la descripción y el README directamente en la terminal. En la página verás:

  • Arriba, ana-lopez / totito y una etiqueta Private.
  • La lista de archivos: .gitignore, README.md, pom.xml. No están target ni las carpetas vacías, por las razones que ya conoces.
  • Encima de la lista, tu nombre, el mensaje del último commit, su hash abreviado y un contador 1 Commit. Al hacer clic en él ves el historial, igual que con git log.
  • Debajo de la lista, tu README.md convertido en una página con formato: los # de Markdown se vuelven títulos. Por eso todo proyecto debe tener un buen README; en el capítulo 10 aprenderás a escribirlo.
Hito El Totito está en GitHub. Aunque tu computadora se dañara mañana, el proyecto y su historial están a salvo en tu cuenta.

La otra forma: crear el repositorio en la página

Si algún día no tienes gh a mano, el mismo resultado se consigue en tres pasos. Te lo muestro porque es lo que verás en muchos tutoriales:

  1. En GitHub, el botón + (arriba a la derecha) → New repository. Nombre totito, privado, y sin marcar «Add a README», «.gitignore» ni licencia (ya tienes esos archivos; si GitHub los crea, tendrás dos historias distintas que juntar).
  2. Conecta tu carpeta con ese repositorio y sube:
git remote add origin https://github.com/tu-usuario/totito.git
git push -u origin main

git remote add origin URL registra el remoto con el nombre origin. git push -u origin main sube la rama main a origin; la -u (de upstream, «corriente arriba») es la que deja emparejadas las dos ramas, lo mismo que hizo gh con set up to track. Solo hace falta la primera vez.

Por qué un commit por paso

  • El historial se vuelve un índice del libro. Cada commit corresponde a un capítulo. Si dentro de un año quieres repasar cómo se hizo la IA, buscas el commit «IA con el algoritmo Minimax» y ves exactamente qué se agregó.
  • Si algo se rompe, sabes dónde. Si el juego compilaba en el capítulo 44 y en el 45 dejó de compilar, el problema está en el último commit, no en cualquier parte de 30 archivos. git diff te muestra justo lo que cambió (capítulo 9).
  • Puedes volver atrás sin miedo. Si un capítulo te sale mal y quieres empezarlo de cero, regresas al commit del capítulo anterior (capítulo 9 explica cómo hacerlo con seguridad).
  • Los commits pequeños son fáciles de entender y revisar. Un commit que agrega un solo archivo explicado en un solo capítulo se entiende de un vistazo; uno que agrega quince archivos de golpe, no.
  • Las etiquetas marcan los logros. v0.1.0 es «el juego funciona en una ventana sencilla»; v1.0.0 es «el juego terminado». Puedes volver a cualquiera de los dos en cualquier momento.
  • La rama protege lo que ya funciona. Toda la Parte VII se hace en interfaz-neon: mientras construyes 24 archivos de interfaz, main sigue teniendo un juego que funciona.
  • Es como se trabaja en la vida real. En cualquier empresa te pedirán commits pequeños con buenos mensajes, ramas para cada tarea y pull requests. El Totito es tu entrenamiento.
¿Por qué los mensajes del plan no llevan tildes? Verás «logica» y «basico» sin tilde. Es la misma decisión que tomamos con los comentarios del código: evitar que una consola antigua o un programa mal configurado muestre caracteres raros. Git maneja tildes sin problema, y en tus propios proyectos puedes usarlas; en el Totito las evitamos para que tu historial coincida letra por letra con el del libro.

Resumen

  • git init -b main crea la carpeta oculta .git y convierte la carpeta del proyecto en un repositorio. Se hace una vez, en la carpeta correcta.
  • git status informa el estado de todo y sugiere el siguiente paso; el .gitignore ya hace que target no aparezca, y las carpetas vacías como src no existen para Git.
  • git add archivo pone cambios en la bandeja; nombrar los archivos es más seguro que git add ..
  • git commit -m "mensaje" guarda la foto; git log --oneline muestra el historial (sal del paginador con q).
  • gh repo create totito --private --source . --remote origin --push crea el repositorio en GitHub, lo conecta como origin y sube los commits; gh repo view --web lo abre en el navegador.
  • El plan de commits del libro hace un commit por paso, usa la rama interfaz-neon para la interfaz, un pull request para juntarla y las etiquetas v0.1.0 y v1.0.0 para las versiones.
Aplícalo fuera del Totito Estos siete pasos son los mismos para cualquier proyecto nuevo, de cualquier lenguaje:
  • Una página web: crea la carpeta, escribe un .gitignore (por ejemplo con node_modules/ si usas Node.js), git init, primer commit con «Estructura inicial…», gh repo create mi-web --public --source . --remote origin --push. Pública, porque quieres enseñarla.
  • Un proyecto que ya existía sin Git (por ejemplo, los ejercicios de la universidad): entra a su carpeta y haz exactamente lo mismo. Git empieza a guardar desde hoy; lo anterior queda como la primera foto.
  • Tus apuntes o un trabajo escrito en Markdown: un repositorio privado te da respaldo en la nube e historial de cada cambio, gratis.
  • Planear los commits antes de empezar: igual que el plan del libro, antes de un proyecto grande escribe en tu README la lista de pasos; cada paso terminado será un commit, y los hitos (primera versión que funciona, versión completa) serán etiquetas.

  1. Ejecuta git log y señala en la salida: el hash completo, la rama a la que apunta HEAD, tu correo y la zona horaria. ¿Coinciden con lo que configuraste en el capítulo 7?
  2. Abre README.md con el Bloc de notas (notepad README.md), agrega al final una línea «Proyecto del libro Java desde cero con el Totito», guarda y ejecuta git status y git status -s. ¿Qué palabra usa Git para el archivo? Después haz git add README.md, git commit -m "README: mencionar el libro" y git push, y comprueba en la página de GitHub que el contador dice 2 commits. Pista: este commit extra no está en el plan, y no pasa nada; tu historial puede tener más commits que el del libro.
  3. Crea un archivo de prueba notas.txt en la carpeta del proyecto (notepad notas.txt, escribe cualquier cosa y guarda). Ejecuta git status. Ahora agrega una línea notas.txt al final del .gitignore y vuelve a ejecutar git status. ¿Qué cambió? Para terminar, quita esa línea del .gitignore y borra el archivo con Remove-Item notas.txt.
  4. Ejecuta git check-ignore -v target y git check-ignore -v src\Prueba.class (aunque ese archivo no exista). Explica qué línea del .gitignore responde en cada caso.
  5. (Reto) Ejecuta gh repo view sin --web y luego gh repo view --json name,visibility,url. ¿Qué te muestra cada uno? Pista: la segunda forma devuelve datos en formato JSON, útil para scripts.
