Capítulo 6Qué es el control de versiones y cómo piensa Git

Antes de escribir un solo comando de Git, vas a entender qué problema resuelve y cómo «ve» tu proyecto por dentro: tres lugares, fotos encadenadas y etiquetas que se mueven. Con esa imagen en la cabeza, todos los comandos de los capítulos 7 a 10 dejan de ser recetas mágicas y se vuelven obvios.

El problema: la carpeta «Totito_final_final2»

Imagina que todavía no conoces Git y estás haciendo el Totito. Un día el juego funciona. Quieres probar un cambio grande (por ejemplo, cambiar todos los colores), pero te da miedo romperlo, así que haces lo que hace casi todo el mundo: copias la carpeta entera y le cambias el nombre. Una semana después tu carpeta Proyectos se ve así:

Totito
Totito - copia
Totito_final
Totito_final2
Totito_final_final2
Totito_final_final2_AHORA_SI
Totito_que_funcionaba_el_martes
Totito_colores_nuevos_NO_TOCAR

Parece una broma, pero es exactamente lo que pasa en oficinas, colegios y universidades con documentos de Word, hojas de Excel y, por supuesto, con programas. Y trae problemas muy concretos:

  • No sabes cuál es la buena. ¿«final_final2» es más nueva que «AHORA_SI»? ¿Cuál compilaba? Tienes que abrir cada una para averiguarlo.
  • No sabes qué cambió entre una y otra. Si el martes funcionaba y hoy no, ¿qué línea tocaste? Tendrías que comparar archivo por archivo, a ojo.
  • No sabes por qué cambió. Aunque encuentres la diferencia, nadie anotó la razón. Dentro de un mes no recordarás por qué cambiaste el color rosa.
  • Ocupa espacio y se mezcla. Cada copia duplica todo, incluidos archivos generados que no hacía falta guardar.
  • Colaborar es un caos. Si un amigo te ayuda, te manda su versión por WhatsApp o en una memoria USB, tú ya cambiaste la tuya, y alguien tiene que juntar las dos a mano… y siempre se pierde algo.
  • Un error a las dos de la mañana borra horas de trabajo. Si guardaste encima de la única copia buena, no hay «deshacer» que valga.

El control de versiones existe para resolver todo eso de una vez.

Control de versiones Es un sistema que guarda el historial completo de los cambios de un proyecto: qué cambió, cuándo, quién lo hizo y por qué. Permite volver a cualquier punto del pasado, comparar versiones, trabajar en varias ideas a la vez sin mezclarlas y juntar el trabajo de varias personas de forma ordenada.

Con control de versiones tienes una sola carpeta Totito. Las «copias» no se ven como carpetas sueltas: viven guardadas dentro del historial, ordenadas, con fecha, autor y una explicación, y puedes sacar cualquiera cuando la necesites.

Dos analogías para quedarte con la idea

  • Los puntos de guardado de un videojuego. Antes de entrar a la pelea difícil, guardas la partida. Si pierdes, vuelves a ese punto en lugar de empezar desde cero. En Git, cada punto de guardado se llama commit, y a diferencia del videojuego puedes tener miles, cada uno con una nota que dice qué habías logrado.
  • Un álbum de fotos con notas. Cada vez que el proyecto llega a un estado que vale la pena recordar, le tomas una foto, la pegas en el álbum y escribes debajo qué se ve. Puedes hojear el álbum hacia atrás, comparar dos fotos y ver qué cambió.

Qué es Git

Git es el programa de control de versiones más usado del mundo. Lo creó Linus Torvalds en 2005 para organizar el desarrollo de Linux, un proyecto con miles de programadores repartidos por todo el planeta. Hoy lo usan desde estudiantes con su primer programa hasta empresas como Microsoft, Google o cualquier banco: si trabajas en software, vas a usar Git.

Tres características de Git que conviene saber desde ya:

  • Es local. Git vive en tu computadora. Funciona sin internet: puedes guardar versiones, ver el historial y crear ramas en un avión. Internet solo hace falta para enviar o recibir cambios de otra copia (por ejemplo, de GitHub).
  • Es distribuido. Cada copia de un proyecto con Git tiene el historial completo, no solo la última versión. Si tu computadora se daña pero el proyecto está en GitHub, no pierdes nada; y si GitHub fallara, tu copia también lo tiene todo.
  • Es de texto y de línea de comandos. Git se maneja con comandos que empiezan con git (por ejemplo git status). NetBeans y otros programas tienen botones para Git, pero por dentro ejecutan esos mismos comandos. En este libro aprendes los comandos en PowerShell (capítulo 3), porque así entiendes lo que hacen los botones.

Cómo piensa Git: los tres lugares

Esta es la idea más importante de toda la Parte II. Para Git, tu proyecto existe en tres lugares al mismo tiempo, y casi todos los comandos sirven para mover cambios de un lugar a otro.

1. El directorio de trabajo: tu mesa

Es la carpeta que ves en el Explorador de Windows: C:\Users\<tu-usuario>\Proyectos\Totito, con su pom.xml, su README.md y, más adelante, la carpeta src con los archivos .java. Ahí editas con NetBeans. Para Git es la mesa de trabajo: lo que hay sobre la mesa puede estar a medias, desordenado o recién roto. Git lo observa, pero no lo guarda por sí solo.

2. El área de preparación: la bandeja de lo que saldrá en la foto

También se llama staging area o index (en inglés). Es una zona intermedia donde pones exactamente los cambios que quieres incluir en la próxima foto. El comando git add mueve un cambio de la mesa a la bandeja.

¿Para qué sirve este paso extra? Para elegir. Supón que en una misma tarde arreglaste un error en Tablero.java y además empezaste a cambiar colores en Tema.java, pero los colores todavía no te convencen. Con el área de preparación puedes poner en la bandeja solo el arreglo del tablero, guardar esa foto con un mensaje claro («Tablero: corregir la detección de empate») y dejar los colores sobre la mesa para seguir probando. Sin la bandeja, cada foto llevaría «todo lo que hay en la mesa», mezclado.

Una comparación de la vida diaria: el carrito del supermercado. Vas metiendo cosas al carrito (git add), puedes sacar alguna si te arrepientes, y solo cuando pagas en la caja (git commit) la compra queda registrada en tu ticket.

3. El repositorio: el álbum

El repositorio («repo», para los amigos) es la base de datos donde Git guarda todas las fotos del proyecto. Físicamente es una carpeta oculta llamada .git dentro de tu carpeta Totito. La crea el comando git init (capítulo 8). El comando git commit toma lo que hay en la bandeja, le saca la foto y la pega en el álbum.

Nunca borres ni edites la carpeta .git Todo el historial vive ahí. Si borras .git, tu código actual sigue en la carpeta, pero pierdes todas las versiones anteriores (salvo que estén en GitHub). Tampoco metas archivos a mano dentro de .git: Git la administra solo.

4. El repositorio remoto: una copia del álbum en internet

Además de esos tres lugares, normalmente hay un cuarto: una copia del repositorio en otra computadora, casi siempre en un servicio como GitHub. Se llama remoto, y por costumbre el principal se llama origin («origen»). git push («empujar») envía tus fotos nuevas al remoto; git pull («jalar») trae las fotos que otros (o tú desde otra computadora) subieron.

Los estados de un archivo

Como consecuencia de los tres lugares, cada archivo de tu carpeta está siempre en uno de estos estados. git status, el comando que más vas a usar, te dice precisamente eso.

EstadoEn inglés (lo que verás en Git)Qué significaEjemplo en el Totito

El recorrido normal de un archivo es: sin seguimiento → (git add) → preparado → (git commit) → sin cambios → (lo editas) → modificado → (git add) → preparado → (git commit) → sin cambios… y así toda la vida del proyecto.

El .gitignore En el capítulo 5 creaste un archivo .gitignore con líneas como target/ y *.class. Es la lista de cosas que Git debe ignorar: archivos que se generan solos al compilar y que no tiene sentido guardar, porque cualquiera puede volver a generarlos desde el código. Así tu álbum solo tiene lo que tú escribiste.

El commit: una foto completa del proyecto

Un commit (en español a veces se dice «confirmación», pero todo el mundo dice commit) es una foto del proyecto entero en un momento dado. Cada commit guarda:

  • El contenido de todos los archivos seguidos tal como estaban en la bandeja. No solo los que cambiaron: la foto es del proyecto completo. (Por dentro Git es muy listo y no duplica los archivos que no cambiaron; reutiliza los de la foto anterior. Por eso un historial de cientos de commits ocupa poco).
  • El autor: nombre y correo (los configuras en el capítulo 7).
  • La fecha y hora.
  • El mensaje: la nota que tú escribes explicando qué cambió y por qué, por ejemplo Tablero: estado y reglas del juego.
  • El padre: una referencia al commit anterior. Así los commits forman una cadena.

Cada commit tiene un identificador único, un número de 40 caracteres hexadecimales (dígitos del 0 al 9 y letras de la a a la f) llamado hash, por ejemplo:

b49d01a6c3c1c9f4020c112a1e7653865b27f213

Git lo calcula a partir del contenido de la foto, del autor, la fecha, el mensaje y el padre. Si cambiara una sola letra de cualquiera de esas cosas, el hash sería completamente distinto. Por eso un commit es inmutable: no se puede modificar sin convertirse en otro commit diferente. En el día a día se usan solo los primeros 7 caracteres (b49d01a), que bastan para distinguirlo.

Una analogía: el hash es como el número de DPI de un commit (o la huella digital). Dos commits distintos nunca tienen el mismo, y con él puedes señalar uno sin ambigüedad: «el error apareció en el commit ebd646d».

Una foto, una idea Un buen commit guarda un cambio con sentido completo: «agregar el color lavanda», «crear la clase Jugador». No «lo que hice hoy». En el capítulo 9 verás por qué los commits pequeños te salvan la vida.

Las ramas: etiquetas que se mueven

Aquí es donde mucha gente se confunde, porque la palabra «rama» hace pensar en una copia del proyecto. No lo es. En Git, una rama es simplemente una etiqueta con un nombre que apunta a un commit. Nada más. Ocupa unos pocos bytes.

En el dibujo de arriba, main es una rama: una etiqueta pegada al commit 7c59777. main («principal») es el nombre que, por convención, lleva la rama principal de un proyecto (en proyectos viejos verás master, el nombre antiguo; en el capítulo 7 configuras Git para que use main).

Lo especial de una rama es que avanza sola: cuando haces un commit nuevo estando «en» main, la etiqueta main se despega del commit viejo y se pega al nuevo. Es como el marcador de un libro que se mueve solo a la última página que leíste.

¿Y para qué quieres más de una rama? Para trabajar en una idea sin estorbar a otra. En la Parte VII del libro construirás toda la interfaz neón en una rama llamada interfaz-neon. Mientras tanto, main se queda tranquila apuntando a la versión 0.1.0, la que ya funciona. Si la interfaz neón saliera mal, main seguiría intacta.

Crear una rama es instantáneo y no copia ningún archivo: Git solo escribe una etiqueta nueva. Por eso en Git se crean ramas para todo, incluso para cambios de diez minutos.

HEAD: «usted está aquí»

En los mapas de los centros comerciales hay un punto rojo que dice «usted está aquí». En Git ese punto se llama HEAD (en mayúsculas). HEAD indica en qué rama estás trabajando ahora y, a través de ella, qué commit tienes sobre la mesa.

  • Normalmente HEAD apunta a una rama: «HEAD → main → 7c59777». Cuando haces un commit, el nuevo commit se cuelga del que señala HEAD, y la rama a la que apunta HEAD avanza.
  • Cuando cambias de rama (git switch interfaz-neon, capítulo 9), HEAD se mueve a la otra etiqueta, y Git cambia los archivos de tu carpeta para que coincidan con el commit de esa rama. Sí: los archivos de tu carpeta cambian. Si en main no existe Tema.java y en interfaz-neon sí, al pasar a main el archivo desaparece de la carpeta, y al volver a interfaz-neon reaparece. No se pierde: está guardado en el álbum.
  • Verás HEAD en la salida de varios comandos, por ejemplo git log muestra (HEAD -> main) junto al commit en el que estás.
«detached HEAD» Si algún día Git te dice You are in 'detached HEAD' state, significa que HEAD apunta directamente a un commit viejo y no a una rama (por ejemplo, porque pediste ver cómo estaba el proyecto en la v0.1.0). Puedes mirar sin problema, pero si haces commits ahí quedan «sueltos», sin etiqueta. Para volver a la normalidad basta con git switch main. No es un error grave; es Git avisándote de que estás de visita en el pasado.

Juntar ramas: merge

Tarde o temprano el trabajo de una rama tiene que volver a la principal. Eso se llama fusionar (en inglés merge). Cuando termines la interfaz neón (capítulo 61), fusionarás interfaz-neon en main, y main pasará a tener el juego completo, versión 1.0.0.

Git sabe fusionar solo la gran mayoría de las veces, incluso si dos personas cambiaron el mismo archivo, siempre que hayan tocado líneas distintas. Si dos ramas cambiaron la misma línea de forma diferente, Git no adivina: te pregunta cuál quieres. Eso es un conflicto, y en el capítulo 9 provocarás uno a propósito para aprender a resolverlo con calma.

Git y GitHub no son lo mismo

Esta confusión es tan común que merece su propia sección.

GitGitHub
Qué esUn programa que instalas en tu computadora (capítulo 4)Un servicio web (una página y unos servidores) de la empresa GitHub, que pertenece a Microsoft
Dónde viveEn tu PC, en la carpeta .git de cada proyectoEn internet: https://github.com
Para qué sirveGuardar versiones, ver el historial, crear ramas, fusionarGuardar una copia de tus repositorios en la nube y colaborar: pull requests, issues, releases, revisión de código, automatizaciones (Actions), tu perfil público como programador
¿Necesita internet?NoSí
¿Necesita cuenta?No (solo tu nombre y correo para firmar los commits)Sí (la creas en el capítulo 7)

La analogía: Git es tu cámara y tu álbum; GitHub es un álbum compartido en la nube (como Google Fotos), donde además tus amigos pueden comentar las fotos y proponerte cambios. Puedes usar Git sin GitHub, pero no GitHub sin Git.

Y hay una tercera pieza: GitHub CLI, el programa gh que instalaste en el capítulo 4. Es una herramienta de línea de comandos para manejar GitHub (crear repos, abrir pull requests, publicar releases) sin salir de PowerShell. Resumiendo: git … trabaja con tu repositorio; gh … habla con la página de GitHub.

Lo que Git no es

  • No es un respaldo automático. Git solo guarda lo que tú le pides con git commit, y solo lo saca de tu PC cuando haces git push. Si trabajas una semana sin hacer commits y se daña el disco, Git no te salva.
  • No es Dropbox ni OneDrive. No sincroniza solo. Y no pongas tu carpeta Proyectos dentro de una carpeta sincronizada por OneDrive: los dos programas pelean por los mismos archivos y pueden dañar la carpeta .git.
  • No es para archivos enormes ni generados. Git está pensado para texto (código, configuración, documentación). Los .jar, .exe, videos o instaladores no van en el repositorio; los instaladores del Totito se publicarán como release (capítulo 67).
  • No es un lugar para contraseñas. Todo lo que entra en un commit queda en el historial para siempre, aunque después lo borres. El capítulo 10 dedica una sección completa a qué no subir nunca.

El camino del Totito con Git

Para que veas a dónde lleva todo esto, así será la historia del Totito de principio a fin (en el capítulo 8 verás el plan de commits detallado):

  1. Capítulo 7: configuras Git con tu nombre y correo, y conectas tu PC con tu cuenta de GitHub.
  2. Capítulo 8: conviertes la carpeta Totito en un repositorio, haces el primer commit con los archivos del capítulo 5 y lo subes a GitHub.
  3. Capítulos 29 a 33: cada archivo de la lógica es un commit en main. Al terminar la primera ventana pones la etiqueta v0.1.0.
  4. Capítulos 38 a 61: creas la rama interfaz-neon y construyes toda la interfaz ahí, un commit por capítulo.
  5. Capítulo 61: abres un pull request de interfaz-neon a main, lo fusionas y etiquetas v1.0.0.
  6. Capítulos 64 y 67: agregas el icono y publicas en GitHub un release con el instalador .exe para que cualquiera lo descargue.

Cuando un comando te sorprenda, pregúntate «¿entre qué lugares está moviendo cosas?» y casi siempre tendrás la respuesta.

Resumen

  • El control de versiones reemplaza las carpetas «final_final2» por un historial ordenado: qué cambió, cuándo, quién y por qué.
  • Git trabaja con tres lugares locales: el directorio de trabajo (tu carpeta), el área de preparación (lo que irá en la próxima foto) y el repositorio (la carpeta .git). git add y git commit mueven cambios entre ellos.
  • Un commit es una foto completa e inmutable del proyecto, con autor, fecha, mensaje, padre y un hash único.
  • El historial es una cadena de commits donde cada uno apunta a su padre.
  • Una rama es una etiqueta móvil que apunta a un commit; main es la principal. HEAD indica en qué rama estás.
  • Merge junta dos ramas; si ambas cambiaron la misma línea, hay un conflicto que resuelves tú.
  • Git es el programa local; GitHub es el servicio web para guardar copias y colaborar; gh maneja GitHub desde PowerShell.
Aplícalo fuera del Totito El modelo de «mesa, bandeja, álbum» sirve para cualquier proyecto de texto, no solo de Java:
  • Una página web personal (HTML y CSS): cada cambio de diseño es un commit; si el nuevo menú queda feo, vuelves al anterior en segundos.
  • Tu tesis o un libro escrito en Markdown o LaTeX: cada capítulo terminado es un commit, y una rama «revision-asesor» guarda los cambios que te pidió tu asesor sin tocar tu versión.
  • Los scripts de PowerShell con los que automatizas tareas: si un script que antes funcionaba deja de hacerlo, el historial te dice exactamente qué línea cambió.
  • Un proyecto en equipo del colegio o la universidad: en lugar de pasarse archivos por WhatsApp, cada quien trabaja en su rama y se fusiona en GitHub.
