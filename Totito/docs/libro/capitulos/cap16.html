Capítulo 16Métodos: funciones, parámetros, retorno y llamadas

Todo el Totito está hecho de métodos: marcarCasilla, verificarGanador, obtenerCopia, trazoNeon, minimax… En este capítulo aprendes qué es exactamente un método, para qué sirve, cómo se declara, qué ocurre por dentro de la computadora cuando lo llamas (la pila de llamadas), cómo viajan los datos de ida y de vuelta, y cómo un método puede llamarse a sí mismo, que es el truco con el que la IA del Totito piensa.

Qué es un método y para qué sirve

Un método es un bloque de código con nombre que realiza una tarea concreta y que se puede ejecutar cuantas veces quieras, desde donde quieras, escribiendo su nombre. A ejecutarlo se le llama llamar (o invocar) al método.

En otros lenguajes se les llama funciones o procedimientos. En Java todo vive dentro de una clase, así que todas las funciones son «métodos» (métodos de alguna clase); en la práctica, en este libro las dos palabras significan lo mismo.

Analogía: el botón «Palomitas» del microondas. Ese botón esconde una pequeña receta: «potencia alta, 2 minutos y 30 segundos, pitar tres veces». Quien lo pulsa no necesita saber los pasos; solo el nombre del botón. Si el fabricante mejora la receta, todos los que pulsan el botón se benefician sin cambiar nada. Un método es eso: una receta con nombre. Algunos botones piden un dato antes (los minutos: un parámetro) y algunos te dan algo al terminar (la comida caliente: un valor de retorno).

¿Por qué el Totito está dividido en tantos métodos en lugar de escribirlo todo seguido en main? Cinco razones, todas visibles en el código:

  1. No repetir. La comprobación «¿hay ganador?» se necesita después de cada jugada del humano, después de cada jugada de la IA, y cientos de miles de veces dentro de Minimax. Está escrita una vez, en verificarGanador(), y se llama desde todos esos sitios. Si hubiera un error en ella, se arreglaría en un solo lugar.
  2. Dar nombre a una idea. if (tablero.tableroLleno()) se lee como una frase; los dos bucles anidados que hay dentro, no. El nombre del método explica qué se hace; el cuerpo, cómo.
  3. Dividir un problema grande. «Hacer un totito» es abrumador. «Marcar una casilla», «ver si alguien ganó», «ver si el tablero está lleno», «copiar el tablero» son problemas pequeños que se resuelven uno a uno. Es la técnica principal de la programación: divide y vencerás.
  4. Probar por partes. En el capítulo 11 probaste marcarCasilla en jshell sin ventanas ni IA. Un método pequeño se prueba solo.
  5. Ocultar detalles. PantallaJuego llama a partida.jugar(fila, columna) y no sabe ni le importa cómo se guardan las casillas. Si mañana el tablero se guardara de otra forma, la pantalla no cambiaría (capítulo 19).

Anatomía de un método: la declaración

Tomemos un método real de Tablero:

public boolean marcarCasilla(int fila, int columna, char ficha) {
    if (fila < 0 || fila > 2 || columna < 0 || columna > 2) {
        return false;
    }
    if (casillas[fila][columna] != VACIA) {
        return false;
    }
    casillas[fila][columna] = ficha;
    return true;
}

A la primera línea (sin el cuerpo) se le llama cabecera o declaración. Y en sentido estricto, la firma de un método es su nombre más los tipos de sus parámetros, en orden: marcarCasilla(int, int, char). La firma es lo que Java usa para identificar a un método; lo verás importar en la sobrecarga.

Puede haber más palabras antes del tipo de retorno: static (lo verás al final de este capítulo y en el 20), final, protected, @Override encima (capítulo 23)… Pero tipo, nombre, paréntesis y cuerpo están siempre.

Tu primer programa dividido en métodos

Este programa reproduce tres métodos del Totito como métodos static de una sola clase (para que funcionen sin crear objetos; el porqué, al final del capítulo). Como aquí no hay un objeto Tablero que guarde sus casillas, la matriz se pasa como primer parámetro:

public class ConMetodos {

    static final char VACIA = ' ';

    public static void main(String[] args) {
        char[][] casillas = new char[3][3];
        reiniciar(casillas);

        boolean ok = marcarCasilla(casillas, 1, 1, 'X');
        System.out.println("¿Se pudo marcar el centro? " + ok);
        System.out.println("¿Y otra vez? " + marcarCasilla(casillas, 1, 1, 'O'));
        System.out.println("¿Y la fila 5? " + marcarCasilla(casillas, 5, 0, 'O'));
        marcarCasilla(casillas, 0, 2, 'O');
        imprimir(casillas);
    }

    /** Deja todas las casillas vacias. */
    static void reiniciar(char[][] casillas) {
        for (int fila = 0; fila < 3; fila++) {
            for (int columna = 0; columna < 3; columna++) {
                casillas[fila][columna] = VACIA;
            }
        }
    }

    /** Coloca la ficha si la casilla existe y esta libre; dice si pudo. */
    static boolean marcarCasilla(char[][] casillas, int fila, int columna, char ficha) {
        if (fila < 0 || fila > 2 || columna < 0 || columna > 2) {
            return false;
        }
        if (casillas[fila][columna] != VACIA) {
            return false;
        }
        casillas[fila][columna] = ficha;
        return true;
    }

    /** Dibuja el tablero con caracteres. */
    static void imprimir(char[][] casillas) {
        for (int fila = 0; fila < 3; fila++) {
            System.out.println(" " + casillas[fila][0] + " | " + casillas[fila][1] + " | " + casillas[fila][2]);
            if (fila < 2) {
                System.out.println("---+---+---");
            }
        }
    }
}

Lee main: son seis líneas que cuentan una historia («reinicia, marca, intenta otra vez, intenta fuera, marca otra, imprime») sin un solo bucle a la vista. Los detalles están en los métodos. El orden en que se escriben los métodos dentro de la clase no importa: main puede llamar a imprimir aunque esté escrito más abajo.

Parámetros y argumentos

Dos palabras que se confunden y conviene separar:

  • Un parámetro es la variable que aparece en la declaración del método: int fila, int columna, char ficha. Es un hueco con nombre que espera un valor.
  • Un argumento es el valor concreto que se pone en la llamada: en marcarCasilla(casillas, 1, 1, 'X') los argumentos son casillas, 1, 1 y 'X'.

Analogía: un formulario tiene casillas con rótulo («Nombre: ____», «Edad: ____»); eso son los parámetros. Lo que escribes en ellas («Ana», «17») son los argumentos. El mismo formulario se llena miles de veces con argumentos distintos.

Al llamar, los argumentos se asignan a los parámetros por posición: el primero al primero, el segundo al segundo. Los nombres no importan: en Partida.jugar se llama tablero.marcarCasilla(fila, columna, jugadores[turno].getFicha()), y en IA_Minimax, copia.marcarCasilla(fila, columna, fichaIA); el tercer argumento se llama distinto en cada caso, pero los dos acaban en el parámetro ficha. Un argumento puede ser cualquier expresión: un literal (1), una variable, una cuenta (profundidad + 1) o incluso otra llamada (jugadores[turno].getFicha(), que se ejecuta primero y entrega su resultado).

El compilador comprueba que la cantidad y los tipos encajen:

Argumentos.java:4: error: method marcarCasilla in class Argumentos cannot be applied to given types;
        marcarCasilla(casillas, 1, 'X');
        ^
  required: char[][],int,int,char
  found:    char[][],int,char
  reason: actual and formal argument lists differ in length

«Requerido: matriz, int, int, char. Encontrado: matriz, int, char». Faltó la columna. Los formal arguments del mensaje son los parámetros y los actual arguments, los argumentos.

El orden importa, y el compilador no siempre te salva. Si escribes marcarCasilla(casillas, 'X', 1, 1), el compilador protesta, pero no por la 'X': protesta porque el último 1 no cabe en el parámetro char ficha (possible lossy conversion from int to char). La 'X' en el parámetro int fila la habría aceptado sin rechistar, convertida a su código, 88 (capítulo 12). Si los dos parámetros fueran int, como fila y columna, intercambiarlos compilaría siempre y pondría la ficha en la casilla simétrica. Por eso los parámetros llevan nombres claros y NetBeans te los muestra mientras escribes la llamada.

return y el tipo de retorno

return hace dos cosas a la vez: termina el método en ese instante y entrega un valor a quien lo llamó. Ese valor ocupa el lugar de la llamada, como si la expresión marcarCasilla(casillas, 1, 1, 'X') se sustituyera por true. Por eso se puede guardar (boolean ok = …), imprimir, usar en un if o pasar a otro método.

  • El valor devuelto tiene que ser del tipo declarado: un método boolean devuelve true o false; verificarGanador(), declarado char, devuelve casillas[i][0] o VACIA; obtenerCopia(), declarado Tablero, devuelve un objeto Tablero; calcularMejorJugada, declarado int[], devuelve un arreglo.
  • Un método puede tener varios return; se ejecuta el primero al que se llegue. marcarCasilla tiene tres: dos para rechazar (las cláusulas de guarda del capítulo 13) y uno al final para aceptar.
  • Todos los caminos deben terminar en un return. Si hay alguna forma de llegar al final sin devolver nada, no compila: 
    SinReturn.java:6: error: missing return statement
    }
    ^
    Ese método decía if (dentro) { return true; } pero no qué devolver si no. Java no adivina.

Métodos void

Un método void hace algo pero no devuelve nada: reiniciar() limpia el tablero, imprimir escribe en pantalla, trazoNeon dibuja. No se puede guardar su resultado (boolean x = tablero.reiniciar(); no compila: no hay resultado). Puede usar return; sin valor para salir antes; así empieza Partida.jugarTurnoIA:

public void jugarTurnoIA() {
    if (!esTurnoDeIA()) {
        return;
    }
    int[] jugada = ia.calcularMejorJugada(tablero);
    jugar(jugada[0], jugada[1]);
}

«Si no le toca a la IA, no hagas nada». Otra cláusula de guarda.

Usar o ignorar lo que se devuelve

Nada obliga a usar el valor de retorno. En IA_Minimax, copia.marcarCasilla(fila, columna, fichaIA); descarta el boolean: la IA ya comprobó en la línea anterior que la casilla estaba vacía, así que sabe que saldrá true. En cambio Partida.jugar sí lo usa, porque ahí la jugada viene de un clic y podría ser inválida. Ignorar un resultado debe ser una decisión consciente, no un descuido.

Qué pasa exactamente en una LLAMADA

Este es el corazón del capítulo. Cuando Java encuentra una llamada como jugar(1, 1), hace esto, siempre en este orden:

  1. Evalúa los argumentos, de izquierda a derecha, hasta tener valores concretos (si un argumento es profundidad + 1, calcula la suma).
  2. Crea un marco (stack frame) nuevo: un espacio de memoria propio de esta llamada, donde vivirán sus parámetros y sus variables locales. Los parámetros nacen inicializados con copias de los argumentos.
  3. Apila el marco encima del marco de quien llamó, en una zona de memoria llamada pila de llamadas (call stack). Además anota «cuando termines, vuelve a tal línea de tal método».
  4. Salta a la primera línea del cuerpo del método y la ejecuta. Mientras tanto, el método que llamó está en pausa, esperando, con todas sus variables intactas en su propio marco.
  5. Al llegar a un return (o a la llave final de un void), desapila el marco: sus parámetros y variables locales desaparecen.
  6. Vuelve exactamente al punto donde se hizo la llamada; el valor devuelto ocupa el lugar de la llamada y la ejecución continúa.
Analogía: la pila de platos (o de encargos). Estás cocinando (main) y te falta azúcar: dejas la receta a medias y vas a la tienda (llamada a jugar). En la tienda te piden la cédula: buscas en tu cartera (llamada a dentroDelTablero). Al encontrarla, vuelves a la tienda justo donde lo dejaste, compras, y vuelves a la cocina, a la línea exacta de la receta donde te habías quedado. Cada encargo nuevo se pone encima de la pila; solo se puede trabajar en el de arriba; al terminarlo se quita y se retoma el de abajo. «El último en entrar es el primero en salir».

Este programa lo hace visible: cada método anuncia cuándo empieza y qué recibe.

public class Pila {
    public static void main(String[] args) {
        System.out.println("main: empiezo");
        boolean valida = jugar(1, 1);
        System.out.println("main: jugar devolvio " + valida);
        System.out.println("main: termino");
    }

    static boolean jugar(int fila, int columna) {
        System.out.println("  jugar(" + fila + ", " + columna + "): empiezo");
        boolean ok = dentroDelTablero(fila, columna);
        System.out.println("  jugar: dentroDelTablero devolvio " + ok);
        return ok;
    }

    static boolean dentroDelTablero(int fila, int columna) {
        System.out.println("    dentroDelTablero(" + fila + ", " + columna + "): calculo y vuelvo");
        return fila >= 0 && fila < 3 && columna >= 0 && columna < 3;
    }
}

La traza de la pila, otra vez

Ahora entiendes por completo el mensaje de una excepción. Si un error ocurre dentro de un método llamado por otro, Java imprime la pila entera tal como estaba en ese momento:

public class PilaError {
    public static void main(String[] args) {
        jugar(3, 0);
    }

    static void jugar(int fila, int columna) {
        marcar(fila, columna);
    }

    static void marcar(int fila, int columna) {
        char[][] casillas = new char[3][3];
        casillas[fila][columna] = 'X';
    }
}
Exception in thread "main" java.lang.ArrayIndexOutOfBoundsException: Index 3 out of bounds for length 3
	at PilaError.marcar(PilaError.java:12)
	at PilaError.jugar(PilaError.java:7)
	at PilaError.main(PilaError.java:3)

Se lee de arriba abajo como la pila del dibujo: el error ocurrió en marcar (línea 12), que había sido llamado desde jugar (línea 7), que había sido llamado desde main (línea 3). La primera línea dice dónde explotó; las de abajo, cómo se llegó ahí. Muchas veces el error de verdad no está en la línea que explotó sino más abajo: aquí, marcar está bien; el problema es que main le pasó un 3. En un programa con ventanas la traza será larga, con muchas líneas de javax.swing; busca las primeras que mencionen tus archivos.

Paso por valor: qué recibe exactamente un método

En el paso 2 de la llamada dijimos que los parámetros reciben copias de los argumentos. Java siempre funciona así; se llama paso por valor. Pero «copia» significa cosas distintas según el tipo, y aquí está una de las ideas más importantes (y más malentendidas) de Java:

import java.util.Arrays;

public class PasoPorValor {
    public static void main(String[] args) {
        int turno = 0;
        cambiarTurno(turno);
        System.out.println("1) turno sigue valiendo " + turno);
        turno = turnoSiguiente(turno);
        System.out.println("2) con return, turno vale " + turno);

        char[] fila = {' ', ' ', ' '};
        ponerX(fila);
        System.out.println("3) fila despues de ponerX: " + Arrays.toString(fila));

        reemplazar(fila);
        System.out.println("4) fila despues de reemplazar: " + Arrays.toString(fila));
    }

    static void cambiarTurno(int turno) {
        turno = 1 - turno;   // cambia SU copia
    }

    static int turnoSiguiente(int turno) {
        return 1 - turno;
    }

    static void ponerX(char[] casillas) {
        casillas[0] = 'X';   // modifica el arreglo al que apunta la copia de la referencia
    }

    static void reemplazar(char[] casillas) {
        casillas = new char[]{'O', 'O', 'O'};   // la copia apunta a otro arreglo; el original no se entera
    }
}
1) turno sigue valiendo 0
2) con return, turno vale 1
3) fila despues de ponerX: [X,  ,  ]
4) fila despues de reemplazar: [X,  ,  ]
  1. Con un primitivo (int, char, boolean…) el método recibe una copia del número. Cambiar su copia no toca la variable de main: turno sigue en 0. Es como darle a alguien una fotocopia de tu examen: puede tacharla entera y tu original sigue igual.
  2. La forma correcta de que un método «cambie» un primitivo es que devuelva el nuevo valor y que quien llama lo asigne: turno = turnoSiguiente(turno).
  3. Con un arreglo u objeto, la variable no contiene el arreglo sino su referencia (su dirección, capítulo 15). El método recibe una copia de la dirección. Con esa dirección llega al mismo arreglo y puede cambiar su contenido: la X aparece en main. Es como darle a alguien una copia de la llave de tu casa: la llave es otra, pero la casa es la misma.
  4. Pero si el método hace que su copia de la dirección apunte a otro arreglo (casillas = new char[]…), solo cambia su llave; la variable de main sigue apuntando al arreglo de siempre.

Esto explica dos decisiones del Totito:

  • calcularMejorJugada(Tablero tablero) recibe la referencia al tablero real de la partida. Si la IA hiciera tablero.marcarCasilla(…) para probar jugadas, las marcaría en la partida de verdad. Por eso siempre trabaja sobre tablero.obtenerCopia().
  • PanelTablero.mostrar(Tablero tablero) no guarda la referencia que recibe, sino que copia las casillas a su propia matriz fichas: lo que se dibuja no puede cambiar a espaldas del panel.
Escucharás decir «en Java los objetos se pasan por referencia». No es exacto, y la línea 4 lo demuestra: si fuera paso por referencia, reemplazar habría cambiado la variable de main. Java pasa siempre por valor; lo que pasa, en el caso de los objetos, es el valor de la referencia. La consecuencia práctica: un método puede modificar el objeto que recibe, pero no puede cambiar qué objeto tiene la variable de quien llamó.

Alcance: dónde existe cada variable

El alcance (scope) de una variable es la zona del código donde existe y se puede usar. La regla general: una variable vive desde que se declara hasta la llave } que cierra el bloque donde se declaró.

  • Variables locales: declaradas dentro de un método. Solo existen en ese método, y solo mientras se ejecuta (viven en su marco de la pila). mejorValor y mejorJugada son locales de calcularMejorJugada.
  • Parámetros: son variables locales que nacen con el valor del argumento.
  • Variables de bloque: declaradas dentro de un for, un if o cualquier par de llaves. Solo existen ahí. La fila de un for muere al terminar el bucle.
  • Campos (o atributos): declarados en la clase, fuera de todo método, como casillas en Tablero o turno en Partida. Los ven todos los métodos de la clase y viven tanto como el objeto (capítulo 18). Por eso marcarCasilla puede usar casillas sin recibirla como parámetro.
public class Alcance {
    static int empates = 0;          // campo: vive mientras viva el programa

    public static void main(String[] args) {
        int victorias = 2;           // local de main
        for (int i = 0; i < 2; i++) {
            int doble = i * 2;       // local del bloque del for
            System.out.println("i = " + i + ", doble = " + doble);
        }
        sumarEmpate();
        sumarEmpate();
        System.out.println("victorias = " + victorias + ", empates = " + empates);
    }

    static void sumarEmpate() {
        empates++;                   // el campo SI se ve desde aqui
        // victorias++;              // no compilaria: victorias es de main
    }
}
i = 0, doble = 0
i = 1, doble = 2
victorias = 2, empates = 2

Si intentas usar una variable fuera de su bloque, el compilador no la encuentra:

FueraDeAlcance.java:6: error: cannot find symbol
        System.out.println(doble);
                           ^
  symbol:   variable doble
  location: class FueraDeAlcance

El mismo «cannot find symbol» del capítulo 11: para el compilador, fuera de su bloque esa variable no existe. Si la necesitas después, declárala antes del bloque (como fila y columna antes del do en el capítulo 14).

Declara cada variable en el alcance más pequeño posible, justo donde la necesitas. El Totito declara Tablero copia dentro del if que la usa, no al principio del método. Cuanto más pequeño el alcance, menos sitios donde algo puede salir mal y menos cosas que tener en la cabeza al leer.

Cuando un parámetro y un campo se llaman igual: this

En el constructor de Jugador:

public Jugador(String nombre, char ficha) {
    this.nombre = nombre;
    this.ficha = ficha;
}

Hay un campo nombre y un parámetro nombre. Dentro del método, el nombre suelto se refiere al más cercano: el parámetro (se dice que el parámetro oculta o «hace sombra» al campo). Para llegar al campo se escribe this.nombre, «el nombre de este objeto». La línea se lee: «guarda en mi campo nombre el valor que me pasaron en el parámetro nombre». Si escribieras nombre = nombre;, asignarías el parámetro a sí mismo y el campo quedaría vacío para siempre. Lo verás a fondo en el capítulo 20.

Sobrecarga: mismo nombre, distintos parámetros

En una clase puede haber varios métodos con el mismo nombre si tienen distintos parámetros (en cantidad, tipo u orden). Se llama sobrecarga (overloading). Java elige cuál ejecutar mirando los argumentos de cada llamada. En Dibujo hay dos trazoNeon:

public static void trazoNeon(Graphics2D g, Shape figura, Color color, float grosor) {
    trazoNeon(g, figura, color, grosor, 1f);
}

public static void trazoNeon(Graphics2D g, Shape figura, Color color, float grosor, float intensidad) {
    // ... el dibujo de verdad: halo, linea principal y centro blanco ...
}

La versión de cuatro parámetros es un atajo: la mayoría de los trazos se dibujan con intensidad normal, así que en lugar de escribir 1f en cada llamada, existe una versión que no la pide y que se limita a llamar a la completa con 1f. Las fichas X y O y varios iconos usan la corta; el marco del tablero (0.8f, algo apagado), las rejillas (0.4f) o un botón con el ratón encima (1.5f) usan la larga. Así el código del dibujo vive en un solo lugar y las llamadas quedan cortas. Este programa imita lo mismo en consola (sin el Graphics2D, para poder ejecutarlo sin ventana):

public class Sobrecarga {
    public static void main(String[] args) {
        trazoNeon("marco", "MORADO", 1.5f, 0.8f);   // 4 argumentos
        trazoNeon("ficha X", "ROSA", 8.5f);          // 3 argumentos: intensidad normal

        System.out.println(42);      // println(int)
        System.out.println('X');     // println(char)
        System.out.println(2.5);     // println(double)
        System.out.println("hola");  // println(String)
    }

    /** Version corta: sin intensidad, usa 1 (como Dibujo.trazoNeon de 4 parametros). */
    static void trazoNeon(String figura, String color, float grosor) {
        trazoNeon(figura, color, grosor, 1f);
    }

    /** Version completa (como Dibujo.trazoNeon de 5 parametros). */

El propio println que llevas usando desde el capítulo 11 está sobrecargado: hay un println(int), un println(char), un println(double), un println(String)… Por eso imprime bien cualquier cosa que le des.

La sobrecarga se decide solo por los parámetros. Dos métodos que se diferencian únicamente en el tipo de retorno (int calcular() y double calcular()) no pueden convivir: en la llamada calcular() Java no sabría cuál elegir. Y no abuses: si dos métodos hacen cosas distintas, merecen nombres distintos. Sobrecarga solo variantes de la misma acción, como hace trazoNeon.

Métodos estáticos y métodos de instancia (introducción)

Habrás notado dos formas de llamar a los métodos en el Totito:

  • Tema.colorDeFicha('X'), Dibujo.trazoNeon(…), Math.max(3, tam * 0.085), Partida.buscarLineaGanadora(tablero): nombre de la clase, punto, método.
  • tablero.marcarCasilla(…), partida.jugar(…), jugador.getFicha(): un objeto concreto (una variable), punto, método.

Los primeros son métodos static (de clase): pertenecen a la clase como un todo y trabajan solo con lo que reciben por parámetro. Math.max no necesita «un Math concreto» para decirte cuál de dos números es mayor. Los segundos son métodos de instancia: pertenecen a cada objeto y trabajan con sus datos. tableroLleno() no tiene sentido sin decir qué tablero: el de la partida, o una de las miles de copias de la IA.

public class EstaticoVsInstancia {
    public static void main(String[] args) {
        // Metodo estatico: se llama con el nombre de la CLASE
        System.out.println("Color de la X: " + Colores.colorDeFicha('X'));
        System.out.println("Mayor de 3 y 8.5: " + Math.max(3, 8.5));

        // Metodo de instancia: se llama sobre un OBJETO concreto
        Contador ana = new Contador();
        Contador luis = new Contador();
        ana.sumar();
        ana.sumar();
        luis.sumar();
        System.out.println("Ana: " + ana.getVictorias() + ", Luis: " + luis.getVictorias());
    }
}

class Colores {
    static String colorDeFicha(char ficha) {
        return ficha == 'X' ? "rosa" : "azul";
    }
}

class Contador {
    private int victorias;

    void sumar() {
        victorias++;
    }

    int getVictorias() {
        return victorias;
    }
}

Eso es imposible con un método estático, que no tiene «su» objeto.

Por la misma razón, un método estático no puede usar directamente los campos de instancia:

«No puedo usar victorias desde un contexto estático»: ¿las victorias de quién? Es el error que verás si desde main intentas usar un campo de la clase sin crear antes un objeto. Por eso en este capítulo todos los métodos de ejemplo son static: los llamamos desde main, que es estático, sin fabricar objetos. En el Totito, Tema y Dibujo son clases de utilidades, todas estáticas, porque no guardan estado: son cajas de herramientas. Tablero, Partida y Jugador son de instancia, porque cada objeto tiene sus propios datos. El capítulo 18 explica los objetos y el 20 profundiza en static.

Recursión: un método que se llama a sí mismo

Un método puede llamar a cualquier método… incluido él mismo. A eso se le llama recursión. Parece un truco de magia, pero con lo que sabes de la pila de llamadas es perfectamente lógico: cada llamada crea su propio marco, con sus propios parámetros, así que una llamada a factorial(3) que hace dentro una llamada a factorial(2) no se pisa con ella.

El ejemplo clásico es el factorial: 4! (se lee «cuatro factorial») es 4 × 3 × 2 × 1 = 24. Observa que 4! = 4 × 3!, y 3! = 3 × 2!, y así hasta 1! = 1. Es decir, el problema se define en función de una versión más pequeña de sí mismo. Eso se traduce directamente:

public class Factorial {
    public static void main(String[] args) {
        System.out.println("Resultado: 4! = " + factorial(4, ""));
    }

    static long factorial(int n, String sangria) {
        System.out.println(sangria + "factorial(" + n + ") empieza");
        if (n <= 1) {                                    // caso base
            System.out.println(sangria + "factorial(" + n + ") devuelve 1");
            return 1;
        }
        long resultado = n * factorial(n - 1, sangria + "   ");   // caso recursivo
        System.out.println(sangria + "factorial(" + n + ") devuelve " + resultado);
        return resultado;
    }
}

      factorial(2) devuelve 2

El parámetro sangria solo sirve para dibujar la profundidad: cada nivel añade tres espacios. Lee la salida como la pila: las llamadas bajan (4, 3, 2, 1) apilando marcos, cada una en pausa en la línea de la multiplicación, esperando el resultado de la de abajo. Cuando factorial(1) devuelve 1 sin llamar a nadie, los marcos se van desapilando hacia arriba, y cada uno completa su multiplicación: 2 × 1 = 2, 3 × 2 = 6, 4 × 6 = 24.

Todo método recursivo necesita dos partes:

  1. Caso base: una situación tan simple que se responde sin volver a llamarse (n <= 1 → 1). Es el freno.
  2. Caso recursivo: se llama a sí mismo con un problema más pequeño, que acerque al caso base (n - 1).

Sin caso base, el método se llama a sí mismo sin fin, apilando marcos hasta llenar la memoria reservada para la pila:

static long factorial(int n) {
    return n * factorial(n - 1);   // falta el caso base
}

Desbordamiento de pila: es el bucle infinito de la recursión (y el que dio nombre al famoso sitio de preguntas de programadores). La traza muestra miles de líneas iguales: la pila llena de marcos de factorial.

Analogía: las muñecas rusas. Para contar cuántas muñecas hay, abres la primera: «una, más las que haya dentro». Para saber cuántas hay dentro, abres la siguiente con la misma regla. Cuando abres una que ya no se abre (el caso base), respondes «una» y vas cerrando hacia fuera, sumando. La recursión es eso: resolver un problema confiando en que la misma receta resolverá el problema de dentro, que es más pequeño.

Cómo usa la recursión el Totito: minimax

La IA del Totito tiene que responder a «¿cuánto vale esta jugada?». Y la respuesta es recursiva: una jugada vale lo que vale la mejor respuesta del rival a ella, que a su vez vale lo que vale mi mejor respuesta a esa respuesta… hasta llegar a un tablero donde la partida terminó (el caso base). Este es el esqueleto de IA_Minimax.minimax, sin los detalles que verás en el capítulo 31:

private int minimax(Tablero tablero, int profundidad, boolean esMax) {
    char ganador = tablero.verificarGanador();
    if (ganador == fichaIA) {               // caso base: gano la IA
        return 10 - profundidad;
    }
    if (ganador == fichaJugador) {          // caso base: gano el humano
        return profundidad - 10;
    }
    if (tablero.tableroLleno()) {           // caso base: empate
        return 0;
    }
    // caso recursivo: para cada casilla vacia, simular la jugada en una copia
    // y llamar a minimax(copia, profundidad + 1, !esMax) con el turno contrario
    ...
}

Las piezas son las mismas que en el factorial: tres casos base (alguien ganó o hubo empate: la partida terminó y se sabe su puntaje) y un caso recursivo que se llama con un problema más pequeño (un tablero con una casilla vacía menos; como solo hay nueve, la recursión siempre llega al fondo). Cada llamada recibe su propia copia del tablero y su propia profundidad, que vive en su marco; por eso pueden coexistir nueve niveles de «y si…» sin mezclarse.

¿Cuántas llamadas son? Este programa usa el Tablero real y un método recursivo con la misma estructura de minimax, pero que en lugar de puntuar cuenta todas las partidas posibles del totito. Necesita el Tablero ya compilado: guárdalo y ejecútalo cuando llegues al capítulo 29 (o léelo ahora y vuelve después):

public class ContarPartidas {
    static long llamadas = 0;

    public static void main(String[] args) {
        Tablero vacio = new Tablero();
        long partidas = contar(vacio, 'X');
        System.out.println("Partidas distintas posibles: " + partidas);
        System.out.println("Llamadas a contar(): " + llamadas);
    }

    /** Cuenta todas las partidas que pueden jugarse a partir de este tablero. */
    static long contar(Tablero tablero, char turno) {
        llamadas++;
        if (tablero.verificarGanador() != Tablero.VACIA || tablero.tableroLleno()) {
            return 1;                                   // caso base: la partida termino
        }
        long total = 0;
        char siguiente = turno == 'X' ? 'O' : 'X';
        for (int fila = 0; fila < 3; fila++) {
            for (int columna = 0; columna < 3; columna++) {
                if (tablero.obtenerCasilla(fila, columna) == Tablero.VACIA) {
                    Tablero copia = tablero.obtenerCopia();
                    copia.marcarCasilla(fila, columna, turno);
                    total += contar(copia, siguiente);  // caso recursivo
                }
            }
        }
        return total;
    }
}

Cuándo usar recursión. Cuando el problema contiene versiones más pequeñas de sí mismo: recorrer carpetas que contienen carpetas, árboles de decisiones de un juego, menús con submenús, fractales. Si el problema es una simple repetición (sumar una lista), un bucle es más claro y no arriesga desbordar la pila.

Buenas costumbres al escribir métodos

  • Nombre con verbo para acciones (marcarCasilla, reiniciar, calcularMejorJugada); forma de pregunta para los que devuelven boolean (esTurnoDeIA, esComputadora, tableroLleno); get… para los que solo devuelven un dato (getNombre, getFicha).
  • Una sola tarea por método. Si para describirlo necesitas «y», probablemente son dos. PantallaJuego separa alPulsarCasilla, despuesDeJugada, programarTurnoIA y actualizar.
  • Cortos: que quepan en la pantalla sin desplazarte. Ningún método de Tablero pasa de veinte líneas.
  • Pocos parámetros: más de 4 o 5 es señal de que quizás falte una clase que los agrupe (capítulo 21).
  • Javadoc encima de cada método público: qué hace, qué devuelve y en qué casos especiales (/** Retorna true si ya no quedan casillas vacias. */).

Resumen

  • Un método es un bloque de código con nombre que se ejecuta al llamarlo; sirve para no repetir, nombrar ideas, dividir problemas, probar por partes y ocultar detalles.
  • Su declaración tiene acceso, tipo de retorno, nombre, parámetros y cuerpo; la firma es el nombre más los tipos de los parámetros.
  • Los parámetros están en la declaración; los argumentos, en la llamada; se emparejan por posición y el compilador revisa cantidad y tipos.
  • return termina el método y entrega un valor del tipo declarado; todos los caminos deben devolver algo; los métodos void no devuelven nada y pueden salir con return;.
  • Cada llamada crea un marco en la pila de llamadas, con sus propios parámetros y variables; al terminar se desapila y se vuelve al punto exacto de la llamada. La traza de una excepción es una foto de esa pila.
  • Java pasa todo por valor: copias de los primitivos y copias de las referencias. Un método puede modificar el objeto recibido, pero no cambiar la variable de quien llamó; por eso la IA trabaja con obtenerCopia().
  • El alcance de una variable termina en la llave que cierra su bloque; this.campo distingue un campo de un parámetro con el mismo nombre.
  • Sobrecarga: mismo nombre, distintos parámetros (trazoNeon de 4 y de 5). Estáticos (Tema.colorDeFicha) frente a de instancia (tablero.tableroLleno()). Recursión: caso base + caso recursivo más pequeño; así piensa minimax.
