Capítulo 24Clases abstractas e interfaces

En este capítulo aprendes a escribir clases «a medias» que obligan a sus hijas a completarlas, y contratos que dicen qué debe saber hacer un objeto sin decir cómo. Son las dos herramientas que permiten que las pantallas del Totito no se conozcan entre sí y que puedas ver una pantalla suelta antes de que exista el resto del juego.

Dos problemas que todavía no sabes resolver

Con lo que viste en los capítulos 22 y 23 ya puedes hacer que una clase herede de otra y que Java llame al método correcto según el objeto real (eso era el polimorfismo). Pero quedan dos huecos:

  1. Clases que no deberían existir solas. En el Totito hay una clase PantallaBase que pinta el fondo y pone el encabezado, pero que no trae ningún botón ni ningún contenido. Una «pantalla base» sola sería una pantalla vacía. ¿Cómo le dices a Java «de esta clase se hereda, pero no se crean objetos»?
  2. Objetos que tienen que hablar sin conocerse. La pantalla del menú tiene un botón «Jugar» que debe llevar a la configuración. ¿Quién cambia de pantalla? Si el menú tuviera que conocer a la clase que guarda todas las pantallas, y esa clase a su vez conociera al menú, quedarían amarradas una con otra. ¿Cómo dices «necesito a alguien que sepa cambiar de pantalla, no me importa quién»?

La respuesta al primer problema es la clase abstracta. La respuesta al segundo es la interfaz. Las vemos en ese orden y al final las comparamos.

Clases abstractas

La idea: una categoría, no una cosa

Entra a una tienda de electrodomésticos y pide «un electrodoméstico». El vendedor te va a preguntar: «¿Cuál? ¿Una licuadora, una refrigeradora, una plancha?». La palabra electrodoméstico describe lo que todos tienen en común (se enchufan, tienen marca, consumen tantos watts), pero en la bodega no hay ninguna caja que diga solo «electrodoméstico». Es una categoría: sirve para agrupar y para describir lo común, no para fabricar.

Una clase abstracta es eso mismo en Java: una clase de la que no se pueden crear objetos con new, que existe para que otras hereden de ella. Puede tener campos, constructores y métodos completos (lo común), y además puede tener métodos abstractos: métodos que solo tienen nombre y parámetros, sin cuerpo, que cada hija está obligada a escribir. Es como un formulario con casillas en blanco: el formulario ya viene impreso, pero cada quien llena su parte.

Cómo se escribe

Un ejemplo pequeño, fuera del Totito: figuras geométricas. Toda figura tiene un nombre y sabe describirse, pero cada una calcula su área de forma distinta.

abstract class Figura {
    private final String nombre;

    protected Figura(String nombre) {
        this.nombre = nombre;
    }

    public abstract double area();

    public void describir() {
        System.out.printf("%s: area = %.2f%n", nombre, area());
    }
}

Pieza por pieza:

  • abstract class Figura: la palabra abstract delante de class dice «esta clase está incompleta a propósito: no se pueden hacer objetos de ella». Lo demás (class, el nombre, la llave {) es como en cualquier clase (capítulo 18).
  • private final String nombre;: un campo normal. Una clase abstracta sí puede guardar datos; las hijas los reciben, aunque al ser private solo los usa la propia Figura (capítulo 19).
  • protected Figura(String nombre): un constructor. «¿Para qué un constructor si no se pueden crear objetos?» Porque cuando creas un Circulo, el Circulo también es una Figura, y su parte de Figura hay que inicializarla: la hija lo llama con super(nombre) (capítulo 22). Se marca protected porque solo las hijas tienen motivo para llamarlo.
  • public abstract double area();: un método abstracto. Fíjate en tres cosas: lleva la palabra abstract, dice qué devuelve (double) y qué recibe (nada, por los paréntesis vacíos ()), y termina en punto y coma en vez de llaves. No hay cuerpo porque la figura genérica no sabe calcular su área; solo promete que toda figura concreta sabrá.
  • public void describir() { ... }: un método completo, con cuerpo. Fíjate que llama a area() aunque area() no tenga cuerpo aquí: cuando se ejecute, el objeto real será un Circulo o un Rectangulo, y por enlace dinámico (capítulo 23) se usará su versión de area().
Regla de las dos direcciones Si una clase tiene aunque sea un método abstracto, la clase tiene que declararse abstract. Pero al revés no: una clase puede ser abstract sin tener ningún método abstracto. El Totito usa justo este segundo caso, como verás enseguida.

Ahora el programa completo, con dos hijas concretas. Guárdalo como Figuras.java en tu carpeta de prácticas:

public class Figuras {
    public static void main(String[] args) {
        Figura[] figuras = {
            new Circulo("rueda", 1.0),
            new Rectangulo("puerta", 2.0, 0.9)
        };
        for (Figura f : figuras) {
            f.describir();
        }
    }
}

abstract class Figura {
    private final String nombre;

    protected Figura(String nombre) {
        this.nombre = nombre;
    }

    /** Cada figura sabe calcular su area, pero cada una a su manera. */
    public abstract double area();

    /** Metodo normal: es igual para todas las figuras. */
    public void describir() {
        System.out.printf("%s: area = %.2f%n", nombre, area());
    }
}

class Circulo extends Figura {
    private final double radio;

    Circulo(String nombre, double radio) {
        super(nombre);
        this.radio = radio;
    }

    @Override
    public double area() {
        return Math.PI * radio * radio;
    }
}

class Rectangulo extends Figura {
    private final double ancho;
    private final double alto;

    Rectangulo(String nombre, double ancho, double alto) {
        super(nombre);
        this.ancho = ancho;
        this.alto = alto;
    }

    @Override
    public double area() {
        return ancho * alto;
    }
}

El arreglo es de tipo Figura[], la clase abstracta. Eso sí se puede: lo que no se puede es crear un objeto Figura, pero una variable o un arreglo de tipo Figura puede guardar cualquier hija. El for llama a describir() sin saber qué figura tiene en la mano.

Lo que Java no te deja hacer (y por qué es bueno)

Prueba a agregar new Figura("misterio") dentro del arreglo. Java se niega antes de ejecutar nada:

Figuras.java:4: error: Figura is abstract; cannot be instantiated
            new Circulo("rueda", 1.0), new Figura("misterio"),
                                       ^
1 error
error: compilation failed

«Figura es abstracta; no se puede instanciar» (instanciar = crear un objeto, una instancia). Tiene todo el sentido: si existiera un objeto Figura a secas, ¿qué devolvería su area()? No tiene cuerpo.

El segundo error útil: una hija que se olvida de completar el formulario. Si escribes class Triangulo extends Figura { } sin método area():

Figuras2.java:11: error: Triangulo is not abstract and does not override abstract method area() in Figura
class Triangulo extends Figura {
^
1 error
error: compilation failed

«Triangulo no es abstracta y no sobrescribe el método abstracto area() de Figura». Tienes dos salidas: escribir el método (lo normal) o declarar Triangulo también como abstract, pasándole la tarea a sus hijas. Los mensajes del compilador salen en inglés aunque tu Windows esté en español; con el tiempo te los aprenderás de memoria.

El compilador como lista de pendientes Los métodos abstractos convierten un olvido (que en ejecución sería un error difícil de encontrar) en un error de compilación con el nombre exacto del método que falta. Cuando una clase tiene que «completar» algo sí o sí, hazlo abstracto y deja que Java te lo recuerde.

En el Totito: PantallaBase

Todas las pantallas del juego (menú, instrucciones, configuración, juego, resultado) comparten el mismo fondo morado con X y O gigantes, el mismo encabezado arriba y una columna central donde se apilan las cosas. Todo eso vive en src/PantallaBase.java, que construirás línea por línea en el capítulo 55:

public abstract class PantallaBase extends JPanel {

    private final JPanel contenido;

    protected PantallaBase(Navegacion navegacion) {
        super(new BorderLayout());
        add(new Encabezado(navegacion::salir), BorderLayout.NORTH);

        contenido = new JPanel();
        contenido.setOpaque(false);
        contenido.setLayout(new BoxLayout(contenido, BoxLayout.Y_AXIS));
        contenido.setBorder(BorderFactory.createEmptyBorder(0, 0, 10, 0));
        add(contenido, BorderLayout.CENTER);
    }

Lee la primera línea: public abstract class PantallaBase extends JPanel. Es pública, es abstracta y hereda de JPanel. Ahora busca en el archivo un método abstracto: no hay ninguno. Tiene métodos completos (agregar, espacio, relleno, fila, paintComponent) y ni uno solo termina en punto y coma sin cuerpo. Entonces, ¿por qué es abstracta?

Porque una PantallaBase sola no tiene sentido: sería un fondo con encabezado y una columna vacía en medio. La palabra abstract aquí no obliga a completar ningún método; documenta y hace cumplir una intención: «esta clase es para heredar de ella». Las cinco pantallas sí son concretas, por ejemplo src/PantallaMenu.java (capítulo 56):

public class PantallaMenu extends PantallaBase {

    public PantallaMenu(Navegacion navegacion) {
        super(navegacion);

La hija llama al constructor del padre con super(navegacion) y después, con agregar(...) y relleno(), pone sus botones en la columna.

¿Qué pasaría si no fuera abstracta?

Quizá pienses: «el constructor es protected, así que de todas formas nadie podría hacer new PantallaBase(...)». Cuidado: recuerda del capítulo 19 que protected deja pasar a las hijas y a todas las clases del mismo paquete. En el Totito todas las clases viven en el paquete por defecto (sin package), así que cualquier clase podría escribir new PantallaBase(navegacion) y obtener una pantalla vacía que nadie pidió. Con abstract, eso es un error de compilación en cualquier parte del programa. La protección no depende de dónde esté el archivo.

Aplícalo en otros sistemas

  • Banco: abstract class Cuenta con saldo, número y depositar() completos, y abstract double calcularInteres(); las hijas CuentaAhorro y CuentaMonetaria calculan cada una su interés. Nadie abre «una cuenta» genérica.
  • Planilla de una empresa: abstract class Empleado con nombre y DPI, y abstract double salarioDelMes(); EmpleadoFijo paga sueldo base, EmpleadoPorHora multiplica horas por tarifa.
  • Otro juego: abstract class Personaje con vida y posición, y abstract void atacar(Personaje otro); el guerrero, el mago y el arquero atacan distinto.

Interfaces

La idea: un contrato, como el tomacorriente

El tomacorriente de tu casa no sabe qué le vas a conectar. Puede ser una licuadora, el cargador del teléfono o una lámpara. No le importa: solo exige que lo que se conecte tenga la forma de enchufe correcta. Y a la licuadora tampoco le importa si la electricidad viene de la red, de una planta o de un panel solar. Los dos lados acordaron una forma común, y gracias a eso cualquiera de un lado funciona con cualquiera del otro.

Una interfaz en Java es esa forma común: una lista de métodos (nombre, parámetros y tipo de retorno) sin código. No guarda datos ni dice cómo se hace nada; solo dice «quien firme este contrato sabrá hacer estas cosas». Una clase «firma» el contrato con la palabra implements y queda obligada a escribir todos esos métodos.

Dos significados de «interfaz» En este libro también hablamos de la interfaz gráfica (las ventanas y botones que ve el jugador). No tiene nada que ver: aquí interface es una palabra de Java para un tipo de contrato entre clases. El contexto siempre deja claro cuál es cuál.

Cómo se escribe: Navegacion, completa

El archivo src/Navegacion.java del Totito (capítulo 39) es una interfaz pura. Aquí está entero:

/**
 * Lo que las pantallas pueden pedir: cambiar a otra pantalla, empezar una
 * partida o cerrar el juego. Lo implementa PanelPrincipal.
 *
 * Gracias a esta interfaz ninguna pantalla conoce a las demas: solo dicen
 * "quiero ir al menu" y PanelPrincipal se encarga.
 */
public interface Navegacion {

    void irAlMenu();

    void irAInstrucciones();

    void irAConfiguracion();

    /** Crea una partida nueva (marcador en cero) y muestra el tablero. */
    void iniciarPartida(Jugador jugador1, Jugador jugador2, Partida.Modo modo);

    /** Muestra la pantalla de victoria o empate de la partida terminada. */
    void mostrarResultado(Partida partida);

    /** Otra partida con los mismos jugadores, conservando el marcador. */
    void jugarDeNuevo();

    void salir();
}

Símbolo por símbolo:

  • public interface Navegacion: en lugar de class se escribe interface. El nombre sigue la misma regla que las clases (mayúscula inicial) y el archivo se llama igual, Navegacion.java.
  • void irAlMenu();: un método sin cuerpo, terminado en ;, igual que un método abstracto. En una interfaz no hace falta escribir public abstract: Java lo da por hecho. Todos los métodos sin cuerpo de una interfaz son automáticamente públicos y abstractos.
  • void iniciarPartida(Jugador jugador1, Jugador jugador2, Partida.Modo modo);: los métodos pueden recibir parámetros como cualquier otro. Partida.Modo es un enum que vive dentro de Partida (capítulo 26).
  • No hay campos, no hay constructor, no hay new. Una interfaz no se puede crear con new Navegacion() a secas, por la misma razón que una clase abstracta: sus métodos no tienen cuerpo.

Lee los nombres de los métodos en voz alta: «ir al menú», «ir a instrucciones», «iniciar partida», «salir». Son exactamente las cosas que una pantalla puede pedir. Ni una más. La interfaz es el menú de servicios.

Firmar el contrato: implements

Quien de verdad sabe cambiar de pantalla es PanelPrincipal (capítulo 61), que guarda las cinco pantallas en un CardLayout (un «mazo de cartas» que muestra una a la vez). Su primera línea y uno de sus métodos:

public class PanelPrincipal extends JPanel implements Navegacion {
    ...
    @Override
    public void irAlMenu() {
        cartas.show(this, MENU);
    }
  • extends JPanel: hereda de JPanel, porque es un panel que se mete en la ventana (capítulo 22).
  • implements Navegacion: además, firma el contrato Navegacion. Desde ese momento Java exige que PanelPrincipal tenga los siete métodos, con los mismos nombres, parámetros y tipos de retorno.
  • @Override: la misma anotación del capítulo 23. Aquí significa «este método cumple uno del contrato». Si te equivocas en el nombre (irAlMenú con tilde, por ejemplo), Java avisa.
  • public void irAlMenu(): tiene que ser public. Como los métodos de la interfaz son públicos, la clase no puede ofrecerlos «más cerrados»; si quitas el public, el compilador se queja de que intentas asignar privilegios de acceso más débiles.

Si a la clase le falta un método del contrato, el error es casi el mismo que con la clase abstracta. Por ejemplo, una clase Controlador implements Navegacion que solo escribe irAConfiguracion() y se olvida de salir():

Incompleta.java:12: error: Controlador is not abstract and does not override abstract method salir() in Navegacion
class Controlador implements Navegacion {
^
1 error
error: compilation failed

Del otro lado: quien usa la interfaz

Ahora mira cómo la usan las pantallas. El constructor de PantallaMenu:

    public PantallaMenu(Navegacion navegacion) {
        super(navegacion);

        BotonNeon jugar = BotonNeon.menu("Jugar", Iconos.JUGAR, Tema.ROSA);
        jugar.addActionListener(e -> navegacion.irAConfiguracion());
        BotonNeon instrucciones = BotonNeon.menu("Instrucciones", Iconos.LIBRO, Tema.AZUL);
        instrucciones.addActionListener(e -> navegacion.irAInstrucciones());
        BotonNeon salir = BotonNeon.menu("Salir", Iconos.SALIR, Tema.MORADO);
        salir.addActionListener(e -> navegacion.salir());

El parámetro es de tipo Navegacion, no PanelPrincipal. El menú no sabe que existe un PanelPrincipal, ni un CardLayout, ni cuántas pantallas hay. Solo sabe que le dieron «alguien que cumple Navegacion», y cuando se pulsa «Jugar» le dice navegacion.irAConfiguracion(). (Lo de e -> ... es una lambda; la explica el capítulo 25. Por ahora léelo como «cuando se pulse, haz esto».)

Y PanelPrincipal, al crear las pantallas, se pasa a sí mismo:

        add(new PantallaMenu(this), MENU);

this es el propio PanelPrincipal (capítulo 20). Como PanelPrincipal implementa Navegacion, es una Navegacion, y se puede pasar donde se pide una. Es la misma regla del capítulo 23 («una variable de tipo padre puede apuntar a un hijo»), pero con interfaces: una variable de tipo interfaz puede apuntar a cualquier objeto de una clase que la implemente.

Pruébalo en pequeño

Este programa reproduce la idea con tres piezas: la interfaz, un controlador que la implementa y una pantalla que solo conoce la interfaz. Al final aparece una segunda Navegacion «de mentira», que explicamos en la sección siguiente. Guárdalo como MiniNavegacion.java:

public class MiniNavegacion {
    public static void main(String[] args) {
        // 1) Con el "jefe" de verdad:
        Controlador jefe = new Controlador();
        PantallaMenu menu = new PantallaMenu(jefe);
        menu.pulsar("Jugar");
        menu.pulsar("Salir");

        // 2) Con una Navegacion "de mentira" (clase anonima), para probar la pantalla sola:
        Navegacion deMentira = new Navegacion() {
            @Override
            public void irAConfiguracion() {
                System.out.println("[prueba] la pantalla pidio ir a configuracion");
            }

            @Override
            public void salir() {
                System.out.println("[prueba] la pantalla pidio salir");
            }
        };
        PantallaMenu menuDePrueba = new PantallaMenu(deMentira);
        menuDePrueba.pulsar("Jugar");
        menuDePrueba.pulsar("Salir");
    }
}

/** Lo que una pantalla puede pedir. No dice COMO se hace. */
interface Navegacion {
    void irAConfiguracion();

    void salir();
}

/** Quien de verdad sabe cambiar de pantalla. */
class Controlador implements Navegacion {
    private String pantallaActual = "menu";

    @Override
    public void irAConfiguracion() {
        pantallaActual = "configuracion";
        System.out.println("Controlador: ahora se ve " + pantallaActual);
    }

    @Override
    public void salir() {
        System.out.println("Controlador: cerrando el juego (estaba en " + pantallaActual + ")");
    }
}

/** La pantalla solo conoce la INTERFAZ, no al Controlador. */
class PantallaMenu {
    private final Navegacion navegacion;

    PantallaMenu(Navegacion navegacion) {
        this.navegacion = navegacion;
    }

    void pulsar(String boton) {
        if (boton.equals("Jugar")) {
            navegacion.irAConfiguracion();
        } else if (boton.equals("Salir")) {
            navegacion.salir();
        }
    }
}

La clase PantallaMenu es la misma en los dos casos; no se cambió ni una letra. Lo que cambió fue el objeto que se le dio. Esa es toda la gracia de una interfaz.

¿Qué pasaría sin la interfaz?

Imagina que el constructor fuera public PantallaMenu(PanelPrincipal principal). Tres consecuencias:

  1. Dependencia circular. PanelPrincipal crea a PantallaMenu, y PantallaMenu necesita a PanelPrincipal. Cada una depende de la otra: no puedes entender, cambiar ni compilar una sin la otra.
  2. Demasiado poder. El menú tendría a mano todos los métodos públicos de PanelPrincipal (y de JPanel, que son cientos): podría cambiarle el tamaño, quitarle pantallas o leer la partida. Con la interfaz solo ve siete métodos, los que necesita.
  3. No se podría ver una pantalla suelta. En este libro construyes las pantallas en los capítulos 56 a 60 y PanelPrincipal recién en el 61. Si las pantallas exigieran un PanelPrincipal, no podrías verlas hasta el final. Gracias a la interfaz, en el capítulo 56 usarás la VistaPrevia con una Navegacion de mentira y verás el menú funcionando semanas antes.

La Navegacion de mentira de VistaPrevia

El archivo herramientas/VistaPrevia.java (capítulo 56) abre una pantalla sola en una ventana. Para crear la pantalla necesita una Navegacion, pero PanelPrincipal todavía no existe. La solución:

            // Una Navegacion "de mentira": cada metodo existe pero no hace nada.
            Navegacion sinNavegacion = new Navegacion() {
                @Override public void irAlMenu() { }
                @Override public void irAInstrucciones() { }
                @Override public void irAConfiguracion() { }
                @Override public void iniciarPartida(Jugador j1, Jugador j2, Partida.Modo modo) { }
                @Override public void mostrarResultado(Partida partida) { }
                @Override public void jugarDeNuevo() { }
                @Override public void salir() { System.exit(0); }
            };

            JPanel pantalla = new PantallaMenu(sinNavegacion);   // <-- AQUI

Parece que hace new Navegacion(), lo que acabamos de decir que no se puede. La diferencia está en la llave { que viene justo después de los paréntesis: eso es una clase anónima, una clase sin nombre que se declara y se usa en el mismo lugar. Se lee así: «crea un objeto de una clase nueva, sin nombre, que implementa Navegacion, y cuyos métodos son estos». Como trae los siete métodos con cuerpo (aunque el cuerpo sea { }, vacío), el contrato queda cumplido. El ; después de la llave de cierre } termina la sentencia de asignación, como en int x = 5;. El capítulo 25 explica las clases anónimas a fondo.

Fíjate en dos detalles. Primero, todos los métodos están vacíos excepto salir(), que cierra el programa: así la X del encabezado y el botón «Salir» funcionan en la vista previa, y el resto de botones simplemente no hacen nada. Segundo, la variable pantalla es de tipo JPanel, el abuelo de PantallaMenu: para meterla en la ventana no hace falta saber qué pantalla es (polimorfismo, capítulo 23).

Doble de prueba Un objeto que se hace pasar por el de verdad para poder probar otra pieza aislada se llama doble de prueba (en inglés test double; según lo que hace se le dice stub, fake o mock). Solo es posible cuando la pieza que pruebas depende de una interfaz y no de una clase concreta. Es la base de las pruebas automáticas que verás en el capítulo 69.

Otras dos interfaces del Totito

PanelTablero.OyenteCasilla: «avísame cuando hagan clic»

PanelTablero (capítulo 48) dibuja el tablero de neón, y se usa en tres lugares: la partida (donde se hace clic), la pantalla de victoria y el ejemplo de las instrucciones (donde no). El panel no decide qué hacer con un clic: solo avisa. Para eso declara, dentro de su propia clase, una interfaz de un solo método:

public class PanelTablero extends JComponent {

    /** Quien quiera enterarse de los clics implementa esta interfaz. */
    public interface OyenteCasilla {
        void casillaPulsada(int fila, int columna);
    }

Una interfaz puede declararse dentro de una clase; desde fuera se nombra PanelTablero.OyenteCasilla, con un punto, como una dirección: «la interfaz OyenteCasilla que está en PanelTablero». Se puso ahí porque solo tiene sentido junto al tablero. El panel guarda un campo private OyenteCasilla oyente; y, cuando detecta un clic válido, llama a oyente.casillaPulsada(filaEncima, columnaEncima). Quien sea el oyente, el panel no lo sabe. En la partida, el oyente es PantallaJuego, que se registra con tablero.setOyente(this::alPulsarCasilla); (esa forma de escribirlo, con ::, es una referencia a método: capítulo 25).

¿Qué pasaría sin la interfaz? PanelTablero tendría que conocer a PantallaJuego y a Partida, y ya no serviría para dibujar el tablero de muestra de las instrucciones ni el de la victoria sin arrastrar toda la lógica del juego. Este estilo de «yo aviso, tú decides» se llama patrón Observador, y el capítulo 27 lo pone en su contexto.

Iconos.Icono: «algo que sabe dibujarse»

En src/Iconos.java (capítulo 42):

    /** Un icono sabe dibujarse en el cuadrado (x, y, tam, tam) con el color dado. */
    @FunctionalInterface
    public interface Icono {
        void dibujar(Graphics2D g, double x, double y, double tam, Color color);
    }

Cada icono del juego (el triángulo de «Jugar», el libro, la puerta de «Salir», la casa, el trofeo) es un objeto que cumple este contrato. BotonNeon guarda un campo private final Iconos.Icono icono; y al pintarse llama a icono.dibujar(...), sin saber si está dibujando un libro o una casa. Para tener un botón con otro dibujo no hay que tocar BotonNeon: basta con darle otro icono. La anotación @FunctionalInterface y la forma en que se escriben los iconos (con lambdas) son tema del capítulo 25.

Programar contra interfaces

Hay un consejo que vas a leer en cualquier libro de diseño: «programa contra interfaces, no contra implementaciones». Quiere decir: cuando declares un parámetro, un campo o una variable, usa el tipo más general que te alcance (la interfaz), no la clase concreta. Así quien te use puede darte cualquier cosa que cumpla el contrato.

Ya lo hiciste sin darte cuenta si escribiste algo como:

List<String> nombres = new ArrayList<>();

List es una interfaz del JDK (la biblioteca que viene con Java) y ArrayList una de sus implementaciones. Si mañana necesitas una LinkedList, cambias solo lo que va después del new; todo el resto del código, que solo conoce List, sigue igual.

El contrato queda en medio, y los dos lados dependen de él, no el uno del otro. A esto se le llama desacoplar: separar dos piezas para que una pueda cambiar (o reemplazarse) sin tocar la otra. El capítulo 27 vuelve sobre el acoplamiento como principio de diseño.

Una clase, varias interfaces; métodos default y static

Varias interfaces a la vez

Una clase solo puede heredar de una clase (extends lleva un solo nombre, capítulo 22), pero puede implementar todas las interfaces que quiera, separadas por comas: class X extends Y implements A, B, C. ¿Por qué esa diferencia? Porque si heredaras de dos clases que tienen un método con el mismo nombre y distinto código, Java no sabría cuál usar. Las interfaces, en cambio, solo prometen: si dos interfaces piden el mismo método, la clase escribe uno y cumple con las dos.

Por eso PanelPrincipal puede ser a la vez un JPanel (hereda) y una Navegacion (implementa). Si Navegacion hubiera sido una clase abstracta en vez de una interfaz, PanelPrincipal habría tenido que elegir entre ser un panel o ser una navegación.

Métodos default y static

Desde Java 8 una interfaz puede traer dos clases de métodos con cuerpo:

  • default: un método ya hecho que todas las clases que implementan la interfaz reciben gratis, y que pueden sobrescribir si quieren. Sirve para agregar comportamiento a un contrato sin romper a quienes ya lo cumplían.
  • static: un método que pertenece a la interfaz misma, no a cada objeto, y se llama con el nombre de la interfaz: Notificador.largoMaximo() (como los static de clases del capítulo 20).

El Totito no los necesita, pero aparecen mucho en el JDK. Este ejemplo de avisos de una escuela junta todo: una interfaz con un método default y uno static, tres clases que la cumplen y una que además implementa una segunda interfaz. Guárdalo como Avisos.java:

import java.util.ArrayList;
import java.util.List;

public class Avisos {
    public static void main(String[] args) {
        List<Notificador> canales = new ArrayList<>();
        canales.add(new Correo("ana@escuela.edu"));
        canales.add(new Sms("5555-1234"));
        canales.add(new CorreoYRegistro("direccion@escuela.edu"));

        for (Notificador canal : canales) {
            canal.enviar("Mañana no hay clases");
            canal.enviarUrgente("Se suspendió el examen");
        }
        System.out.println("Largo máximo de un aviso: " + Notificador.largoMaximo());
    }
}

interface Notificador {
    void enviar(String mensaje);

    /** Metodo default: todas las clases lo reciben ya hecho (pueden cambiarlo). */
    default void enviarUrgente(String mensaje) {
        enviar("URGENTE: " + mensaje);
    }

    /** Metodo static: pertenece a la interfaz, no a cada objeto. */
    static int largoMaximo() {
        return 160;
    }
}

interface Registrable {
    String registro();
}

class Correo implements Notificador {
    private final String direccion;

    Correo(String direccion) {
        this.direccion = direccion;
    }

    @Override
    public void enviar(String mensaje) {
        System.out.println("Correo a " + direccion + ": " + mensaje);
    }
}

class Sms implements Notificador {
    private final String telefono;

    Sms(String telefono) {
        this.telefono = telefono;
    }

    @Override
    public void enviar(String mensaje) {
        System.out.println("SMS a " + telefono + ": " + mensaje);
    }

    @Override
    public void enviarUrgente(String mensaje) {
        enviar("!!! " + mensaje.toUpperCase() + " !!!");
    }
}

/** Una clase puede implementar VARIAS interfaces a la vez. */
class CorreoYRegistro extends Correo implements Registrable {
    private int enviados;

    CorreoYRegistro(String direccion) {
        super(direccion);
    }

    @Override
    public void enviar(String mensaje) {
        super.enviar(mensaje);
        enviados++;
        System.out.println("   (" + registro() + ")");
    }

    @Override
    public String registro() {
        return "avisos enviados: " + enviados;
    }
}

Sigue el recorrido: Correo no escribió enviarUrgente, así que usa el default, que antepone «URGENTE:» y llama a su enviar. Sms lo sobrescribió con signos de exclamación y mayúsculas. CorreoYRegistro hereda de Correo, implementa además Registrable y cuenta los envíos; como su enviar se llama también desde el default, el urgente también se cuenta (por eso el segundo dice 2). El ciclo for no sabe nada de esto: solo ve Notificador.

Fíjate en Runnable en PanelPrincipal: el panel no sabe cómo se cierra el juego (eso depende de la ventana), así que pide «una acción para cuando haya que salir». TotitoApp le pasa su método cerrar. Es la misma idea de Navegacion en miniatura.

Un ejemplo con Comparable: una tabla de posiciones que se ordena sola porque cada puntaje sabe compararse con otro. Guárdalo como Ranking.java:

import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

public class Ranking {
    public static void main(String[] args) {
        List<Puntaje> tabla = new ArrayList<>();
        tabla.add(new Puntaje("Ana", 7));
        tabla.add(new Puntaje("Luis", 12));
        tabla.add(new Puntaje("Sofía", 9));

        Collections.sort(tabla);   // funciona porque Puntaje implementa Comparable
        for (Puntaje p : tabla) {
            System.out.println(p.nombre() + " -> " + p.victorias());
        }
    }
}

class Puntaje implements Comparable<Puntaje> {
    private final String nombre;
    private final int victorias;

    Puntaje(String nombre, int victorias) {
        this.nombre = nombre;
        this.victorias = victorias;
    }

    String nombre() {
        return nombre;
    }

    int victorias() {
        return victorias;
    }

    /** Negativo: yo voy antes; positivo: voy despues; cero: empate. */
    @Override
    public int compareTo(Puntaje otro) {
        return Integer.compare(otro.victorias, this.victorias);   // de mayor a menor
    }
}
java Ranking.java
Luis -> 12
Sofía -> 9
Ana -> 7

Collections.sort fue escrito hace muchos años por gente que nunca oyó hablar de tu clase Puntaje. Aun así la ordena, porque solo le pide una cosa: que cumpla Comparable. Lo de <Puntaje> entre ángulos indica con qué tipo se compara (se llaman «genéricos»; aquí basta con leerlo como «comparable con otro Puntaje»). Integer.compare(a, b) devuelve negativo si a < b, cero si son iguales y positivo si a > b; al poner primero otro se invierte el orden y queda de mayor a menor.

¿Interfaz o clase abstracta?

Las dos tienen métodos sin cuerpo y ninguna se puede crear con new. Entonces, ¿cuál usar? Esta tabla resume las diferencias:

La regla práctica:

  • Si lo que quieres compartir es código y datos entre clases muy parecidas (todas las pantallas pintan el mismo fondo y tienen la misma columna), usa una clase abstracta. PantallaBase no podría ser una interfaz: necesita el campo contenido, un constructor que arme el encabezado y un paintComponent completo.
  • Si lo que quieres es un contrato entre piezas que no se parecen (un panel de Swing y una clase anónima de prueba), usa una interfaz. Navegacion no debería ser una clase abstracta: PanelPrincipal ya hereda de JPanel y no podría heredar de nada más.
  • Si dudas, empieza por una interfaz. Es lo más flexible y lo que menos amarra a quien la implementa.
No crees interfaces «por si acaso» Una interfaz que solo tiene una implementación y nunca tendrá otra (ni siquiera un doble de prueba) agrega un archivo más sin ganar nada. En el Totito hay una interfaz por cada lugar donde de verdad hay, o puede haber, más de un «enchufado»: Navegacion tiene dos (el panel real y el de mentira), Icono tiene trece, OyenteCasilla existe para que el tablero sirva en tres pantallas.

Resumen

  • Una clase abstracta (abstract class) no se puede crear con new; existe para que otras hereden. Puede tener campos, constructores y métodos completos.
  • Un método abstracto no tiene cuerpo (termina en ;) y obliga a cada hija concreta a escribirlo; si no, el compilador da error.
  • PantallaBase es abstracta sin métodos abstractos: la palabra abstract impide crear una pantalla vacía, cosa que protected solo no lograría en el paquete por defecto.
  • Una interfaz (interface) es un contrato: lista de métodos públicos sin código. Una clase lo firma con implements y debe escribirlos todos.
  • Navegacion desacopla las pantallas de PanelPrincipal: cada pantalla solo pide servicios, y por eso puede probarse con una Navegacion de mentira (la clase anónima de VistaPrevia).
  • OyenteCasilla e Icono son interfaces de un solo método: «avísame» y «sé dibujarte».
  • Una clase hereda de una sola clase pero puede implementar muchas interfaces; las interfaces pueden traer métodos default y static.
  • Programa contra interfaces: declara parámetros y variables con el tipo más general que te sirva (List, Navegacion).
