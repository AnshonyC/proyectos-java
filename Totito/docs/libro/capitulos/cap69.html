Terminaste el Totito y sabes llevar sus ideas a otros programas. Este capítulo es el mapa de lo que viene: organizar el código en paquetes, probarlo automáticamente con JUnit, conocer JavaFX, guardar datos en una base de datos, hacer aplicaciones web y móviles, y una forma de seguir aprendiendo por tu cuenta.

Cada sección es una puerta, no una habitación entera: verás qué es cada cosa, por qué existe y un ejemplo mínimo que funciona. Lo que hay de práctica (paquetes y JUnit) se hizo sobre una copia del Totito; haz tú lo mismo, en una rama, para no tocar la versión publicada.

1. Paquetes: carpetas con nombre para tus clases

Qué son

Un paquete es un grupo de clases con un nombre, que en el disco corresponde a una carpeta. Ya los usaste sin crearlos: javax.swing es el paquete donde vive JButton, java.awt el de Color, y java.util el de Arrays. Por eso los import del capítulo 11 llevan esos prefijos: import javax.swing.JButton; quiere decir «la clase JButton del paquete javax.swing».

Los paquetes sirven para tres cosas:

  • Ordenar. Con 29 clases en una sola carpeta el Totito todavía se entiende; con 300 no. Los paquetes son las carpetas de un archivero.
  • Evitar choques de nombres. Tu Tablero y el Tablero de una librería ajena pueden convivir si están en paquetes distintos.
  • Controlar la visibilidad. Un miembro sin modificador (ni public, ni private, ni protected) es visible solo dentro de su paquete. Es el nivel «de paquete» que se mencionó en el inventario del capítulo 68.

Por convención, el nombre se escribe en minúsculas y empieza por un dominio al revés, para que sea único en el mundo: com.github.tuusuario.totito. Si no tienes dominio, tu usuario de GitHub cumple la misma función.

Por qué el Totito no los usa

Todas las clases del Totito están en el paquete por defecto: el que no tiene nombre, el <default package> que ves en NetBeans. Se eligió así a propósito, por tres razones: el proyecto original venía así, cada archivo empieza directamente con sus import (una línea menos que explicar al principiante) y todos los comandos son cortos (java -cp out TotitoApp).

Pero tiene un límite serio: las clases del paquete por defecto no se pueden importar desde una clase que sí tenga paquete. No existe una forma de escribir import Tablero;. Mientras todo esté en el paquete por defecto no se nota; el día que quieras usar Tablero desde otro proyecto organizado en paquetes —por ejemplo, la aplicación web de la sección 5—, no podrás. Por eso, en cuanto un proyecto crece o se comparte, se organiza en paquetes.

Cómo migrar el Totito a paquetes

Una división natural sigue la separación que ya tiene el código: la lógica por un lado y la interfaz por otro.

src\
  totito\
    logica\      Tablero, Jugador, IA_Minimax, Partida
    interfaz\    las otras 25 clases (Tema, BotonNeon, PantallaMenu, TotitoApp...)

Los pasos, en una rama nueva:

git switch -c paquetes
  1. Crea los paquetes. En NetBeans: clic derecho en Source Packages → New → Java Package… → escribe totito.logica → Finish. Repite con totito.interfaz. NetBeans crea las carpetas src\totito\logica y src\totito\interfaz.
  2. Mueve las clases. Arrastra Tablero.java, Jugador.java, IA_Minimax.java y Partida.java sobre totito.logica, y el resto sobre totito.interfaz. NetBeans abre el diálogo Move Class; acepta con Refactor. Esa herramienta hace los dos cambios siguientes por ti.
  3. La línea package. Cada archivo debe empezar declarando su paquete, antes de cualquier import: 
    package totito.logica;

/**
  4. Los import entre paquetes. Las clases de interfaz que usan a las de logica necesitan importarlas. Así empieza PantallaJuego.java después de migrar: 
    package totito.interfaz;

import totito.logica.Jugador;
import totito.logica.Partida;

import java.awt.Color;
import javax.swing.Timer;
    Con import totito.logica.Partida;, también Partida.Modo y Partida.Estado quedan disponibles.
  5. El nombre completo de la clase principal cambia de TotitoApp a totito.interfaz.TotitoApp. Hay que corregirlo en el pom.xml (en exec.mainClass y en mainClass), en el comando para ejecutar sin NetBeans y en el --main-class de jpackage: 
    javac -encoding UTF-8 -d out (Get-ChildItem -Path src -Recurse -Filter *.java).FullName
java -cp out totito.interfaz.TotitoApp
    El comodín src\*.java ya no alcanza, porque los archivos están en subcarpetas. Get-ChildItem -Path src -Recurse -Filter *.java busca los .java en src y en todas sus subcarpetas, y .FullName entrega la ruta completa de cada uno; los paréntesis hacen que PowerShell resuelva esa lista antes de pasársela a javac.
  6. Las herramientas. VistaPrevia, PruebaConsola y GeneradorIcono siguen en el paquete por defecto; como ahora tienen que importar las clases del juego, agrégales al principio import totito.logica.*; e import totito.interfaz.*; según lo que usen.

Se hizo esta migración en una copia: con solo agregar las líneas package e import compiló sin ningún otro cambio, porque todas las clases y los métodos que se usan entre paquetes ya eran public. El .jar quedó con Main-Class: totito.interfaz.TotitoApp en su manifiesto y jdeps siguió respondiendo java.base,java.desktop.

Una prueba de buen diseño En la copia migrada, ninguna clase de totito.logica importa nada de totito.interfaz. La flecha va en un solo sentido: la interfaz conoce la lógica y la lógica no conoce la interfaz. Si algún día escribes un import totito.interfaz... dentro de logica, el paquete te avisa de que estás mezclando responsabilidades (capítulo 27).
Git Haz el commit en la rama y, si te gusta el resultado, ábrelo como Pull Request, igual que la interfaz neón en el capítulo 61: 
git add -A
git commit -m "Organizar el codigo en los paquetes totito.logica y totito.interfaz"
git push -u origin paquetes
gh pr create --base main --head paquetes --title "Paquetes" --body "Mueve las clases a totito.logica y totito.interfaz"
git add -A registra también los archivos que «desaparecieron» de src\ al moverse; Git detecta que son los mismos y los muestra como renombrados.

2. Pruebas automáticas con JUnit 5

Por qué

En el capítulo 62 hiciste una lista de pruebas manuales: abrir el juego, hacer tres en línea, comprobar el empate… Funciona, pero hay que repetirla cada vez que cambias algo, y nadie lo hace. Una prueba automática es un método que prepara una situación, ejecuta el código y comprueba el resultado, sin que tú mires nada. Cientos de ellas corren en un par de segundos. Si un cambio rompe una regla que antes funcionaba (una regresión), te enteras en el momento, no cuando un usuario se queja.

JUnit es la librería de pruebas más usada en Java. Su versión 5 se llama también JUnit Jupiter. (Existe ya JUnit 6, que se usa de la misma forma; aquí se usa la 5 porque es la que vas a encontrar en casi todos los proyectos y tutoriales.)

Gracias a que Partida no sabe nada de Swing, se puede probar sin abrir una sola ventana. Esa decisión del capítulo 38 se paga aquí.

Paso 1: el pom.xml

Hay que agregar tres cosas al pom.xml del Totito: la dependencia de JUnit, la carpeta de las pruebas y el plugin que las ejecuta. Este es el pom.xml completo con los cambios:

<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 http://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>
    <groupId>com.mycompany</groupId>
    <artifactId>Totito</artifactId>
    <version>1.0-SNAPSHOT</version>
    <packaging>jar</packaging>
    <properties>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
        <!-- Funciona con JDK 17 o mas nuevo. -->
        <maven.compiler.release>17</maven.compiler.release>
        <!-- Clase que arranca el juego (boton Run de NetBeans). -->
        <exec.mainClass>TotitoApp</exec.mainClass>
    </properties>
    <dependencies>
        <!-- JUnit 5: solo para las pruebas, no viaja dentro del .jar. -->
        <dependency>
            <groupId>org.junit.jupiter</groupId>
            <artifactId>junit-jupiter</artifactId>
            <version>5.14.4</version>
            <scope>test</scope>
        </dependency>
    </dependencies>
    <build>
        <!-- El codigo vive en src/ (sin paquetes), no en src/main/java. -->
        <sourceDirectory>src</sourceDirectory>
        <!-- Las pruebas viven en test/, fuera de src/. -->
        <testSourceDirectory>test</testSourceDirectory>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.13.0</version>
            </plugin>
            <plugin>
                <!-- Ejecuta las pruebas en mvn test y mvn package. -->
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-surefire-plugin</artifactId>
                <version>3.5.6</version>
            </plugin>
            <plugin>
                <!-- Deja el .jar ejecutable con doble clic o con java -jar. -->
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-jar-plugin</artifactId>
                <version>3.4.2</version>
                <configuration>
                    <archive>
                        <manifest>
                            <mainClass>TotitoApp</mainClass>
                        </manifest>
                    </archive>
                </configuration>
            </plugin>
        </plugins>
    </build>
</project>
  • <dependencies> es la lista de librerías ajenas que usa el proyecto. Maven las descarga solo la primera vez (necesitas internet) y las guarda en C:\Users\<tu-usuario>\.m2.
  • Una dependencia se identifica con tres datos: groupId (quién la publica), artifactId (qué es) y version. Son las «coordenadas» que buscarías en search.maven.org.
  • <scope>test</scope>: JUnit solo existe para las pruebas. No se puede usar desde src\ y no viaja dentro del .jar (se comprobó: el .jar no contiene nada de JUnit).
  • <testSourceDirectory>test</testSourceDirectory>: las pruebas van en una carpeta test\ al lado de src\. Hay que decirlo porque el Totito usa una estructura propia (capítulo 5).
  • maven-surefire-plugin es el plugin que encuentra y ejecuta las pruebas. Se fija su versión, como se hizo con los otros dos, para que el resultado no dependa de la versión de Maven.
No pongas las pruebas dentro de src En los proyectos Maven «normales» las pruebas van en src\test\java. En el Totito no, porque src\ entero es código del programa: todo lo que haya dentro se compila como parte del juego, donde JUnit no está disponible. Se probó, y Maven se detiene con package org.junit.jupiter.api does not exist. Por eso la carpeta es test\, fuera de src\.

Paso 2: la clase de pruebas

Crea la carpeta y el archivo desde la carpeta del proyecto:

New-Item -ItemType Directory -Force test | Out-Null
New-Item test\PartidaTest.java

Al recargar el proyecto, NetBeans muestra un nodo nuevo, Test Packages, con PartidaTest.java dentro. Escribe esto:

import static org.junit.jupiter.api.Assertions.assertArrayEquals;
import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertFalse;
import static org.junit.jupiter.api.Assertions.assertNull;
import static org.junit.jupiter.api.Assertions.assertSame;
import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.junit.jupiter.api.Assertions.assertTrue;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;

/**
 * Pruebas automaticas de las reglas del Totito (clase Partida).
 * Ninguna abre ventanas: solo usan la logica.
 */
class PartidaTest {

    private Jugador ana;
    private Jugador beto;
    private Partida partida;

    /** Se ejecuta antes de CADA prueba: todas empiezan de cero. */
    @BeforeEach
    void prepararPartida() {
        ana = new Jugador("Ana", 'X');
        beto = new Jugador("Beto", 'O');
        partida = new Partida(ana, beto, Partida.Modo.DOS_JUGADORES);
    }

    /** Ayudante (no es prueba): Ana completa la fila 0. */
    private void anaGanaEnLaPrimeraFila() {
        partida.jugar(0, 0);   // Ana  X
        partida.jugar(1, 0);   // Beto O
        partida.jugar(0, 1);   // Ana  X
        partida.jugar(1, 1);   // Beto O
        partida.jugar(0, 2);   // Ana  X: tres en la fila 0
    }

    @Test
    void tresEnLaPrimeraFilaEsVictoria() {
        anaGanaEnLaPrimeraFila();

        assertEquals(Partida.Estado.VICTORIA, partida.getEstado());
        assertSame(ana, partida.getGanador());
        assertEquals(1, partida.getVictorias(0));
        assertEquals(0, partida.getVictorias(1));
        assertArrayEquals(new int[]{0, 0, 0, 2}, Partida.buscarLineaGanadora(partida.getTablero()));
    }

    @Test
    void tableroLlenoSinLineaEsEmpate() {
        //  X | O | X
        //  X | O | O
        //  O | X | X
        int[][] jugadas = {{0, 0}, {0, 1}, {0, 2}, {1, 1}, {1, 0}, {1, 2}, {2, 1}, {2, 0}, {2, 2}};
        for (int[] j : jugadas) {
            assertTrue(partida.jugar(j[0], j[1]));
        }

        assertEquals(Partida.Estado.EMPATE, partida.getEstado());
        assertNull(partida.getGanador());
        assertEquals(1, partida.getEmpates());
    }

    @Test
    void casillaOcupadaNoSeAceptaYNoCambiaElTurno() {
        assertTrue(partida.jugar(1, 1));          // Ana pone X en el centro
        assertFalse(partida.jugar(1, 1));         // Beto intenta la misma casilla

        assertSame(beto, partida.getJugadorEnTurno());
        assertEquals('X', partida.getTablero().obtenerCasilla(1, 1));
    }

    @Test
    void despuesDeGanarNoSePuedeSeguirJugando() {
        anaGanaEnLaPrimeraFila();
        assertFalse(partida.jugar(2, 2));
    }

    @Test
    void reiniciarLimpiaElTableroPeroConservaElMarcador() {
        anaGanaEnLaPrimeraFila();
        partida.reiniciar();

        assertEquals(Partida.Estado.EN_CURSO, partida.getEstado());
        assertEquals(Tablero.VACIA, partida.getTablero().obtenerCasilla(0, 0));
        assertEquals(1, partida.getVictorias(0));
    }

    @Test
    void dosJugadoresConLaMismaFichaEsUnError() {
        Jugador otraX = new Jugador("Carla", 'X');
        assertThrows(IllegalArgumentException.class,
                () -> new Partida(ana, otraX, Partida.Modo.DOS_JUGADORES));
    }

    @Test
    void laComputadoraTapaLaFilaQueIbaAGanarAna() {
        Partida contraIA = new Partida(ana, new Jugador("Computadora", 'O'), Partida.Modo.CONTRA_IA);
        contraIA.jugar(0, 0);          // Ana  X en una esquina
        contraIA.jugarTurnoIA();       // la computadora responde
        contraIA.jugar(0, 1);          // Ana amenaza: X X _ en la fila 0
        contraIA.jugarTurnoIA();

        assertEquals('O', contraIA.getTablero().obtenerCasilla(0, 2));
    }
}

Lo nuevo, de arriba abajo:

  • import static …Assertions.assertEquals; El import static trae un método estático en lugar de una clase. Gracias a él se escribe assertEquals(…) en vez de Assertions.assertEquals(…).
  • class PartidaTest no lleva public: JUnit 5 no lo necesita. El nombre termina en Test porque así lo busca Surefire.
  • @BeforeEach es una anotación (como @Override, capítulo 23): le dice a JUnit «ejecuta este método antes de cada prueba». Así cada prueba recibe una Partida recién creada y ninguna depende de lo que hizo otra. Es una regla de oro: las pruebas deben poder ejecutarse en cualquier orden.
  • @Test marca un método como prueba. JUnit los encuentra y los ejecuta todos. Los nombres son frases largas a propósito: cuando una falla, el nombre ya te dice qué regla se rompió.
  • anaGanaEnLaPrimeraFila() no lleva @Test: es un ayudante que reúne jugadas que se repiten en varias pruebas.
  • Cada prueba sigue tres pasos, conocidos como Preparar, Actuar, Comprobar: crear la situación (lo hace @BeforeEach), hacer las jugadas y verificar el resultado.
  • Las aserciones son las comprobaciones. Si una no se cumple, la prueba falla:
    AserciónComprueba que…
    assertEquals(esperado, real)los dos valores son iguales. Primero va lo que esperas y después lo que dio el programa; al revés, los mensajes de error confunden.
    assertTrue(x) / assertFalse(x)la condición es verdadera / falsa.
    assertSame(a, b)son el mismo objeto (la misma referencia, capítulo 18), no solo parecidos.
    assertNull(x)el valor es null.
    assertArrayEquals(a, b)dos arreglos tienen los mismos elementos en el mismo orden. (assertEquals con arreglos compararía referencias.)
    assertThrows(Tipo.class, () -> …)el código de la lambda lanza esa excepción. Si no la lanza, la prueba falla.
  • La prueba de la casilla ocupada comprueba dos cosas que el usuario nunca vería a simple vista: que jugar devuelve false y que el turno no pasó a Beto «por error».
  • La prueba de la IA usa el modo CONTRA_IA: Ana amenaza con dos X en la fila 0 y se comprueba que la computadora tapa la casilla (0, 2). No hace falta conocer la primera respuesta de la IA para escribir la prueba.

3. JavaFX frente a Swing

Swing (1998) es la biblioteca gráfica que viene dentro del JDK, y la que usaste en todo el libro. JavaFX es su sucesora moderna. Desde Java 11 ya no viene incluida: es un proyecto aparte, OpenJFX, que se agrega como dependencia de Maven.

SwingJavaFX
InstalaciónViene en el JDKDependencia aparte (org.openjfx:javafx-controls)
EstiloA mano, con paintComponent (como el neón del Totito)Con CSS, el mismo lenguaje de estilos de las páginas web
Diseño de pantallasEn código (layouts)En código o en archivos FXML, que se dibujan con Scene Builder
Efectos y animacionesSe programan (Timer, capas de transparencia)Incluidos: sombras, desenfoque, transiciones
EstadoEstable y mantenido, sin novedades grandesSe sigue desarrollando, con versiones nuevas cada seis meses
Cuándo elegirloProgramas sencillos, mantener código existente, cero dependenciasProgramas de escritorio nuevos con mucho trabajo visual

Para que te hagas una idea, este es un botón «neón» en JavaFX. El halo, que en el Totito son seis trazos en Dibujo.trazoNeon, aquí es una línea de CSS: dropshadow. El ejemplo se compiló con javafx-controls 21.0.12 (la versión que acompaña al JDK 21):

import javafx.application.Application;
import javafx.scene.Scene;
import javafx.scene.control.Button;
import javafx.scene.layout.StackPane;
import javafx.stage.Stage;

/** Un boton neon en JavaFX: el estilo va en CSS, no en paintComponent. */
public class HolaFX extends Application {

    @Override
    public void start(Stage ventana) {
        Button jugar = new Button("Jugar");
        jugar.setStyle("-fx-background-color: #1C1740; -fx-text-fill: white;"
                + " -fx-font-size: 22px; -fx-background-radius: 30;"
                + " -fx-border-color: #FF3BD4; -fx-border-radius: 30; -fx-border-width: 2;"
                + " -fx-effect: dropshadow(gaussian, #FF3BD4, 18, 0.3, 0, 0);");
        jugar.setOnAction(e -> System.out.println("¡A jugar!"));

        StackPane raiz = new StackPane(jugar);
        raiz.setStyle("-fx-background-color: linear-gradient(to bottom, #1C1740, #0E0B24);");

        ventana.setTitle("Hola, JavaFX");
        ventana.setScene(new Scene(raiz, 400, 300));
        ventana.show();
    }

    public static void main(String[] args) {
        launch(args);
    }
}

Las ideas son las mismas, con otros nombres: la ventana es un Stage (escenario), su contenido una Scene (escena), los paneles con layout son StackPane, VBox, GridPane, y setOnAction reemplaza a addActionListener. Lo que aprendiste de color, tipografía, jerarquía y separación entre lógica e interfaz se traslada entero: Partida funcionaría sin cambiar una línea detrás de una interfaz JavaFX.

Ejecutar JavaFX Un programa JavaFX no se ejecuta con un simple java -cp: necesita que los módulos de JavaFX estén en el module path. Lo más sencillo es crear el proyecto en NetBeans con File → New Project → Java with Maven → JavaFX Application, que configura el plugin javafx-maven-plugin por ti. Para empaquetarlo, jpackage funciona igual que en el capítulo 65.

4. Bases de datos con JDBC

La idea

El gestor de tareas del capítulo 68 guarda en un archivo de texto. Funciona mientras los datos sean pocos y los use una sola persona. Cuando son miles de productos, se buscan de muchas formas o los usan varias cajas a la vez, se usa una base de datos: un programa especializado en guardar datos en tablas (filas y columnas, como una hoja de cálculo), buscarlos rápido y no perderlos aunque se vaya la luz. Se le habla en SQL, un lenguaje propio: SELECT nombre FROM producto WHERE existencias <= 10.

JDBC (Java Database Connectivity) es la parte de Java que habla con las bases de datos. Viene en el JDK (paquete java.sql) y funciona igual con todas; lo único que cambia es el driver, una librería que traduce para cada base concreta (MySQL, PostgreSQL, SQLite…). Las piezas son cuatro:

PiezaQué es
ConnectionLa conexión abierta con la base. Se obtiene con DriverManager.getConnection(url).
PreparedStatementUna orden SQL con huecos ? que se rellenan con setString, setInt…
ResultSetLas filas que devuelve un SELECT. Se recorren con while (filas.next()).
SQLExceptionLa excepción de cualquier problema con la base.

Un ejemplo mínimo con SQLite

SQLite es una base de datos que vive en un solo archivo y no necesita instalar ningún servidor: perfecta para empezar y para programas de escritorio. Solo hay que agregar su driver al pom.xml, dentro de <dependencies>:

<dependency>
    <groupId>org.xerial</groupId>
    <artifactId>sqlite-jdbc</artifactId>
    <version>3.53.4.0</version>
</dependency>

Este programa crea la tabla de productos del inventario, inserta tres y consulta los que están por agotarse:

import java.math.BigDecimal;
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.sql.Statement;

/** Guarda productos en una base de datos SQLite (un solo archivo: tienda.db) y los lee. */
public class PruebaBD {

    public static void main(String[] args) throws SQLException {
        // La "direccion" de la base: con SQLite es el nombre del archivo.
        String url = "jdbc:sqlite:tienda.db";

        try (Connection conexion = DriverManager.getConnection(url)) {
            try (Statement sql = conexion.createStatement()) {
                sql.execute("CREATE TABLE IF NOT EXISTS producto ("
                        + " codigo TEXT PRIMARY KEY,"
                        + " nombre TEXT NOT NULL,"
                        + " precio TEXT NOT NULL,"
                        + " existencias INTEGER NOT NULL)");
                sql.execute("DELETE FROM producto");   // para que el ejemplo empiece limpio
            }

            String insertar = "INSERT INTO producto (codigo, nombre, precio, existencias) VALUES (?, ?, ?, ?)";
            try (PreparedStatement ps = conexion.prepareStatement(insertar)) {
                agregar(ps, "A01", "Arroz 1 lb", "5.50", 37);
                agregar(ps, "F02", "Frijol negro 1 lb", "8.75", 10);
                agregar(ps, "C03", "Café molido 400 g", "32.00", 3);
            }

            String consulta = "SELECT codigo, nombre, precio, existencias FROM producto"
                    + " WHERE existencias <= ? ORDER BY nombre";
            try (PreparedStatement ps = conexion.prepareStatement(consulta)) {
                ps.setInt(1, 10);
                try (ResultSet filas = ps.executeQuery()) {
                    System.out.println("Productos con 10 o menos:");
                    while (filas.next()) {
                        BigDecimal precio = new BigDecimal(filas.getString("precio"));
                        System.out.println("  " + filas.getString("codigo") + "  "
                                + filas.getString("nombre") + "  Q" + precio
                                + "  quedan " + filas.getInt("existencias"));
                    }
                }
            }
        }
    }

    private static void agregar(PreparedStatement ps, String codigo, String nombre, String precio,
                                int existencias) throws SQLException {
        ps.setString(1, codigo);
        ps.setString(2, nombre);
        ps.setString(3, precio);
        ps.setInt(4, existencias);
        ps.executeUpdate();
    }
}

Ejecutándolo (con Run File, Shift+F6, en NetBeans) se obtiene:

Productos con 10 o menos:
  C03  Café molido 400 g  Q32.00  quedan 3
  F02  Frijol negro 1 lb  Q8.75  quedan 10
  • "jdbc:sqlite:tienda.db" es la URL de la base: el protocolo (jdbc), el driver (sqlite) y el archivo. Si no existe, se crea en la carpeta desde donde se ejecuta el programa. Para MySQL sería algo como jdbc:mysql://servidor:3306/tienda, con usuario y contraseña.
  • Todo va dentro de try-con-recursos (capítulo 26): la conexión, las órdenes y los resultados se cierran solos al salir del bloque, aunque haya un error. Dejar conexiones abiertas es uno de los errores más comunes con bases de datos.
  • CREATE TABLE IF NOT EXISTS crea la tabla solo la primera vez. PRIMARY KEY hace que no pueda haber dos productos con el mismo código: la base de datos cuida esa regla por ti.
  • El precio se guarda como texto ("5.50") y se lee de vuelta con new BigDecimal(...): así no se pierde ni un centavo en el camino.
  • El mismo PreparedStatement se reutiliza para insertar tres veces: se rellenan los ? y se ejecuta con executeUpdate().
Nunca armes SQL pegando textos Sería tentador escribir "SELECT * FROM producto WHERE nombre = '" + busqueda + "'". Si alguien escribe en el buscador ' OR '1'='1, la orden cambia de significado y devuelve toda la tabla; con otras frases, podría borrarla. Se llama inyección SQL y es uno de los ataques más antiguos y frecuentes. Con PreparedStatement y ?, el texto del usuario siempre se trata como un dato, nunca como parte de la orden.

En el inventario del capítulo 68, todo esto iría en la clase AlmacenInventario: el resto del programa no se entera de si los datos están en un archivo o en una base. Es la misma separación de siempre.

5. Aplicaciones web con Spring Boot

Hasta ahora, tus programas se instalan en cada computadora. Una aplicación web corre en un servidor y la usan muchas personas desde el navegador o desde otras aplicaciones, sin instalar nada. En Java, la herramienta más usada para hacerlas es Spring Boot: un conjunto de librerías que, a partir de unas pocas anotaciones, monta un servidor web completo dentro de tu programa.

Lo más interesante para ti es que tu lógica no cambia. Para comprobarlo se hizo un experimento: un servicio web que recibe un tablero del Totito y responde la jugada de IA_Minimax. Se copiaron Tablero e IA_Minimax sin tocar su código —solo con la línea package al principio, porque Spring Boot exige paquetes: aquí se ve en la práctica lo de la sección 1— y se agregó una clase:

package com.tunombre.totitoweb;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

/**
 * Atiende la direccion /jugada. Recibe el tablero como 9 letras (X, O o -,
 * fila por fila) y responde la jugada de IA_Minimax en formato JSON.
 */
@RestController
public class JugadaControlador {

    /** Lo que se responde. Un record es una clase de datos escrita en una linea. */
    public record Jugada(int fila, int columna) {
    }

    @GetMapping("/jugada")
    public Jugada jugada(@RequestParam String tablero) {
        Tablero t = new Tablero();
        for (int i = 0; i < 9; i++) {
            char c = tablero.charAt(i);
            if (c == 'X' || c == 'O') {
                t.marcarCasilla(i / 3, i % 3, c);
            }
        }
        int[] mejor = new IA_Minimax('O', 'X').calcularMejorJugada(t);
        return new Jugada(mejor[0], mejor[1]);
    }
}
  • @RestController le dice a Spring que esta clase atiende peticiones web y que lo que devuelva se convierte en JSON, el formato de texto con el que se comunican las aplicaciones.
  • @GetMapping("/jugada") conecta la dirección /jugada con el método, y @RequestParam String tablero toma el valor que viene en la dirección después de ?tablero=.
  • Un record es una forma corta de escribir una clase de datos inmutable: record Jugada(int fila, int columna) equivale a una clase como Jugador, con sus campos final, su constructor y sus métodos de lectura.

Con el programa en marcha, al abrir en el navegador http://localhost:8080/jugada?tablero=XX--O---- (X en las dos primeras casillas de la fila 0, O en el centro) se obtiene:

{"fila":0,"columna":2}

La IA, ahora en la web, tapa la fila. Ese mismo servicio lo podría usar una página web, una app de teléfono o el propio Totito de escritorio. (La prueba se hizo con Spring Boot 4.1.1 y la dependencia spring-boot-starter-webmvc; el proyecto completo tiene además una clase con @SpringBootApplication y un main de dos líneas.)

Cómo empezar con Spring Boot Entra en start.spring.io, elige Maven, Java, la versión estable más nueva de Spring Boot, escribe tu paquete (com.tuusuario.lo-que-sea) y agrega la dependencia Spring Web. Descarga el zip, descomprímelo en $HOME\Proyectos y ábrelo en NetBeans como cualquier proyecto Maven. Trae un archivo mvnw.cmd para usar Maven sin instalarlo: .\mvnw.cmd spring-boot:run arranca el servidor en http://localhost:8080. Lo siguiente que aprenderás ahí: Spring Data JPA para bases de datos (sin escribir JDBC a mano) y Thymeleaf para páginas HTML.

6. Android y Kotlin

Las apps de Android se escriben en Kotlin o en Java, con Android Studio (gratuito, de Google). Desde 2019, Google recomienda Kotlin: un lenguaje que corre sobre la misma máquina virtual que Java, que puede usar cualquier clase Java y que se escribe más corto. Por ejemplo, toda la clase Jugador del capítulo 30 en Kotlin es:

data class Jugador(val nombre: String, val ficha: Char)

Una línea: val es como un campo final con su getter, y data class genera además la comparación y el texto para imprimirla. Las ideas que ya tienes —clases, objetos, herencia, interfaces, lambdas, excepciones, separar lógica e interfaz— son las mismas. La interfaz de Android no usa Swing: hoy se escribe con Jetpack Compose, donde cada pantalla es una función que describe lo que se ve. Un buen primer proyecto es, cómo no, un Totito para el teléfono: Tablero y Partida se pueden usar tal cual desde Kotlin.

7. Cómo seguir aprendiendo

Practicar

Programar se aprende programando, igual que nadar. Tres formas de hacerlo con constancia:

  • Proyectos propios. Los cinco del capítulo 68 y, sobre todo, uno que resuelva algo tuyo: el control de gastos de tu casa, el inventario del negocio de un familiar. La motivación de usar lo que haces no la da ningún curso.
  • Ejercicios cortos. Sitios como Exercism (con su sección de Java y comentarios de mentores voluntarios) o los retos de diciembre de Advent of Code entrenan la lógica en sesiones de 20 minutos.
  • Mejorar el Totito. La lista «Ideas pendientes» del README es un plan de trabajo ya escrito: niveles de dificultad, alternar quién empieza, animaciones con Timer, jugar con las teclas 1–9.

Un ritmo realista: una hora al día, cinco días por semana. En tres meses habrás hecho los cinco proyectos y escrito más código que en todo este libro.

Leer código ajeno

Los escritores leen mucho; los programadores también deberían. Empieza por el propio Java: en NetBeans, haz Ctrl+clic sobre JButton o ArrayList en cualquier archivo y verás el código fuente real del JDK, con sus comentarios. Después busca en GitHub proyectos pequeños de lo que te interese (tetris java swing, inventory java) y léelos con estas preguntas: ¿qué clases tiene?, ¿quién llama a quién?, ¿dónde está la lógica y dónde la interfaz?, ¿qué haría yo distinto? No necesitas entenderlo todo para aprender mucho.

Contribuir en GitHub

Contribuir a un proyecto de código abierto es la mejor práctica de trabajo en equipo que existe, y lo que aprendiste en el capítulo 10 es exactamente el proceso:

  1. Busca proyectos con la etiqueta good first issue (en GitHub, Issues → filtrar por esa etiqueta). Son tareas que los mantenedores marcaron como buenas para recién llegados.
  2. Lee el README.md y el CONTRIBUTING.md del proyecto: cuentan cómo prefieren trabajar.
  3. Comenta en el issue que te gustaría trabajar en él, antes de empezar.
  4. Haz un fork, clónalo, crea una rama, haz commits pequeños con buenos mensajes y abre el Pull Request: gh repo fork dueño/proyecto --clone, git switch -c arreglo-tal, …, gh pr create.
  5. Responde a la revisión con amabilidad y paciencia. Que te pidan cambios es normal, no un rechazo.

Las primeras contribuciones no tienen que ser código: corregir una falta en la documentación o traducir un texto al español también cuenta, y te enseña el proceso completo sin presión.

Lo que te llevas Al empezar el libro no sabías qué era un ;. Ahora sabes escribir clases, separar responsabilidades, dibujar una interfaz, usar Git como un profesional y entregar un programa con instalador. Lo que falta no es otro tipo de conocimiento: es más práctica con las mismas ideas.

Resumen

  • Los paquetes ordenan las clases en carpetas con nombre. El Totito usa el paquete por defecto por sencillez, pero sus clases no se pueden importar desde otros paquetes; migrarlo es agregar package e import y usar el nombre completo de la clase principal.
  • JUnit 5 automatiza las pruebas: @Test, @BeforeEach y aserciones como assertEquals o assertThrows. En el Totito las pruebas van en test\ y se ejecutan con Alt+F6 o al construir.
  • JavaFX es la alternativa moderna a Swing, con estilos CSS; las ideas de diseño y de arquitectura son las mismas.
  • JDBC conecta Java con bases de datos: Connection, PreparedStatement (siempre con ?) y ResultSet, dentro de try-con-recursos. SQLite es la forma más sencilla de empezar.
  • Spring Boot convierte tu lógica en un servicio web; Tablero e IA_Minimax funcionaron en la web sin cambiar su código.
  • Android se programa hoy con Kotlin, que usa las mismas ideas de POO con una sintaxis más corta.
  • Para seguir: documentación oficial, práctica constante, leer código ajeno y contribuir en GitHub.
Aplícalo fuera del Totito Cada tema de este capítulo es la pieza que suele faltar en los programas reales:
  • Las pruebas automáticas son obligatorias en casi cualquier empresa: muchos equipos no aceptan un Pull Request sin pruebas que cubran el cambio.
  • Los paquetes son el primer paso para convertir el kit neón en una librería que todos tus proyectos usen desde su pom.xml, en lugar de copiar archivos.
  • JDBC con SQLite convierte el inventario del capítulo 68 en un programa que una tienda puede usar de verdad.
  • Un servicio con Spring Boot permite que el mismo inventario se consulte desde la caja, desde la bodega y desde el teléfono del dueño.
