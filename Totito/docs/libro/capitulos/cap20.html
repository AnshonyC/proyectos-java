Capítulo 20Constructores, this, static y final

En los capítulos 18 y 19 creaste objetos con new y los protegiste con private. Ahora vas a entender las cuatro palabras que deciden cómo nace un objeto, cómo se nombra a sí mismo, qué comparte con los demás y qué ya no puede cambiar: el constructor, this, static y final. Aparecen en casi todos los archivos del Totito; después de este capítulo vas a poder leer cualquiera de sus primeras líneas sin dudar.

Por qué importan estas cuatro palabras

Abre mentalmente Partida.java (lo escribirás en el capítulo 38). Sus primeras líneas de contenido son estas:

public static final char FICHA_INICIAL = 'X';

private final Tablero tablero = new Tablero();
private final Jugador[] jugadores;
private final Modo modo;
private final IA_Minimax ia;
private final int[] victorias = new int[2];
private int empates;

private int turno;
private Estado estado;
private Jugador ganador;

public Partida(Jugador jugador1, Jugador jugador2, Modo modo) {
    ...
    this.jugadores = new Jugador[]{jugador1, jugador2};
    this.modo = modo;
    ...
}

En esas pocas líneas hay un static, seis final, varios this y un constructor. Cada una de esas palabras es una decisión de diseño, no un adorno: dice si el dato es de la partida o de todas las partidas, si puede cambiar durante el juego o no, y cuándo y cómo se llena. Quien sabe leerlas entiende la clase antes de leer sus métodos. Vamos una por una.

1. El constructor: el momento en que nace un objeto

La idea

Piensa en la inscripción de un alumno en un colegio. Nadie entra a la lista de alumnos sin llenar el formulario: nombre, fecha de nacimiento, grado. El formulario existe para que ningún alumno quede a medias, sin nombre o sin grado. El constructor es ese formulario: un bloque de código especial que Java ejecuta una sola vez, justo cuando el objeto nace, para dejarlo completo y listo para usarse.

Cómo se escribe

El constructor más sencillo del Totito es el de Jugador (capítulo 30):

public Jugador(String nombre, char ficha) {
    this.nombre = nombre;
    this.ficha = ficha;
}

Símbolo por símbolo:

  • public: cualquiera puede crear jugadores (capítulo 19).
  • Jugador: el constructor se llama exactamente igual que la clase, con la misma mayúscula. Así lo reconoce Java.
  • No hay tipo de retorno: ni void, ni int, nada. Un método normal dice qué devuelve; el constructor no devuelve nada por su cuenta, porque quien entrega el objeto terminado es new.
  • (String nombre, char ficha): los parámetros, igual que en un método (capítulo 16). Son los datos del «formulario».
  • { … }: el cuerpo. Aquí se copian los parámetros a los atributos del objeto.
  • this.nombre = nombre;: «el nombre de este objeto recibe el valor del parámetro nombre». Lo de this lo explicamos a fondo en la sección 2.

Y se usa así, por ejemplo en PantallaConfiguracion.comenzar() (capítulo 58):

new Jugador(jugador1.getNombre(), fichaJugador1)
Si le pones void, deja de ser constructor Escribir public void Jugador(String nombre, char ficha) compila sin error… pero ya no es un constructor: es un método normal que, por casualidad, se llama igual que la clase. Entonces new Jugador("Ana", 'X') falla, porque el constructor con dos parámetros ya no existe. Es uno de los errores más desconcertantes para quien empieza: el constructor nunca lleva tipo de retorno.

Qué pasa exactamente al escribir new

Cuando Java ejecuta new Jugador("Ana", 'X') ocurren cinco cosas, siempre en este orden:

  1. Reserva memoria en el montón (el heap, capítulo 18) para un objeto Jugador: espacio para un String y un char.
  2. Pone valores por defecto en todos los atributos: null en nombre y el carácter 0 en ficha.
  3. Ejecuta las inicializaciones escritas en la declaración, como private final Tablero tablero = new Tablero(); en Partida.
  4. Ejecuta el cuerpo del constructor, con los argumentos "Ana" y 'X'.
  5. Devuelve la referencia al objeto ya terminado, que normalmente guardas en una variable.

El paso 3 explica por qué en Partida algunos atributos se llenan en la misma línea donde se declaran (tablero, victorias) y otros dentro del constructor (jugadores, modo, ia): los primeros no dependen de nada que llegue de fuera, siempre son «un tablero nuevo» y «dos contadores en cero»; los segundos dependen de los parámetros, así que solo se pueden llenar cuando el constructor ya los recibió. Es la regla práctica: si el valor inicial es siempre el mismo, en la declaración; si depende de parámetros, en el constructor.

El constructor por defecto

¿Y si una clase no tiene ningún constructor escrito? Entonces Java le regala uno invisible, sin parámetros y con el cuerpo vacío: el constructor por defecto. Gracias a él, new Lampara() funciona aunque nadie lo haya escrito. Pruébalo:

public class DemoValoresPorDefecto {

    public static void main(String[] args) {
        Lampara lampara = new Lampara();   // nadie escribio un constructor... y funciona
        System.out.println("watts     = " + lampara.watts);
        System.out.println("brillo    = " + lampara.brillo);
        System.out.println("encendida = " + lampara.encendida);
        System.out.println("letra     = " + (int) lampara.letra + " (el caracter numero 0, invisible)");
        System.out.println("marca     = " + lampara.marca);
    }
}

class Lampara {
    int watts;          // numero entero
    double brillo;      // numero con decimales
    boolean encendida;  // verdadero o falso
    char letra;         // un caracter
    String marca;       // un objeto (referencia)
}

Guárdalo como DemoValoresPorDefecto.java en tu carpeta de prácticas y ejecútalo. Java 11 o superior compila en memoria y ejecuta un archivo de un solo paso; la clase que tiene main debe ser la primera del archivo, y debajo pueden ir otras clases sin public:

También hay atributos que confían en el valor por defecto a propósito: en Partida, private int empates; no se inicializa porque el marcador debe empezar en 0, y en TarjetaJugador, private boolean esComputadora; empieza en false porque toda tarjeta nace siendo de un humano.

Y esto es bueno: un jugador sin nombre ni ficha no tiene sentido en el Totito, y el compilador te impide crearlo. El constructor es la primera línea de defensa de las invariantes que viste en el capítulo 19.

Un constructor que trabaja: Tablero

Un constructor puede hacer más que copiar parámetros. El de Tablero (capítulo 29) no recibe nada, pero prepara la matriz y la vacía:

public Tablero() {
    casillas = new char[3][3];
    reiniciar();
}

Fíjate en la llamada a reiniciar(). Ese mismo método se usa al terminar una partida para empezar otra. El constructor lo reutiliza en vez de repetir los dos for que llenan el tablero de VACIA. ¿Qué pasaría si el constructor tuviera su propia copia de esos bucles? Funcionaría hoy, pero el día que cambiaras la forma de vaciar el tablero tendrías que acordarte de cambiarla en dos sitios. Partida hace lo mismo: su constructor termina con reiniciar();, que pone el estado en EN_CURSO y elige quién empieza.

Un constructor también puede negarse a crear el objeto si los datos no sirven. El de Partida empieza así:

if (jugador1.getFicha() == jugador2.getFicha()) {
    throw new IllegalArgumentException("Los dos jugadores no pueden usar la misma ficha");
}

Si los dos jugadores tienen la misma ficha, el objeto nunca llega a existir: Java lanza una excepción (capítulo 26) y new no devuelve nada. Así es imposible que en el programa circule una partida «X contra X».

En otros programas El constructor es donde se garantiza que un objeto nace válido. Una CuentaBancaria exige el titular y arranca con saldo 0 en la declaración; un Producto rechaza un precio negativo con una excepción; una Cita médica exige fecha y paciente. Si un dato es obligatorio, va como parámetro del constructor; si no, puede tener un valor inicial fijo.

2. this: «yo mismo»

La idea

En un salón de clases, cuando cada alumno dice «mi cuaderno», todos usan la misma palabra y sin embargo cada uno se refiere a su cuaderno. La palabra this es ese «mi»: dentro de un método o constructor, this es una referencia al objeto que está ejecutando el código en ese momento. Si hay cien jugadores, el mismo código del constructor de Jugador se ejecuta cien veces, y cada vez this apunta a un objeto distinto.

Uso 1: distinguir el atributo del parámetro

En el constructor de Jugador hay dos cosas llamadas nombre: el atributo del objeto y el parámetro. Dentro del constructor, el nombre suelto se refiere al parámetro, porque es la variable más cercana (se dice que el parámetro hace sombra al atributo). Para alcanzar el atributo hay que decir this.nombre: el punto significa «el nombre que pertenece a this».

Mira lo que pasa si se te olvida:

public class DemoSombra {

    public static void main(String[] args) {
        Mascota olvidadiza = new Mascota("Firulais");
        System.out.println("Nombre guardado: " + olvidadiza.getNombre());
    }
}

class Mascota {

    private String nombre;

    public Mascota(String nombre) {
        nombre = nombre;   // sin this: el parametro se asigna a si mismo
    }

    public String getNombre() {
        return nombre;
    }
}
Nombre guardado: null

Compila sin un solo error y, sin embargo, el nombre se perdió: la línea nombre = nombre; copió el parámetro en sí mismo y el atributo se quedó con su valor por defecto, null. Es un error silencioso clásico. Con this.nombre = nombre; queda resuelto. (Si además el atributo fuera final, como en el Jugador real, el compilador sí avisaría de que nunca se le asignó valor: otra ventaja de final, que verás en la sección 6.)

¿Por qué no ponerle otro nombre al parámetro? Podrías escribir Jugador(String n, char f) y nombre = n; sin this. Funciona, pero n y f no dicen nada a quien usa la clase, y NetBeans muestra los nombres de los parámetros al autocompletar. La costumbre de Java es usar el mismo nombre y this., y es la que sigue todo el Totito.

Uso 2: pasarse a sí mismo como argumento

this es una referencia como cualquier otra, así que se puede entregar a otro objeto. En el constructor de PanelPrincipal (capítulo 61):

pantallaJuego = new PantallaJuego(this);
pantallaResultado = new PantallaResultado(this);
add(new PantallaMenu(this), MENU);

Cada pantalla necesita a «alguien» a quien pedirle «llévame al menú». Ese alguien es el propio PanelPrincipal, que se presenta diciendo this: «yo soy tu navegación». Y en cartas.show(this, MENU) le dice al CardLayout «muestra la carta MENU dentro de mí». Cómo puede un PanelPrincipal pasar por Navegacion lo verás en el capítulo 24.

Uso 3: leer los atributos de otro objeto de la misma clase

En Tablero.obtenerCopia():

copia.casillas[fila][columna] = this.casillas[fila][columna];

Aquí this no es obligatorio (sin él significaría lo mismo), pero aclara la lectura: a la izquierda, las casillas de la copia; a la derecha, las mías. Cuando hay dos objetos de la misma clase en juego, poner this. evita confusiones.

Uso 4 y 5: this(...) y return this

Hay dos usos más: this(...) para llamar a otro constructor de la misma clase (sección 3) y return this; para encadenar llamadas (sección 4). Y uno que verás en el capítulo 25: this::cerrar, que en TotitoApp entrega «mi método cerrar» a otro objeto.

Dónde no existe this this solo tiene sentido cuando hay un objeto ejecutando el código. En un método static (sección 5) no lo hay, así que this no se puede usar ahí.

3. Sobrecarga de constructores y this(...)

La idea

En una cafetería puedes pedir «un café», y te dan el tamaño mediano de siempre, o pedir «un café grande». Es el mismo producto con un detalle por defecto o con el detalle que tú indicas. Una clase puede tener varios constructores, siempre que se distingan por sus parámetros (cuántos, de qué tipo, en qué orden). A eso se le llama sobrecarga de constructores, la misma idea que la sobrecarga de métodos del capítulo 16.

Dónde está en el Totito: Tarjeta

La caja de cristal (capítulo 43) se puede crear de dos maneras:

public Tarjeta(Color color) {
    this(color, 30);
}

public Tarjeta(Color color, int arco) {
    this.color = color;
    this.arco = arco;
    setOpaque(false);
    setAlignmentX(CENTER_ALIGNMENT);
}

El segundo constructor es el completo: recibe el color y el redondeo de las esquinas (arco) y hace todo el trabajo. El primero es un atajo: solo pide el color y le pasa el trabajo al completo con el arco «de siempre», 30 píxeles. La línea clave, símbolo por símbolo:

  • this seguido de paréntesis: «llama a otro constructor de esta misma clase». No es this.algo, es this(...).
  • (color, 30): los argumentos. Java elige el constructor cuya lista de parámetros encaja: un Color y un int, o sea, el segundo.
  • ;: es una instrucción más.

Así se usan los dos en el juego:

Tarjeta tarjeta = new Tarjeta(Tema.MORADO);        // PantallaMenu: arco de 30
super(color, 26);                                   // TarjetaJugador: arco de 26

(La segunda línea usa super(...), el primo de this(...) que llama al constructor de la clase padre; lo verás en el capítulo 22.)

this(...) va en la primera línea La llamada a otro constructor tiene que ser la primera instrucción del cuerpo. Java exige que el objeto termine de construirse en un solo lugar antes de hacer cualquier otra cosa. Si pones algo antes, el compilador se queja con un error que dice que la llamada al constructor debe ser la primera instrucción. Después de this(...) sí puedes escribir más código.

Míralo funcionar

public class DemoConstructores {

    public static void main(String[] args) {
        Caja normal = new Caja("morado");
        Caja cuadrada = new Caja("rosa", 4);
        System.out.println(normal.describir());
        System.out.println(cuadrada.describir());
    }
}

class Caja {

    private final String color;
    private final int arco;

    /** Constructor corto: usa el arco "de siempre". */
    public Caja(String color) {
        this(color, 30);
        System.out.println("  (constructor corto termino)");
    }

    /** Constructor completo: aqui vive la logica de verdad. */
    public Caja(String color, int arco) {
        System.out.println("  constructor completo: color=" + color + ", arco=" + arco);
        this.color = color;
        this.arco = arco;
    }

    public String describir() {
        return "Caja " + color + " con esquinas de " + arco + " px";
    }
}
  constructor completo: color=morado, arco=30
  (constructor corto termino)
  constructor completo: color=rosa, arco=4
Caja morado con esquinas de 30 px
Caja rosa con esquinas de 4 px

Sigue el orden de las líneas: para la caja morada, primero corre el constructor completo (llamado desde this(color, 30)) y después el resto del constructor corto. Para la rosa, Java eligió directamente el de dos parámetros.

Qué pasaría sin this(...)

Tendrías que copiar las cuatro líneas del constructor completo dentro del corto. Hoy serían cuatro; mañana, cuando Tarjeta necesite una línea más (un borde, un cursor), habría que recordar agregarla en los dos. Tarde o temprano uno de los dos queda desactualizado y aparecen tarjetas que se comportan distinto según cómo se crearon. Con this(...) la lógica vive en un solo lugar.

La misma idea se aplica a los métodos: Dibujo.trazoNeon tiene una versión de cuatro parámetros que llama a la de cinco con intensidad 1f:

public static void trazoNeon(Graphics2D g, Shape figura, Color color, float grosor) {
    trazoNeon(g, figura, color, grosor, 1f);
}
En otros programas Producto(String nombre) que llama a Producto(nombre, 0.0) para productos aún sin precio; Alumno(String nombre) que llama a Alumno(nombre, "Primero básico"); Enemigo(int x, int y) en un juego, que llama a Enemigo(x, y, 100) con la vida completa. Siempre el mismo patrón: un constructor completo y atajos que le delegan.

4. Constructores privados y métodos de fábrica

La idea

En un restaurante no entras a la cocina a combinar tú los ingredientes: pides «el combo 1» o «el desayuno chapín» del menú, y la cocina sabe qué lleva cada uno. Los métodos de fábrica son ese menú: métodos static con nombres claros que crean el objeto por ti con la combinación correcta. Y para que nadie se meta a la cocina, el constructor se hace private.

Dónde está en el Totito: BotonNeon

El constructor de BotonNeon (capítulo 44) recibe siete datos:

private BotonNeon(String texto, Iconos.Icono icono, Color color, Color colorFinal,
                  Estilo estilo, int ancho, int alto) {

Es private: solo el código de la propia clase puede escribir new BotonNeon(...). Desde fuera, los botones se piden por el menú:

/** Boton grande del menu principal. */
public static BotonNeon menu(String texto, Iconos.Icono icono, Color color) {
    return new BotonNeon(texto, icono, color, color, Estilo.MENU, 384, 88);
}

/** Pildora rellena con un degradado de "desde" a "hasta". */
public static BotonNeon pildora(String texto, Iconos.Icono icono, Color desde, Color hasta, int ancho, int alto) {
    return new BotonNeon(texto, icono, desde, hasta, Estilo.PILDORA, ancho, alto);
}

/** Pildora oscura con borde morado. */
public static BotonNeon contorno(String texto, Iconos.Icono icono, int ancho, int alto) {
    return new BotonNeon(texto, icono, Tema.MORADO, Tema.MORADO, Estilo.CONTORNO, ancho, alto);
}

/** Boton cuadrado sin texto. Ponerle setToolTipText para que se entienda. */
public static BotonNeon icono(Iconos.Icono icono, Color color) {
    return new BotonNeon("", icono, color, color, Estilo.ICONO, 58, 58);
}

Analicemos menu:

  • public static: se llama a través de la clase, sin tener todavía ningún botón: BotonNeon.menu(...). (Por qué hace falta static aquí lo entenderás en la sección 5: aún no existe un objeto al que pedírselo.)
  • BotonNeon: el tipo que devuelve, un botón.
  • menu: el nombre dice qué clase de botón obtienes. Eso no lo puede hacer un constructor, que siempre se llama como la clase.
  • return new BotonNeon(texto, icono, color, color, Estilo.MENU, 384, 88);: la fábrica sí puede usar el constructor privado, porque está dentro de la clase. Rellena ella sola los cuatro datos que el botón de menú siempre lleva igual: el color final es el mismo color, el estilo es MENU y el tamaño es 384 × 88.

Y así se ve desde PantallaMenu (capítulo 56):

BotonNeon jugar = BotonNeon.menu("Jugar", Iconos.JUGAR, Tema.ROSA);

Una línea que se lee casi en español: «un botón de menú que dice Jugar, con el icono de jugar, en rosa».

Qué pasaría sin fábricas

Con el constructor público, cada pantalla escribiría:

new BotonNeon("Jugar", Iconos.JUGAR, Tema.ROSA, Tema.ROSA, BotonNeon.Estilo.MENU, 384, 88)

Siete argumentos en los que es fácil equivocarse: intercambiar ancho y alto, olvidar repetir el color, poner 380 en un botón y 384 en otro. Los números 384 y 88 estarían repetidos en tres sitios, y cambiar el tamaño de los botones del menú significaría buscarlos todos. Con la fábrica, el diseño de «un botón de menú» vive en un solo método.

Fábricas que hacen trabajo extra: Rotulo

Rotulo (capítulo 46) también tiene el constructor privado y tres fábricas: titulo, seccion y leyenda. La de sección hace algo que un constructor no podría hacer tan claramente: crea el objeto, le ajusta un dato y después lo entrega.

public static Rotulo seccion(String texto, String subtitulo, int ancho) {
    Rotulo r = new Rotulo(Tipo.SECCION, texto, Tema.fuenteEspaciada(Font.BOLD, 17f, 0.3f),
            Tema.LAVANDA, Tema.LAVANDA, ancho, subtitulo == null ? 28 : 48);
    r.subtitulo = subtitulo;
    return r;
}

Fíjate en subtitulo == null ? 28 : 48: la fábrica decide la altura según haya o no subtítulo. Quien la usa no tiene que saberlo.

Métodos que devuelven this: encadenar

Rotulo agrega otro truco. Sus métodos conIcono y conSubrayado modifican el rótulo y terminan con return this;:

public Rotulo conIcono(Iconos.Icono icono, Color color) {
    this.icono = icono;
    this.colorIcono = color;
    return this;
}

Como devuelven el mismo objeto, se pueden encadenar, uno detrás del otro, en una sola expresión. Así lo hace PantallaInstrucciones (capítulo 57):

tarjeta.add(Rotulo.titulo("Cómo jugar", 36f, Tema.TEXTO, Tema.LAVANDA, ANCHO_PASOS, 70)
        .conIcono(Iconos.LIBRO, Tema.ROSA)
        .conSubrayado(Tema.ROSA, Tema.AZUL));

Se lee de arriba abajo: un título «Cómo jugar», con icono de libro, con subrayado rosa-azul. Cada punto llama a un método sobre lo que devolvió el anterior, que siempre es el mismo rótulo. A este estilo se le llama interfaz fluida.

Tu propia fábrica

public class DemoFabrica {

    public static void main(String[] args) {
        Boton jugar = Boton.menu("Jugar");
        Boton volver = Boton.contorno("Volver", 300, 52);
        Boton cerrar = Boton.icono("X").conAyuda("Cerrar el juego");
        System.out.println(jugar);
        System.out.println(volver);
        System.out.println(cerrar);
        // Boton raro = new Boton("Hola", "?", 1, 1);   // no compila: el constructor es privado
    }
}

class Boton {

    private final String texto;
    private final String estilo;
    private final int ancho;
    private final int alto;
    private String ayuda = "";

    private Boton(String texto, String estilo, int ancho, int alto) {
        this.texto = texto;
        this.estilo = estilo;
        this.ancho = ancho;
        this.alto = alto;
    }

    public static Boton menu(String texto) {
        return new Boton(texto, "MENU", 384, 88);
    }

    public static Boton contorno(String texto, int ancho, int alto) {
        return new Boton(texto, "CONTORNO", ancho, alto);
    }

    public static Boton icono(String simbolo) {
        return new Boton(simbolo, "ICONO", 58, 58);
    }

    /** Devuelve el mismo boton para poder encadenar llamadas. */
    public Boton conAyuda(String ayuda) {
        this.ayuda = ayuda;
        return this;
    }

    @Override
    public String toString() {
        return estilo + " \"" + texto + "\" " + ancho + "x" + alto
                + (ayuda.isEmpty() ? "" : " (ayuda: " + ayuda + ")");
    }
}

CONTORNO "Volver" 300x52

El método toString con @Override es el texto que Java usa cuando imprimes el objeto; lo verás en los capítulos 22 y 23. Si quitas las barras // de la línea comentada, el compilador te dirá que Boton(...) tiene acceso privado: justo lo que querías.

En otros programas El propio Java está lleno de fábricas: List.of("a", "b"), LocalDate.of(2026, 10, 12), Integer.valueOf("42"), BorderFactory.createEmptyBorder(...) (que el Totito usa en sus pantallas). En una tienda: Descuento.porcentaje(10) y Descuento.fijo(25), dos fábricas que crean el mismo tipo de objeto con significados distintos que un constructor con un double no podría expresar. En un banco: Cuenta.deAhorro(titular) y Cuenta.monetaria(titular). Este patrón tiene nombre, Factory Method, y lo retomarás en el capítulo 27.

5. static: lo que es de la clase, no de cada objeto

La idea

En un aula, cada alumno tiene su cuaderno: lo que escribe uno no aparece en el de otro. Pero hay un solo pizarrón, compartido por todos. Lo que pertenece a cada objeto (el cuaderno) es un miembro de instancia; lo que pertenece a la clase y es uno solo para todos (el pizarrón) es un miembro static. La palabra viene de «estático» porque existe desde que la clase se carga y no nace ni muere con cada objeto.

Campos static: Tablero.VACIA

public static final char VACIA = ' ';

Palabra por palabra:

  • public: cualquier clase puede leerla.
  • static: hay una sola VACIA, de la clase Tablero, no una por tablero. Aunque la IA cree miles de copias del tablero al pensar, la constante no se multiplica.
  • final: no se puede cambiar (sección 6).
  • char VACIA = ' ': es un carácter, el espacio en blanco.

Como es de la clase, se usa con el nombre de la clase, sin crear ningún objeto: Tablero.VACIA. Así aparece en IA_Minimax, Partida, PanelTablero y PruebaConsola:

if (tablero.obtenerCasilla(fila, columna) == Tablero.VACIA) {

Si VACIA no fuera static, para leerla necesitarías un tablero concreto (tablero.VACIA), lo cual no tiene sentido: «qué significa casilla vacía» es una regla del juego, no un dato de un tablero en particular.

Lo mismo pasa con toda la paleta del juego en Tema (capítulo 40):

public static final Color ROSA = new Color(0xFF, 0x3B, 0xD4);

Hay un solo rosa para todo el programa, y cualquier componente lo pide con Tema.ROSA. Otras constantes del Totito: Partida.FICHA_INICIAL, PanelPrincipal.ANCHO y ALTO, CampoTexto.MAXIMO, Tarjeta.MARGEN.

Métodos static: herramientas que no necesitan un objeto

Un método static se llama con el nombre de la clase y trabaja solo con lo que recibe por parámetros (y con otros miembros static). Ejemplo de Tema:

public static Color conAlfa(Color color, int alfa) {
    return new Color(color.getRed(), color.getGreen(), color.getBlue(),
            Math.max(0, Math.min(255, alfa)));
}

Para hacer un color más transparente no hace falta ningún «objeto tema»: entra un color y un número, sale otro color. Por eso se llama Tema.conAlfa(Tema.MORADO, 40). Igual que Math.max, que usas sin crear ningún «objeto matemáticas».

Un caso más interesante es Partida.buscarLineaGanadora:

public static int[] buscarLineaGanadora(Tablero tablero) {

Está dentro de Partida porque trata de las reglas del juego, pero es static porque no usa nada de una partida concreta: ni turnos, ni jugadores, ni marcador; solo el tablero que recibe. Y eso tiene una consecuencia práctica muy concreta: PanelTablero.mostrar la llama así:

lineaGanadora = Partida.buscarLineaGanadora(tablero);

El tablero de ejemplo de la pantalla de instrucciones no tiene ninguna partida detrás (se crea un Tablero suelto en PantallaInstrucciones.tableroDeEjemplo()). Si el método no fuera static, habría que inventar una Partida con dos jugadores falsos solo para preguntar dónde está la raya. Al ser static, basta con el tablero.

main es static, y por eso

Ahora entiendes por fin el static de public static void main(String[] args) (capítulo 11). Cuando arranca el programa, todavía no existe ningún objeto: Java necesita un método al que se pueda llamar con solo el nombre de la clase. Por eso main es static, y lo primero que hace casi siempre es crear objetos: new TotitoApp().

La regla de oro de static

Un método static no tiene this, así que no puede tocar los atributos de instancia directamente: ¿de cuál de todos los objetos serían? Si lo intentas:

public class DemoContextoEstatico {

    private String nombre = "Ana";

    public static void main(String[] args) {
        System.out.println(nombre);
    }
}
DemoContextoEstatico.java:6: error: non-static variable nombre cannot be referenced from a static context
        System.out.println(nombre);
                           ^
1 error
error: compilation failed

«La variable no estática nombre no se puede usar desde un contexto estático». Es el error más común de quien empieza: escribe todo en main y luego quiere usar un atributo. La solución es crear un objeto (new DemoContextoEstatico().nombre) o, si de verdad es un dato compartido, hacerlo static. Lo contrario sí está permitido: un método de instancia puede usar cosas static sin problema, como hace Tablero.reiniciar() con VACIA.

Un contador compartido

Los campos static que sí cambian son menos comunes, pero conviene verlos una vez para entender la diferencia entre «uno por objeto» y «uno para todos»:

public class DemoStatic {

    public static void main(String[] args) {
        System.out.println("Inicio de main. Tickets creados: " + Ticket.getCreados());
        Ticket a = new Ticket("Ana");
        Ticket b = new Ticket("Luis");
        Ticket c = new Ticket("Marta");
        System.out.println(a.describir());
        System.out.println(b.describir());
        System.out.println(c.describir());
        System.out.println("Tickets creados: " + Ticket.getCreados());
        System.out.println("Precio con IVA de 100: " + Ticket.conIva(100.0));
        System.out.println("Moneda: " + Ticket.MONEDA);
    }
}

class Ticket {

    /** Constante: una sola, compartida, que nunca cambia. */
    public static final String MONEDA = "GTQ";
    /** Contador compartido por TODOS los tickets. */
    private static int creados = 0;
    /** Se calcula una vez, cuando Java carga la clase. */
    private static final double IVA = calcularIva();

    /** De cada ticket: su propio numero y su propio cliente. */
    private final int numero;
    private final String cliente;

    public Ticket(String cliente) {
        creados++;
        this.numero = creados;
        this.cliente = cliente;
    }

    private static double calcularIva() {
        System.out.println("  [Java carga la clase Ticket y calcula el IVA]");
        return 0.12;
    }

    public static int getCreados() {
        return creados;
    }

    public static double conIva(double monto) {
        return Math.round(monto * (1 + IVA) * 100) / 100.0;   // redondeado a centavos
    }

    public String describir() {
        return "Ticket #" + numero + " de " + cliente;
    }
}
  [Java carga la clase Ticket y calcula el IVA]
Inicio de main. Tickets creados: 0
Ticket #1 de Ana
Ticket #2 de Luis
Ticket #3 de Marta
Tickets creados: 3
Precio con IVA de 100: 112.0
Moneda: GTQ

Tres cosas para observar:

  1. creados es uno solo: cada constructor lo incrementa, y por eso cada ticket recibe un número distinto. En cambio numero y cliente son de cada ticket.
  2. La línea entre corchetes salió antes de «Inicio de main». ¿Por qué? Para imprimir esa frase, Java primero tiene que calcular Ticket.getCreados(); como es la primera vez que se usa la clase Ticket, la carga en ese momento, y al cargarla inicializa sus campos static, en el orden en que están escritos: MONEDA, creados y luego IVA, que llama a calcularIva(). Esa inicialización ocurre una sola vez en toda la ejecución.
  3. conIva es static porque solo necesita el monto y la constante IVA.

Inicialización estática en el Totito: la fuente del juego

En Tema hay dos líneas seguidas que usan justo ese mecanismo:

private static final List<String> FAMILIAS = Arrays.asList(
        "Nunito", "Poppins", "Montserrat", "Segoe UI", "Helvetica Neue",
        "Ubuntu", "Arial", "Liberation Sans", "DejaVu Sans");

private static final String FAMILIA = elegirFamilia();

elegirFamilia() le pregunta al sistema operativo qué fuentes tiene instaladas y elige la primera de la lista que exista. Esa pregunta es lenta (el sistema revisa cientos de fuentes). Como FAMILIA es static final, se hace una sola vez, cuando se carga Tema, y luego todas las llamadas a Tema.fuente(...) (hay decenas por cada repintado de la pantalla) usan el resultado guardado. Si fuera un cálculo dentro de fuente(), el juego le preguntaría al sistema operativo por las fuentes cada vez que dibuja un texto.

Y el orden importa más de lo que parece. Mira qué pasa si se invierten esas dos declaraciones:

import java.util.Arrays;
import java.util.List;

public class DemoOrdenEstatico {

    public static void main(String[] args) {
        System.out.println("Bien ordenado:  " + TemaBien.FAMILIA);
        System.out.println("Mal ordenado:   " + TemaMal.FAMILIA);
    }
}

class TemaBien {
    private static final List<String> FAMILIAS = Arrays.asList("Nunito", "Arial");
    static final String FAMILIA = elegir();      // FAMILIAS ya tiene valor

    private static String elegir() {
        try {
            for (String familia : FAMILIAS) {
                return familia;                  // la primera de la lista
            }
        } catch (RuntimeException e) {
            // si algo falla, la generica
        }
        return "SansSerif";
    }
}

class TemaMal {
    static final String FAMILIA = elegir();      // se ejecuta ANTES de la linea de abajo
    private static final List<String> FAMILIAS = Arrays.asList("Nunito", "Arial");

    private static String elegir() {
        try {
            for (String familia : FAMILIAS) {    // FAMILIAS todavia es null
                return familia;
            }
        } catch (RuntimeException e) {
            // el NullPointerException cae aqui, en silencio
        }
        return "SansSerif";
    }
}
Bien ordenado:  Nunito
Mal ordenado:   SansSerif

En TemaMal, cuando se calcula FAMILIA, la lista FAMILIAS todavía tiene su valor por defecto, null. Recorrer null provoca un NullPointerException, que el catch atrapa en silencio, y el programa termina usando la fuente genérica sin avisar. El juego seguiría funcionando, pero se vería con otra letra y nadie sabría por qué. Por eso en Tema la lista va primero. (El try/catch lo estudiarás en el capítulo 26.)

static que cambia = variable global Un campo static que no es final lo puede modificar cualquier parte del programa, en cualquier momento: es una variable global, y los errores que provoca son difíciles de rastrear («¿quién cambió esto?»). Fíjate en un dato: en todo el Totito no hay ni un solo campo static que cambie; todos son static final. El marcador, por ejemplo, vive en cada Partida (victorias, empates) y no en un contador global. Usa static para constantes y para métodos-herramienta; para datos que cambian, usa objetos.

6. Clases de utilidades: solo static, y nadie puede crearlas

Algunas clases del Totito son puras cajas de herramientas: todo lo que tienen es static. Dibujo (capítulo 41) empieza así:

public final class Dibujo {

    private Dibujo() {
    }

Un constructor privado y vacío. Parece no hacer nada, y esa es su función: impedir que alguien escriba new Dibujo(). Un objeto Dibujo no tendría sentido: no guarda ningún dato; sus métodos (preparar, trazoNeon, dibujarFicha…) se usan como Dibujo.trazoNeon(...). Si no estuviera ese constructor, Java regalaría el de por defecto (público), y alguien podría crear objetos Dibujo inútiles, o confundirse pensando que hace falta uno para dibujar. Tema e Iconos siguen el mismo patrón. La palabra final delante de class la verás en la sección siguiente.

El JDK hace exactamente lo mismo con Math (de donde sale el Math.max que usa Tema.conAlfa) y con Arrays (el Arrays.asList de Tema y el java.util.Arrays.fill de PanelTablero): no puedes hacer new Math().

En otros programas Una clase Formatos con Formatos.moneda(123.5) que devuelve "Q123.50"; una clase Validaciones con Validaciones.esCorreo(texto) y Validaciones.esDpiValido(numero); una clase Fechas con Fechas.edad(fechaNacimiento) para el sistema de una escuela. Si un método solo transforma lo que recibe en lo que devuelve, sin recordar nada, es un buen candidato a herramienta static.

7. final: «esto ya no cambia»

La idea

Hay cosas que se escriben con lápiz y cosas que se escriben con pluma. El número de DPI de una persona se escribe con pluma: una vez asignado, no cambia. La edad, en cambio, se escribe con lápiz. final es la pluma de Java: un valor final se asigna exactamente una vez, y el compilador vigila que nadie lo intente cambiar después.

final en atributos

En Jugador:

private final String nombre;
private final char ficha;

Un jugador no cambia de nombre ni de ficha en medio de la partida. Con final, eso deja de ser una costumbre y se vuelve una garantía: el compilador exige que cada atributo final reciba valor una vez, ya sea en su declaración o en todos los constructores, y prohíbe cualquier asignación posterior. Si algún día un constructor nuevo se olvida de asignar nombre, el programa no compila. Así es como Jugador se vuelve inmutable (capítulo 19).

Lo más útil de final es lo que comunica. Vuelve a mirar los atributos de Partida del principio del capítulo:

Atributo¿final?Qué te dice
tablero, jugadores, modo, ia, victoriassíSe fijan al crear la serie de partidas y la acompañan hasta el final.
empates, turno, estado, ganadornoCambian durante el juego: son lo que hay que vigilar al buscar un error.

Sin leer un solo método ya sabes qué partes de la partida se mueven. Un detalle curioso: ia es final aunque a veces valga null:

this.ia = modo == Modo.CONTRA_IA ? new IA_Minimax(jugador2.getFicha(), jugador1.getFicha()) : null;

final no prohíbe null; prohíbe cambiar el valor. En el modo de dos jugadores, ia es null para siempre, y eso es justo lo que se quiere.

Cuidado: final fija la referencia, no el objeto

Esta es la confusión más frecuente con final. En Partida:

private final Tablero tablero = new Tablero();
private final int[] victorias = new int[2];

y sin embargo, más abajo, se hace tablero.reiniciar() y victorias[turno]++. ¿No que eran final? Recuerda del capítulo 18 que una variable de objeto guarda una referencia (una flecha hacia el objeto). final congela la flecha: tablero apuntará siempre al mismo tablero, nunca a otro. Pero el tablero en sí puede cambiar por dentro. Es como una casa con dirección fija: la dirección no cambia, pero los muebles de adentro sí se pueden mover. Si quieres que el contenido tampoco cambie, la clase misma tiene que diseñarse inmutable, como Jugador (todos sus atributos final y de tipos que no cambian, y ningún método que los modifique).

final en variables locales

También se puede usar en una variable dentro de un método. Si intentas reasignarla:

public class DemoFinal {

    public static void main(String[] args) {
        final int limite = 14;
        limite = 20;
        System.out.println(limite);
    }
}
DemoFinal.java:5: error: cannot assign a value to final variable limite
        limite = 20;
        ^
1 error
error: compilation failed

«No se puede asignar un valor a la variable final limite». En el Totito aparece en Dibujo.trazoNeon: final int capas = 6;, que deja claro que el número de capas del halo no cambia durante el bucle. Y en JuegoMain (capítulo 33) hay un uso con un motivo técnico importante:

final int f = fila;
final int c = columna;
boton.addActionListener((ActionEvent e) -> manejarClicCasilla(f, c));

La lambda (capítulo 25) se ejecutará mucho después, cuando el usuario haga clic, y Java solo le deja usar variables que no cambien. fila sí cambia (es la variable del for), así que se copia a f, que es final. Lo entenderás del todo en el capítulo 25.

Constantes: static + final

Juntas, las dos palabras forman una constante: un solo valor (static) que nunca cambia (final). Por convención se escriben en MAYUSCULAS_CON_GUIONES_BAJOS: Tablero.VACIA, Tema.ROSA, PantallaJuego.PAUSA_IA_MS. Así, cuando lees PAUSA_IA_MS en medio del código, sabes de inmediato que es una constante y dónde buscarla. Por qué conviene sacar los números sueltos a constantes con nombre lo verás en el capítulo 27.

final en clases y métodos

public final class Tema significa que nadie puede heredar de Tema: no puede existir una clase TemaOscuro extends Tema. Para una clase de utilidades tiene todo el sentido: no hay nada que extender. Dibujo e Iconos también son final, y en el JDK lo es String, para que nadie pueda crear un «String falso» que se comporte distinto. Un método final, por su parte, no puede ser reemplazado por las clases hijas; el Totito no usa ninguno, pero lo entenderás bien cuando veas herencia y sobrescritura en los capítulos 22 y 23.

Pon final por defecto Una buena costumbre es declarar final todo atributo que no tengas un motivo claro para cambiar, y quitarlo solo cuando haga falta. Cuantas menos cosas cambian, menos lugares hay donde puede esconderse un error. El Totito lo hace así: de los nueve atributos de instancia de Partida, cinco son final, y los cuatro que no lo son son justo los que el juego necesita cambiar.

Todo junto: leer el principio de una clase

Con lo de este capítulo, el principio de PantallaJuego (capítulo 59) se lee de corrido:

private static final int PAUSA_IA_MS = 450;
private static final int PAUSA_RESULTADO_MS = 1200;

private final Navegacion navegacion;
private final PanelMarcador marcador = new PanelMarcador();
private final Rotulo turno = Rotulo.titulo("", 26f, Tema.TEXTO, Tema.TEXTO, 590, 44);

private Partida partida;
private Timer pendiente;
  • Dos constantes privadas (static final): tiempos que no cambian y que solo usa esta pantalla.
  • Cuatro atributos final: la navegación (llega por el constructor) y tres componentes que se crean en la propia declaración (uno de ellos con una fábrica, Rotulo.titulo). La pantalla siempre muestra el mismo marcador, el mismo letrero y el mismo tablero.
  • Dos atributos que cambian: la partida que se está mostrando (cambia cada vez que empiezas una nueva) y el temporizador pendiente, que a veces es null.

Y su constructor empieza con super(navegacion); (capítulo 22) seguido de this.navegacion = navegacion;. Ya no hay ninguna palabra misteriosa.

Resumen

  • El constructor se llama como la clase, no tiene tipo de retorno y se ejecuta una vez al hacer new; su trabajo es dejar el objeto completo y válido. Si no escribes ninguno, Java pone uno vacío; si escribes alguno, ese regalo desaparece.
  • new reserva memoria, pone valores por defecto (0, false, null), ejecuta las inicializaciones de los atributos y luego el cuerpo del constructor.
  • this es «el objeto que está ejecutando este código»: sirve para distinguir atributo de parámetro, para pasarse a otro objeto y para devolverse (return this).
  • La sobrecarga de constructores con this(...) (primera línea) deja la lógica en un solo constructor completo; Tarjeta(Color) delega en Tarjeta(Color, int).
  • Un constructor privado con métodos de fábrica (BotonNeon.menu, Rotulo.titulo) da nombres claros a cada forma de crear el objeto y evita repetir datos.
  • static es de la clase, no de cada objeto: constantes como Tablero.VACIA y herramientas como Tema.conAlfa o Partida.buscarLineaGanadora. Un método static no tiene this. Los campos static se inicializan una vez, en orden, al cargar la clase.
  • Las clases de utilidades (Dibujo, Tema, Iconos) tienen constructor privado y son final.
  • final se asigna una sola vez: en atributos comunica qué no cambia; en una referencia fija la flecha, no el contenido del objeto; en una clase impide heredarla.
