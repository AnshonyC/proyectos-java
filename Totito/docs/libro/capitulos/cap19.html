Capítulo 19Encapsulamiento

Una clase no solo junta datos y métodos: también decide quién puede tocar qué. En este capítulo aprenderás a esconder los datos de un objeto detrás de métodos que hacen cumplir sus reglas, que es lo que impide que en el Totito alguien ponga dos fichas en la misma casilla o le cambie el nombre a un jugador a media partida.

El problema: la puerta trasera

Al final del capítulo 18, la clase Producto tenía su regla «no vendas más de lo que hay» dentro del método vender. Pero cualquiera podía saltársela escribiendo directamente en el atributo. Mira lo que pasa con una cuenta bancaria escrita así (CuentaInsegura.java):

public class CuentaInsegura {

    public static void main(String[] args) {
        Cuenta cuenta = new Cuenta();
        cuenta.titular = "Marta";
        cuenta.saldo = 1000;

        // En otro rincon del programa, alguien se equivoca:
        cuenta.saldo = cuenta.saldo - 1500;

        System.out.println(cuenta.titular + " tiene Q" + cuenta.saldo);
    }
}

class Cuenta {
    String titular;
    double saldo;
}

Una cuenta de débito con 500 quetzales negativos. Nadie validó nada porque no había dónde validar: el saldo era un número al alcance de cualquier línea del programa. En un programa de diez líneas lo ves enseguida; en uno de diez mil, el error aparece en un reporte semanas después y tienes que revisar cada sitio que toca saldo para encontrar al culpable.

La idea: la ventanilla del banco

En un banco de verdad tú no entras a la bóveda a sacar billetes. Vas a la ventanilla, pides retirar 1500 quetzales y el cajero revisa tu saldo; si no alcanza, te dice que no. La bóveda está cerrada para el público; la ventanilla está abierta, pero tiene reglas. Y si mañana el banco cambia de bóveda o de sistema, a ti te da igual: la ventanilla sigue funcionando igual.

Eso es el encapsulamiento: los datos de un objeto se guardan «dentro de una cápsula», cerrados al resto del programa, y solo se pueden consultar o cambiar a través de los métodos que la clase decide ofrecer. Esos métodos son la ventanilla: hacen cumplir las reglas.

Encapsular es ocultar el estado interno de un objeto (sus atributos) y exponer solo un conjunto de operaciones seguras (sus métodos públicos). Así, el objeto es el único responsable de que sus datos sean válidos, y el resto del programa no depende de cómo están guardados por dentro.

Otra imagen: el control remoto de la televisión. Tiene botones para subir el volumen, pero no te deja poner el volumen en −8 ni en 3000. No sabes (ni te importa) cómo está hecho el circuito; solo usas los botones, y los botones no te dejan romper nada.

Los modificadores de acceso

Java controla quién puede ver cada atributo, método o clase con unas palabras que se ponen al principio de la declaración, llamadas modificadores de acceso. Hay cuatro niveles:

ModificadorQuién puede usarloAnalogíaEjemplo en el Totito
privateSolo el código escrito dentro de la misma clase.Tu diario personal.private char[][] casillas; en Tablero
(nada: acceso de paquete)Cualquier clase del mismo paquete.La refrigeradora de la casa: la usa toda la familia, no los vecinos.void setConConfeti(boolean conConfeti) en PantallaResultado.TarjetaConConfeti

Un paquete es una carpeta lógica que agrupa clases relacionadas (por ejemplo, java.util o javax.swing, de donde vienen los import que viste en el capítulo 11). El Totito no declara paquete: todas sus clases están en el «paquete por defecto» (en NetBeans, <default package>), así que para ellas el acceso de paquete equivale casi a público. Por eso el Totito escribe private de forma explícita en todo lo que quiere esconder. protected tiene sentido con la herencia, y lo retomarás en el capítulo 22.

Símbolo por símbolo

    private char[][] casillas;
  • private — el modificador: solo los métodos de Tablero pueden leer o escribir este atributo.
  • char[][] — el tipo: una matriz de caracteres (capítulo 15).
  • casillas — el nombre del atributo.
  • ; — fin de la declaración.

El modificador siempre va primero. Si hay varios modificadores (private static final, por ejemplo), el de acceso suele ir al principio por costumbre. También se aplica a métodos (private void alPulsarCasilla(...)), a constructores (private BotonNeon(...), capítulo 20) y a clases (public class Tablero).

La cuenta bien hecha

Ahora la versión encapsulada (CuentaSegura.java). Los datos son privados y la única forma de mover dinero es por la ventanilla:

public class CuentaSegura {

    public static void main(String[] args) {
        Cuenta cuenta = new Cuenta("Marta");
        cuenta.depositar(1000);
        System.out.println("Retirar 1500: " + cuenta.retirar(1500));
        System.out.println("Retirar 300:  " + cuenta.retirar(300));
        System.out.println("Depositar -50: " + cuenta.depositar(-50));
        System.out.println(cuenta.getTitular() + " tiene Q" + cuenta.getSaldo());
    }
}

class Cuenta {
    private final String titular;
    private double saldo;

    public Cuenta(String titular) {
        this.titular = titular;
    }

    public boolean depositar(double monto) {
        if (monto <= 0) {
            return false;
        }
        saldo = saldo + monto;
        return true;
    }

    public boolean retirar(double monto) {
        if (monto <= 0 || monto > saldo) {
            return false;
        }
        saldo = saldo - monto;
        return true;
    }

    public String getTitular() {
        return titular;
    }

    public double getSaldo() {
        return saldo;
    }
}
Retirar 1500: false
Retirar 300:  true
Depositar -50: false
Marta tiene Q700.0

Observa tres decisiones de diseño:

  1. No hay setSaldo. El saldo no se «pone»; cambia solo por depósitos y retiros, que son las operaciones que tienen sentido en un banco. Cada una revisa sus reglas antes de tocar el dato.
  2. Los métodos avisan si rechazan algo devolviendo false. Quien llama decide qué hacer (mostrar un mensaje, por ejemplo). Otra opción es lanzar una excepción; las verás en el capítulo 26.
  3. El titular es final: se fija en el constructor y nunca cambia. Más abajo verás por qué eso es tan útil.

La gran ganancia: ahora la regla «el saldo nunca es negativo» se cumple siempre, y para estar seguro de ello solo tienes que leer una clase de 30 líneas, no el programa entero.

Getters y setters

Cuando un dato privado sí debe poder leerse desde fuera, se ofrece un método que lo devuelve. A ese método se le llama getter (del inglés get, «obtener»), y si se permite cambiarlo, el método que lo cambia es un setter (set, «poner»). Los nombres siguen una convención que respetan casi todos los programas Java del mundo:

  • getNombre() para leer el atributo nombre;
  • setNombre(String nombre) para cambiarlo;
  • isActivo() (o, en español, nombres como estaAprobado() o esTurnoDeIA()) para los boolean.

En el Totito se mezcla el prefijo inglés get/set (porque es una convención que reconocen las herramientas y otros programadores) con el resto del nombre en español: getNombre, getFicha, getTablero, setOyente, setInteractivo. Es una decisión común en equipos que programan en español.

Anatomía de un getter

    public String getNombre() {
        return nombre;
    }
  • public — se puede llamar desde cualquier clase: es la ventanilla.
  • String — el tipo que devuelve, el mismo del atributo.
  • getNombre — el nombre, según la convención.
  • () — no recibe nada.
  • return nombre; — devuelve el valor del atributo de este objeto.

Un setter con reglas

Un setter que solo hace this.nota = nota; no protege nada: es casi lo mismo que un atributo público. El valor de un setter está en lo que revisa o provoca. En un sistema escolar (Escuela.java):

public class Escuela {

    public static void main(String[] args) {
        Alumno alumno = new Alumno("Sofia");
        alumno.setNota(88);
        System.out.println("Poner 150: " + alumno.setNota(150));
        System.out.println("Poner -5:  " + alumno.setNota(-5));
        System.out.println(alumno.getNombre() + " tiene " + alumno.getNota()
                + (alumno.estaAprobado() ? " (aprobada)" : " (reprobada)"));
    }
}

class Alumno {
    public static final int NOTA_MINIMA = 61;

    private final String nombre;
    private int nota;

    public Alumno(String nombre) {
        this.nombre = nombre;
    }

    public String getNombre() {
        return nombre;
    }

    public int getNota() {
        return nota;
    }

    /** Solo acepta notas de 0 a 100. Devuelve false si la rechaza. */
    public boolean setNota(int nota) {
        if (nota < 0 || nota > 100) {
            return false;
        }
        this.nota = nota;
        return true;
    }

    public boolean estaAprobado() {
        return nota >= NOTA_MINIMA;
    }
}

Fíjate en estaAprobado(): no es el getter de ningún atributo, sino una pregunta calculada. Quien usa Alumno no necesita saber que la nota mínima es 61 (en Guatemala es lo habitual en muchos colegios; en otro país podría ser 60 o 70). Si cambia, cambia una línea en un solo lugar.

Setters que hacen algo más: los del Totito

En la interfaz del Totito, varios setters no se limitan a guardar el valor: además piden que el componente se vuelva a dibujar. Por ejemplo, en src/PanelTablero.java (capítulo 48):

    public void setInteractivo(boolean interactivo) {
        this.interactivo = interactivo;
        actualizarCursor();
        repaint();
    }

Si interactivo fuera un atributo público y alguien escribiera tablero.interactivo = true;, el valor cambiaría pero la pantalla no: el cursor seguiría siendo la flecha normal y nada se repintaría hasta que, por casualidad, otra cosa provocara un dibujo. El setter garantiza que «cambiar el dato» y «actualizar lo que se ve» ocurran siempre juntos. Lo mismo hacen Rotulo.setTexto (capítulo 46) y TarjetaJugador.setComputadora (capítulo 49), que además guarda lo que el usuario había escrito para devolvérselo si vuelve al modo de dos jugadores.

Cuándo NO poner un setter

Un error muy común al empezar es generar automáticamente un getter y un setter para cada atributo (NetBeans hasta tiene un menú para hacerlo). Eso devuelve la puerta trasera, solo que más larga. Pregúntate por cada atributo:

  • ¿Tiene que verlo alguien de fuera? Si no, ni getter.
  • ¿Tiene sentido que alguien lo cambie directamente? Muchas veces no: el saldo cambia por depósitos; las casillas cambian por jugadas; el nombre de un jugador no cambia a media partida.
  • Si sí puede cambiar, ¿qué reglas debe cumplir el valor nuevo y qué más debe ocurrir al cambiarlo?

En vez de pedir los datos a un objeto para decidir tú, pídele que haga el trabajo: no hagas if (cuenta.getSaldo() >= monto) cuenta.setSaldo(cuenta.getSaldo() - monto); desde fuera; llama cuenta.retirar(monto) y deja que la cuenta decida. A esta idea se le llama «dile, no le preguntes» (tell, don't ask).

Por qué casillas es private en el Tablero

Este es el comienzo de src/Tablero.java, la primera clase que escribirás en el capítulo 29:

public class Tablero {

    public static final char VACIA = ' ';

    private char[][] casillas;

    public Tablero() {
        casillas = new char[3][3];
        reiniciar();
    }

La matriz de casillas es privada, y nada en la clase la devuelve entera. Para leer hay obtenerCasilla(fila, columna); para escribir, marcarCasilla(fila, columna, ficha); para vaciar, reiniciar(). Imagina que fuera pública. Cualquier clase podría hacer cualquiera de estas cosas:

  • tablero.casillas[1][1] = 'O'; encima de una X: hacer trampa borrando la ficha del rival.
  • tablero.casillas[1][1] = 'Z';: una ficha que no existe, y verificarGanador() podría declarar ganador a «Z».
  • tablero.casillas[3][0] = 'X';: un índice fuera de rango, y el programa se cae con ArrayIndexOutOfBoundsException.
  • tablero.casillas = new char[4][4];: cambiar el tamaño, y los ciclos de 0 a 2 dejarían de revisar la cuarta fila.
  • tablero.casillas = null;: y la siguiente jugada termina en un NullPointerException.

Y hay una segunda razón, igual de importante: libertad para cambiar por dentro. Hoy el tablero es un char[3][3]. Mañana podrías guardarlo como un arreglo de 9 posiciones, o como un texto de 9 letras. Como nadie de fuera toca casillas, solo tendrías que reescribir los métodos de Tablero; Partida, IA_Minimax, PanelTablero y PruebaConsola seguirían llamando a obtenerCasilla(fila, columna) sin enterarse del cambio. Si casillas fuera público y diez clases lo usaran directamente, cambiarlo significaría corregir diez clases.

Empieza por private La regla práctica: todo atributo nace private. Solo abres algo cuando hay un motivo claro, y entonces lo abres de la forma más estrecha posible (un getter mejor que un setter; un método con reglas mejor que un setter). En todo el Totito no hay un solo atributo de instancia público; lo único público que no es un método son constantes static final como Tablero.VACIA, que no se pueden cambiar (capítulo 20).

Invariantes: las promesas de una clase

Un invariante es una condición que la clase promete que siempre es cierta para cualquiera de sus objetos, pase lo que pase, desde que el constructor termina. Es como la regla de un portero de edificio: «aquí no entra nadie sin anotarse». Si el portero la cumple siempre, quien está dentro puede confiar en que todos los que ve se anotaron.

Los invariantes del Tablero son:

  1. Siempre hay exactamente 3×3 casillas.
  2. Cada casilla contiene VACIA o una ficha.
  3. Una casilla ocupada no se vuelve a ocupar (solo reiniciar() la vacía).

El constructor establece los dos primeros (crea la matriz de 3×3 y la llena de VACIA con reiniciar()), y el único método que escribe una ficha los defiende. Es marcarCasilla:

    public boolean marcarCasilla(int fila, int columna, char ficha) {
        if (fila < 0 || fila > 2 || columna < 0 || columna > 2) {
            return false;
        }
        if (casillas[fila][columna] != VACIA) {
            return false;
        }
        casillas[fila][columna] = ficha;
        return true;
    }
  • El primer if es el portero de los límites: con los operadores || (capítulo 13) rechaza cualquier fila o columna fuera de 0 a 2. Si no estuviera, una jugada en la fila 3 haría caer el programa.
  • El segundo if es el portero de la regla del juego: si la casilla no está vacía, no se toca. Si no estuviera, un doble clic sobre una X la convertiría en O.
  • Solo si pasa los dos controles se escribe la ficha y se responde true. A esta forma de escribir (comprobar primero, salir pronto con return, y dejar el trabajo para el final) se le llama cláusulas de guarda.

Compruébalo con una versión del tablero que copia esas mismas líneas (TableroProtegido.java):

public class TableroProtegido {

    public static void main(String[] args) {
        Tablero tablero = new Tablero();
        System.out.println("X en 1,1 -> " + tablero.marcarCasilla(1, 1, 'X'));
        System.out.println("O en 1,1 -> " + tablero.marcarCasilla(1, 1, 'O'));
        System.out.println("O en 3,0 -> " + tablero.marcarCasilla(3, 0, 'O'));
        System.out.println("O en 0,-1 -> " + tablero.marcarCasilla(0, -1, 'O'));
        System.out.println("O en 0,0 -> " + tablero.marcarCasilla(0, 0, 'O'));
        System.out.println("Casilla 1,1 = " + tablero.obtenerCasilla(1, 1));
        System.out.println("Casilla 0,0 = " + tablero.obtenerCasilla(0, 0));
    }
}

class Tablero {
    public static final char VACIA = ' ';

    private char[][] casillas;

    public Tablero() {
        casillas = new char[3][3];
        for (int fila = 0; fila < 3; fila++) {
            for (int columna = 0; columna < 3; columna++) {
                casillas[fila][columna] = VACIA;
            }
        }
    }

    public boolean marcarCasilla(int fila, int columna, char ficha) {
        if (fila < 0 || fila > 2 || columna < 0 || columna > 2) {
            return false;
        }
        if (casillas[fila][columna] != VACIA) {
            return false;
        }
        casillas[fila][columna] = ficha;
        return true;
    }

    public char obtenerCasilla(int fila, int columna) {
        return casillas[fila][columna];
    }
}

O en 3,0 -> false

La O que intentó pisar la X fue rechazada, igual que las jugadas fuera del tablero, y la X sigue en su sitio. Gracias a esto, el resto del juego puede confiar a ciegas: verificarGanador() no necesita preguntarse si hay letras raras, y la IA del capítulo 31 puede llamar a marcarCasilla sobre sus copias sin miedo.

Los invariantes de la Partida

Partida (capítulo 38) se monta encima del tablero y agrega sus propias promesas: los turnos se alternan, una partida terminada no acepta más jugadas y el marcador solo sube cuando de verdad alguien gana. Todo eso vive en su método jugar, y por eso turno, estado, victorias y empates son privados:

    public boolean jugar(int fila, int columna) {
        if (estado != Estado.EN_CURSO) {
            return false;
        }
        if (!tablero.marcarCasilla(fila, columna, jugadores[turno].getFicha())) {
            return false;
        }

La primera guarda impide jugar después de una victoria (sin ella, alguien podría seguir poniendo fichas sobre un tablero ya ganado y sumar dos victorias en una misma partida). La segunda delega en el portero del tablero: si la casilla no vale, la partida tampoco cambia de turno. La pantalla de juego (capítulo 59) solo tiene que llamar partida.jugar(fila, columna) y redibujar si devolvió true; no repite ni una regla.

Inmutabilidad: el Jugador que no cambia

Algunos objetos no deberían cambiar nunca después de nacer. Tu fecha de nacimiento, el número de serie de una computadora o un billete de 20 quetzales: si quieres «otro valor», es otro objeto. Un objeto así se llama inmutable.

Jugador es inmutable. Mira de nuevo src/Jugador.java (capítulo 30):

public class Jugador {

    private final String nombre;
    private final char ficha;

    public Jugador(String nombre, char ficha) {
        this.nombre = nombre;
        this.ficha = ficha;
    }

Cada atributo lleva dos protecciones:

  • private: nadie de fuera puede tocarlo.
  • final: ni siquiera la propia clase puede cambiarlo después del constructor. Se le asigna valor una sola vez y queda fijo. (El capítulo 20 cuenta todos los usos de final.)

Y no hay ningún setter. El compilador hace cumplir esto con dos errores distintos. Si alguien agrega a Jugador un método para cambiar el nombre:

    public void cambiarNombre(String nuevo) {
        this.nombre = nuevo;
    }
CambiarNombre.java:19: error: cannot assign a value to final variable nombre
        this.nombre = nuevo;
            ^
1 error

Y si un constructor se olvida de darle valor a un atributo final (aquí, un constructor que solo recibe el nombre):

    public Jugador(String nombre) {
        this.nombre = nombre;
    }
OlvidarFicha.java:14: error: variable ficha might not have been initialized
    }
    ^
1 error

«La variable ficha podría no haber sido inicializada». Es decir, final obliga a que cada jugador nazca completo: no puede existir un jugador sin ficha.

Por qué conviene que el jugador sea inmutable

El mismo objeto Jugador lo comparten muchas partes del juego a la vez: la Partida lo guarda en su arreglo jugadores, el PanelMarcador lee su nombre y su ficha para dibujar el marcador, la pantalla de juego escribe «Turno de Ana» y la PantallaResultado escribe «¡Ganó Ana!». Recuerda del capítulo 18 que todos ellos tienen referencias al mismo objeto. Si alguno pudiera cambiar la ficha de Ana de X a O a media partida, los demás verían el cambio sin aviso: el tablero tendría X de una jugadora que ahora «juega con O», y verificarGanador() declararía un ganador que no corresponde a nadie. Con un objeto inmutable puedes repartir referencias con total tranquilidad: nadie puede estropearlo.

Para empezar otra partida con otros nombres no se modifica el jugador: PantallaConfiguracion crea dos Jugador nuevos. Crear objetos es barato; perseguir un error de datos compartidos, carísimo.

Ya conoces otra clase inmutable: String. Por eso texto.toUpperCase() no cambia texto, sino que devuelve un String nuevo (capítulo 17). IA_Minimax sigue la misma idea: sus dos fichas, fichaIA y fichaJugador, son private final.

final no siempre significa «no cambia nada» En Partida está la línea private final int[] victorias = new int[2]; y, sin embargo, jugar hace victorias[turno]++. ¿Cómo? final fija la referencia: la variable victorias apuntará siempre al mismo arreglo. Pero el contenido de ese arreglo sí puede cambiar. Lo mismo con private final Tablero tablero: siempre es el mismo tablero, pero sus casillas cambian con cada jugada. Un objeto solo es inmutable si todos sus atributos son final y además son primitivos u objetos inmutables (como String y char en Jugador).

Fugas: cuando un getter abre la bóveda

Ojo con una trampa sutil. Poner private en un atributo no sirve de mucho si después un getter entrega la referencia a ese mismo objeto mutable: quien la recibe puede modificar el original por dentro. A eso se le llama una fuga de encapsulamiento. Es como si el cajero, en vez de darte tus billetes, te prestara la llave de la bóveda.

Con arreglos se ve muy claro (FugaDeArreglo.java):

import java.util.Arrays;

public class FugaDeArreglo {

    public static void main(String[] args) {
        Boleta boleta = new Boleta(new int[]{85, 90, 78});

        int[] prestadas = boleta.getNotasConFuga();
        prestadas[0] = 0;   // alguien "solo queria mirar"...
        System.out.println("Tras la fuga:  " + Arrays.toString(boleta.getNotasSeguras()));

        int[] copia = boleta.getNotasSeguras();
        copia[1] = 0;       // esto solo cambia la copia
        System.out.println("Tras la copia: " + Arrays.toString(boleta.getNotasSeguras()));
    }
}

class Boleta {
    private final int[] notas;

    public Boleta(int[] notas) {
        this.notas = notas.clone();          // guardo mi propia copia
    }

    /** MAL: entrega la referencia al arreglo interno. */
    public int[] getNotasConFuga() {
        return notas;
    }

    /** BIEN: entrega una copia; el original queda protegido. */
    public int[] getNotasSeguras() {
        return notas.clone();
    }
}
Tras la fuga:  [0, 90, 78]
Tras la copia: [0, 90, 78]

El 85 se convirtió en 0 a través del getter con fuga, aunque notas es private final. En cambio, modificar lo que devolvió getNotasSeguras() no afectó a la boleta: el segundo 90 sigue intacto. El método clone() de un arreglo crea uno nuevo con los mismos valores. Fíjate también en el constructor: guarda un clone() de lo que recibe, para que quien le pasó el arreglo no pueda cambiarlo después desde fuera. A esto se le llama copia defensiva.

La fuga que el Totito acepta, y por qué

Seamos honestos: el Totito tiene una fuga parecida. Partida ofrece:

    public Tablero getTablero() {
        return tablero;
    }

Devuelve el tablero real. Con él, cualquiera podría saltarse los turnos de la partida llamando marcarCasilla directamente. Este programa lo demuestra con versiones mini de las dos clases (TrampaPorElGetter.java):

public class TrampaPorElGetter {

    public static void main(String[] args) {
        MiniPartida partida = new MiniPartida();
        partida.jugar(1, 1);                              // X juega bien, por la puerta
        System.out.println("Turno de: " + partida.getFichaEnTurno());

        // Truco: saltarse a la partida y escribir en su tablero
        partida.getTablero().marcarCasilla(0, 0, 'X');
        partida.getTablero().marcarCasilla(2, 2, 'X');

        System.out.println("Turno de: " + partida.getFichaEnTurno() + " (la partida no se entero)");
        partida.getTablero().imprimir();
    }
}

class MiniPartida {
    private final Tablero tablero = new Tablero();
    private char fichaEnTurno = 'X';

    public boolean jugar(int fila, int columna) {
        if (!tablero.marcarCasilla(fila, columna, fichaEnTurno)) {
            return false;
        }
        fichaEnTurno = fichaEnTurno == 'X' ? 'O' : 'X';
        return true;
    }

    public char getFichaEnTurno() {
        return fichaEnTurno;
    }

    public Tablero getTablero() {
        return tablero;                                   // entrega el tablero REAL
    }
}

class Tablero {
    private final char[][] casillas = {
        {' ', ' ', ' '}, {' ', ' ', ' '}, {' ', ' ', ' '}
    };

    public boolean marcarCasilla(int fila, int columna, char ficha) {
        if (fila < 0 || fila > 2 || columna < 0 || columna > 2 || casillas[fila][columna] != ' ') {
            return false;
        }
        casillas[fila][columna] = ficha;
        return true;
    }

    public void imprimir() {
        for (char[] fila : casillas) {
            System.out.println(" " + fila[0] + " | " + fila[1] + " | " + fila[2]);
        }
    }
}

Tres X en diagonal, y la partida sigue creyendo que le toca a O. El tablero protegió sus reglas (ninguna casilla se pisó), pero las reglas de la partida (los turnos) quedaron fuera de juego porque alguien entró por el tablero en vez de por la partida.

¿Por qué el Totito lo deja así? Porque en el juego real getTablero() solo se usa para leer: PantallaJuego y PantallaResultado lo pasan a PanelTablero.mostrar(...) para dibujarlo, y nadie más lo pide. Es un programa pequeño escrito por una sola persona, y la alternativa tiene un costo. Pero conviene que conozcas las tres formas de cerrar esa fuga, para cuando el programa crezca:

  1. Devolver una copia: return tablero.obtenerCopia();. Seguro y sencillo; cuesta crear un tablero nuevo en cada llamada (en el Totito sería insignificante).
  2. Ofrecer solo lo necesario: en vez de entregar el tablero, que Partida tenga su propio obtenerCasilla(fila, columna) que pregunte al tablero.
  3. Entregar una vista de solo lectura: una interfaz con obtenerCasilla y sin marcarCasilla. Las interfaces llegan en el capítulo 24.

Y fíjate en que el Totito sí se protege en el otro sentido. PanelTablero.mostrar (capítulo 48) no se guarda la referencia al tablero: copia cada casilla a su propia matriz fichas, con fichas[fila][columna] = tablero.obtenerCasilla(fila, columna);. Así, el dibujo nunca depende de un objeto que otro podría cambiar mientras Swing está pintando. Y el constructor de Partida hace this.jugadores = new Jugador[]{jugador1, jugador2};: crea su propio arreglo en lugar de aceptar uno de fuera que alguien podría modificar después. Son copias defensivas, igual que la de Boleta.

También se encapsulan los métodos

private no es solo para atributos. Un método privado es un «ayudante interno»: lo usa la clase para organizar su trabajo, pero no forma parte de lo que ofrece al resto del programa. En el Totito:

  • IA_Minimax.minimax(...) (capítulo 31) es private: hacia fuera, la IA solo ofrece calcularMejorJugada(tablero). Cómo piense por dentro es asunto suyo.
  • Tema.elegirFamilia() (capítulo 40) es private: se usa una sola vez, al cargar la clase, para escoger la fuente.
  • PantallaJuego.alPulsarCasilla, despuesDeJugada, programarTurnoIA y esperar (capítulo 59) son privados: son los engranajes de la pantalla. Lo público es comenzar(partida).

Cada método público es una promesa: otras clases lo van a usar y, si mañana lo cambias o lo borras, se rompen. Un método privado lo puedes renombrar, partir en dos o eliminar sin miedo, porque sabes que nadie de fuera lo usa. Cuanto menos público tenga una clase, más fácil es mejorarla.

¿Qué habría pasado sin encapsulamiento?

La primera ventana del Totito, JuegoMain (capítulo 33), ya usa Tablero y Jugador a través de sus métodos. Gracias a eso, cuando en la Parte VII se construye la interfaz de neón, esas clases se reutilizan tal cual, sin cambiar una sola línea, como dice el comentario al inicio de Partida.java: «Reutiliza tal cual las clases originales del proyecto». Si JuegoMain hubiera metido la mano en casillas directamente, cualquier cambio en el tablero habría obligado a revisar también la ventana vieja, y la nueva interfaz habría tenido que repetir todas las validaciones. El encapsulamiento es lo que permite que una clase escrita hoy siga sirviendo, sin tocarla, en el programa de mañana.

Resumen

  • Encapsular es ocultar los datos de un objeto y ofrecer solo operaciones que respetan sus reglas: la bóveda cerrada y la ventanilla abierta.
  • Los modificadores de acceso son private (solo la clase), acceso de paquete (sin palabra), protected (paquete e hijas) y public (todos). Empieza siempre por private.
  • Los getters y setters siguen la convención getX/setX; un setter vale por lo que valida o provoca, y muchas veces lo correcto es no tener setter, sino operaciones con sentido (depositar, marcarCasilla).
  • Un invariante es una promesa que la clase cumple siempre; Tablero.marcarCasilla la defiende con cláusulas de guarda que rechazan jugadas fuera de rango o en casillas ocupadas.
  • Jugador es inmutable gracias a private final y a no tener setters; por eso se puede compartir sin peligro entre la partida, el marcador y las pantallas.
  • final fija la referencia, no el contenido: un arreglo final puede cambiar por dentro.
  • Un getter que devuelve un objeto mutable interno provoca una fuga; se cierra con copias defensivas, métodos más específicos o vistas de solo lectura.
Aplícalo fuera del Totito Cada vez que un dato tenga reglas, enciérralo y dale una ventanilla:
  • Banco: el saldo es privado y solo cambia con depositar, retirar y transferir, que validan montos y dejan registro. Nunca un setSaldo.
  • Escuela: Alumno.setNota rechaza valores fuera de 0 a 100, y el carné del alumno es final: no cambia nunca después de la inscripción.
  • Tienda: Producto.existencias es privado; vender(cantidad) no deja bajar de cero y reabastecer(cantidad) no acepta negativos. Un Producto con código y nombre final se puede compartir entre el inventario y las facturas.
  • Otro juego: la vida de un personaje es privada; recibirDanio(puntos) nunca la deja por debajo de 0 y curar(puntos) nunca por encima del máximo. La lista de enemigos se entrega como copia para que la pantalla no pueda borrar enemigos por error.
