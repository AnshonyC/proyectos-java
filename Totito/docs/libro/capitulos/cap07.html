Capítulo 7Configurar Git y GitHub

En este capítulo creas tu cuenta de GitHub, la proteges con verificación en dos pasos, le dices a Git quién eres y cómo debe comportarse en Windows, y conectas tu computadora con GitHub usando gh. Se hace una sola vez por computadora, y si queda bien hecho no vuelves a pensar en ello.

Antes de empezar: comprueba las herramientas

En el capítulo 4 instalaste Git y GitHub CLI con winget. Abre PowerShell (si lo tenías abierto desde antes de instalar, ciérralo y ábrelo de nuevo para que se actualice el PATH) y comprueba que los dos responden:

git --version
gh --version

Deberías ver algo parecido a esto (los números de versión pueden ser más altos; no importa):

git version 2.55.0.windows.5
gh version 2.102.0 (2026-09-30)
https://github.com/cli/cli/releases/tag/v2.102.0

El final .windows.5 indica que es Git for Windows, la versión de Git preparada para Windows. Si en lugar de eso PowerShell dice que git «no se reconoce como nombre de un cmdlet, función, archivo de script o programa ejecutable», vuelve al capítulo 4: casi siempre se arregla cerrando y abriendo PowerShell o reinstalando con winget.

Paso 1: crear tu cuenta de GitHub

GitHub es gratis para lo que harás en este libro (y para la mayoría de proyectos personales): repositorios públicos y privados ilimitados, pull requests, issues y releases.

  1. Abre el navegador y entra a https://github.com/signup.
  2. Escribe tu correo electrónico. Usa uno que revises y que vayas a conservar muchos años: ahí llegan los avisos de seguridad y es tu forma de recuperar la cuenta.
  3. Elige una contraseña larga. GitHub pide al menos 15 caracteres, o al menos 8 si incluye un número y una letra minúscula; cuanto más larga, mejor. No reutilices la de tu correo ni la de otra página.
  4. Elige tu nombre de usuario (en inglés, username). Piensa bien este: será la dirección de tu perfil (https://github.com/tu-usuario) y aparecerá en la dirección de todos tus repositorios, por ejemplo https://github.com/tu-usuario/totito. Consejos más abajo.
  5. Decide si quieres recibir correos de novedades (no hace falta).
  6. Resuelve la verificación de que eres una persona (un pequeño rompecabezas).
  7. GitHub te manda un código a tu correo. Cópialo en la página para confirmar la dirección.
  8. Si te pregunta por un plan, elige el gratuito (Free). Las preguntas sobre «para qué usarás GitHub» son opcionales; puedes saltarlas.
Cómo elegir tu nombre de usuario Piensa que algún día se lo vas a dar a una empresa como parte de tu currículum. Funciona bien tu nombre y apellido unidos con guion (ana-lopez), o una variante corta si ya está tomado (analopez-gt, alopezdev). Evita apodos que dentro de cinco años te den vergüenza, números al azar (xX_ana_99_Xx) y mayúsculas mezcladas. Se puede cambiar después, pero los enlaces viejos dejan de funcionar. En este libro usaremos ana-lopez como ejemplo: donde lo veas, pon el tuyo.

Paso 2: la verificación en dos pasos

La verificación en dos pasos (en inglés two-factor authentication, 2FA) significa que para entrar a tu cuenta no basta con la contraseña: además hace falta un código que solo tú tienes, normalmente en tu teléfono. Así, aunque alguien robe o adivine tu contraseña, no puede entrar.

¿Por qué tanta seguridad para un juego de totito? Porque tu cuenta de GitHub, con el tiempo, guardará todo tu código, quizás proyectos de trabajo, y la usarás para entrar a otros servicios. Además, GitHub exige la verificación en dos pasos a quienes suben código: si no la activas al crear la cuenta, en algún momento te lo pedirá y no podrás seguir hasta hacerlo. Mejor dejarla lista desde el principio.

Lo más cómodo es usar una aplicación autenticadora en el teléfono, como Google Authenticator o Microsoft Authenticator (gratis en la tienda de tu teléfono). Estas aplicaciones generan un código de 6 dígitos que cambia cada 30 segundos.

  1. En GitHub, haz clic en tu foto (arriba a la derecha) → Settings (Configuración).
  2. En el menú de la izquierda, entra a Password and authentication.
  3. Pulsa Enable two-factor authentication.
  4. GitHub muestra un código QR. En la aplicación autenticadora del teléfono pulsa «+» o «Agregar cuenta» → «Escanear código QR» y apunta la cámara a la pantalla.
  5. La aplicación muestra una entrada «GitHub» con un número de 6 dígitos. Escríbelo en la página de GitHub para comprobar que funciona.
  6. GitHub te muestra los códigos de recuperación (recovery codes): una lista de códigos de un solo uso para entrar si pierdes el teléfono. Descárgalos y guárdalos en un lugar seguro fuera de la computadora (impresos en un cajón, o en un gestor de contraseñas). Sin el teléfono y sin estos códigos, puedes perder tu cuenta para siempre.
  7. Confirma que los guardaste y termina.

Desde ahora, cuando inicies sesión en GitHub en un navegador nuevo, te pedirá la contraseña y luego el código del teléfono. GitHub también ofrece otras opciones (llaves de acceso o passkeys, la aplicación GitHub Mobile, mensajes de texto en algunos países); puedes agregarlas como respaldo desde la misma página.

Los códigos de recuperación son tan valiosos como tu contraseña No los guardes en la carpeta del proyecto, no los subas a ningún repositorio, no se los mandes a nadie. Quien los tenga puede entrar a tu cuenta sin tu teléfono.

Paso 3: tu correo privado de GitHub

Cada commit que hagas llevará grabado un nombre y un correo (lo configuras en el paso 4). Si el repositorio es público, cualquiera puede ver ese correo, y hay robots que recorren GitHub recolectando direcciones para mandar spam. GitHub te da una dirección especial que no recibe correo pero que identifica tus commits como tuyos:

  1. En Settings entra a Emails.
  2. Activa Keep my email addresses private («mantener privadas mis direcciones de correo»).
  3. Justo debajo aparece tu dirección privada, con esta forma: 12345678+ana-lopez@users.noreply.github.com (el número es el identificador de tu cuenta). Cópiala: la usarás en el siguiente paso.
  4. Opcional pero recomendable: activa también Block command line pushes that expose my email. Si por error configuras tu correo real, GitHub rechazará el push y te avisará, en lugar de publicarlo.

Si prefieres usar tu correo real (por ejemplo, para que una empresa te encuentre), también está bien; solo tenlo en cuenta al hacer públicos tus repositorios.

Paso 4: decirle a Git quién eres (git config)

Git guarda su configuración en archivos de texto, y el comando para leerla y cambiarla es git config. Hay tres niveles, del más general al más particular:

NivelOpciónDónde se guarda (Windows)A qué afecta
Sistema--systemC:\Program Files\Git\etc\gitconfigA todos los usuarios de la PC. Lo escribe el instalador; no lo toques.
Global--globalC:\Users\<tu-usuario>\.gitconfigA todos tus repositorios. Aquí va casi todo.
Local--local (o nada).git\config dentro de cada proyectoSolo a ese repositorio.

Si un ajuste aparece en varios niveles, gana el más particular: local antes que global, global antes que sistema. Así puedes, por ejemplo, usar tu correo personal en todos tus proyectos (global) y el del trabajo en un repositorio concreto (local).

Tu nombre y tu correo

Escribe estos dos comandos con tus datos (las comillas son necesarias porque el nombre lleva espacio):

git config --global user.name "Ana López"
git config --global user.email "12345678+ana-lopez@users.noreply.github.com"

Pieza por pieza:

  • git config: el subcomando de Git para la configuración.
  • --global: guárdalo en tu archivo personal, para todos tus proyectos.
  • user.name: el nombre del ajuste. Los ajustes de Git tienen la forma sección.nombre; aquí la sección es user (usuario) y el ajuste es name (nombre).
  • "Ana López": el valor. Usa tu nombre real, como quieres que aparezca como autora o autor de tus commits. No es tu nombre de usuario de GitHub (aunque puede coincidir).
  • user.email: el correo que irá en cada commit. GitHub lo usa para asociar tus commits a tu cuenta y mostrar tu foto junto a ellos; por eso debe ser un correo registrado en tu cuenta o tu dirección noreply.

Los comandos no muestran nada si salen bien. Así es Git: el silencio significa «hecho».

El nombre y el correo no son una contraseña user.name y user.email son solo una firma que Git escribe en cada commit; no te dan acceso a nada. Quien sube los cambios a GitHub se identifica de otra forma (con gh auth login, en el paso 5). Por eso también puedes hacer commits sin internet y sin cuenta.

Si te saltas este paso, el primer git commit fallará con un mensaje como este, que ahora ya sabes leer: «por favor, dime quién eres», y te sugiere los dos comandos de arriba.

Author identity unknown

*** Please tell me who you are.

Run

  git config --global user.email "you@example.com"
  git config --global user.name "Your Name"

to set your account's default identity.
Omit --global to set the identity only in this repository.

fatal: unable to auto-detect email address (got 'ana@LAPTOP-ANA.(none)')

La rama principal se llama main

git config --global init.defaultBranch main

Cuando creas un repositorio nuevo (git init, capítulo 8), Git crea la primera rama. Durante años se llamó master; hoy GitHub y la mayoría de proyectos usan main, y es el nombre que usa este libro. Este ajuste (init.defaultBranch, «rama por defecto al iniciar») hace que tus repositorios nuevos empiecen directamente con main. Sin él, según cómo se instaló Git, podrías terminar con una rama master en tu PC y una main en GitHub, que es un lío innecesario. (En el capítulo 8 verás además git init -b main, que pide main de forma explícita para un repositorio concreto; con los dos, no hay forma de equivocarse).

Los finales de línea en Windows: core.autocrlf

git config --global core.autocrlf true

Para entender este ajuste hay que saber algo que casi nadie te cuenta: al final de cada línea de un archivo de texto hay caracteres invisibles que indican «aquí termina la línea». Y no todos los sistemas usan los mismos:

SistemaFinal de líneaNombreCódigo
WindowsDos caracteres: retorno de carro + salto de líneaCRLF (Carriage Return + Line Feed)\r\n
Linux y macOSUn carácter: salto de líneaLF (Line Feed)\n

Los nombres vienen de las máquinas de escribir: «retorno de carro» era devolver el carro a la izquierda y «salto de línea» era bajar el papel un renglón. Windows heredó los dos; Linux y macOS se quedaron con uno.

¿Por qué importa? Si tú guardas Tablero.java con CRLF y un compañero en Linux lo guarda con LF, Git vería que todas las líneas del archivo cambiaron, aunque nadie tocó el código. El historial se llenaría de cambios falsos y aparecerían conflictos absurdos.

Con core.autocrlf true Git hace de traductor automático:

  • Al guardar en el repositorio (git add / git commit): convierte CRLF en LF. En el repositorio todo queda con LF, el estándar del mundo Git.
  • Al sacar archivos a tu carpeta (cuando cambias de rama, haces pull o clonas): convierte LF en CRLF, para que el Bloc de notas y los programas de Windows los vean bien.

Tú nunca notas nada, y tu repositorio funciona igual en Windows, Linux o macOS. El instalador de Git for Windows normalmente ya deja este ajuste activado a nivel de sistema; escribirlo en tu configuración global garantiza que esté, por si acaso.

A veces, al hacer git add, verás un aviso como este:

warning: in the working copy of 'README.md', LF will be replaced by CRLF the next time Git touches it

Traducción: «en tu copia de trabajo, el archivo README.md tiene finales LF; la próxima vez que Git lo toque, los cambiará por CRLF». Aparece cuando un archivo fue creado con finales de Linux (por ejemplo, por una herramienta o copiado de internet). No es un error y no tienes que hacer nada: es Git avisando de la traducción que va a hacer.

Para equipos mixtos: .gitattributes En proyectos donde colaboran personas con Windows, Linux y macOS, se suele agregar al repositorio un archivo .gitattributes con la línea * text=auto. Hace lo mismo que core.autocrlf, pero viaja con el repositorio, así que funciona aunque alguien no haya configurado su Git. Para el Totito no hace falta.

El editor de Git

Algunos comandos de Git necesitan que escribas un texto largo; por ejemplo, git commit sin la opción -m, o un git merge que crea un commit de fusión. En esos casos Git abre un editor de texto, espera a que escribas, guardes y cierres, y luego continúa.

El problema: el editor que Git for Windows trae configurado por defecto es Vim, un editor de terminal muy potente pero desconcertante si nunca lo usaste (no se sale con la X ni con Ctrl+C). Elige uno que conozcas:

# Opción A: el Bloc de notas de Windows
git config --global core.editor notepad
# Opción B: Visual Studio Code, si lo instalaste (capítulo 4)
git config --global core.editor "code --wait"
  • Con el Bloc de notas, cuando Git lo abra, escribe el mensaje, guarda con Ctrl+S y cierra la ventana: hasta que no la cierres, Git espera.
  • Con Visual Studio Code, la opción --wait («espera») es imprescindible: le dice a VS Code que no devuelva el control hasta que cierres la pestaña del mensaje. Sin ella, Git creería que ya terminaste y encontraría el mensaje vacío.
Bloc de notas con pestañas (Windows 11) El Bloc de notas nuevo de Windows 11 abre los archivos en pestañas. Si ya tenías otra ventana del Bloc de notas abierta, a veces el mensaje se abre como una pestaña más y Git no se entera de cuándo terminas; el síntoma es que Git dice Aborting commit due to empty commit message («cancelando el commit porque el mensaje está vacío») sin darte tiempo de escribir. Soluciones: cierra todas las ventanas del Bloc de notas antes de hacer el commit; o en el Bloc de notas ve a Configuración → «Apertura de archivos» y elige abrirlos en una ventana nueva; o usa VS Code. En el libro casi siempre escribiremos el mensaje con -m, así que el editor aparecerá poco.
Si ya te atrapó Vim Si alguna vez la terminal se llena de líneas que empiezan con ~ y no sabes salir, estás en Vim. Para guardar y salir: pulsa Esc, escribe :wq y Enter. Para salir sin guardar (y cancelar la operación): Esc, :q! y Enter.

Cómo se comporta git pull

git config --global pull.rebase false

Cuando traes cambios de GitHub con git pull y tú también tenías commits nuevos, Git tiene que juntar las dos historias. Hay varias formas de hacerlo, y las versiones recientes de Git, si no le dijiste cuál prefieres, se niegan a elegir y te muestran un aviso largo (You have divergent branches and need to specify how to reconcile them). Con pull.rebase false le dices: «júntalas con un merge normal», que es lo que verás en el capítulo 9 y lo más fácil de entender cuando empiezas.

Comprobar la configuración

git config --global --list
user.name=Ana López
user.email=12345678+ana-lopez@users.noreply.github.com
init.defaultbranch=main
core.autocrlf=true
core.editor=notepad
pull.rebase=false

Git muestra los nombres de los ajustes en minúsculas (init.defaultbranch): no te preocupes, Git no distingue mayúsculas en los nombres de ajustes. Si algo quedó mal escrito, vuelve a ejecutar el comando con el valor correcto y se sobrescribe. También puedes preguntar por un solo ajuste:

git config user.email

Y si quieres ver el archivo tal cual (es texto normal), ábrelo con el Bloc de notas:

notepad $HOME\.gitconfig
[user]
	name = Ana López
	email = 12345678+ana-lopez@users.noreply.github.com
[init]
	defaultBranch = main
[core]
	autocrlf = true
	editor = notepad
[pull]
	rebase = false

Cada sección va entre corchetes y debajo están sus ajustes. Puedes editarlo a mano, pero es más seguro usar git config, que no comete errores de formato.

Paso 5: conectar tu PC con GitHub (gh auth login)

Hasta ahora Git sabe tu nombre, pero GitHub no sabe que esta computadora es tuya. Cuando hagas git push, GitHub preguntará «¿y tú quién eres?». Desde 2021 GitHub ya no acepta tu contraseña para esto: exige un token (una especie de contraseña larga, generada para un uso concreto, que se puede revocar sin cambiar tu contraseña real). Crear y guardar tokens a mano es engorroso; GitHub CLI lo hace por ti.

gh auth login

El comando hace varias preguntas. Se responde con las flechas del teclado y Enter. Vamos una por una.

Pregunta 1: dónde usas GitHub

? Where do you use GitHub?  [Use arrows to move, type to filter]
> GitHub.com
  Other

«¿Dónde usas GitHub?». Elige GitHub.com, la página pública. Other es para empresas que tienen su propio servidor de GitHub (GitHub Enterprise). En versiones antiguas de gh la pregunta dice What account do you want to log into?, con las opciones GitHub.com y GitHub Enterprise Server: es lo mismo.

Pregunta 2: el protocolo

? What is your preferred protocol for Git operations on this host?  [Use arrows to move, type to filter]
> HTTPS
  SSH

«¿Qué protocolo prefieres para las operaciones de Git?». Un protocolo es el «idioma» con el que tu PC y GitHub se comunican. Elige HTTPS; más abajo te explico la diferencia con SSH y por qué HTTPS es lo más sencillo en Windows.

Pregunta 3: que Git use tus credenciales

? Authenticate Git with your GitHub credentials? (Y/n)

«¿Autenticar Git con tus credenciales de GitHub?». Responde Y (sí, o simplemente Enter, porque la mayúscula indica la respuesta por defecto). Esto es lo que hace que después git push funcione sin pedirte nada: gh se registra como el «ayudante de credenciales» de Git para github.com. Cada vez que Git necesite identificarse ante GitHub, le preguntará a gh, y gh le dará el token.

Pregunta 4: cómo iniciar sesión

? How would you like to authenticate GitHub CLI?  [Use arrows to move, type to filter]
> Login with a web browser
  Paste an authentication token

«¿Cómo quieres autenticarte?». Elige Login with a web browser (iniciar sesión con el navegador). La otra opción es para pegar un token que hayas creado a mano, algo que no necesitas.

El código de un solo uso

! First copy your one-time code: 1A2B-3C4D
Press Enter to open https://github.com/login/device in your browser...
  1. gh muestra un código de un solo uso de 8 caracteres (el tuyo será distinto). Anótalo o selecciónalo y cópialo.
  2. Pulsa Enter. Se abre el navegador en https://github.com/login/device. Si no se abre solo, abre tú esa dirección.
  3. Si no habías iniciado sesión en GitHub en ese navegador, inicia sesión (contraseña y código del teléfono).
  4. Escribe el código de 8 caracteres y pulsa Continue.
  5. GitHub te muestra que la aplicación GitHub CLI pide permiso para acceder a tu cuenta (repositorios, organizaciones, gists). Revisa que diga GitHub CLI y pulsa Authorize github (autorizar). Puede pedirte confirmar con tu contraseña o con el código del teléfono.
  6. La página dice que el dispositivo quedó conectado. Vuelve a PowerShell.
✓ Authentication complete.
- gh config set -h github.com git_protocol https
✓ Configured git protocol
✓ Logged in as ana-lopez

«Autenticación completa», «protocolo de Git configurado (HTTPS)», «sesión iniciada como ana-lopez». Listo.

El código es como una llave temporal Nunca escribas en github.com/login/device un código que te haya mandado otra persona («hola, pon este código para ganar un premio»): estarías dándole acceso a tu cuenta desde su computadora. Solo usa códigos que acabas de ver en tu propia terminal.

Comprobar que quedó bien

gh auth status
github.com
  ✓ Logged in to github.com account ana-lopez (keyring)
  - Active account: true
  - Git operations protocol: https
  - Token: gho_************************************
  - Token scopes: 'gist', 'read:org', 'repo', 'workflow'
  • Logged in to github.com account ana-lopez (keyring): sesión iniciada; keyring significa que el token se guardó en el Administrador de credenciales de Windows, el almacén cifrado de contraseñas del sistema, y no en un archivo de texto.
  • Git operations protocol: https: Git usará HTTPS.
  • Token: gho_****: el token, oculto con asteriscos a propósito. No necesitas verlo nunca.
  • Token scopes: los permisos del token. repo permite manejar tus repositorios (lo esencial para push); read:org leer tus organizaciones; gist crear gists (fragmentos de código); workflow modificar automatizaciones de GitHub Actions.

Si miras otra vez git config --global --list, verás unas líneas nuevas que agregó gh, del estilo credential.https://github.com.helper=!'C:\Program Files\GitHub CLI\gh.exe' auth git-credential. Son las que conectan Git con gh: déjalas tal cual.

HTTPS o SSH: dos formas de hablar con GitHub

Git puede comunicarse con GitHub de dos maneras. Cada repositorio de GitHub tiene una dirección para cada una:

HTTPS:  https://github.com/ana-lopez/totito.git
SSH:    git@github.com:ana-lopez/totito.git
HTTPSSSH
Cómo te identificasCon un token, que guarda y entrega gh (o el Administrador de credenciales de Git)Con un par de llaves: una privada que nunca sale de tu PC y una pública que subes a GitHub
PreparaciónNinguna extra: gh auth login ya lo dejó listoGenerar las llaves con ssh-keygen y subir la pública a GitHub
Puerto de red443, el mismo de las páginas web: funciona casi en cualquier red22: algunas redes de empresas, colegios o cafés lo bloquean
Ideal paraEmpezar, Windows, redes restringidasQuien usa varias computadoras o servidores Linux y quiere no depender de tokens

Las dos son igual de seguras si se usan bien. En este libro usamos HTTPS con gh porque no requiere ningún paso extra y funciona igual en todas las redes.

Si algún día quieres usar SSH

No hace falta para el Totito, pero así se hace, para que lo reconozcas cuando lo veas. Windows 10 y 11 ya traen el cliente de SSH:

# 1) Crear el par de llaves (Enter para aceptar la ubicación; luego una frase de paso)
ssh-keygen -t ed25519 -C "12345678+ana-lopez@users.noreply.github.com"
# 2) Dar a gh permiso para administrar llaves (abre el navegador como antes)
gh auth refresh -h github.com -s admin:public_key
# 3) Subir la llave PUBLICA (la que termina en .pub) a tu cuenta
gh ssh-key add $HOME\.ssh\id_ed25519.pub --title "Laptop de Ana"
# 4) Probar la conexion
ssh -T git@github.com

La primera vez, el paso 4 pregunta si confías en el servidor (Are you sure you want to continue connecting?): escribe yes. Si todo está bien, responde Hi ana-lopez! You've successfully authenticated, but GitHub does not provide shell access. («¡Hola! Te autenticaste bien, pero GitHub no da acceso a una terminal»), que es exactamente lo esperado.

La llave privada no se comparte jamás El archivo id_ed25519 (sin .pub) es tu llave privada: quien lo tenga puede hacerse pasar por ti ante GitHub. Nunca lo copies a un repositorio, ni lo mandes por correo. Solo el .pub se sube a GitHub.

Resumen

  • Tu cuenta de GitHub necesita un nombre de usuario pensado para el largo plazo y la verificación en dos pasos, con los códigos de recuperación guardados fuera de la PC.
  • La dirección noreply de GitHub protege tu correo real en los commits públicos.
  • git config --global guarda tus ajustes en C:\Users\<tu-usuario>\.gitconfig; los niveles son sistema, global y local, y gana el más particular.
  • user.name y user.email firman tus commits; no son una contraseña.
  • init.defaultBranch main hace que tus repos empiecen con main; core.autocrlf true traduce los finales de línea CRLF (Windows) ↔ LF (repositorio); core.editor evita quedar atrapado en Vim; pull.rebase false define cómo se juntan historias al hacer pull.
  • gh auth login (GitHub.com → HTTPS → Y → navegador → código) guarda un token en el Administrador de credenciales de Windows y conecta Git con GitHub. gh auth status lo comprueba.
  • HTTPS y SSH son igual de seguros; HTTPS con gh es lo más sencillo y es lo que usa el libro.
Aplícalo fuera del Totito Esta configuración es por computadora, no por proyecto: a partir de ahora sirve para todo lo que hagas.
  • Una segunda computadora (la del trabajo, una laptop nueva): repites los pasos 4 y 5 en ella, con el mismo nombre y correo, y tus commits se verán igual desde las dos.
  • Correo distinto para el trabajo: dentro del repositorio de la empresa ejecuta git config user.email "ana.lopez@empresa.com" (sin --global); solo ese repositorio usará el correo de la empresa.
  • Proyectos en GitLab o Bitbucket: git config y los finales de línea funcionan igual; solo cambia la herramienta de inicio de sesión (por ejemplo, GitLab tiene su propia CLI, glab auth login, con el mismo estilo).
  • Cualquier servicio que ofrezca verificación en dos pasos (tu correo, tu banco, tus redes sociales): actívala con la misma aplicación autenticadora y guarda sus códigos de recuperación igual que los de GitHub.
Ejercicios
  1. Ejecuta git config --global --list y comprueba que aparecen los seis ajustes de este capítulo. Luego ejecuta git config --show-origin user.name: ¿qué archivo te muestra? Pista: debería ser tu .gitconfig.
  2. Entra a https://github.com/tu-usuario y completa tu perfil: foto, nombre y una línea de biografía («Aprendiendo Java con el Totito»). Así se verá tu portada cuando alguien visite tus repositorios.
  3. Abre el Administrador de credenciales de Windows (búscalo en el menú Inicio como «Administrador de credenciales» → «Credenciales de Windows») y, en «Credenciales genéricas», busca una entrada cuyo nombre empiece con gh:github.com. No la borres ni la edites: solo comprueba que el token está guardado ahí y no en un archivo.
  4. Escribe en un papel, con tus palabras, qué hace core.autocrlf true en el git add y qué hace al cambiar de rama. Después explica por qué sin él un compañero con Linux vería «cambiadas» todas las líneas de tus archivos.
  5. (Reto) Ejecuta gh auth status y gh api user --jq .login. El segundo comando pide a la API de GitHub los datos de tu usuario y muestra solo el campo login. ¿Qué imprime? Pista: tu nombre de usuario; si es así, gh está hablando con GitHub correctamente.
