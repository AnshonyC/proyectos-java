Capítulo 5Crear el proyecto Totito

En este capítulo nace el Totito: creas su carpeta y sus subcarpetas, escribes los tres archivos que lo definen (pom.xml, .gitignore y README.md) entendiendo cada línea, lo abres en NetBeans, recorres la interfaz del editor y haces la primera compilación. Todavía no hay juego, pero sí hay un proyecto real, con la misma estructura que tendrá cuando esté terminado.

Qué es un proyecto y por qué empezar por aquí

Un programa no es un solo archivo: el Totito terminado tiene 29 archivos de código Java, tres utilidades, dos imágenes y varios archivos de configuración. Un proyecto es la carpeta que reúne todo eso, organizado de forma que tanto las personas como las herramientas sepan dónde está cada cosa: dónde está el código, qué versión de Java usar, cómo se llama el programa, qué clase lo arranca y qué archivos no hay que guardar en el historial.

Empezar por la estructura, antes que por el código, es lo que se hace en cualquier empresa: es como trazar los cimientos y las habitaciones de una casa antes de poner muebles. Si la estructura está bien desde el principio, cada archivo que agregues después tendrá su sitio, y las herramientas (NetBeans, Maven, Git, jpackage) funcionarán sin sorpresas.

Paso 1: las carpetas

Abre PowerShell y escribe:

cd $HOME\Proyectos
New-Item -ItemType Directory -Force Totito
cd Totito
New-Item -ItemType Directory -Force src, herramientas, recursos
ls

Ya conoces estos comandos del capítulo 3. La novedad es la cuarta línea: New-Item acepta varias rutas separadas por comas, así que crea las tres carpetas de una vez. El ls final debería mostrar:

    Directorio: C:\Users\ana\Proyectos\Totito

Mode                 LastWriteTime         Length Name
----                 -------------         ------ ----
d-----        12/10/2026     11:02                herramientas
d-----        12/10/2026     11:02                recursos
d-----        12/10/2026     11:02                src

A partir de ahora, todos los comandos del proyecto se ejecutan desde esta carpeta, $HOME\Proyectos\Totito. Si cierras PowerShell, al volver a abrirlo empieza por cd $HOME\Proyectos\Totito. Cada carpeta tiene un motivo:

CarpetaQué contendráPor qué aparte
srcEl código del juego: Tablero.java, Partida.java, PantallaMenu.java… Todo lo que forma parte del programa que se instala.src es la abreviatura de source, «código fuente». Es lo que Maven compila y mete en el .jar final.
herramientasProgramas auxiliares que te ayudan a construir el juego, pero que no son el juego: PruebaConsola.java (capítulo 32), VistaPrevia.java (capítulo 56) y GeneradorIcono.java (capítulo 64).Si estuvieran en src, viajarían dentro del programa instalado sin servirle de nada al jugador. Separarlos mantiene limpio el producto final.
recursosArchivos que no son código: el icono totito.ico y la imagen totito.png (capítulo 64).Los usa el empaquetador para fabricar el instalador; no forman parte del código.

Hay dos carpetas más que aparecerán solas y que no debes crear: target, donde Maven deja el resultado de cada compilación (la verás al final de este capítulo), y dist, donde dejarás el programa empaquetado en la Parte VIII.

Separar lo que se escribe de lo que se genera. En un proyecto hay archivos que escribes tú (el código, la configuración) y archivos que fabrica una herramienta a partir de ellos (las clases compiladas, el .jar, el instalador). Los primeros son valiosos y se guardan en Git; los segundos se pueden volver a fabricar en cualquier momento y no se guardan. Por eso viven en carpetas separadas (target, dist), fáciles de borrar e ignorar. Esta idea aparece en cualquier proyecto de software, en cualquier lenguaje.

Paso 2: qué es Maven

Antes de escribir el primer archivo, necesitas saber para quién lo escribes. Maven es una herramienta de construcción (build tool): un programa que sabe convertir un proyecto Java en un programa terminado. Construir implica varios pasos (borrar lo viejo, compilar cada archivo, empaquetarlo todo en un .jar…) y Maven los hace siempre igual, en el orden correcto, en cualquier computadora. NetBeans lo trae incluido: cuando pulses Clean and Build, NetBeans le pasará el trabajo a Maven.

Maven lee un único archivo de configuración, el pom.xml. POM significa Project Object Model, «modelo del proyecto»: es la ficha de identidad del proyecto y el conjunto de instrucciones para construirlo. Si una carpeta tiene un pom.xml, NetBeans la reconoce como proyecto Maven. Sin él, es solo una carpeta.

¿Por qué usar Maven y no simplemente el compilador javac? Para un archivo suelto, javac basta (lo usarás en el capítulo 11). Pero en un proyecto real, Maven aporta tres cosas: repetibilidad (todos construyen igual, con las mismas versiones), convención (cualquier programador Java del mundo que vea un pom.xml sabe cómo construir tu proyecto) y automatización (sabe descargar lo que necesita, empaquetar y mucho más). Es el estándar de la industria, junto con su pariente Gradle.

Paso 3: el pom.xml

Crear el archivo

Desde la carpeta del proyecto:

New-Item -ItemType File pom.xml
notepad pom.xml

La primera línea crea el archivo vacío; la segunda lo abre en el Bloc de notas. Crear el archivo antes de abrirlo evita una trampa clásica: si guardas un archivo nuevo desde el Bloc de notas, a veces le agrega .txt al final y terminas con pom.xml.txt, que Maven no reconoce. Escribe (o copia) exactamente este contenido, guarda con Ctrl+S y cierra el Bloc de notas:

<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 http://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>
    <groupId>com.mycompany</groupId>
    <artifactId>Totito</artifactId>
    <version>1.0-SNAPSHOT</version>
    <packaging>jar</packaging>
    <properties>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
        <!-- Funciona con JDK 17 o mas nuevo. -->
        <maven.compiler.release>17</maven.compiler.release>
        <!-- Clase que arranca el juego (boton Run de NetBeans). -->
        <exec.mainClass>TotitoApp</exec.mainClass>
    </properties>
    <build>
        <!-- El codigo vive en src/ (sin paquetes), no en src/main/java. -->
        <sourceDirectory>src</sourceDirectory>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.13.0</version>
            </plugin>
            <plugin>
                <!-- Deja el .jar ejecutable con doble clic o con java -jar. -->
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-jar-plugin</artifactId>
                <version>3.4.2</version>
                <configuration>
                    <archive>
                        <manifest>
                            <mainClass>TotitoApp</mainClass>
                        </manifest>
                    </archive>
                </configuration>
            </plugin>
        </plugins>
    </build>
</project>

Son 39 líneas. La segunda es muy larga: escríbela entera en un solo renglón. Los espacios del principio de cada línea (la sangría) no son obligatorios para Maven, pero hacen que se vea qué está dentro de qué; respétalos. Comprueba que se guardó bien:

ls
cat pom.xml

En la lista debe aparecer pom.xml (no pom.xml.txt) con un tamaño de unos 1700 bytes, y cat debe mostrar el contenido completo.

Lo mínimo de XML para leerlo

El pom.xml está escrito en XML (eXtensible Markup Language), un formato de texto para guardar datos organizados. Con cuatro ideas lo lees entero:

  • Etiquetas. Una palabra entre < y >. <version> es una etiqueta de apertura y </version>, con la barra, la etiqueta de cierre. Lo que hay entre ambas es el valor: <version>1.0-SNAPSHOT</version> significa «la versión es 1.0-SNAPSHOT». El conjunto se llama elemento.
  • Anidación. Un elemento puede contener otros, como cajas dentro de cajas. <properties> contiene tres elementos; <build> contiene <plugins>, que contiene dos <plugin>. Lo que se abre dentro de algo debe cerrarse dentro de ese algo, antes de que este se cierre.
  • Atributos. Datos extra dentro de la etiqueta de apertura, con la forma nombre="valor", como en la línea 2.
  • Comentarios. Todo lo que va entre <!-- y --> es una nota para personas; Maven lo ignora.

XML distingue mayúsculas de minúsculas: <artifactId> y <artifactid> son etiquetas distintas. Y es estricto: una etiqueta mal cerrada hace que todo el archivo sea inválido. Es una buena preparación para Java, que es igual de exigente.

El pom.xml, línea por línea

Línea 1 — <?xml version="1.0" encoding="UTF-8"?>

La declaración XML: anuncia «esto es un documento XML, versión 1.0, y su texto está guardado en UTF-8». Va siempre en la primera línea, sin nada antes (ni siquiera un espacio o una línea en blanco). No es una etiqueta que haya que cerrar; los signos <? y ?> la distinguen.

Línea 2 — <project xmlns=… xsi:schemaLocation=…>

Abre el elemento raíz, <project>, que contiene todo lo demás y se cierra en la línea 39. Sus atributos dicen a qué «vocabulario» pertenecen las etiquetas: xmlns (XML namespace, «espacio de nombres») indica que son las del POM de Maven versión 4.0.0, y xsi:schemaLocation indica dónde está publicado el esquema, un documento que describe qué etiquetas son válidas y dónde. No hace falta entender cada dirección: no son páginas que Maven visite al compilar, sino nombres únicos. Gracias a ellas, NetBeans puede ofrecerte autocompletado y marcarte errores mientras editas el POM. Se copia siempre igual, en todos los proyectos Maven.

Línea 3 — <modelVersion>4.0.0</modelVersion>

La versión del formato del POM (no de tu programa). Desde hace muchos años es siempre 4.0.0. Es obligatoria: sin ella Maven no sabe cómo leer el resto.

Líneas 4 a 6 — las coordenadas del proyecto

    <groupId>com.mycompany</groupId>
    <artifactId>Totito</artifactId>
    <version>1.0-SNAPSHOT</version>

Estas tres líneas son la identidad del proyecto, sus coordenadas. En Maven, todo (tu proyecto, cada librería, cada plugin) se identifica con estos tres datos, como una dirección postal de tres partes:

  • groupId: quién lo hace, el «grupo» u organización. Por convención se escribe como un dominio de internet al revés: si tu empresa fuera miempresa.com.gt, el groupId sería gt.com.miempresa. Al revés, porque así se ordena de lo general a lo particular, igual que las rutas de carpetas. com.mycompany («mi compañía») es el valor que NetBeans pone por defecto en los proyectos nuevos; el Totito lo conserva y el libro también, para que todo coincida.
  • artifactId: el nombre del producto. Maven llama artefacto a lo que produce un proyecto. Es Totito, y es parte del nombre del archivo final: Totito-1.0-SNAPSHOT.jar. NetBeans también lo usa como nombre del proyecto.
  • version: la versión del artefacto. El sufijo -SNAPSHOT («instantánea») es una convención de Maven que significa «versión en desarrollo, todavía cambiando». En este libro no la tocarás: el .jar se llamará siempre Totito-1.0-SNAPSHOT.jar y los comandos de empaquetado del capítulo 65 cuentan con ese nombre. Los números de versión que verá el público (v0.1.0, v1.0.0) se ponen con etiquetas de Git y en el instalador, como verás en los capítulos 9 y 67.

Línea 7 — <packaging>jar</packaging>

Qué tipo de artefacto produce el proyecto. Un .jar (Java ARchive) es un archivo comprimido, como un .zip, que contiene las clases compiladas del programa y una ficha descriptiva. Es la forma estándar de distribuir un programa Java (capítulo 63). Otros valores posibles son war, para aplicaciones web, o pom, para proyectos que agrupan otros.

Líneas 8 a 14 — las propiedades

    <properties>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
        <!-- Funciona con JDK 17 o mas nuevo. -->
        <maven.compiler.release>17</maven.compiler.release>
        <!-- Clase que arranca el juego (boton Run de NetBeans). -->
        <exec.mainClass>TotitoApp</exec.mainClass>
    </properties>

<properties> es una lista de ajustes con nombre y valor que leen Maven y sus plugins. Cada etiqueta interior es el nombre de un ajuste:

  • project.build.sourceEncoding = UTF-8 (línea 9). Indica en qué codificación están guardados los archivos de código. Una codificación es la tabla que convierte letras en bytes; UTF-8 incluye todos los caracteres de todos los idiomas, incluidas tildes, eñes y signos como «¡» y «¿». Sin esta línea, Maven en Windows podría leer tus archivos con una codificación antigua y el texto «¡Ganó Luis!» aparecería en pantalla como Â¡GanÃ³ Luis!. Es lo mismo que hace la opción -encoding UTF-8 de javac que verás en el capítulo 11.
  • El comentario de la línea 10 explica la línea siguiente: es una buena costumbre comentar los valores cuyo motivo no es obvio. Fíjate en que está escrito sin tildes («mas»), por la razón del capítulo 1.
  • maven.compiler.release = 17 (línea 11). Le dice al compilador: «genera un programa que funcione en Java 17 o más nuevo, y no me dejes usar nada que no exista en Java 17». Tú tienes el JDK 21, que sabe compilar para versiones anteriores. ¿Por qué 17 y no 21? Para que el Totito funcione también en computadoras que tengan Java 17, otra versión LTS muy extendida. Y la segunda mitad de la frase es la importante: si por error usaras algo que solo existe en Java 21, el compilador te lo diría en lugar de dejarte crear un programa que fallaría en Java 17.
  • El comentario de la línea 12 anuncia la línea 13.
  • exec.mainClass = TotitoApp (línea 13). Todo programa Java empieza por una clase que tiene un método especial llamado main (capítulo 11). Esta propiedad le dice a NetBeans cuál es esa clase cuando pulsas Run Project. TotitoApp todavía no existe: la escribirás en el capítulo 61. Hasta entonces, para ejecutar una clase concreta usarás Run File (Shift+F6), que ejecuta el archivo que tienes abierto; lo verás en los capítulos 32 y 33.

Línea 15 — <build>

Abre la sección que dice cómo construir el proyecto. Se cierra en la línea 38.

Líneas 16 y 17 — dónde está el código

        <!-- El codigo vive en src/ (sin paquetes), no en src/main/java. -->
        <sourceDirectory>src</sourceDirectory>

Esta línea merece atención, porque es la decisión de diseño más importante del archivo. Maven sigue el principio de convención sobre configuración: si colocas cada cosa donde Maven espera, no hace falta configurar nada. Y Maven espera el código en src\main\java, con las pruebas en src\test\java, normalmente organizado además en paquetes (subcarpetas como src\main\java\gt\com\miempresa\totito\).

El Totito se aparta de esa convención a propósito y lo dice aquí: <sourceDirectory>src</sourceDirectory> significa «el código está directamente en la carpeta src». Los motivos:

  • Sencillez para aprender. Todas las clases quedan en una sola carpeta, sin paquetes. Tu atención va al código, no a navegar carpetas anidadas.
  • Funciona igual sin Maven. El comando javac -encoding UTF-8 -d out src\*.java compila todo el juego sin NetBeans ni Maven, porque todos los .java están en el mismo sitio.
  • Así nació el proyecto. El código original del Totito estaba en src, y con esta línea no hubo que moverlo.

Como el código no tiene paquetes, en NetBeans las clases aparecerán en Source Packages → <default package> («paquete por defecto»). Para un proyecto de aprendizaje del tamaño del Totito es perfectamente válido. En proyectos grandes y profesionales se usan la convención de Maven y los paquetes, que ayudan a organizar cientos de clases y evitan choques de nombres; el capítulo 69 te cuenta cómo dar ese paso.

No pongas nada que no sea código en src. Maven compila todo lo que encuentre ahí. Si dejas en src una copia vieja de una clase (por ejemplo, Tablero - copia.java), Maven intentará compilarla y fallará con errores confusos. Las copias de seguridad van fuera del proyecto, o mejor aún, en Git.

Línea 18 — <plugins>

Abre la lista de plugins. Un plugin es un complemento que hace un trabajo concreto. Maven por sí solo casi no sabe hacer nada: compilar lo hace el plugin de compilación, empaquetar lo hace el plugin de jar, borrar lo hace el plugin de limpieza, y así. En esta lista no se declaran todos los plugins que se usan (Maven ya tiene unos por defecto), sino solo los que queremos configurar o cuya versión queremos fijar.

Líneas 19 a 23 — el plugin de compilación

            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.13.0</version>
            </plugin>

Fíjate en que el plugin se identifica con las mismas tres coordenadas que tu proyecto: groupId (los plugins oficiales son de org.apache.maven.plugins), artifactId (maven-compiler-plugin, el que compila) y version. Es el mismo sistema de direcciones para todo.

Este bloque no configura nada; solo fija la versión 3.13.0. ¿Para qué? Si no se indica, Maven usa una versión por defecto que depende de la versión de Maven instalada, y algunas de esas versiones por defecto son tan antiguas que no entienden el ajuste maven.compiler.release de la línea 11. Fijar la versión también garantiza que el proyecto se construya igual en tu computadora, en la de otra persona y dentro de cinco años: es una práctica recomendada en cualquier proyecto Maven.

Líneas 24 a 36 — el plugin de jar, con su configuración

            <plugin>
                <!-- Deja el .jar ejecutable con doble clic o con java -jar. -->
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-jar-plugin</artifactId>
                <version>3.4.2</version>
                <configuration>
                    <archive>
                        <manifest>
                            <mainClass>TotitoApp</mainClass>
                        </manifest>
                    </archive>
                </configuration>
            </plugin>

El maven-jar-plugin es el que fabrica el .jar, fijado en su versión 3.4.2 por la misma razón que el anterior. Este sí lleva <configuration>: una sección con los ajustes propios del plugin. Leída de afuera hacia adentro: en la configuración, para el archivo .jar (archive), en su manifiesto (manifest), la clase principal (mainClass) es TotitoApp.

El manifiesto es una pequeña ficha de texto que todo .jar lleva dentro, en META-INF\MANIFEST.MF. Con esta configuración, el plugin escribe en ella la línea Main-Class: TotitoApp. Esa línea es la que permite abrir el juego con doble clic sobre el .jar, o con java -jar target\Totito-1.0-SNAPSHOT.jar: Java lee el manifiesto, ve qué clase arranca el programa y la ejecuta. Sin ella, Java respondería «no hay ningún atributo de manifiesto principal». Así se ve el manifiesto que genera este POM:

Manifest-Version: 1.0
Created-By: Maven JAR Plugin 3.4.2
Build-Jdk-Spec: 21
Main-Class: TotitoApp

El capítulo 63 explica el .jar y su manifiesto a fondo.

¿Por qué TotitoApp aparece dos veces (líneas 13 y 32)? Porque la usan dos herramientas distintas: la línea 13 la lee NetBeans para el botón Run (que ejecuta las clases compiladas sin fabricar el .jar), y la línea 32 la lee el plugin de jar para el manifiesto. Si algún día cambiaras la clase principal, habría que cambiar las dos. En los ejercicios verás cómo evitar esa repetición.

Líneas 37 a 39 — los cierres

</plugins>, </build> y </project> cierran, en orden inverso, lo que se abrió en las líneas 18, 15 y 2. Es como cerrar cajas anidadas: primero la de adentro. Si falta uno de estos cierres, el archivo entero es inválido.

Copia el POM, pero entiéndelo. En la práctica, nadie escribe un pom.xml de memoria: se parte de una plantilla (NetBeans crea una al hacer File → New Project) o de otro proyecto. Lo que sí hacen los buenos programadores es saber qué hace cada línea, para poder cambiarla con confianza. Esa es la meta de esta sección.

Paso 4: el .gitignore

Git, la herramienta de historial que conocerás en la Parte II, guarda en el historial los archivos que le indiques. El archivo .gitignore es la lista de lo que Git debe ignorar: archivos que no deben guardarse nunca. Crea el archivo y ábrelo:

New-Item -ItemType File .gitignore
notepad .gitignore

El nombre empieza con un punto y no tiene nada antes: se llama literalmente .gitignore. Escribe este contenido, guarda y cierra:

target/
out/
dist/
*.class
nbproject/private/
.idea/
.vscode/
Thumbs.db
desktop.ini

Cada línea es un patrón: una regla que describe nombres de archivo. Una barra al final (target/) significa «la carpeta con este nombre y todo lo que contiene»; un asterisco (*.class) es el mismo comodín que en PowerShell, «cualquier texto». Línea por línea:

PatrónQué ignoraPor qué
target/La carpeta donde Maven deja las clases compiladas y el .jar.Todo lo de ahí se regenera con un Clean and Build. Guardarlo llenaría el historial de archivos que cambian en cada compilación.
out/La carpeta donde deja las clases el comando javac -d out.Igual que target, pero para cuando compiles sin Maven (capítulo 11).
dist/El programa empaquetado: la carpeta portable y el instalador (capítulos 65 y 66).Pesan decenas de megabytes y se fabrican a partir del código. El instalador se publica en GitHub de otra forma, como Release (capítulo 67).
*.classCualquier clase compilada, esté donde esté.Red de seguridad por si alguna vez compilas en otra carpeta. Un .class es un archivo generado, nunca se escribe a mano.
nbproject/private/Ajustes privados de NetBeans.Guardan rutas de tu computadora y preferencias personales que no le sirven a nadie más. Aparecen sobre todo en proyectos no-Maven, pero conviene tenerlo previsto.
.idea/La configuración del editor IntelliJ IDEA.Si algún día abres el proyecto con otro editor (o lo hace otra persona), su configuración personal no debe mezclarse con el proyecto.
.vscode/La configuración de Visual Studio Code.Mismo motivo.
Thumbs.dbLa caché de miniaturas que Windows crea en carpetas con imágenes.Es un archivo del sistema, no del proyecto. Aparecería en recursos en cuanto vieras el icono en el Explorador.
desktop.iniAjustes de cómo el Explorador muestra una carpeta.También es de Windows, no del proyecto.

La regla general detrás de esta lista: en Git va lo que escribes tú y lo que necesita cualquier persona para construir el proyecto; no va lo que se genera, lo personal ni lo del sistema operativo. El capítulo 10 añade otra categoría que nunca debe subirse: contraseñas y claves.

NetBeans puede crear, en la raíz del proyecto, archivos como nbactions.xml o nb-configuration.xml si cambias ciertas opciones del proyecto. Esos sí se pueden guardar en Git: describen cómo se ejecuta el proyecto y le sirven a cualquiera que lo abra con NetBeans.

Paso 5: el README.md

El README («léeme») es la carta de presentación del proyecto: lo primero que lee cualquier persona que lo encuentra, y lo que GitHub muestra en la página principal de tu repositorio. También es para ti dentro de seis meses, cuando no recuerdes cómo se ejecutaba. Crea el archivo:

New-Item -ItemType File README.md
notepad README.md

Y escribe esto (puedes cambiar el texto a tu gusto):

# Totito

Juego del Totito (tres en raya) en Java, con interfaz neón hecha en Swing.
Proyecto construido paso a paso con el libro «Java desde cero con el Totito».

## Requisitos

- JDK 17 o más nuevo (el libro usa Eclipse Temurin 21).
- Apache NetBeans (opcional: también se compila con Maven o con javac).

## Cómo ejecutarlo

1. En NetBeans: *File → Open Project* y elegir la carpeta `Totito`.
2. *Run → Clean and Build Project* (Shift+F11).
3. *Run → Run Project* (F6).

## Estado

En construcción: estructura inicial del proyecto.

La extensión .md significa Markdown, un formato de texto con unas pocas marcas sencillas que GitHub convierte en una página con formato:

EscribesSe ve como
# TotitoUn título grande (un # = nivel 1).
## RequisitosUn subtítulo (dos ## = nivel 2).
- textoUna viñeta de lista.
1. textoUn elemento de lista numerada.
*texto*Texto en cursiva. Con dos asteriscos, **texto**, en negrita.
`Totito`Texto en letra de código (entre acentos graves).

Una línea en blanco separa los párrafos. Lo bueno de Markdown es que, incluso sin convertir, se lee bien como texto plano. Irás completando este README a lo largo del libro, a medida que el Totito crezca.

Paso 7: abrir el proyecto en NetBeans

  1. Abre NetBeans.
  2. Elige File → Open Project… (Archivo → Abrir proyecto), o presiona Ctrl+Shift+O.
  3. En la ventana que aparece, navega hasta C:\Users\<tu-usuario>\Proyectos. Verás la carpeta Totito con un icono especial: NetBeans ya detectó que tiene un pom.xml y que es un proyecto Maven.
  4. Haz clic una vez sobre Totito (no entres en ella) y pulsa Open Project.

El proyecto aparece en el panel de la izquierda. La primera vez, NetBeans puede tardar un poco: indexa el proyecto (lo analiza para poder ayudarte después) y quizá descargue piezas de Maven; verás una barra de progreso en la esquina inferior derecha. Si muestra un aviso de que el proyecto tiene problemas (project problems) por plugins que faltan, haz clic derecho en el proyecto, elige Resolve Project Problems… y luego Resolve: lo arregla descargándolos.

Si NetBeans no reconoce la carpeta como proyecto, el problema casi siempre está en el pom.xml: o se llama pom.xml.txt (compruébalo con ls en PowerShell), o no está directamente dentro de Totito, o tiene un error de XML. En este último caso, ábrelo en el Bloc de notas y compáralo línea por línea con el del libro.

Recorrido por NetBeans

NetBeans es un programa grande y al principio abruma. No necesitas conocerlo entero: estas son las partes que usarás durante el libro. Para orientarte, el Apéndice C reúne los atajos de teclado.

Projects: la vista lógica del proyecto

El panel Projects (Proyectos; Ctrl+1), arriba a la izquierda, muestra el proyecto Totito organizado por su significado, no por sus carpetas. Al desplegarlo verás nodos como:

  • Source Packages (paquetes de código fuente): el código, es decir, la carpeta src que indicaste en sourceDirectory. Mientras src esté vacía, puede que este nodo no aparezca todavía o aparezca vacío. Desde el capítulo 29 verás aquí <default package> con tus clases, y es donde harás clic derecho → New → Java Class… para crearlas.
  • Dependencies (dependencias): librerías externas que el proyecto usa. El Totito no usa ninguna: todo lo que necesita viene con Java.
  • Project Files (archivos del proyecto): ahí está el pom.xml. Doble clic para abrirlo en el editor.

Files: la vista real de las carpetas

Junto a la pestaña Projects está Files (Archivos; Ctrl+2). Muestra la carpeta del proyecto tal como es en el disco, igual que el Explorador: aquí sí verás herramientas, recursos, .gitignore y README.md, que la vista Projects no muestra porque no son código. Usarás Files para abrir las utilidades de herramientas y para ver la carpeta target.

El editor

El área grande del centro es el editor. Cada archivo abierto tiene su pestaña arriba. Abre el pom.xml con doble clic y observa que NetBeans colorea el XML: etiquetas de un color, valores de otro, comentarios en gris. Si borras a propósito un >, verás aparecer una marca roja en el margen; deshazlo con Ctrl+Z. Con el código Java, el editor hará mucho más: te avisará de errores al momento, completará nombres con Ctrl+Espacio y dará formato con Alt+Shift+F.

Navigator: el esquema del archivo

El panel Navigator (Navegador; Ctrl+7), normalmente abajo a la izquierda, muestra la estructura del archivo que tienes abierto. Con el pom.xml verás el árbol de elementos (project, properties, build…). Con una clase Java mostrará sus métodos y variables, y será la forma más rápida de saltar a una parte concreta de un archivo largo.

Output: lo que dicen las herramientas

El panel Output (Salida; Ctrl+4), abajo, muestra los mensajes de Maven cuando compilas y lo que tu programa escribe cuando lo ejecutas. Es el equivalente a la terminal dentro de NetBeans. Cuando algo falle, la explicación estará ahí; si el error es de compilación, los nombres de archivo con número de línea son enlaces: haz clic y NetBeans te lleva a la línea.

Menús y barra de herramientas

Los menús que más usarás: File (archivo: abrir y guardar), Edit (editar: copiar, buscar), Source (código: formatear, comentar), Refactor (reorganizar: renombrar algo en todo el proyecto), Run (ejecutar y compilar), Debug (depurar, capítulo 62), Team (Git; el libro usa Git desde PowerShell) y Window (ventanas: abrir y cerrar paneles). En la barra de herramientas, los botones principales son el martillo (Build, compilar), el martillo con escoba (Clean and Build, limpiar y compilar) y el triángulo verde (Run, ejecutar).

Si cierras un panel sin querer, ábrelo de nuevo desde el menú Window, o usa Window → Reset Windows para devolver toda la ventana a su distribución original. Es el botón de pánico de NetBeans y no borra nada de tu proyecto.

Comprobar la codificación UTF-8

Como el pom.xml declara UTF-8, NetBeans lo usa para leer y guardar los archivos del proyecto. Compruébalo: clic derecho sobre el proyecto Totito → Properties (Propiedades) → categoría Sources. El campo Encoding debe decir UTF-8. No lo cambies desde ahí: si lo hicieras, NetBeans modificaría tu pom.xml. Pulsa Cancel.

Además, en Help → About la línea System debería incluir UTF-8 (lo viste en el capítulo 4). Con el JDK 21 es lo normal. Si en tu caso dijera otra cosa (por ejemplo Cp1252) y más adelante vieras tildes rotas en el panel Output, la solución es agregar -J-Dfile.encoding=UTF-8 dentro de la línea netbeans_default_options del archivo netbeans.conf de NetBeans (en C:\Program Files\NetBeans-25\netbeans\etc\), editándolo con el Bloc de notas abierto como administrador. Probablemente no lo necesites.

Paso 8: el primer Clean and Build

Ahora vas a pedirle a Maven que construya el proyecto, aunque todavía no haya código. Parece no tener sentido, pero sirve para comprobar que el pom.xml está bien escrito, que NetBeans encuentra el JDK y que Maven puede descargar lo que necesita. Si algo de eso falla, mejor descubrirlo ahora que con 29 clases escritas.

Elige Run → Clean and Build Project (Ejecutar → Limpiar y construir proyecto) o presiona Shift+F11. También puedes hacer clic derecho en el proyecto y elegir Clean and Build. Mira el panel Output. La primera vez aparecerán muchas líneas de descargas (Downloading… Downloaded…): Maven está bajando de internet los plugins del POM. Las siguientes veces ya los tendrá guardados y será mucho más rápido. Al final verás algo parecido a esto:

Los números de versión de algunos plugins y algunas líneas pueden ser distintos según la versión de Maven que trae NetBeans. Lo que importa es la última parte: BUILD SUCCESS, «construcción exitosa». Lee la salida de arriba abajo, porque cuenta exactamente lo que pasó:

  • Scanning for projects / Building Totito 1.0-SNAPSHOT: Maven leyó tu POM y reconoció las coordenadas com.mycompany:Totito, versión 1.0-SNAPSHOT, empaquetado jar.
  • Cada línea --- plugin:versión:objetivo --- es un paso, ejecutado por su plugin (compiler es el maven-compiler-plugin, jar el maven-jar-plugin, y así). Los pasos forman el ciclo de vida de Maven, siempre en este orden: clean (borrar target), resources (copiar archivos que no son código; no hay, por eso lo salta), compile (compilar con el plugin 3.13.0 que fijaste), tres pasos de pruebas automáticas (testResources, testCompile y test; el Totito no tiene, el capítulo 69 te las presenta), jar (empaquetar con el 3.4.2) e install. Clean and Build equivale a pedirle a Maven «clean» y luego «install», que incluye todos los pasos anteriores.
  • Nothing to compile: no hay ninguna clase todavía, así que no hay nada que compilar. Correcto.
  • JAR will be empty: es un aviso (no un error): «el .jar va a quedar vacío». Lógico, porque no hay clases. Desaparecerá en cuanto escribas la primera, en el capítulo 29.
  • Installing … .m2\repository: el paso install copia el .jar a una carpeta de tu usuario, C:\Users\<tu-usuario>\.m2\repository, el repositorio local de Maven. Ahí guarda también los plugins que descargó, para no volver a bajarlos. Es una caché: si alguna vez se daña, se puede borrar y Maven la vuelve a llenar.

Ahora mira el panel Files: apareció la carpeta target, con el Totito-1.0-SNAPSHOT.jar recién fabricado y algunas carpetas de trabajo de Maven. Es exactamente la carpeta que tu .gitignore excluye: todo lo que hay ahí se acaba de generar y se puede regenerar con otro Clean and Build.

Hito El proyecto Totito existe: tiene su estructura, su pom.xml, su .gitignore y su README.md, NetBeans lo reconoce y Maven lo construye con BUILD SUCCESS. Desde aquí, cada clase que escribas se compilará con este mismo botón.

Paso 9: guardar el primer avance en Git

Git Según el plan de commits del libro, el primer commit (una fotografía del proyecto en el historial) guarda estos tres archivos con el mensaje «Estructura inicial del proyecto Totito». Todavía no lo hagas: Git necesita configurarse primero (capítulo 7) y antes conviene entender qué es un commit (capítulo 6). En el capítulo 8 volverás a esta misma carpeta y ejecutarás exactamente esto: 
cd $HOME\Proyectos\Totito
git init -b main
git add pom.xml .gitignore README.md
git commit -m "Estructura inicial del proyecto Totito"
Fíjate en que se guardan solo esos tres archivos: las carpetas vacías (src, herramientas, recursos) no se guardan, porque Git solo registra archivos, y target queda fuera gracias al .gitignore. Las carpetas entrarán en el historial cuando tengan su primer archivo.

Resumen

  • El proyecto vive en $HOME\Proyectos\Totito, con src (código del juego), herramientas (utilidades que no van en el programa) y recursos (icono). target y dist se generan solas.
  • Maven construye el proyecto siguiendo el pom.xml: coordenadas (groupId, artifactId, version), empaquetado jar, propiedades y plugins.
  • sourceEncoding UTF-8 protege las tildes; release 17 garantiza que el juego funcione en Java 17 o más nuevo; exec.mainClass y el mainClass del manifiesto indican que TotitoApp arranca el juego.
  • sourceDirectory = src se aparta de la convención src/main/java para tener todas las clases juntas, sin paquetes (<default package>).
  • Fijar las versiones de los plugins hace que la construcción sea igual en cualquier computadora.
  • El .gitignore excluye lo generado (target, out, dist, .class), lo personal de cada editor y los archivos de Windows.
  • El README.md, en Markdown, presenta el proyecto en GitHub.
  • En NetBeans: Projects, Files, editor, Navigator y Output; Clean and Build (Shift+F11) debe terminar en BUILD SUCCESS.
Aplícalo fuera del Totito Todo proyecto, de cualquier tamaño, empieza igual:
  • Cualquier proyecto Java con Maven: una API con Spring Boot o una aplicación de escritorio de inventario tienen un pom.xml con la misma forma: coordenadas, propiedades, y una sección <dependencies> donde se agregan librerías (por ejemplo, un conector de base de datos), que se identifican con las mismas tres coordenadas que viste en los plugins.
  • Proyectos en otros lenguajes: Node.js tiene su package.json, Python su pyproject.toml, .NET su .csproj. Cambia el formato, pero la idea es la misma: un archivo que dice qué es el proyecto, con qué versión se construye y qué necesita.
  • El .gitignore de cualquier repositorio: la regla «lo escrito sí, lo generado y lo personal no» sirve igual para un sitio web (ignorar node_modules/), un proyecto de Python (__pycache__/) o un documento de LaTeX (los .aux y .log).
  • Organizar cualquier trabajo en carpetas: separar originales, auxiliares y entregables (por ejemplo, en un proyecto de diseño: fuentes, bocetos, exportados) evita entregar un borrador por error.
