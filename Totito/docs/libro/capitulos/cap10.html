Capítulo 10Colaborar y publicar en GitHub

Git guarda tu historia; GitHub la convierte en un lugar de trabajo compartido. En este capítulo recorres la página de un repositorio, aprendes el flujo rama → pull request → revisión → fusión que usarás en el capítulo 61, anotas tareas con issues, invitas colaboradores, entiendes los forks, escribes un buen README, eliges una licencia y sabes qué no debe subirse nunca. En la pestaña Code conviene conocer:

  • El selector de ramas (un botón que dice main): elige otra rama para ver sus archivos tal como están en ella.
  • La línea del último commit, con tu foto, el mensaje, el hash y la fecha, y a la derecha el contador de commits (N Commits): al hacer clic ves el historial, como git log, y al hacer clic en un commit ves su diff, en rojo y verde.
  • Al entrar a un archivo, el botón History muestra los commits que lo tocaron, y Blame muestra, línea por línea, qué commit la escribió por última vez («blame» significa «culpar», pero sirve más para entender el porqué de una línea que para culpar a nadie).
  • El botón verde <> Code da la dirección para clonar el repositorio (HTTPS o SSH) y la opción Download ZIP.
  • Al pulsar la tecla . (punto) en la página de un repositorio, GitHub abre un editor de código en el navegador. Útil para cambios rápidos desde otra computadora.

Pull requests: proponer, revisar y fusionar

Un pull request (PR; en español a veces «solicitud de extracción», aunque nadie lo dice así) es una petición para fusionar una rama en otra, con una página propia en GitHub donde se ve el diff completo, se comenta línea por línea, se aprueba o se piden cambios, y finalmente se fusiona con un botón o un comando. El nombre viene de «pídele al dueño que jale (pull) mis cambios».

En un equipo, es la forma estándar de que nadie meta código en main sin que otra persona lo mire. ¿Y si trabajas solo, como en el Totito? Igual vale la pena:

  • Revisas tu propio trabajo con otros ojos: ver el diff completo de la rama en la página de GitHub hace saltar errores que en NetBeans no ves.
  • Queda escrito qué se fusionó, cuándo y por qué, con su descripción y sus comentarios. El PR #1 del Totito contará la historia de toda la interfaz neón.
  • Se pueden ejecutar comprobaciones automáticas antes de fusionar (Actions).
  • Practicas el flujo que te pedirán en cualquier trabajo.

El flujo completo, paso a paso

Así es el flujo que harás en el capítulo 61 con la rama interfaz-neon (y el que harás en cualquier proyecto con equipo):

  1. Crear la rama desde una main actualizada (en el Totito lo haces al empezar la Parte VII, capítulo 38):
git switch main
git pull
git switch -c interfaz-neon
  1. Trabajar y hacer commits en la rama, uno por capítulo, como siempre.
  2. Subir la rama a GitHub. La primera vez con -u, para emparejarla:
git push -u origin interfaz-neon
remote:
remote: Create a pull request for 'interfaz-neon' on GitHub by visiting:
remote:      https://github.com/ana-lopez/totito/pull/new/interfaz-neon
remote:
To https://github.com/ana-lopez/totito.git
 * [new branch]      interfaz-neon -> interfaz-neon
branch 'interfaz-neon' set up to track 'origin/interfaz-neon'.

Las líneas que empiezan con remote: las escribe GitHub: te sugiere crear un pull request y te da el enlace. Las siguientes veces basta con git push. Subir la rama con frecuencia tiene una ventaja extra: tu trabajo a medias también está respaldado en GitHub.

  1. Abrir el pull request:
gh pr create --base main --head interfaz-neon --title "Interfaz neon completa (v1.0.0)" --body-file $HOME\pr-interfaz.md
PiezaQué hace
gh pr createCrea un pull request en el repositorio de la carpeta actual
--base mainLa rama destino: a dónde quieres llevar los cambios
--head interfaz-neonLa rama origen: la que tiene los cambios. Si estás en ella, puedes omitirla
--title "..."El título del PR: una frase clara, como el de un commit
--body-file $HOME\pr-interfaz.mdToma la descripción de un archivo de texto. Para descripciones cortas sirve --body "texto"

Escribir la descripción en un archivo es más cómodo que en una sola línea de PowerShell. Créalo fuera de la carpeta del proyecto, para que no termine en un commit por accidente: notepad $HOME\pr-interfaz.md lo crea en tu carpeta personal. Una buena descripción de PR responde cuatro preguntas:

## Que cambia
Toda la interfaz neon del Totito: menu, instrucciones, configuracion,
partida y pantalla de resultado, con sus componentes (BotonNeon,
Tarjeta, Rotulo, PanelTablero...). La logica (Tablero, Jugador,
IA_Minimax) no se toco; Partida la une con la interfaz.

## Por que
Pasar de la ventana basica de la v0.1.0 al diseno final (v1.0.0).

## Como probarlo
1. Clean and Build en NetBeans y Run (F6).
2. Jugar una partida de 2 jugadores y una contra la IA.
3. Comprobar victoria, empate, "Jugar de nuevo" y "Menu principal".

Si prefieres no usar comandos, gh pr create --web abre el formulario en el navegador con las ramas ya elegidas. Y si escribes gh pr create sin opciones, te pregunta todo de forma interactiva. Al terminar, gh imprime la dirección del PR, por ejemplo https://github.com/ana-lopez/totito/pull/1: el número 1 es su identificador.

  1. Revisar. Esto se puede hacer en la terminal o en la página:
gh pr list
gh pr view 1
gh pr diff 1
gh pr view 1 --web

gh pr list muestra los PR abiertos; gh pr view 1 su descripción y estado; gh pr diff 1 el diff completo (sal con q); --web lo abre en el navegador. La página de un PR tiene cuatro pestañas:

PestañaContenido
ConversationLa descripción, los comentarios, las revisiones y, al final, el botón para fusionar
CommitsLa lista de commits de la rama (en el Totito, uno por capítulo)
ChecksEl resultado de las comprobaciones automáticas (Actions), si hay
Files changedEl diff de todos los archivos. Pasando el ratón por una línea aparece un + azul para comentar esa línea. El botón Review changes permite enviar la revisión como comentario (Comment), aprobación (Approve) o petición de cambios (Request changes)

Desde la terminal también se comenta y se revisa:

gh pr comment 1 --body "Probado en Windows 11: menu, partida y empate funcionan."
gh pr review 1 --comment --body "Revisar el contraste del texto suave en la tarjeta del jugador."

Si la revisión pide cambios, no se abre otro PR: haces los commits en la misma rama y git push; el PR se actualiza solo con los commits nuevos. Así se ve, en la conversación, qué se pidió y cómo se resolvió.

No puedes aprobar tu propio PR GitHub no deja que el autor de un PR lo apruebe (gh pr review --approve sobre tu propio PR da error). Trabajando solo, tu «revisión» consiste en leer el diff completo y dejar un comentario con lo que probaste. Cuando tengas colaboradores, ellos aprueban.
  1. Fusionar:
gh pr merge 1 --merge --delete-branch

gh pr merge fusiona el PR. La opción que elijas decide cómo queda el historial; GitHub ofrece tres, y las verás también en el botón verde de la página:

OpciónBotón en la páginaQué haceCuándo conviene
--mergeCreate a merge commitFusión de tres vías con commit de fusión, como en el capítulo 9. Todos los commits de la rama se conservanCuando los commits de la rama cuentan una historia que quieres conservar. Es la que usa el Totito: cada capítulo de la Parte VII queda como un commit
--squashSquash and mergeAplasta todos los commits de la rama en uno solo en mainRamas cortas con commits de prueba («wip», «arreglo typo») que no aportan
--rebaseRebase and mergeCopia los commits de la rama uno a uno encima de main, sin commit de fusiónEquipos que prefieren un historial en línea recta

--delete-branch borra la rama en GitHub y en tu PC después de fusionar (su trabajo ya está en main). gh además te deja en main actualizada. Si fusionaste desde la página, actualiza tú:

git switch main
git pull
git branch -d interfaz-neon
git fetch --prune

git fetch --prune («podar») borra de tu PC las referencias a ramas remotas que ya no existen en GitHub, para que git branch -a no muestre ramas fantasma.

  1. Etiquetar la versión, ya en main: git tag -a v1.0.0 -m "Totito 1.0.0: interfaz neon" y git push --tags.
Hito (capítulo 61) Cuando hagas este flujo con la interfaz neón, el PR #1 quedará en la pestaña Pull requests → Closed con la etiqueta morada Merged, y main tendrá el Totito v1.0.0.
PR en borrador y PR pequeños gh pr create --draft abre un PR en borrador: sirve para enseñar trabajo a medias y recibir opiniones antes de terminarlo; no se puede fusionar hasta que lo marques como listo (gh pr ready 1). Y en general, cuanto más pequeño el PR, mejor la revisión: el de la interfaz neón es grande porque el libro lo hace en una sola rama para que veas el proceso completo; en un equipo real se partiría en varios PR (uno para los componentes, otro para cada pantalla…).

Issues: la lista de pendientes del proyecto

Un issue («asunto», «tema») es una ficha para anotar algo que hay que hacer: un error, una mejora, una idea, una pregunta. Cada issue tiene un número, un título, una descripción, comentarios, etiquetas y un estado (abierto o cerrado). Es mucho mejor que una lista en un papel porque se enlaza con el código: un PR puede decir «esto resuelve el #3» y el issue se cierra solo.

El README del proyecto de referencia termina con una lista de «Ideas pendientes». Son candidatos perfectos para issues:

gh issue create --title "Niveles de dificultad para la IA" --body "Opcion facil: la IA hace a veces una jugada al azar en lugar de la de Minimax." --label enhancement
gh issue create --title "Jugar con el teclado (teclas 1 a 9)" --label enhancement
gh issue list
Showing 2 of 2 open issues in ana-lopez/totito

ID  TITLE                                  LABELS       UPDATED
#2  Jugar con el teclado (teclas 1 a 9)    enhancement  less than a minute ago
#1  Niveles de dificultad para la IA       enhancement  about 1 minute ago
  • --title y --body: título y descripción. Si omites el --body, gh te lo pregunta.
  • --label enhancement: una etiqueta. Todo repositorio nuevo trae algunas: bug (error), enhancement (mejora), documentation, question, good first issue (buena para quien empieza)… Puedes crear las tuyas en Issues → Labels.
  • gh issue view 1 muestra uno; gh issue close 1 lo cierra; gh issue comment 1 --body "..." comenta.

Los issues y los PR comparten la numeración: si ya existen los issues #1 y #2, el siguiente PR será el #3 (por eso en tu repositorio el PR de la interfaz neón podría no ser el #1; no importa).

Cerrar issues automáticamente

Si la descripción de un PR (o el mensaje de un commit que llega a main) incluye Closes #1, Fixes #1 o Resolves #1, GitHub cierra el issue #1 cuando el PR se fusiona, y deja el enlace entre los dos. Por ejemplo, en el cuerpo de un commit: git commit -m "IA_Minimax: agregar nivel facil" -m "Closes #1".

Cómo se escribe un buen issue de error

Titulo: El marcador suma dos victorias si se hace doble clic al ganar

Pasos para reproducirlo:
1. Modo 2 jugadores.
2. Hacer la jugada ganadora con doble clic rapido.

Resultado esperado: el marcador suma 1.
Resultado obtenido: el marcador suma 2.

Version: v1.0.0, Windows 11. Captura adjunta.

Pasos exactos, lo esperado, lo obtenido y la versión. Con eso, cualquiera (incluido tú dentro de un mes) puede reproducir el error sin preguntar nada.

Colaboradores: dar acceso a otras personas

Si un amigo va a programar contigo en el Totito, necesita permiso para subir a tu repositorio:

  1. En la página del repositorio: Settings → Collaborators (GitHub puede pedirte confirmar con tu contraseña o el código del teléfono).
  2. Add people → escribe su nombre de usuario o correo de GitHub → Add … to this repository.
  3. Tu amigo recibe una invitación por correo (o en https://github.com/notifications) y debe aceptarla.
  4. Él descarga el proyecto con gh repo clone ana-lopez/totito (o git clone https://github.com/ana-lopez/totito.git), que crea la carpeta totito con todo el historial y el remoto origin ya configurado.

Desde la terminal, la invitación también se puede enviar por la API de GitHub: gh api -X PUT repos/ana-lopez/totito/collaborators/usuario-del-amigo.

En un repositorio personal, un colaborador puede hacer casi todo: subir commits, crear ramas, fusionar PR. Aun así, acuerden trabajar siempre con ramas y PR: cada quien en su rama, y a main solo por PR revisado por el otro. Ese acuerdo vale más que cualquier permiso.

Forks: tu propia copia de un proyecto ajeno

¿Y si quieres contribuir a un proyecto donde no eres colaborador, por ejemplo una librería pública que tiene un error? No puedes subir a su repositorio, pero puedes hacer un fork («bifurcación»): una copia completa del repositorio en tu cuenta, donde sí puedes subir. Desde tu fork abres un PR hacia el repositorio original, y sus dueños deciden si lo aceptan.

gh repo fork dueno-original/proyecto --clone
cd proyecto
git remote -v
origin	https://github.com/ana-lopez/proyecto.git (fetch)
origin	https://github.com/ana-lopez/proyecto.git (push)
upstream	https://github.com/dueno-original/proyecto.git (fetch)
upstream	https://github.com/dueno-original/proyecto.git (push)

gh repo fork … --clone crea el fork en tu cuenta, lo descarga, y configura dos remotos: origin (tu fork, donde subes) y upstream («corriente arriba», el original, de donde traes novedades). El flujo es el mismo de siempre: rama, commits, git push -u origin mi-arreglo y gh pr create (gh propone por defecto el repositorio original como destino). Para traer los cambios nuevos del original a tu fork: git pull upstream main estando en tu main, y luego git push; o el botón Sync fork en la página de tu fork.

Licencias: qué pueden hacer otros con tu código

Aquí hay una sorpresa para casi todo el mundo: si publicas código sin licencia, legalmente nadie puede usarlo, copiarlo ni modificarlo, aunque esté público en GitHub. Sin licencia rige el derecho de autor por defecto: «todos los derechos reservados». Las personas pueden verlo (y hacer un fork dentro de GitHub, según sus términos de uso), pero no reutilizarlo en sus proyectos. Una licencia es el permiso por escrito que tú, como autor, das a los demás.

Cómo agregar la licencia

Lo más fácil es dejar que GitHub escriba el archivo:

  1. En la pestaña Code: Add file → Create new file.
  2. Como nombre escribe LICENSE (en mayúsculas, sin extensión). Aparece un botón Choose a license template («elegir una plantilla de licencia»): púlsalo.
  3. Elige MIT License, revisa que el año y el nombre sean los correctos y pulsa Review and submit.
  4. Pulsa Commit changes…, deja el mensaje (o escribe Agregar licencia MIT), con la opción de hacer el commit directamente en main, y confirma.
  5. Ese commit existe en GitHub pero no en tu PC. Tráelo:
git switch main
git pull

Y ya tienes LICENSE en tu carpeta. GitHub mostrará «MIT license» en el panel About. (También podrías crear el archivo en NetBeans, pegar el texto y hacer el commit tú; el resultado es el mismo).

Esto no es asesoría legal Para un proyecto personal o de aprendizaje, la MIT es una elección sencilla y segura. Si algún día publicas software de una empresa o con código de otras personas, revisa con quien corresponda qué licencia usar, y respeta las licencias de las librerías que incluyas.

Releases: publicar versiones para descargar

Un release («lanzamiento») es una versión publicada del proyecto en la página de GitHub: se basa en una etiqueta (v1.0.0), tiene un título, unas notas que explican qué trae, y archivos adjuntos (assets), como el instalador .exe. Es la respuesta a una pregunta importante: si los .exe no van en el repositorio (ver la sección siguiente), ¿cómo los descarga la gente? Por los Releases.

En el capítulo 67, cuando tengas el instalador, lo publicarás con un comando como este (allí se explica cada parte, las notas de la versión y el versionado SemVer):

gh release create v1.0.0 dist\instalador\Totito-1.0.0.exe --title "Totito 1.0.0" --notes "Primera version completa con interfaz neon."

El release aparecerá en el panel derecho de la pestaña Code, con un botón de descarga para el instalador y, automáticamente, el código fuente comprimido de esa versión.

Qué NO subir nunca

Todo lo que llega a un commit se queda en el historial para siempre, y todo lo que se sube a un repositorio público lo pueden leer en minutos robots que recorren GitHub buscando secretos. Por eso esta lista no tiene excepciones:

Si ya subiste un secreto

Pasa, incluso a profesionales. El orden de los pasos importa:

  1. Considéralo robado, desde ya. No importa que el repositorio sea privado ni que lo borres en cinco minutos.
  2. Revócalo o cámbialo en el servicio de origen: cambia la contraseña, borra el token (los de GitHub, en Settings → Developer settings), genera una clave nueva. Este es el paso que de verdad te protege.
  3. Sácalo del proyecto como viste en el capítulo 9: git rm --cached archivo, agrégalo al .gitignore, commit y push.
  4. Si además quieres borrarlo del historial, existen herramientas que reescriben todos los commits (git filter-repo, BFG Repo-Cleaner). Es una operación delicada que obliga a forzar el push y a que todos vuelvan a clonar; por eso el paso 2 nunca se salta: aunque limpies el historial, alguien pudo haberlo copiado antes.
GitHub te echa una mano, pero no confíes en ello GitHub revisa los pushes en busca de formatos conocidos de tokens y claves (su push protection y el secret scanning) y puede bloquear el envío o avisarte en la pestaña Security. Ayuda, pero no reconoce todo, y menos una contraseña normal. La protección real es tu costumbre: leer git status y git diff --staged antes de cada commit.

Proteger la rama main

Cuando hay más de una persona, conviene que GitHub impida subir directamente a main y obligue a pasar por un PR aprobado. Eso se llama protección de ramas:

  1. En el repositorio: Settings → Rules → Rulesets → New ruleset → New branch ruleset (en versiones anteriores de la página: Settings → Branches → Add branch protection rule).
  2. Dale un nombre (proteger-main), pon Enforcement status en Active y, en Target branches, agrega la rama por defecto (main).
  3. Activa las reglas que quieras. Las más útiles: Require a pull request before merging (nadie sube directo; con un número mínimo de aprobaciones si hay equipo), Block force pushes (nadie puede reescribir el historial de main), Restrict deletions (nadie puede borrar main) y, si usas Actions, Require status checks to pass (no se fusiona si la compilación falla).
  4. Guarda con Create.
Repositorios privados con plan gratuito Con una cuenta gratuita, GitHub solo aplica estas reglas en repositorios públicos. En un repositorio privado gratuito las opciones aparecen, pero no se hacen cumplir (hace falta un plan de pago). Si tu Totito es privado, la protección de main depende de tu disciplina: todo cambio a main entra por PR, aunque GitHub no te obligue.

Para ir más allá: GitHub Actions

La pestaña Actions permite que GitHub haga trabajo por ti en sus servidores cada vez que pasa algo (un push, un PR). Lo más común es la integración continua (CI): compilar y probar el proyecto automáticamente para saber, antes de fusionar, si algo se rompió. Es opcional y el libro no lo necesita, pero así de poco hace falta para el Totito. Crea el archivo .github\workflows\compilar.yml (con las carpetas .github y workflows) con este contenido:

name: Compilar

on:
  push:
    branches: [main]
  pull_request:

jobs:
  compilar:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven
      - run: mvn -B package
  • El formato es YAML: la sangría (con espacios, nunca tabuladores) indica qué va dentro de qué.
  • on: cuándo se ejecuta: en cada push a main y en cada pull request.
  • runs-on: ubuntu-latest: en una máquina Linux de GitHub (el juego es Java, compila igual en cualquier sistema).
  • steps: descargar el código (checkout), instalar el JDK 21 de Temurin (el mismo que instalaste en el capítulo 4) y compilar con Maven (-B es «modo por lotes», sin colores ni preguntas).

Haz commit y push. En la pestaña Actions verás la ejecución con un círculo amarillo (en curso), y luego una marca verde (todo bien) o una X roja (falló, con el registro para ver por qué). En cada PR, la pestaña Checks mostrará el resultado. Gracias al permiso workflow que pidió gh auth login (capítulo 7), puedes subir este archivo sin problemas.

Buenas prácticas de Git y GitHub: la lista

Todo lo de la Parte II, condensado. Vuelve a esta lista cuando dudes.

Al configurar

  1. Activa la verificación en dos pasos y guarda los códigos de recuperación fuera de la PC.
  2. Configura user.name y user.email (mejor la dirección noreply) antes del primer commit.
  3. En Windows, core.autocrlf true; rama por defecto main; un editor que sepas usar.
  4. Crea el .gitignore antes del primer commit.

Al trabajar

  1. git pull al empezar, git push al terminar cada tarea.
  2. git status siempre; git diff --staged antes de cada commit.
  3. Commits pequeños y atómicos: un cambio lógico, completo, que compile.
  4. Mensajes con una primera línea de 50 caracteres o menos, en infinitivo o imperativo, y el porqué en el cuerpo.
  5. Prefiere git add archivo a git add ., o revisa la lista antes del commit.
  6. No hagas commit de código que no compila en main.

Con ramas

  1. main siempre funciona. El trabajo nuevo, en una rama con nombre descriptivo.
  2. Ramas cortas: fusiónalas pronto y bórralas al terminar.
  3. A main se llega por PR, aunque trabajes solo; protégela si el repositorio lo permite.
  4. Ante un conflicto: calma, lee las marcas, decide, compila, prueba, y solo entonces git add y commit.

Al deshacer

  1. Lo que no subiste se puede reescribir (--amend, reset); lo que subiste se corrige con git revert.
  2. Nunca git push --force sobre main ni sobre ramas compartidas.
  3. Antes de un reset --hard, un git stash; después de un susto, git reflog.

Al publicar

  1. Nunca subas secretos, archivos generados ni archivos enormes. Si se escapa un secreto: cámbialo primero, limpia después.
  2. Un README que diga qué es, cómo se ve, cómo se usa y cómo se construye; una licencia explícita.
  3. Etiquetas anotadas con SemVer (v1.0.0) para cada versión, y los binarios en Releases.
  4. Issues para los pendientes; Closes #n para enlazarlos con los PR.

Resumen

  • La página de un repositorio se organiza en pestañas: Code (archivos, historial, README, releases), Issues, Pull requests, Actions, Settings y otras.
  • El flujo profesional es rama → commits → git push -u origin rama → gh pr create → revisión (comentarios, cambios con más commits) → gh pr merge → git pull en main → etiqueta. El Totito lo usa en el capítulo 61 con --merge, para conservar un commit por capítulo.
  • Los issues anotan errores e ideas; Closes #n en un PR los cierra al fusionar.
  • Los colaboradores suben al repositorio original; los forks son copias en tu cuenta desde las que propones PR a proyectos ajenos.
  • Un buen README explica qué es, cómo se ve, cómo se usa y cómo se construye; sin licencia, nadie puede reutilizar tu código, y la MIT lo permite con la única condición de conservar tu aviso.
  • Los releases publican versiones con sus instaladores; los secretos, los archivos generados y los enormes nunca van al repositorio, y un secreto filtrado se cambia antes que nada.
  • La protección de ramas obliga a pasar por PR (en repos públicos con el plan gratuito); en privados gratuitos, la regla la cumples tú.
Aplícalo fuera del Totito Este es exactamente el flujo de trabajo de la industria:
  • En tu primer empleo te asignarán un issue, crearás una rama con su número (fix/42-marcador-doble), abrirás un PR con Closes #42, un compañero lo revisará y, cuando las comprobaciones de Actions estén en verde, se fusionará. Ya lo sabes hacer.
  • Para contribuir a código abierto: busca en proyectos que uses issues con la etiqueta good first issue, haz un fork, arregla, y abre tu PR. Es una de las mejores formas de aprender y de que te conozcan.
  • Como portafolio: tres o cuatro repositorios públicos con buen README, capturas, licencia y releases descargables dicen más de ti que un currículum. El Totito puede ser el primero.
  • En un trabajo de grupo: un repositorio con colaboradores, un issue por tarea asignado a cada integrante, y la regla de que nada entra a main sin PR revisado por otro. Se acabaron los «¿quién borró mi parte?».
