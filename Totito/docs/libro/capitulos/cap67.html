Capítulo 67Publicar: versiones, etiquetas y GitHub Releases

Llegó el momento de compartir el Totito con el mundo. En este capítulo aprendes a numerar versiones con sentido, a publicar el instalador y la versión portable en una página de descargas de GitHub con un solo comando, a escribir notas de versión que la gente entienda, a explicar el aviso de SmartScreen que verán quienes lo descarguen y qué es la firma de código, y a dar a cada archivo una huella digital para que nadie pueda cambiarlo sin que se note.

Versiones semánticas: qué significa 1.0.0

Desde el capítulo 33 llevas usando números como v0.1.0 y v1.0.0. No son números al azar: siguen una convención muy extendida llamada versionado semántico (Semantic Versioning, o SemVer), en la que cada número tiene un significado. Una versión tiene tres partes separadas por puntos:

MAYOR . MENOR . PARCHE
  1   .   0   .   0
ParteEn inglésSe sube cuando…Ejemplo con el Totito
PARCHEPATCHCorriges errores sin cambiar lo que el programa hace1.0.1: arreglas que el marcador no sumaba los empates en cierto caso
MENORMINORAñades funciones nuevas, y todo lo anterior sigue funcionando igual1.1.0: añades niveles de dificultad para la IA (una idea pendiente del README)
MAYORMAJORHaces cambios que rompen algo de lo anterior, y quien lo usaba tiene que adaptarse2.0.0: el juego pasa a guardar las estadísticas en un archivo con un formato nuevo, incompatible con el de la versión 1

Las reglas de cómo se suben son mecánicas:

  • Al subir un número, los de su derecha vuelven a cero: de 1.0.3 con una función nueva se pasa a 1.1.0, no a 1.1.3. De 1.4.2 con un cambio incompatible se pasa a 2.0.0.
  • Los números no son decimales: después de 1.9.0 viene 1.10.0, que es mayor que 1.9.0.
  • Una versión publicada no se modifica nunca. Si el instalador 1.0.0 tenía un error, no se reemplaza: se publica el 1.0.1.
  • La versión 0.x.y significa «en desarrollo inicial, todo puede cambiar». Por eso la primera ventana del Totito fue la 0.1.0 (capítulo 33).
  • La 1.0.0 es una declaración: «esta es la primera versión estable, completa y pensada para que la use cualquiera». Por eso el Totito con la interfaz neón terminada, probado y empaquetado, es la 1.0.0.
  • Para versiones de prueba antes de una definitiva se añade un guion y una etiqueta: 1.1.0-beta.1, 1.1.0-rc.1 (release candidate, «candidata a versión»). Son anteriores a la 1.1.0.
¿Para qué sirve todo esto? Para que el número comunique. Quien ve que pasaste de 1.0.0 a 1.0.1 sabe que puede actualizar sin miedo: solo se corrigieron errores. Si ve 2.0.0, sabe que debe leer las notas antes. Y las herramientas también lo entienden: Windows Installer compara las versiones para decidir si un instalador es una actualización (capítulo 66).

Una versión, tres lugares

En tu proyecto la versión aparece en varios sitios y conviene que cuenten la misma historia:

DóndeValor ahoraQuién lo ve
Etiqueta de Gitv1.0.0Quien mira el repositorio. Por convención la etiqueta lleva una v delante
--app-version de jpackage (o MiVersion en Inno Setup)1.0.0Quien instala: Configuración → Aplicaciones, propiedades del .exe
Nombres de los archivosTotito-1.0.0.exe, Totito-1.0.0-portable.zipQuien descarga
<version> del pom.xml1.0-SNAPSHOTSolo Maven y tú (capítulo 63)

Las tres primeras deben coincidir siempre. La del pom.xml es interna; en proyectos más grandes también se alinea (se cambia a 1.0.0 al publicar y a 1.1.0-SNAPSHOT al empezar la siguiente), pero eso cambia el nombre del .jar y todos los comandos de empaquetado, así que en este libro la dejamos quieta.

La etiqueta v1.0.0

Una etiqueta (tag, capítulo 9) es un nombre fijo pegado a un commit concreto, como un marcapáginas que no se mueve. La creaste en el capítulo 61, al fusionar la rama interfaz-neon. Comprueba que existe, en tu equipo y en GitHub:

cd $HOME\Proyectos\Totito
git switch main
git pull
git tag
git ls-remote --tags origin

git tag lista las etiquetas locales (deberías ver v0.1.0 y v1.0.0); git ls-remote --tags origin lista las que hay en GitHub. Si v1.0.0 aparece en local pero no en GitHub, súbela:

git push origin v1.0.0

Y si no la creaste, créala ahora (anotada, con mensaje) y súbela:

git tag -a v1.0.0 -m "Totito 1.0.0: interfaz neon"
git push origin v1.0.0
¿Y el icono, que vino después? Si seguiste el plan del libro, el commit «Icono del programa» (capítulo 64) es posterior a la etiqueta v1.0.0. ¿Es un problema? Compruébalo: 
git diff v1.0.0 --stat -- src
Si no imprime nada, el código del juego (src) es idéntico al de la etiqueta: el icono y el generador solo afectan al empaquetado, no al juego. El instalador que vas a publicar corresponde exactamente al Totito 1.0.0. Lo que no debes hacer es mover o borrar una etiqueta ya publicada para «incluir» el icono: otras personas podrían haberla descargado ya, y las etiquetas son una promesa de que ese nombre siempre significa el mismo código. La lección para tu próximo proyecto: prepara el icono y el empaquetado antes de poner la etiqueta de la versión.

Preparar los archivos

Una publicación se fabrica siempre desde un estado limpio y conocido del código. Lista de comprobación, en orden:

  1. git status dice que no hay cambios pendientes, y estás en main actualizado (git pull).
  2. Clean and Build en NetBeans (o mvn clean package).
  3. La lista de pruebas manuales del capítulo 62, completa.
  4. Carpeta portable y ZIP (capítulo 65). Empieza de cero para no mezclar restos de pruebas: 
    if (Test-Path dist) { Remove-Item -Recurse -Force dist }
New-Item -ItemType Directory -Force dist\entrada | Out-Null
Copy-Item target\Totito-1.0-SNAPSHOT.jar dist\entrada\
    y luego el comando jpackage --type app-image del capítulo 65 y el Compress-Archive.
  5. Instalador (capítulo 66), con tu UUID.
  6. Instalar el .exe y abrir el portable una última vez.

Al final, comprueba que tienes los dos archivos con los nombres exactos:

Get-ChildItem dist\instalador\Totito-1.0.0.exe, dist\Totito-1.0.0-portable.zip

La primera línea de la lista anterior, if (Test-Path dist) { ... }, se lee así: «si existe la carpeta dist, bórrala con todo lo que tiene». Test-Path devuelve True o False, y el if de PowerShell funciona como el de Java (capítulo 13).

Huellas digitales: SHA-256

Cuando alguien descarga tu instalador, ¿cómo sabe que es exactamente el que tú publicaste y no uno dañado durante la descarga o, peor, modificado por alguien con malas intenciones que lo subió a otra página? Con una huella digital del archivo.

Qué es un hash. Una función hash lee todos los bytes de un archivo y produce un número de tamaño fijo, su hash o suma de comprobación (checksum). SHA-256 es una de las más usadas: produce 256 bits, que se escriben como 64 cifras hexadecimales. Tiene dos propiedades que la hacen útil: el mismo archivo da siempre el mismo hash, y si cambia un solo byte, el hash cambia por completo. Además, es imposible en la práctica fabricar otro archivo con el mismo hash. Es como la huella dactilar de una persona: no te dice nada de cómo es, pero sirve para comprobar que es ella.

PowerShell calcula hashes con Get-FileHash (SHA-256 es el algoritmo que usa si no dices otro):

Get-FileHash dist\instalador\Totito-1.0.0.exe
Algorithm       Hash                                                                   Path
---------       ----                                                                   ----
SHA256          4C1D8E0A9B7F3E2D6A5C4B3A2918F7E6D5C4B3A29180F7E6D5C4B3A2918F7E6D       C:\Users\tu-usuario\...

(Ese hash es un ejemplo inventado: el tuyo será otro, y cambiará cada vez que vuelvas a fabricar el instalador, porque incluye fechas y detalles de la compilación.)

Para publicarlos, lo habitual es un archivo de texto con el hash y el nombre de cada archivo, llamado por costumbre SHA256SUMS.txt. Esta línea lo crea con los dos archivos:

Get-FileHash dist\instalador\Totito-1.0.0.exe, dist\Totito-1.0.0-portable.zip | ForEach-Object { "{0}  {1}" -f $_.Hash.ToLower(), (Split-Path $_.Path -Leaf) } | Set-Content dist\SHA256SUMS.txt
ParteQué hace
Get-FileHash archivo1, archivo2Calcula el hash de los dos y produce dos objetos con las propiedades Algorithm, Hash y Path
|La tubería: pasa cada resultado al comando siguiente
ForEach-Object { ... }Repite el bloque por cada objeto; dentro, $_ es el objeto de esta vuelta (como la variable de un for-each, capítulo 14)
"{0} {1}" -f a, bArma un texto poniendo a en el lugar {0} y b en {1}, separados por dos espacios (el formato estándar de estos archivos)
$_.Hash.ToLower()El hash en minúsculas, como lo escriben la mayoría de herramientas
Split-Path $_.Path -LeafDel camino completo, solo el nombre del archivo (la «hoja» de la ruta)
Set-Content dist\SHA256SUMS.txtGuarda las líneas en ese archivo

Mira el resultado con Get-Content dist\SHA256SUMS.txt: dos líneas, cada una con 64 cifras y un nombre. Ese archivo también se publica.

¿Cómo lo comprueba quien descarga? En su PowerShell, en la carpeta de descargas:

(Get-FileHash .\Totito-1.0.0.exe).Hash -eq "pega-aqui-el-hash-publicado"

Si responde True, el archivo es idéntico al tuyo. -eq es el operador de igualdad de PowerShell (el == de Java) y, con textos, no distingue mayúsculas de minúsculas, así que da igual cómo esté escrito el hash.

Notas de versión que sirven

Las notas de versión (release notes) son el texto que acompaña a una publicación. Las leerá gente que no es programadora, así que deben responder, en este orden, a lo que se pregunta quien llega a la página:

  1. ¿Qué es esto? Una frase.
  2. ¿Qué archivo descargo? Con el nombre exacto y para quién es cada uno.
  3. ¿Qué necesito? Sistema operativo, si hace falta Java (¡no!), espacio.
  4. ¿Qué hay de nuevo? En una primera versión, qué trae; en las siguientes, qué cambió.
  5. ¿Qué puede salir raro? Problemas conocidos, como el aviso de SmartScreen.
  6. ¿Cómo compruebo el archivo? Los hashes.

Escríbelas en un archivo Markdown (el formato del README, capítulo 10) dentro de dist:

notepad dist\notas-1.0.0.md

El Bloc de notas te preguntará si quieres crear el archivo: responde que sí. Un ejemplo completo:

El clásico juego del totito (tres en línea) con interfaz neón, para dos
personas en el mismo equipo o contra una IA que nunca pierde.

## Descarga

| Archivo | Para quién |

**Requisitos:** Windows 10 u 11 de 64 bits. **No necesitas instalar Java**: el juego trae el suyo.

## Verificar la descarga (SHA-256)

Los hashes de los dos archivos están en `SHA256SUMS.txt`. En PowerShell:
`Get-FileHash .\Totito-1.0.0.exe`

Fíjate en lo que no lleva: detalles internos («refactoricé PantallaBase»), jerga sin explicar ni la lista de todos los commits. Eso está en el historial de Git para quien lo quiera. Para versiones siguientes se añade una sección «Cambios» con frases como «Corregido: el marcador no sumaba los empates al volver a jugar». Una buena costumbre es pensar en tu tía leyendo la página: si entiende qué descargar y qué hacer cuando salga el aviso, las notas están bien.

Publicar con gh release create

Una Release (publicación) de GitHub es una página asociada a una etiqueta del repositorio, con un título, unas notas y archivos adjuntos para descargar (los assets). Es el lugar correcto para los archivos fabricados que no van en el código (capítulos 63 y 65). Con la GitHub CLI que configuraste en el capítulo 7, se crea con un comando. La forma corta, con las notas en la misma línea:

gh release create v1.0.0 dist\instalador\Totito-1.0.0.exe dist\Totito-1.0.0-portable.zip --title "Totito 1.0.0" --notes "Primera version estable del Totito con interfaz neon. Descarga Totito-1.0.0.exe para instalarlo, o el .zip para usarlo sin instalar. No necesita Java."

Y la forma recomendada, con las notas del archivo Markdown, el archivo de hashes y una comprobación extra:

gh release create v1.0.0 dist\instalador\Totito-1.0.0.exe dist\Totito-1.0.0-portable.zip dist\SHA256SUMS.txt --title "Totito 1.0.0" --notes-file dist\notas-1.0.0.md --verify-tag
ParteQué hace
gh release createCrear una publicación en el repositorio de la carpeta actual (el que configuraste como origin)
v1.0.0La etiqueta a la que se asocia. Si no existiera en GitHub, gh la crearía desde el último commit de main; por eso conviene la opción --verify-tag
Los archivosSe suben como assets, con su nombre de archivo. Puedes poner tantos como quieras
--title "Totito 1.0.0"El título grande de la página
--notes "..."Las notas, escritas en la propia línea. Cómodo para un texto corto; incómodo para varios párrafos
--notes-file dist\notas-1.0.0.mdLas notas, leídas de un archivo Markdown. Mejor para textos largos con títulos y tablas
--verify-tagAbortar si la etiqueta no existe en GitHub, en vez de crearla en un commit que quizá no es el que querías

Subir unas decenas de megas tarda según tu internet. Al terminar, gh escribe la dirección de la publicación:

https://github.com/tu-usuario/totito/releases/tag/v1.0.0

Si prefieres revisarla antes de que la vea nadie, añade --draft: se crea como borrador, visible solo para ti. Cuando estés conforme, la publicas desde la página (botón Publish release) o con gh release edit v1.0.0 --draft=false.

Otras órdenes útiles de la misma familia:

ComandoPara qué

No reemplaces archivos de una versión ya publicada. --clobber existe para corregir un error en los primeros minutos, no para cambiar el instalador de la 1.0.0 una semana después. Si alguien ya lo descargó y anotó su hash, el archivo nuevo no coincidirá y parecerá manipulado. Si hay un error, publica la 1.0.1.

Si tu repositorio es privado

Las publicaciones de un repositorio privado solo las ven quienes tienen acceso a él. Para compartir el Totito con el mundo, el repositorio tiene que ser público. Antes de hacerlo, repasa el capítulo 10: que no haya contraseñas, tokens ni datos personales en ningún commit del historial. Luego, en la página del repositorio: Settings → General, al final, Danger Zone → Change visibility → Make public. O desde PowerShell:

gh repo edit --visibility public --accept-visibility-change-consequences

La última opción es la forma de decirle a gh «sé lo que hago»; las versiones más nuevas de gh la exigen y las antiguas no la conocen (si te da error por ella, quítala).

La página de Releases

Abre la publicación con gh release view v1.0.0 --web. Esto es lo que verás, y lo que verá cualquier visitante:

  • El título «Totito 1.0.0» y una etiqueta verde Latest («la más reciente»): GitHub la pone sola a la versión más nueva.
  • La etiqueta v1.0.0 y el commit al que apunta.
  • Tus notas, con el Markdown ya convertido: títulos, tabla, negritas.
  • La sección Assets con tus tres archivos, su tamaño y, en la interfaz actual de GitHub, también su huella SHA-256. Debajo, dos archivos que GitHub añade solo: Source code (zip) y Source code (tar.gz), el código fuente del repositorio en el momento de la etiqueta.

En la página principal del repositorio, en la columna de la derecha, aparece ahora un recuadro Releases con la última versión. Es por ahí por donde entrará la mayoría de la gente.

El aviso de SmartScreen

Ahora haz la prueba que hará cualquier persona: con el navegador, descarga tu propio Totito-1.0.0.exe desde la página de la publicación y ábrelo. Lo más probable es que veas, antes que el asistente de instalación, una ventana azul:

Windows protegió su PC

Microsoft Defender SmartScreen impidió el inicio de una aplicación
no reconocida. Ejecutar esta aplicación puede poner en riesgo su PC.

Más información
                                                   [ No ejecutar ]

Si pulsas Más información, la ventana muestra el nombre del archivo y «Editor: Editor desconocido», y aparece un botón nuevo, Ejecutar de todas formas. Al pulsarlo, el instalador sigue normalmente. (Los textos exactos pueden variar un poco según tu versión de Windows: «su PC» o «tu PC», por ejemplo.) Puede que el navegador también avise al descargar, diciendo que el archivo «no se descarga habitualmente»; en Edge, desde el menú ⋯ del aviso puedes elegir Conservar.

Por qué aparece

SmartScreen es una protección de Windows contra programas maliciosos descargados de internet. No analiza qué hace tu programa: decide por reputación. Funciona más o menos así:

  1. Cuando un navegador descarga un archivo, Windows le pega una marca invisible que dice «este archivo vino de internet» (se llama Mark of the Web, «marca de la web»).
  2. Al abrir un archivo con esa marca, SmartScreen consulta a Microsoft: «¿cuánta gente ha ejecutado este archivo sin problemas?, ¿quién lo publicó?».
  3. Tu instalador es nuevo (nadie lo ha descargado antes) y no está firmado (no dice quién lo publicó de forma verificable). Sin historial y sin identidad, SmartScreen no puede saber si es de fiar, y prefiere avisar.

Por eso no lo viste cuando abriste el instalador desde dist: lo fabricaste tú en tu equipo y no tiene la marca de internet. Y por eso aparecerá también con el ZIP portable: al extraerlo, los archivos heredan la marca y Totito.exe producirá el mismo aviso la primera vez.

No es un error de tu programa ni significa que tenga un virus: le pasa a cualquier programa nuevo de un autor independiente. Pero asusta, y mucha gente cierra la ventana. Por eso lo explicamos en las notas de la versión.

No enseñes a saltarse avisos a ciegas. «Ejecutar de todas formas» es razonable cuando sabes de dónde viene el archivo: de la página oficial de tu repositorio, enlazada por ti. Pide a quien lo descargue que lo haga solo desde ahí, no desde copias en otras páginas, y que, si quiere asegurarse, compare el hash. Esa es la diferencia entre confiar en un programa y confiar en cualquier cosa.

Con el tiempo, si muchas personas descargan y ejecutan el mismo archivo sin problemas, SmartScreen puede ir dejando de avisar, porque el archivo gana reputación. Pero no hay un número fijo ni garantía, y cada versión nueva es un archivo nuevo que empieza de cero. La forma de llevar la reputación de una versión a la siguiente es la firma de código.

La firma de código

Firmar un programa es adjuntarle una firma digital que demuestra dos cosas: quién lo publicó (identidad) y que nadie lo modificó desde que se firmó (integridad). Se hace con un certificado de firma de código, un documento digital que emite una autoridad de certificación (una empresa en la que Windows confía, como DigiCert, Sectigo o Certum) después de comprobar tu identidad con documentos.

Un programa firmado muestra en el Control de cuentas de usuario y en SmartScreen el nombre verificado del editor en vez de «Editor desconocido». Y como la reputación de SmartScreen se asocia también al certificado, las versiones siguientes firmadas con él no empiezan de cero.

OpciónPara quiénCosto aproximadoNotas

Los precios cambian cada año y dependen del proveedor: tómalos como orden de magnitud y compara antes de comprar. Lo importante es la idea: la firma es opcional. Ningún programa necesita estar firmado para funcionar. Es una inversión en confianza que tiene sentido cuando tu programa lo usan desconocidos o lo vendes; para el Totito, no hace falta.

Si algún día firmas, la herramienta de Windows es signtool.exe, que viene con el kit de desarrollo de Windows (Windows SDK). jpackage no firma en Windows por sí mismo, así que el orden sería: fabricar la carpeta con --type app-image, firmar Totito.exe, fabricar el instalador a partir de esa carpeta ya firmada (jpackage acepta --app-image dist\app\Totito en lugar de --input) y, por último, firmar el instalador. Cada proveedor de certificados explica su comando exacto.

Cualquier persona del mundo con Windows puede entrar a tu página de Releases, descargar el instalador o la versión portable, comprobar su huella SHA-256 y jugar, sin saber nada de Java. Empezaste el libro sin haber programado nunca y terminaste con un programa propio publicado.

Resumen

  • Versionado semántico: MAYOR.MENOR.PARCHE. Parche para correcciones, menor para funciones compatibles, mayor para cambios que rompen algo; 1.0.0 es la primera versión estable.
  • Una versión publicada no se modifica: los errores se corrigen con una versión nueva. Las etiquetas publicadas no se mueven.
  • La etiqueta de Git, la versión del instalador y los nombres de los archivos deben coincidir.
  • Get-FileHash calcula el SHA-256 de un archivo; publicarlo en SHA256SUMS.txt permite comprobar que la descarga es idéntica.
  • Las notas de versión responden: qué es, qué descargar, qué se necesita, qué hay de nuevo, qué puede salir raro y cómo verificar.
  • gh release create v1.0.0 archivos --title ... --notes-file ... --verify-tag crea la publicación con sus archivos; edit, upload, view y delete la gestionan.
  • SmartScreen avisa en programas nuevos sin firma descargados de internet: «Más información» → «Ejecutar de todas formas». No es un virus: es falta de reputación.
  • La firma de código demuestra identidad e integridad; cuesta dinero, es opcional y tiene sentido para programas de uso público o comercial.
Aplícalo fuera del Totito
  • Cualquier programa que entregues a otros (un trabajo de la universidad, una herramienta para tu trabajo): publícalo como Release con su versión, sus notas y sus hashes. Quien lo reciba sabrá exactamente qué versión tiene y podrás decirle «actualiza a la 1.2.0» en vez de «te mando el archivo nuevo por WhatsApp».
  • Librerías y proyectos de código abierto: el versionado semántico es el contrato con quien usa tu código. Maven, npm y casi todos los gestores de paquetes confían en él para decidir qué actualizaciones son seguras.
  • Verificar lo que descargas tú: muchas descargas oficiales (el propio JDK de Temurin, distribuciones de Linux, programas de seguridad) publican su SHA-256. Ahora sabes comprobarlo con Get-FileHash antes de instalar.
  • Un negocio que vende software: el ciclo completo de este capítulo (versión, etiqueta, notas, hashes, firma de código) es exactamente el que siguen las empresas, solo que automatizado con GitHub Actions u otros servicios de integración continua.
Ejercicios
  1. Para cada cambio, di qué versión publicarías partiendo de la 1.0.0: (a) corriges una falta de ortografía en las instrucciones; (b) añades sonidos al marcar; (c) añades jugar con el teclado y corriges un error del marcador, en la misma publicación; (d) cambias el formato de un archivo de estadísticas guardado, y los archivos viejos ya no se pueden leer. Pista: cuando hay varios cambios, manda el más importante.
  2. Calcula el SHA-256 de tu instalador, cambia el nombre de una copia del archivo y vuelve a calcularlo. ¿Cambió el hash? Explica por qué. Pista: el hash depende del contenido, no del nombre.
  3. Crea una publicación de prueba como borrador: gh release create v0.0.1-prueba dist\SHA256SUMS.txt --title "Prueba" --notes "Borrador de prueba" --draft --target main. Mírala con gh release view v0.0.1-prueba --web y bórrala con gh release delete v0.0.1-prueba --cleanup-tag. Pista: --cleanup-tag borra también la etiqueta que se creó para el borrador; si tu versión de gh no la tiene, borra la etiqueta con git push origin --delete v0.0.1-prueba.
  4. Escribe las notas de versión de una hipotética 1.1.0 que añade tres niveles de dificultad para la IA y corrige un error de la pantalla de resultado. Sigue los seis puntos de este capítulo y pon la sección «Cambios» al principio.
  5. Reto: pide a dos personas con Windows que descarguen el Totito desde tu enlace releases/latest, sin ayuda más allá de las notas. Anota en qué paso dudaron (¿el aviso de SmartScreen?, ¿qué archivo elegir?) y mejora las notas con gh release edit según lo que observes.
